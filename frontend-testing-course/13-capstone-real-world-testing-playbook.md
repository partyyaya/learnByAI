# 13｜期末專題：前端測試落地手冊

> 這章是整門課的整合實戰。你要把測試能力從「會寫」變成「能落地、能維護、能交付」。

## 專題目標

- 針對一個真實前端專案，建立完整測試策略。
- 產出單元、整合、E2E 的最小可行測試組合。
- 將測試流程接入 CI 並可持續執行。
- 交付一份團隊可使用的測試落地文件。

## 專題範圍建議

可選任一情境：

- 會員與登入系統
- 電商購物車與結帳流程
- 後台管理表單與權限流程

## 交付物（必交）

1. **測試策略文件**
   - 功能風險分級
   - 分層測試規劃（Unit/Integration/E2E）
   - 測試範圍與不測範圍
2. **可執行測試套件**
   - 單元測試至少 10 支
   - 整合測試至少 5 支
   - E2E 至少 3 支（關鍵旅程）
3. **CI 設定**
   - PR 自動測試流程
   - 失敗報告與排查紀錄
4. **維護規範**
   - fixture/factory 管理方式
   - flaky test 處理流程

## 專題里程碑（建議兩週）

| 時程 | 目標 | 產出 |
|------|------|------|
| Day 1-2 | 風險盤點與測試設計 | 測試策略草稿 |
| Day 3-6 | 單元與整合測試實作 | 第一版測試套件 |
| Day 7-9 | E2E 與 CI 串接 | 可執行 pipeline |
| Day 10 | 整理報告與發表 | 完整交付包 |

## 評分標準（示例）

- 測試策略完整度：30%
- 測試品質與可讀性：30%
- CI 落地與可重現性：20%
- 失敗排查與改進能力：20%

## 發表建議架構

1. 產品風險與測試邊界怎麼定義。
2. 為什麼這些流程放 Unit / Integration / E2E。
3. 實作過程遇到的最大問題與解法。
4. 下一步如何擴充與維護。

## 常見失敗原因

- 花太多時間追求覆蓋率數字，忽略關鍵流程。
- E2E 寫太多導致 CI 時間過長。
- 沒有測試資料策略，後期維護成本爆炸。

## 面試與實務延伸

- 你會如何在 30 分鐘內介紹你做過的測試架構？
- 如果公司要你在 1 個月內提升線上品質，你的落地順序是什麼？
- 你如何衡量測試導入是否真的帶來效益？

## 最終驗收清單

- [ ] 我有一份可對外說明的測試策略文件。
- [ ] 測試套件可在本機與 CI 重現。
- [ ] 我能說清楚測試設計的取捨與限制。
- [ ] 我具備把測試導入新專案或既有專案的能力。
