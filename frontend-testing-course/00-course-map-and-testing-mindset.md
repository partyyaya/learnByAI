# 00｜課程地圖與測試思維

> 先看這份文件，再開始寫第一支測試。這章會幫你建立「為什麼要測」與「從哪裡開始」的完整地圖。

## 學習目標

完成本章後，你應該可以：

- 說明前端測試在團隊開發中的價值，而不只把它當成 KPI。
- 理解「單元、整合、E2E」的角色分工與成本差異。
- 知道新手導入測試時，第一步要做什麼、不該做什麼。
- 規劃自己接下來 4 到 8 週的學習節奏。

## 適合對象

- 幾乎沒寫過測試的前端工程師。
- 想補齊測試能力的自學者與轉職者。
- 團隊正在導入測試流程，想建立共同語言的技術成員。

## 為什麼前端工程師需要測試

### 1. 降低改動風險

當需求快速變動時，測試是你的「安全網」。它讓你在重構時有信心，而不是靠手動點擊祈禱。

### 2. 加快協作速度

測試能把預期行為寫成可執行規格，減少「這功能到底算不算壞掉」的溝通成本。

### 3. 提升交付品質

把 bug 擋在 PR 或 CI 階段，通常比上線後救火便宜得多。

## 常見迷思與更好的觀念

- 迷思：測試會拖慢開發。
  - 觀念：前期會變慢，但後期改動速度更快，且回歸成本更低。
- 迷思：測試覆蓋率高就代表品質好。
  - 觀念：覆蓋率只是指標，重點是是否覆蓋高風險行為。
- 迷思：E2E 最貼近真實，所以全部都用 E2E。
  - 觀念：E2E 成本高、維護難，應只覆蓋關鍵旅程。

## 本課程的教學原則

1. **先學會判斷，再學會寫法**：你要先知道測什麼，再決定怎麼測。
2. **以使用者行為為中心**：優先驗證「使用者能不能完成任務」。
3. **小步快跑**：每章都要有可執行產出，不追求一次到位。
4. **框架無關**：核心觀念可套用到 React、Vue、Angular。

## 你現在就能開始的最小行動

1. 建立 `tests/` 或 `src/__tests__/` 目錄。
2. 選定測試工具鏈（本課程預設：Vitest + Testing Library + Playwright）。
3. 從一個「純函式」開始寫第一支測試（例如金額格式化、表單驗證）。
4. 把測試命令放進 `package.json`，確保團隊可一鍵執行。
