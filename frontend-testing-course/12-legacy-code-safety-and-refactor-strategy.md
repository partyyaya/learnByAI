# 12｜舊系統補測與重構策略

> 真實工作裡，你很少從零開始。這章教你在舊程式碼環境中，逐步建立「可重構的安全網」。

## 學習目標

- 為 legacy code 制定可執行的補測優先順序。
- 使用 characterization tests 先凍結既有行為。
- 透過小步重構降低風險，而不是一次大改。
- 建立團隊可持續的補測節奏。

## 前置知識

- 已完成 `11` 章，理解 CI 與品質門檻。
- 具備基本重構經驗（函式抽取、模組拆分）。

## 為什麼舊系統難測

- 耦合高：UI、資料、副作用混在一起。
- 缺少邊界：網路、儲存、商業邏輯沒有分層。
- 行為不明：沒文件、沒測試，只剩線上現象。

## 補測策略：先保護，再重構

### 第一步：盤點高風險區

- 曾出事故的模組。
- 常改動且影響營運的流程。
- 團隊最害怕碰的檔案。

### 第二步：寫 Characterization Tests

- 先記錄「目前行為」，不先判斷好壞。
- 目標是建立保護網，避免重構時引入新問題。

### 第三步：抽邊界與小步重構

- 將網路呼叫、時間、儲存抽成可替換依賴。
- 讓核心規則進入可單元測試的純邏輯層。

## 實作模式建議

1. 每次只重構一小塊，保持 PR 可 review。
2. 每次重構前先補 1 到 2 支保護測試。
3. 保持測試全綠再進下一步。

## 反模式

- 一次重寫整個 legacy 模組。
- 沒補保護測試就直接重構。
- 把測試全寫成 E2E，導致慢且難定位。

## 面試與實務延伸

- 當主管只給一週時間，你如何安排 legacy 補測優先順序？
- 你如何證明「補測 + 小步重構」比直接重寫更低風險？
- 如果既有行為本身有 bug，characterization test 應怎麼處理？

## 本章練習

1. 選一個團隊最常出事的舊模組。
2. 寫 3 支 characterization tests（至少一支錯誤路徑）。
3. 抽出一個可測試的純函式並補單元測試。

## 驗收清單

- [ ] 我有一份 legacy 高風險模組清單。
- [ ] 我能先補保護測試再重構。
- [ ] 重構後行為在測試保護下保持穩定。
