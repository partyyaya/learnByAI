# 01｜測試基礎與品質模型

> 這章的重點不是記工具，而是建立判斷力：什麼該測、為什麼測、放在哪一層測最划算。

## 學習目標

- 理解測試金字塔（或 Testing Trophy）的核心精神。
- 能用風險思維決定測試優先順序。
- 區分「功能行為」與「實作細節」並避免脆弱測試。
- 產出一份自己專案可用的測試範圍定義。

## 前置知識

- 已閱讀 `00` 章，知道測試導入目標。
- 具備 JavaScript/TypeScript 與基本前端開發經驗。

## 測試分層：不是越多越好，而是越精準越好

### 單元測試（Unit）

- 對象：函式、工具邏輯、純計算流程。
- 特性：速度快、定位快、成本低。
- 風險：若測太多內部實作，重構時容易全部壞掉。

### 整合測試（Integration）

- 對象：元件間互動、狀態管理、API 邊界。
- 特性：可驗證功能流程，價值高。
- 風險：測試資料與環境管理不佳時，容易不穩定。

### 端對端測試（E2E）

- 對象：真實使用者旅程（登入、下單、付款、送出表單）。
- 特性：信心高，最接近真實情境。
- 風險：執行慢、維護成本高，不適合大量覆蓋細節。

## 風險分級：先測最會出事的地方

建議用兩軸判斷：

- **影響程度（Impact）**：壞掉時影響多少使用者/收入/營運。
- **發生機率（Likelihood）**：這段程式是否常改、常出錯、依賴複雜。

| 風險區域 | 例子 | 建議策略 |
|---------|------|----------|
| 高影響 + 高機率 | 結帳流程、權限判斷 | 單元 + 整合 + E2E 共同覆蓋 |
| 高影響 + 低機率 | 核心匯率計算 | 單元測試為主，補少量整合 |
| 低影響 + 高機率 | UI 細節樣式邏輯 | 單元或元件測試，避免重 E2E |
| 低影響 + 低機率 | 靜態說明頁 | 可降低自動化優先級 |

## 測什麼，不測什麼

### 建議測

- 商業規則與條件分支（折扣、權限、狀態轉換）。
- 重要互動流程（表單提交流程、錯誤提示、重試）。
- 跨模組邊界（API 回應、資料轉換、狀態同步）。

### 不建議測（或降低優先）

- 第三方套件自身行為（除非你有客製化包裝）。
- 純展示內容且無互動邏輯的頁面。
- 與使用者價值無關的內部實作細節（例如私有方法順序）。

## 好測試的四個特徵

1. **可讀**：三個月後你還看得懂意圖。
2. **可靠**：結果穩定，不會隨機紅燈。
3. **可維護**：需求改變時，修改成本合理。
4. **有價值**：失敗訊號能指出真正風險。

## 常見反模式

- 把 snapshot 當主要保護機制。
- 每個按鈕都寫 E2E，導致 CI 超慢。
- 過度 mock，最後測到的不是實際系統行為。
- 把覆蓋率當唯一目標，忽略高風險區域仍未覆蓋。

## 實作任務：建立你的測試範圍地圖

1. 列出目前專案 5 個核心功能。
2. 為每個功能評估 Impact / Likelihood（高、中、低）。
3. 決定每個功能要放在哪一層測試（Unit/Integration/E2E）。
4. 做出一份「本月先補測 Top 3」清單。
