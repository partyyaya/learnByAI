# 第 06 章:Web 攻擊地圖 —— OWASP Top 10 與 Burp Suite

> 偵察篇(第 04–05 章)結束後,你手上已經有一張目標的地圖:哪些主機活著、開了哪些 port、跑著什麼服務。
> 現在鏡頭要拉近到最肥美、也最常被打的那個 port —— 80 / 443,也就是 Web。

> 把這一章當成 Web 篇的「作戰指揮所」:先看懂地圖、備好武器,後面每一章才知道自己在打哪一格。

## 6.1 為什麼 Web 是最大的攻擊面

回想第 00 章的「攻擊面思維」:攻擊面 = 所有攻擊者可以嘗試互動的入口總和。在所有攻擊面裡,Web 幾乎永遠是最大的一塊,原因有三:

**原因一:人人都連得到。**
一台內部資料庫可能只有內網能碰,但一個 Web 網站的存在意義就是「讓全世界的瀏覽器都能連上」。你把服務丟到 443 port,等於在網路上開了一家 24 小時營業、地址公開、任何人都能推門進來的店。攻擊者不需要先突破防火牆、不需要 VPN,打開瀏覽器就能開始戳。

**原因二:功能複雜。**
現代 Web 應用早就不是幾頁靜態 HTML。它有登入、購物車、金流、檔案上傳、後台管理、第三方登入、API、WebSocket……每多一個功能,就多一段處理使用者輸入的程式碼,也就多一個可能寫錯的地方。**複雜度是安全的天敵**——功能越多,開發者越難把每一條路徑都想周全。

**原因三:輸入點多到嚇人。**
這是重點。一個看起來「只是查詢商品」的頁面,背後可能有:URL 路徑、query string 參數、表單欄位、隱藏欄位、Cookie、各種 HTTP header(`User-Agent`、`Referer`、`X-Forwarded-For`)、JSON body、上傳的檔名……**每一個都是使用者可控的輸入,每一個都是潛在的注入點**。

> **心智模型**:如果說一台伺服器是一棟房子,那 Web 應用就是那扇「永遠開著、掛著歡迎光臨、而且門後有一百條走廊」的正門。偵察篇教你找到這棟房子,Web 攻防篇教你走遍每一條走廊、推每一扇內門。攻擊面越大,防守越難、破口越多——這就是為什麼 OWASP Top 10 幾乎主宰了真實世界的資安事件。

這也是為什麼這門課用了整整八章(06–13)講 Web:對前端 / 後端 / 全端工程師來說,這就是你天天在蓋、也天天被打的戰場。

## 6.2 複習:Web 的信任邊界與 HTTP 攻擊面

第 00 章講過最重要的一條駭客思維:**凡是「輸入」都是不可信的**。第 02 章講過 HTTP 請求長什麼樣。這一節把兩者接起來,用**攻擊者的視角**重看一個 HTTP 請求。

先看一個平凡到不行的請求——使用者按下「查看訂單」:

```
GET /order?id=1001 HTTP/1.1          ← 請求行:方法 + 路徑 + 參數 id=1001
Host: shop.example.com               ← 要連的網站(可竄改,SSRF/host 注入常從這下手)
Cookie: session=abc123; role=user    ← 身分憑證(攻擊者第一個想改的地方:role=admin?)
User-Agent: Mozilla/5.0 ...          ← 瀏覽器指紋(可任意偽造,有些後端會拿它做判斷)
Referer: https://shop.example.com/   ← 來源頁(可偽造,別拿它當安全檢查)
X-Forwarded-For: 1.2.3.4             ← 宣稱的來源 IP(可偽造,拿它做 IP 白名單就完蛋)
```

開發者眼中,這是「使用者要看 1001 號訂單」。**攻擊者眼中,這整個請求裡沒有一個字是可信的**:

| 欄位 | 開發者的假設 | 攻擊者會做什麼 |
|------|-------------|---------------|
| `id=1001` | 使用者只會看自己的訂單 | 改成 `id=1002` 看別人的(IDOR,第 12 章) |
| `id` 的值 | 是個數字 | 塞 `1001' OR '1'='1` 試 SQL 注入(第 07 章) |
| `Cookie: role=user` | 前端只給一般人 user | 直接改成 `role=admin`(存取控制,第 12 章) |
| `Host` | 就是我的網域 | 改成內網位址試 SSRF(第 10 章) |
| `X-Forwarded-For` | 反映真實來源 IP | 偽造成 `127.0.0.1` 繞過「僅限內網」限制 |
| 上傳檔名 `a.jpg` | 是張圖片 | 改成 `a.php` 試上傳漏洞(第 13 章) |

> **心智模型:信任邊界。** 你的伺服器程式碼、資料庫是牆內(可信);瀏覽器送來的**整個 HTTP 請求**都是牆外(不可信)。這道牆最危險的性質是:**攻擊者不透過你的網頁操作,而是直接構造 HTTP 請求打你的後端**。你在前端寫的 `maxlength="10"`、`<select>` 下拉限制、`type="number"`、JavaScript 檢查——對一個手動送封包的攻擊者來說,**全部形同不存在**。

這一句話是整個 Web 攻防篇的地基,值得再說一次:**所有前端驗證都只是使用者體驗,不是安全防線。** 而本章要學的 Burp Suite,正是「繞過前端、直接改寫 HTTP 請求」這件事的標準工具。6.9 節你會親眼看到它的威力。

## 6.3 【地圖】OWASP Top 10(2021 版)逐項概覽

**OWASP(Open Worldwide Application Security Project)** 是一個推廣 Web 安全的非營利組織,它每隔幾年根據全球真實漏洞資料統計,發布一份「最常見、最嚴重的 Web 風險前十名」清單,就是大名鼎鼎的 **OWASP Top 10**。它是全世界資安人的共通語言:面試會問、滲透報告會引用、稽核會對照。

以下是 **2021 版**(目前最新的定稿版本)的逐項白話概覽,以及**它對應本課哪一章深入**。這張表就是 Web 攻防篇的目錄索引,建議看完在腦中留個印象:

| 編號 | 名稱 | 一句白話 | 本課深入章節 |
|------|------|---------|-------------|
| **A01** | 存取控制失效 (Broken Access Control) | 使用者能碰到不該碰的東西(看別人的資料、做管理員的動作) | **第 12 章** |
| **A02** | 加密機制失效 (Cryptographic Failures) | 該加密的沒加密、加密方式太弱、憑證沒驗好(如明碼傳輸、爛雜湊存密碼) | **第 02 章**(TLS)、**第 17 章** |
| **A03** | 注入 (Injection) | 把使用者輸入當成程式碼 / 指令執行(SQL、命令、XSS) | **第 07、08、09 章** |
| **A04** | 不安全設計 (Insecure Design) | 不是寫錯,是「設計時就沒想到安全」(如轉帳沒做防重放) | 貫穿全課(呼應**第 00 章**) |
| **A05** | 安全設定錯誤 (Security Misconfiguration) | 預設密碼沒改、debug 模式上線、雲端桶開放、錯誤訊息噴細節 | **第 19 章** |
| **A06** | 危險 / 過時元件 (Vulnerable and Outdated Components) | 用了有已知漏洞的套件 / 框架 / 伺服器版本(如 Log4Shell) | **第 05 章**(指紋)、**第 14 章** |
| **A07** | 認證失效 (Identification and Authentication Failures) | 登入機制爛:弱密碼、可爆破、session 管理差、JWT 亂用 | **第 11 章** |
| **A08** | 軟體與資料完整性失效 (Software and Data Integrity Failures) | 信任沒驗過的資料 / 更新 / 反序列化物件(供應鏈攻擊、不安全反序列化) | **第 13 章** |
| **A09** | 記錄與監控失效 (Security Logging and Monitoring Failures) | 被打了卻沒 log、沒告警,事後查不出來 | **第 20、21 章** |
| **A10** | SSRF (Server-Side Request Forgery) | 誘使伺服器幫攻擊者去打它碰得到的內部目標 | **第 10 章** |

幾個值得先點破的觀念:

- **注意名次的變化透露的重點。** A01「存取控制失效」在 2021 版**衝到第一名**——這告訴我們:比起花俏的技術漏洞,「權限沒管好」才是現實中最普遍的災難。所以第 12 章雖然聽起來樸實,卻是含金量極高的一章。
- **A04「不安全設計」是 2021 版的新品項,也是最抽象的一項。** 它談的不是「程式碼寫錯」,而是「需求 / 架構階段就沒把安全考慮進去」。這正是第 00 章「找設計者沒預期的用法」那條思維的另一面——很多漏洞不是 bug,是設計本身有缺陷,再多輸入驗證也補不回來。
- **XSS 被併進 A03 了。** 早期版本 XSS 自成一類,2021 版把它歸到「注入」大類底下(因為本質都是「把資料當程式碼」)。我們在第 09 章專章講。

> **這張表就是你的作戰地圖。** 接下來每讀一章,回來這裡對一格:「我現在打的是 Top 10 的哪一項?」全局感建立起來,你就不會迷失在一堆招式裡,而是清楚知道每個漏洞在整張版圖的位置。

## 6.4 Web 應用架構與信任邊界:資料流過哪裡、哪裡該檢查

要知道漏洞會出現在哪,先要看懂一個典型 Web 應用「資料是怎麼流動的」。把一次請求的旅程畫出來:

```
[使用者瀏覽器]  ←— 不可信!所有前端驗證在這,對攻擊者無效
     │  HTTP 請求(可任意竄改)
     ▼
━━━━━━━━━━ 信任邊界①(最重要的一道牆)━━━━━━━━━━
     │
[後端伺服器 / 應用程式]  ←— 你控制的地方,真正的安全檢查必須在這做
     │           │
     │(SQL)     │(HTTP 呼叫)
     ▼           ▼
━━ 邊界② ━━   ━━ 邊界③ ━━
[資料庫]      [第三方 API / 內部服務]
```

逐層看每道邊界上「攻擊者想幹嘛、你該檢查什麼」:

- **邊界①:瀏覽器 → 後端(最關鍵)。** 這是攻擊者主戰場。所有使用者輸入都在這裡跨進來。你要做的是**輸入驗證**(這值我到底收不收)與**授權檢查**(這個使用者有沒有權限做這件事)。A01、A03、A07 大多發生在這道牆沒守好。
- **邊界②:後端 → 資料庫。** 如果後端把使用者輸入「原封不動拼進 SQL 字串」,注入就發生在這(A03,第 07 章)。守法是**參數化查詢**(第 07 章會講到你會背)。
- **邊界③:後端 → 第三方 / 內部服務。** 如果後端「拿使用者給的網址去發請求」,SSRF 就發生在這(A10,第 10 章)。

> **心智模型:資料每穿過一道信任邊界,就要「換一次驗證的心態」。** 從瀏覽器進到後端,要問「這輸入乾淨嗎、這人有權限嗎」;從後端寫進資料庫,要問「這值有沒有被當成 SQL 語法」;從後端打外部,要問「這個目標網址是使用者能控制的嗎」。**新手最大的錯覺是「前端擋過了就安全了」——但前端根本不在信任邊界內。** 真正的檢查一定要在牆內(後端)重做一遍。

## 6.5 攻擊者的 Web 工具鏈:各自的定位

打 Web 不是只靠一個神器,而是一組各司其職的工具。先建立「什麼時候用哪個」的直覺:

| 工具 | 定位 | 什麼時候用 |
|------|------|-----------|
| **瀏覽器開發者工具** | 看網頁「表面」發生什麼 | 快速看 Network 面板、改 DOM、看 Cookie、讀前端 JS |
| **`curl`** | 命令列手動發請求 | 精準控制單一請求、寫進腳本自動化、驗證某個 payload |
| **Burp Suite** | Web 攻防的瑞士刀(本章主角) | 攔截 / 改包 / 重送 / 爆破,幾乎所有手動測試都用它 |
| **OWASP ZAP** | Burp 的免費開源替代 | 想全免費、要接 CI/CD 自動掃描時 |

三點補充:

- **開發者工具是「唯讀 + 輕改」的層級。** 它讓你看見瀏覽器已經知道的事(送了什麼、收了什麼、Cookie 是什麼),也能改 DOM——但**它改的是前端,改不了「已經送出的請求」重送**。要攔截、改寫、重放請求,得靠代理型工具。
- **`curl` 是你最誠實的朋友。** 它不像瀏覽器會自動加一堆 header、自動帶 Cookie、自動跑 JS。你送什麼它就送什麼,完全可控。驗證一個 payload、或把攻擊寫進腳本時,`curl` 最乾淨。第 6.9 節會用到。
- **Burp 與 ZAP 是同一類(攔截代理),競爭關係。** 業界事實標準是 Burp(尤其它的 Repeater / Intruder 手感好),但 Burp 免費版(Community)功能受限;ZAP 完全免費開源,適合預算有限或要自動化。這門課以 Burp 為主,但觀念完全相通,你學會 Burp 就會 ZAP。

> **心智模型**:開發者工具是「觀景窗」,`curl` 是「手術刀」,Burp 是「整間手術室」。新手常只用觀景窗就以為看懂了,高手是三者搭配:用開發者工具快速偵查、用 Burp 攔截與改寫、必要時用 `curl` 精準複現。

## 6.6 【核心】Burp Suite 上手:攔截代理的原理

這一節是本章的技術核心。Burp 的一切能力,都建立在一個簡單的概念上:**它是一個坐在你的瀏覽器和伺服器之間的中間人代理(proxy)**。

### 代理攔截的原理

正常情況下,瀏覽器直接跟伺服器對話:

```
[瀏覽器] ──── 請求 ────▶ [伺服器]
[瀏覽器] ◀─── 回應 ──── [伺服器]
```

裝了 Burp 之後,你把瀏覽器設定成「所有流量都先送給 Burp」,於是變成:

```
[瀏覽器] ──▶ [Burp 代理] ──▶ [伺服器]      ← 請求先經過 Burp,你可以攔下來看、改
[瀏覽器] ◀── [Burp 代理] ◀── [伺服器]      ← 回應也先經過 Burp,你可以看、改
```

Burp 站在中間,**每一個進出的封包它都看得到、都能暫停、都能竄改再放行**。這就是它為什麼那麼強:它讓你脫離瀏覽器 UI 的限制,直接在 HTTP 這一層動手。

> **心智模型:Burp 就是坐在你和伺服器中間的攔截器,讓你看見並改寫每一個封包。** 前端 JavaScript 的種種限制(欄位長度、下拉選單、按鈕 disabled)都發生在瀏覽器裡;但請求一旦離開瀏覽器,就會先落到 Burp 手上——這時前端限制早已「執行完畢、拋在腦後」,你面對的是一份純文字的 HTTP 請求,想怎麼改就怎麼改。這具體印證了第 00 章那句「前端驗證對攻擊者無效」。

### 設定步驟(概念流程)

1. **啟動 Burp,找到 Proxy → Options,確認監聽埠。** Burp 預設在 `127.0.0.1:8080` 開一個代理監聽埠。
2. **把瀏覽器的 proxy 指向 Burp。** 兩種常見做法:
   - 用 Burp 內建的瀏覽器(Proxy → Intercept → Open Browser),它已經配好、最省事。
   - 或給你日常的瀏覽器裝 proxy 切換擴充套件(如 FoxyProxy),把 HTTP/HTTPS proxy 都指到 `127.0.0.1:8080`。
3. **打開 Intercept(攔截)開關,連一個網站,看流量有沒有被 Burp 攔下來。** 攔到了,代表代理通了。

### 為什麼要裝 Burp 的 CA 憑證才能攔 HTTPS?

這是新手第一個卡關的地方:設好代理後,連 `http://` 網站正常,一連 `https://` 網站瀏覽器就跳出一堆「你的連線不是私人連線」警告,或 Burp 根本攔不到。原因跟第 02 章的 **TLS** 直接相關。

回想第 02 章:HTTPS = HTTP + TLS,TLS 的兩個核心保證是**加密**(別人看不到內容)和**身分驗證**(你連的真的是那個網站,靠憑證)。而 Burp 想攔 HTTPS,本質上就是要做一件 TLS 極力防範的事——**中間人攻擊(MITM)**。

問題出在:當瀏覽器要連 `https://shop.example.com`,Burp 代理必須「假扮」成那個網站來跟瀏覽器建立 TLS 連線。但 Burp 沒有 `shop.example.com` 的真憑證(那把私鑰在真正的伺服器手上),所以 Burp 只能**當場自己簽發一張假的 `shop.example.com` 憑證**。瀏覽器一看:「這張憑證是 Burp 自己簽的,不是我信任的憑證機構(CA)簽的」——於是跳警告、拒絕連線。這正是 TLS 在保護你不被中間人竊聽,運作完全正常。

解法是:**手動把 Burp 的 CA 憑證加進你(自己這台測試機)的信任清單**。這樣一來,Burp 當場簽發的假憑證,因為是「你信任的 Burp CA」簽的,瀏覽器就會接受。整個 TLS 攔截流程變成:

```
[瀏覽器] ══TLS══▶ [Burp]         ← Burp 用「自己簽的假憑證」跟瀏覽器談 TLS
                                     (因為你信任了 Burp CA,所以這段成立)
                  [Burp] ══TLS══▶ [真伺服器]  ← Burp 再用正常方式跟真伺服器談 TLS
```

於是明碼在 Burp 中間現形,你看得到、改得到,兩端卻都以為自己在跟對方安全通訊。

> **關鍵安全提醒**:裝 Burp CA 憑證,等於「主動在自己這台機器上開了一個中間人後門」——只該裝在你的**測試機 / 靶場環境**,而且測完最好移除。**絕對不要**把 Burp CA 憑證裝到你日常辦公、網銀用的機器上;更不要被人騙著裝了來路不明的 CA 憑證——那等於把你所有 HTTPS 流量的攔截權交給對方。這也反過來讓你更懂第 02 章:**HTTPS 的安全性,建立在「你只信任該信任的 CA」這個前提上。**

## 6.7 Burp 核心模組:各自幹嘛

Burp 是一整套工具的集合。剛上手不用全會,先掌握這幾個高頻模組:

| 模組 | 功能 | 使用頻率 |
|------|------|---------|
| **Proxy** | 攔截 / 放行 / 檢視 / 修改往返的請求與回應 | 開機必開 |
| **Repeater** | 把單一請求抓過來,反覆修改、重送、看回應 | ⭐ 最常用 |
| **Intruder** | 自動化爆破:標記 payload 位置,批次灌一堆值 | 高 |
| **Decoder** | 各種編碼 / 解碼(URL、Base64、HTML 實體、Hex…) | 中 |
| **Comparer** | 逐字元比對兩份回應的差異 | 中 |
| **Target(Site map)** | 把逛過的所有 URL / 端點整理成網站地圖 | 高 |

重點模組展開講:

- **Proxy —— 一切的入口。** 6.6 講的攔截就在這。核心操作三件:**Intercept(攔住不放,讓你改)**、**Forward(放行)**、**Drop(丟棄這個請求)**。攔截開關別一直開著,不然每個請求都要手動放行會很煩;實務上多半關掉 intercept,靠 **HTTP history**(Proxy → HTTP history)回頭翻看所有經過的流量,看到有趣的再送去 Repeater。
- **Repeater —— 你會用最多的模組。** 手法是:在 HTTP history 或任何地方右鍵「Send to Repeater」,請求就複製到 Repeater。接著你可以**反覆修改這個請求、按 Send 重送、看回應怎麼變**。測注入、測參數竄改、測授權,九成手動測試都在 Repeater 裡「改一個字、送出、看差異」地反覆進行。**它就是 Web 版的「科學實驗:改一個變因,觀察結果」。**
- **Intruder —— 自動化的爆破引擎。** 當你要試的不是一個值,而是「一整份清單」(如試 1000 組密碼、試 id 從 1 到 9999、試一堆 XSS payload),手動送太慢。Intruder 讓你在請求裡用 `§` 標記「payload 位置」,再灌一份 payload 清單進去,它自動一發一發送、把每次的回應狀態碼 / 長度 / 時間列成表格讓你比對。哪一發跟其他不一樣,往往就是命中的那一發。(注意:免費版 Intruder 會被嚴重限速,認真爆破需要付費版或改用腳本 / `ffuf` 這類工具。)
- **Decoder / Comparer —— 輔助小工具。** 攔到一段看不懂的字串(像 `dXNlcj1hZG1pbg==`),丟進 Decoder 一解是 Base64 的 `user=admin`;想知道「輸入合法帳號」和「輸入不存在帳號」兩份回應差在哪(可能洩漏帳號是否存在),丟進 Comparer 逐字元 diff。

> **心智模型**:Proxy 是「看見」,Repeater 是「手動精修一發」,Intruder 是「自動海灌一片」。絕大多數漏洞是這樣挖出來的:**Proxy 發現可疑點 → Send to Repeater 手動確認 → 需要窮舉時再上 Intruder。** 記住這條動線,Burp 就從一堆按鈕變成一套流程。

## 6.8 探索一個 Web app 的方法論(Mapping the Application)

拿到一個授權測試的目標,不要急著亂丟 payload。老手的第一步永遠是**繪製地圖(mapping)**——把整個應用摸熟、把所有輸入點記下來。這一步做得越徹底,後面找洞越有效率。方法論如下:

**① 像真的使用者一樣走過所有功能。**
開著 Burp 攔截(或至少開著 HTTP history),把網站每個功能都點一遍:註冊、登入、改個資、搜尋、下單、上傳、登出、找回密碼……每點一次,Burp 的 site map 就多記一個端點。**你逛得越全,site map 越完整。** 別漏掉登入後才出現的頁面、以及不同角色(一般 user vs admin)看到的不同功能。

**② 記錄所有輸入點。**
一邊逛,一邊在心裡(或筆記,呼應第 00 章的筆記習慣)標記每一個「使用者能塞值的地方」:每個 URL 參數、每個表單欄位、每個隱藏欄位、Cookie、可疑的 header。這份清單就是你後面逐一測試注入 / 越權 / XSS 的**打擊名單**。

**③ 挖隱藏參數與 API。**
使用者看得到的功能只是冰山一角。打開瀏覽器開發者工具的 Network 面板,或翻 Burp history,常會發現:
- 前端 JS 呼叫的 **API 端點**(如 `/api/v1/users/1001`),這些往往比網頁本身更好打(有時 API 忘了做前端有做的檢查)。
- 表單裡的**隱藏欄位**(`<input type="hidden" name="price" value="100">`)——這是 6.9 節的經典靶子。
- 註解、JS 檔裡洩漏的**未公開端點、除錯參數**(如 `?debug=true`)。

**④ 做技術指紋(fingerprinting)。**
判斷這站用什麼技術蓋的,能大幅縮小攻擊方向。線索包括:
- HTTP 回應 header:`Server: nginx`、`X-Powered-By: PHP/7.4`、`Set-Cookie: PHPSESSID=...`(PHP)、`JSESSIONID`(Java)。
- 網址副檔名 `.php` / `.jsp` / `.aspx`、前端框架特徵、錯誤頁的樣式。
- 這一步跟第 05 章的服務指紋一脈相承,也直接連到 A06「危險 / 過時元件」——知道版本,就能去查它有沒有已知 CVE(第 14 章)。

> **心智模型:先畫地圖,再開火。** 沒 mapping 就亂打,像在黑房間裡揮拳。mapping 的產出是一份「所有入口 + 每個入口用什麼技術」的清單——後面每一章的攻擊,本質上都是「拿這份清單,逐一在每個入口試對應的招式」。**滲透測試 80% 的價值在偵查與 mapping,20% 才在最後那一下利用。**

## 6.9 參數竄改實作:親眼看到「前端擋不住攻擊者」

理論講完,來做一個能徹底改變你世界觀的實驗。這是每個開發者都該親手做一次的:**證明前端的限制對攻擊者毫無意義**。以下情境都在你自己的靶場(如第 01 章的 DVWA / Juice Shop)進行。

### 情境:改一個「前端寫死」的隱藏欄位

假設一個購物頁面,前端 HTML 是這樣的:

```html
<!-- 商品頁的表單,價格是後端算好、寫進 hidden 欄位的 -->
<form action="/checkout" method="POST">
  <input type="hidden" name="product_id" value="42">   <!-- 商品編號 -->
  <input type="hidden" name="price" value="1000">      <!-- 價格,使用者「看不到也改不到」-->
  <button type="submit">結帳</button>                  <!-- 使用者只能按這顆按鈕 -->
</form>
```

開發者的心態:「價格是我後端算好塞進 hidden 的,使用者在畫面上根本改不到。」

**攻擊者的做法:根本不透過畫面。** 按下結帳,Burp 攔到這個請求:

```
POST /checkout HTTP/1.1              ← 用 POST 送出結帳
Host: shop.example.com
Content-Type: application/x-www-form-urlencoded   ← 表單編碼格式
Content-Length: 26

product_id=42&price=1000            ← body:商品 42、價格 1000(這一行就是可以改的地方)
```

在 Burp Repeater 裡,把 `price=1000` 改成 `price=1`,按 Send:

```
product_id=42&price=1               ← 改成 1 元!前端的 hidden 限制完全被繞過
```

如果後端笨到「相信 body 送來的 price」,你就用 1 元買到了商品。這是真實世界反覆發生的漏洞,屬於 A04 不安全設計 / A01 存取控制的範疇。**教訓:價格這種敏感值,後端必須自己用 `product_id` 去資料庫查,絕不能相信前端送來的 `price`。**

### 更多同類竄改手法(都在 Repeater 裡試)

- **改 HTTP 方法。** 有些後端對 `GET` 和 `POST` 的權限檢查不一致。把 `POST /admin/delete` 改成 `GET`,或反過來,有時能繞過檢查。也可試 `PUT`、`DELETE`、冷門的 `PATCH`。
- **改 `Content-Type`。** 把 `application/x-www-form-urlencoded` 改成 `application/json`,或反過來送不同格式的 body,某些後端解析邏輯不同,可能繞過過濾或觸發不同程式路徑(XXE、注入常這樣試,第 08 章)。
- **加 / 改參數。** 試著在 body 或 query 加上前端沒送的參數,如 `&role=admin`、`&isAdmin=true`、`&debug=1`。有些後端會「多的欄位照收」,這叫**參數污染 / 大量賦值(mass assignment)**,是越權的常見門路(第 12 章)。
- **改 `id`、序號類參數。** 把 `id=1001` 改成 `1002`,看能不能撈到別人的資料——這就是 IDOR 的原型(第 12 章)。

用一行 `curl` 也能重現上面的「1 元購買」,證明這根本不需要瀏覽器:

```bash
curl -X POST https://shop.example.com/checkout \    # 用 POST 打結帳端點
  -H "Cookie: session=abc123" \                     # 帶上登入後的 session cookie
  -d "product_id=42&price=1"                         # body 直接送 price=1,前端?不存在的
```

> **心智模型(再強調一次,因為太重要):前端是給「守規矩的使用者」用的,攻擊者根本不進你的前端。** hidden 欄位、disabled 按鈕、`maxlength`、下拉選單、JavaScript 驗證——這些**全部**只是 UX,不是安全。這個實驗做完,你應該對第 00 章那句「真正的安全檢查一定要在伺服器端做」有了肌肉記憶。後面 07–13 章的每一個攻擊,骨子裡都是這句話的變奏。

## 6.10 防禦視角總綱:Web 安全的四大支柱

這門課紅藍並重(第 00 章)。這一節建立**整個 Web 攻防篇共用的防禦地基**——後面 07–13 章每一種攻擊的防禦,幾乎都是這四根支柱的具體應用。先把大原則刻進腦裡,細節到各章補。

### 支柱一:輸入驗證(用白名單,不用黑名單)

在信任邊界①(後端收到輸入的第一時間)就檢查:這個值我到底收不收?

- **白名單(allow-list)優於黑名單(deny-list)。** 黑名單是「列出壞東西擋掉」——但攻擊者的花招無窮,你永遠列不完(擋了 `<script>`,他用 `<img onerror>`)。白名單是「只允許明確合法的」——如「郵遞區號必須是 5 位數字」「角色只能是 user / editor / admin 三者之一」,不符合就拒絕。範圍小、好定義、擋得乾淨。
- **在後端做**(前端可以加驗證改善體驗,但**不能取代**後端驗證)。

### 支柱二:輸出編碼(要看場合,context-aware)

輸入進得來難免,關鍵是**輸出時別讓資料變成程式碼**。同一段資料,輸出到不同場合要用不同的編碼方式:

- 輸出到 **HTML 內文** → HTML 實體編碼(`<` 變 `&lt;`),防 XSS(第 09 章)。
- 拼進 **SQL** → 用參數化查詢,別用字串編碼硬拼(第 07 章)。
- 放進 **HTML 屬性 / JS / URL** → 各有各的編碼規則。

> **心智模型**:輸入驗證是「門口安檢」(這人 / 這包裹能不能進),輸出編碼是「出場時把危險品裝進防爆箱」(確保資料到了目的地不會被當成指令引爆)。兩者缺一不可——很多人只做安檢忘了防爆箱,XSS 就是這樣中的。

### 支柱三:最小權限(Least Privilege)

每個元件、每個帳號,只給它「完成工作所需的最小權限」,不多給。

- Web 應用連資料庫的帳號,不需要 `DROP TABLE` 權限就別給——這樣就算被 SQL 注入,損害也有限(第 07 章)。
- 一般使用者的 session 不該能碰管理員功能(A01,第 12 章)。
- 這是第 00 章「打斷 kill chain 任一環」思維的落實:**假設某一層一定會被突破,用最小權限把爆炸半徑壓到最小。**

### 支柱四:縱深防禦(Defense in Depth)

不要把安全押在單一道防線上。輸入驗證 + 輸出編碼 + 最小權限 + WAF + 監控告警……**每一層獨立、任何一層失守還有下一層接住**。這是第 00 章 kill chain 的直接對應:防守方只要在其中一環攔下攻擊,整條攻擊鏈就斷了。

### WAF 的角色與侷限

**WAF(Web Application Firewall,Web 應用防火牆)** 是擋在應用前面、檢查 HTTP 流量、擋掉看起來像攻擊的請求(如帶 `' OR '1'='1` 的封包)的一道防線。它在縱深防禦裡有價值,但**必須認清它的侷限**:

- **WAF 是黑名單思維**,靠比對「已知攻擊特徵」。攻擊者有大量**繞過(bypass)**手法:改編碼、拆字、大小寫變形、塞註解……讓 payload 長得不像特徵卻仍有效。
- **WAF 不理解你的業務邏輯。** 它擋得住長得像 SQL 注入的字串,但擋不住「把 `id=1001` 改成 `1002`」這種完全合法卻越權的請求(A01 / IDOR)。
- **WAF 是「補丁」不是「解法」。** 真正的修補在程式碼(參數化查詢、輸出編碼、授權檢查)。把 WAF 當唯一防線,等於用 OK 繃蓋住沒消毒的傷口。

> **一句話定位 WAF**:它是縱深防禦裡「爭取時間、擋掉大量自動化雜訊、緩解未修補漏洞」的一層,**不是**「裝了就安全」的萬靈丹。程式碼層的四大支柱做好,WAF 才是加分;程式碼稀爛,WAF 只是拖延受駭的時間。

## 6.11 本章小結

- **Web 是最大的攻擊面**:人人連得到、功能複雜、輸入點多。這是本課用八章(06–13)講 Web 的原因。
- **攻擊者視角看 HTTP**:URL 參數、header、Cookie、body、上傳檔名——請求裡沒有一個字可信。**所有前端驗證都只是 UX,不是安全防線**(呼應第 00、02 章)。
- **OWASP Top 10 是作戰地圖**:A01 存取控制(第 12 章)、A02 加密(第 02、17 章)、A03 注入(第 07–09 章)、A04 不安全設計(貫穿)、A05 設定錯誤(第 19 章)、A06 危險元件(第 05、14 章)、A07 認證(第 11 章)、A08 完整性 / 反序列化(第 13 章)、A09 記錄監控(第 20、21 章)、A10 SSRF(第 10 章)。
- **信任邊界與資料流**:最關鍵的檢查在「瀏覽器 → 後端」這道牆;資料每穿一道邊界就要換一次驗證心態。
- **工具鏈定位**:開發者工具(觀景窗)、`curl`(手術刀)、Burp(整間手術室)、ZAP(免費替代)。
- **Burp 核心**:它是坐在你和伺服器中間的攔截代理;要攔 HTTPS 必須裝 Burp CA 憑證(因為它在對你自己做 MITM,呼應第 02 章 TLS)。核心動線:Proxy 發現 → Repeater 精修 → Intruder 海灌。
- **方法論**:先 mapping(走遍功能、記錄輸入點、挖 API、做指紋),再開火。
- **參數竄改實驗**:在 Repeater 改 hidden 欄位 / HTTP 方法 / Content-Type / 加參數,親眼證明「前端擋不住攻擊者」。
- **防禦四大支柱**:輸入驗證(白名單)、輸出編碼(看場合)、最小權限、縱深防禦。WAF 是有用的一層,但有繞過空間、不懂業務邏輯,不能當唯一防線。這是 07–13 章防禦的共同基礎。

> **下一章預告**:地圖看完、武器上手,該打第一場硬仗了。第 07 章我們攻 OWASP Top 10 的 **A03 注入**裡最經典、也最危險的一種——**SQL Injection(SQL 注入)**。你會看到一個 `' OR '1'='1` 是怎麼讓登入直接被繞過、`UNION SELECT` 怎麼把整個資料庫撈出來、盲注(blind injection)在看不到回應時怎麼用「時間差」一個 bit 一個 bit 問出密碼。當然,也會學到那句你以後會背的防禦真言:**參數化查詢(prepared statements)**。本章學的 Burp Repeater,下一章就是你的主戰武器。
