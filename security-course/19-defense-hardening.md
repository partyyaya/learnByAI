# 第 19 章:防禦體系與系統加固(Defense in Depth & Hardening)

> 從第 04 章到第 18 章,你一路扮紅隊:掃描、注入、XSS、提權、破密碼、釣魚……每一章末尾我都逼你回答一句
> 「如果我是開發者,這行程式該怎麼寫才不會中?」——那些是**點狀防禦**,一個洞配一帖藥。這一章開始換位子:
> 你坐進藍隊,要把散落在前面十幾章的防禦招式,**收斂成一套系統性的防禦體系**。這正是這門課真正的目的地——
> 回想第 00 章那句話:我們學攻擊,是為了**以攻代防、讓系統更安全**。攻擊只是手段,把門鎖好才是目的。
> 這一章先講三根「心法支柱」(縱深防禦、最小權限、零信任)加上一條主軸(縮小攻擊面),再給你一份從主機、網路、
> Web 應用到機密管理、開發流程、備份的**加固清單**。學完你會明白:加固就是「**把每扇門鎖好、把沒用的門直接拆掉**」。

## 19.1 從「點狀防禦」到「防禦體系」

前面每一章的防禦都是**針對單一漏洞**的:SQLi 用參數化查詢(第 07 章)、XSS 用輸出編碼(第 09 章)、SSRF 擋內網位址(第 10 章)、越權用伺服器端授權檢查(第 12 章)……這些都對,但如果你的安全觀只停在「哪個漏洞配哪帖藥」,你會**永遠慢攻擊者半拍**——因為漏洞是列不完的,今天補了 SQLi,明天冒出一個反序列化;你補得完已知的,補不完未知的。

成熟的防禦不是「一個一個補洞」,而是**建立一套讓漏洞就算存在、也難以被利用、被利用了危害也有限的體系**。這套體系有兩個層次:

```
心法(為什麼這樣防)     →     加固清單(具體怎麼做)
────────────────────         ──────────────────────
縱深防禦                       主機/OS 加固、SSH 加固
最小權限                       修補管理、安全基線
零信任                         網路防火牆、網路分段
縮小攻擊面                     Web 安全標頭、機密管理
                              安全開發流程、備份韌性
```

> **心智模型:防禦是「地基」,不是「補丁」。** 補丁思維是被動的——攻擊者打一拳,你擋一拳,你只能守住你「想得到」的攻擊。體系思維是主動的——你先把整個系統的**結構**弄穩(權限收緊、攻擊面縮小、多層設防),於是就算冒出一個你沒預料的新漏洞,它也很難單獨造成大災難。這門課的攻擊篇是教你「攻擊者想得到哪些拳」,而這一篇要教你「怎麼站得穩到不怕挨拳」。

這一章我把「怎麼防」寫得跟前面「怎麼打」一樣詳盡——因為**防守才是這門課的終點**。第 20 章(偵測)、第 21 章(事件回應)會接著講「萬一還是被打進來怎麼辦」,但一切的起點,是先把這一章的門鎖好。

## 19.2 防禦心法:四個必須內化的核心觀念

工具和清單會過時,**心法不會**。這四個觀念是整個藍隊防禦的地基,前面各章其實已經零散提過,這裡把它們收斂、講透。

### 支柱一:縱深防禦(Defense in Depth)——多層獨立防線

**別把安全押在單一一道牆上。** 設計多層彼此獨立的防線,一層被突破,還有下一層擋著。這正是第 09 章 XSS 防禦的精神——輸出編碼是主力,萬一漏了,CSP 是第二道牆,再漏了,HttpOnly cookie 讓攻擊者偷不到 session,層層疊起來。

回扣第 00 章的 **Cyber Kill Chain**:攻擊是一條七階段的鏈(偵察→武器化→遞送→利用→安裝→C2→行動),你**不需要擋住全部,只要打斷任何一環,整條鏈就斷**。縱深防禦就是「在鏈的多個環節都設下攔截」,讓攻擊者每前進一步都要再突破一道關卡。

```
單層防禦(脆弱)              縱深防禦(強韌)
─────────────              ─────────────
   [ 一道高牆 ]               [ 邊界防火牆 ]     ← 破了…
       │                     [ 網路分段 ]       ← 還有…
   破了就全完                 [ 主機加固 ]       ← 還有…
                             [ 最小權限 ]       ← 還有…
                             [ 輸入驗證/編碼 ]   ← 還有…
                             [ 加密與備份 ]     ← 最後一道底線
```

> **心智模型:城堡不是只有一道城牆。** 中世紀城堡有護城河、外牆、內牆、箭塔、城堡主樓層層設防,不是因為造牆的人不會蓋堅固的牆,而是因為**任何單一防線都可能失守**。資安同理:防火牆會被繞過、WAF 有規則盲點、程式碼會有 bug——所以你要讓攻擊者「就算過了第一關,也還在你的第二、第三關裡」。

### 支柱二:最小權限(Least Privilege)——只給剛好夠用的權限

**每個帳號、每個服務、每支程式,都只給它「完成工作所需的最小權限」,一點都不多給。** 這直接對應第 12 章(存取控制)與第 16 章(提權後滲透)的教訓:

- 一個只需要讀資料庫的網站服務,就**別用 root/管理員身分跑**——萬一它被 RCE 攻破,攻擊者拿到的也只是那個受限帳號,而不是整台機器(第 16 章的提權會困難得多)。
- 資料庫連線帳號只給它該碰的那幾張表的權限,別給 `DROP`、別給 `FILE`——就算 SQLi 得手(第 07 章),損害也被框住。
- 員工帳號別預設就是管理員;需要時再臨時提升(just-in-time)。

> **心智模型:給鑰匙,不給萬能鑰匙。** 你請的水電工,你只給他大門和廚房的鑰匙,不會給他保險箱鑰匙。最小權限就是「按需給鑰匙」——這樣任何一把鑰匙被偷,損失都是**局部**的。它的威力在於**遏制爆炸半徑(blast radius)**:攻擊者攻破一個點,能横向擴散的範圍被死死限制住。

### 支柱三:零信任(Zero Trust)——不因「在內網」就信任

傳統的「城牆式」安全有個致命假設:**內網 = 可信,外網 = 不可信**。防火牆守在邊界,只要進了內網,彼此之間幾乎暢通無阻。這個假設被第 10 章的 **SSRF** 打得粉碎——攻擊者根本不用「進」內網,他讓**你的伺服器**(一台在內網、被大家信任的機器)去替他打內網位址、去打雲端 metadata 拿金鑰。「在內網」這件事,對攻擊者來說一文不值。

**零信任(Zero Trust)的核心是一句話:「Never trust, always verify(永不信任,每次都驗證)」。** 不論請求來自內網還是外網,每一次存取都要重新驗證身分與權限,不因為「它在防火牆裡面」就放行。

```
傳統邊界安全                     零信任
────────────                    ──────────
外網 →[防火牆]→ 內網            每個請求,不管來自哪,都要:
                內部全信任        ① 驗證身分(你是誰?)
                彼此暢通          ② 檢查權限(你能做這件事嗎?)
                                 ③ 最小授權(只給這次需要的)
一旦破牆 → 內部横著走            破牆進來 → 每碰一個服務都被再擋一次
```

> **心智模型:別再用「內外」分敵我。** 零信任把「信任邊界」(第 00 章)從「網路的外圍」搬進了「每一個資源的門口」。它其實是「最小權限」在網路架構層的延伸——既然任何一台內部主機都可能已經被攻陷(這也是第 20 章 Assume Breach 的前提),那就不該有任何一台主機「因為在內網」而享有免驗證的特權。

### 主軸:縮小攻擊面(Attack Surface Reduction)——把沒用的門拆掉

前三根支柱是「怎麼守門」,這條主軸更狠:**乾脆把不需要的門直接拆掉**。攻擊面(第 00、05 章)是「所有攻擊者可以嘗試互動的入口總和」——開的 port、對外的 API、安裝的軟體、啟用的功能、存在的帳號……**每一項都是一扇可能沒鎖好的門**。

> **心智模型:最安全的門,是不存在的門。** 一個你關掉的服務,不會有 0-day;一個你移除的套件,不會有 CVE;一個你刪掉的預設帳號,不會被暴力破解。加固最高投報率的動作,往往不是「把某扇門鎖得更牢」,而是「**問這扇門到底需不需要存在**」。這是貫穿本章所有加固清單的總指導原則——每加固一項,先問:「這個能不能直接關掉/移除?」

這四個觀念會在下面的加固清單裡反覆出現。清單只是心法的具體化;真正要記住的是心法。

## 19.3 主機加固:關門、拆門、鎖門

從最底層的主機/作業系統開始。一台剛裝好的伺服器,預設狀態通常**遠比它需要的更開放**——這就是加固要收拾的。主機加固可以拆成三個動作:**拆門(移除)、關門(停用)、鎖門(強化剩下的)**。

### 加固清單:主機/OS 層

| 動作 | 具體做法 | 對應的攻擊(前面章節) |
|------|---------|---------------------|
| **關掉不用的服務與 port** | 停用並移除不需要的 daemon,只留必要服務對外 | 掃描列舉(第 05 章)——關掉的 port 掃不到 |
| **移除預設帳號、改預設密碼** | 刪 guest/test 帳號、改掉出廠預設密碼 | 密碼攻擊(第 15 章)、弱憑證 |
| **最小安裝(minimal install)** | 只裝必要套件,不裝編譯器/桌面環境到伺服器 | 縮小攻擊面、減少 living-off-the-land 工具(第 16 章) |
| **檔案與目錄權限** | 移除多餘的 SUID/SGID、敏感檔設對權限、不用 777 | 提權(第 16 章)、路徑穿越讀檔(第 13 章) |
| **SSH 加固** | 禁 root 登入、改用金鑰、限制來源(下面詳述) | SSH 暴力破解(第 11、15 章) |
| **核心與帳號政策** | 密碼複雜度、登入失敗鎖定、`umask` 收緊 | 暴力破解、憑證填充 |

### SSH 加固:逐行拆解 sshd_config

SSH 是伺服器最常見的管理入口,也是掃描與暴力破解的頭號目標(你在第 05、11、15 章打過,第 20 章的 auth.log 也全是它的失敗紀錄)。把 SSH 鎖好,是主機加固最該先做的一件事。編輯 `/etc/ssh/sshd_config`:

```bash
# /etc/ssh/sshd_config —— 改完記得 sudo systemctl restart sshd 才生效
PermitRootLogin no              # ① 禁止 root 直接登入。攻擊者最想要的就是 root,先斷這條路;
                                #    要管理就用一般帳號登入再 sudo(留下稽核紀錄,第 20 章)
PasswordAuthentication no       # ② 關掉密碼登入,改用金鑰 —— 這一行直接「根治」SSH 暴力破解:
                                #    沒有密碼可猜,Hydra 打再久也沒用(第 11、15 章)
PubkeyAuthentication yes        # ③ 啟用公鑰認證(把你的公鑰放進 ~/.ssh/authorized_keys)
PermitEmptyPasswords no         # ④ 禁止空密碼帳號登入(基本衛生)
MaxAuthTries 3                  # ⑤ 單條連線最多試 3 次認證就斷線,拖慢暴力破解
AllowUsers deploy admin         # ⑥ 白名單:只有 deploy、admin 能 SSH,其餘帳號一律拒絕
                                #    (最小權限:預設拒絕、明列放行,而非「全開再一個個關」)
Port 2222                       # ⑦ 改掉預設 22 port,避開海量無腦掃描 —— 這是「減噪」不是「安全」,
                                #    別以為改 port 就安全了(這叫 security by obscurity,治標)
ClientAliveInterval 300         # ⑧ 閒置 300 秒送一次探測包
ClientAliveCountMax 0           # ⑨ 探測無回應就斷線 —— 清掉沒登出的殭屍 session
X11Forwarding no                # ⑩ 關掉用不到的 X11 轉發(縮小攻擊面)
```

> **新手誤區**:以為「把 SSH port 改成 2222 就安全了」(第 ⑦ 行)。錯。改 port 只是讓自動化掃描少騷擾你,一個認真的攻擊者用 `nmap -sV`(第 05 章)幾秒就找到它。真正讓 SSH 固若金湯的是**第 ②③ 行——關掉密碼認證、改用金鑰**:把「猜密碼」這條攻擊路徑從根本上拿掉。這才是「拆門」而非「把門藏起來」。

> **心智模型:預設拒絕(default deny),明列放行(allow-list)。** 看第 ⑥ 行——不是「列出禁止的帳號」,而是「只列出允許的帳號,其他全拒」。這跟第 09 章講的「白名單勝過黑名單」是同一個道理:你永遠列不完「所有壞的」,但你數得清「所有好的」。這個原則等一下在防火牆(19.5)還會再出現一次。

## 19.4 修補管理與安全基線:投報率最高的防禦

### 修補(Patching):最無聊、也最重要

如果只能做一件防禦,我會叫你**把修補做好**。原因很現實——回想第 14 章:**絕大多數真實世界的入侵,打的不是什麼高深的 0-day,而是「早就有修補、但受害者沒裝」的已知漏洞(known CVE)**。Metasploit 裡那些現成的 exploit 模組,九成以上針對的是已公開、已有補丁的 CVE。攻擊者不需要多聰明,他只要掃到一台「三個月沒更新」的機器就夠了。

```
攻擊者的日常                              防守方的對策
──────────────                          ──────────────
① 掃到你的服務版本(第 05 章)            ① 及時套用安全更新
② 查這版本有沒有已知 CVE                  ② 訂閱 CVE / 廠商安全公告
③ 從 Metasploit / Exploit-DB 抓現成      ③ 建立修補時程(高危 CVE 幾天內修)
   exploit(第 14 章)                     ④ 用漏洞掃描器(第 05 章的 Nessus/
④ 打進去                                    OpenVAS)定期盤點「我有哪些沒修的洞」
```

> **心智模型:修補是「補投報率最高的洞」。** 0-day 又貴又稀有,攻擊者捨不得浪費在你身上;但一個公開三個月、你還沒修的 CVE,是**免費的、現成的、全世界都能打的**入口。你連錢都不用花、只要按時更新,就能把「最多人走的那條攻擊路」直接封死。它一點都不性感,卻是 CP 值最高的防禦——**別讓你的系統成為那個「用已知漏洞就能打進去」的軟柿子。**

實務要點:區分**測試環境先驗、再上生產**(避免更新弄壞服務),對「無法立即修補」的系統做**緩解措施**(虛擬補丁、隔離、關閉受影響功能),並對過保 EOL(End of Life)的軟體/系統排除役——EOL 的東西不再有安全更新,等於一扇**永遠不會再上鎖**的門。

### 安全基線與 Benchmark:別靠感覺加固

「我覺得這樣應該夠安全了」——加固最怕靠感覺。業界的做法是對照**公認的安全基線(security baseline)**,逐條檢查、逐條達標:

- **CIS Benchmarks**:由 Center for Internet Security 針對各種系統(Linux、Windows、Nginx、Docker、雲端服務……)發布的**逐項加固檢查清單**,每一條都寫明「該設什麼、為什麼、怎麼設」。這是全世界最常用的加固參考,照著做就不會漏掉基本項。
- **自動化檢測工具**:不用人工一條一條核對——
  - **Lynis**:Linux/Unix 的開源稽核工具,跑一次就掃描全系統的加固狀態、給你一個**硬化分數(hardening index)**和一串改進建議(本章 19.10 就用它)。
  - **OpenSCAP**:依 SCAP 標準(常搭配 CIS/DISA STIG profile)自動檢測系統是否符合基線,能產出合規報告。

```bash
# Lynis:對本機做一次完整安全稽核(需 root 才能檢查到系統層設定)
sudo lynis audit system         # 掃描完會給 Hardening index: XX/100 與一串 [SUGGESTION]
```

> **關鍵認知**:安全基線把「加固」從**個人手藝**變成**可量化、可重複、可稽核的工程**。你不再需要「記得」該關哪些服務、該設哪些權限——照 CIS Benchmark 逐條走、用 Lynis/OpenSCAP 打分數,加固就變成一件「有標準、有分數、能追蹤進步」的事。這也是 19.10 靶場練習「加固前後跑 Lynis 對照分數」的意義。

## 19.5 網路防禦:防火牆、分段與收斂對外暴露

主機鎖好了,再往外一層看網路。網路防禦的目標有兩個:**把不該對外的東西藏起來(縮小攻擊面)**,以及**限制攻擊者進來後的横向移動(遏制爆炸半徑)**。

### 防火牆:入向與「常被漏掉」的出向(egress)

防火牆的基本原則跟 SSH 一樣——**預設拒絕、明列放行**。但新手幾乎都只管**入向(ingress)**,忘了**出向(egress)**才是現代攻擊的關鍵防線:

```bash
# 以 ufw(Uncomplicated Firewall)示範,原則:兩個方向都「預設拒絕」
sudo ufw default deny incoming          # ① 入向預設全拒 —— 沒明白放行的 port 一律關(縮小攻擊面)
sudo ufw default deny outgoing          # ② 出向也預設全拒 —— 這步最多人漏做,卻超級關鍵!
sudo ufw allow 443/tcp                  # ③ 入向只放行真正對外的服務(這裡是 HTTPS)
sudo ufw allow from 10.0.0.0/24 to any port 22   # ④ SSH 只准內部管理網段連,不對全世界開
sudo ufw allow out 53                   # ⑤ 出向白名單:放行 DNS(否則連網域都解析不了)
sudo ufw allow out 443/tcp              # ⑥ 出向放行 HTTPS(套件更新、必要的 API 呼叫)
sudo ufw enable                         # ⑦ 啟用防火牆
```

**為什麼出向防火牆這麼重要?** 因為它直接掐住了攻擊者得手後的兩條命脈:

- **擋 C2 外連**:攻擊者拿到 shell 後,第一件事往往是「回連(call back)」到他的 C2 伺服器(第 00 章 Kill Chain 第 ⑥ 環)。如果你的伺服器**只被允許連 DNS 和幾個特定目的地**,那個回連請求會直接被防火牆丟掉——鏈就在這裡斷了。
- **緩解 SSRF 與資料外洩**:回扣第 10 章——SSRF 的殺傷力在於「讓伺服器去打它本不該打的位址」(內網、雲端 metadata `169.254.169.254`)。出向防火牆用「預設拒絕」把伺服器能主動連出去的目的地**收斂到最小**,就算 SSRF 觸發了,那個請求也到不了雲端 metadata。這是零信任(19.2)在網路層的體現:**連你自己的伺服器要往外連,都得先驗證「這是不是它該連的地方」。**

> **心智模型:防火牆要管「進」,更要管「出」。** 大家都記得鎖大門(入向),卻忘了——小偷進來後要把贓物搬出去、要打電話回總部(出向)。把出向鎖死,等於「就算他進來了,東西也搬不出去、電話也打不出去」。這是縱深防禦裡極其划算的一層。

### 網路分段(Segmentation):切斷横向移動

**別把所有東西塞在同一個扁平的大網段裡。** 把網路切成多個區段(segment / VLAN),彼此之間用防火牆規則嚴格管控——這直接對應第 16 章的教訓:攻擊者拿下一台機器後,最想做的就是**横向移動(lateral movement)**,從這台跳到那台,一路摸到核心資料庫。

```
扁平網路(危險)                      分段網路(強韌)
────────────                        ──────────────
[Web][DB][員工電腦][備份]            ┌─ DMZ 區 ──┐  ┌─ 內部服務區 ─┐  ┌─ 資料區 ─┐
  全在同一網段,彼此暢通               │ Web 伺服器 │→ │ 應用伺服器   │→ │ 資料庫    │
  攻破 Web → 直接摸到 DB              └───────────┘  └─────────────┘  └──────────┘
                                       只開必要的連線方向與 port,跨區都要過防火牆
                                       攻破 Web,也到不了資料區(除非再突破一道)
```

- **DMZ(非軍事區)**:對外服務(Web、郵件)放這裡,和內部網路隔開——就算對外服務被打穿,攻擊者也還被卡在 DMZ,進不了內網核心。
- **微分段(micro-segmentation)**:分段做到極致,甚至同一應用的不同服務之間也彼此隔離,只放行明確需要的連線——這就是零信任架構的網路實作。

### VPN 與收斂對外暴露

- **VPN**:管理介面、後台、資料庫這類**根本不該對公網開放**的東西,藏到 VPN 後面——要先通過 VPN 驗證,才碰得到它們。等於把一大片攻擊面從「全世界可及」縮成「只有通過驗證的人可及」。
- **收斂對外暴露(reduce external exposure)**:定期用攻擊者的視角(第 04、05 章 OSINT + 掃描)盤點「我到底有哪些東西對公網開著?」——那台忘了關的測試伺服器、那個 debug 沒關的 API、那個直接曝露公網的資料庫 port(這是資料外洩的經典成因),全都要找出來關掉。**你對外開的每一個東西,攻擊者遲早會掃到。**

## 19.6 Web 應用防禦收束:把第 2 篇的防禦收成一張清單

第 2 篇(第 06–13 章)你打了一輪 Web 漏洞,每章也都學了對應防禦。這裡把它們**收斂成一份可以直接拿去 code review 的清單**——這就是「點狀防禦收斂成體系」最具體的示範。

| 防禦措施 | 擋住什麼 | 對應章節 |
|---------|---------|---------|
| **參數化查詢(prepared statements)** | SQL 注入 | 第 07 章(核心真言) |
| **輸出編碼(context-aware encoding)** | XSS | 第 09 章 |
| **輸入驗證(白名單、正向驗證)** | 各類注入的輔助防線 | 第 07–09 章 |
| **伺服器端授權檢查(每個請求都驗)** | IDOR、越權 | 第 12 章 |
| **檔案上傳驗證、路徑正規化** | 上傳惡意檔、路徑穿越 | 第 13 章 |
| **安全的 cookie 屬性** | session 竊取、CSRF | 第 09、11、10 章 |
| **HTTP 安全標頭** | XSS、點擊劫持、降級攻擊 | 第 09 章 + Nginx 課程 |
| **CSRF token / SameSite** | CSRF | 第 10 章 |

其中最能「一次設定、全站受益」的是**安全標頭**與**安全 cookie**——因為它們是在 Web 伺服器/框架層統一設定,不用逐支程式碼改。

### HTTP 安全標頭:在 Nginx 一次設好

這些標頭是給**瀏覽器**的指令,告訴它「對這個網站要多小心」。用 Nginx 反向代理統一加上(詳見 Nginx 課程 `../nginx/README.md` 第 08 章安全設定、第 06 章 SSL/HTTPS):

```nginx
# 放在 server { } 區塊內。always 確保連錯誤回應(4xx/5xx)也會帶上這些標頭
server {
    # ① HSTS:強制瀏覽器之後「一律走 HTTPS」,連一次 HTTP 都不給走
    #    擋降級攻擊與中間人(第 17 章),max-age 是記住多久(秒),這裡是一年
    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;

    # ② CSP:限制頁面只能從哪些來源載入/執行資源,是 XSS 的第二道牆(第 09 章)
    #    這裡:資源預設只准本站、禁用 object、鎖住 base-uri
    add_header Content-Security-Policy "default-src 'self'; object-src 'none'; base-uri 'self'" always;

    # ③ 禁止本頁被塞進 <iframe>,擋點擊劫持(clickjacking)
    add_header X-Frame-Options "DENY" always;

    # ④ 禁止瀏覽器「自己猜」內容型別(MIME sniffing),擋因猜錯型別而觸發的 XSS
    add_header X-Content-Type-Options "nosniff" always;

    # ⑤ 控制 Referer 外洩:跨站時只送來源網域、不送完整網址,避免洩漏內部路徑或 token
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;
}
```

### 安全的 Cookie 設定

session cookie 是攻擊者最想偷的東西(第 09、11 章),三個屬性缺一不可:

```
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax
```

- `HttpOnly`:**JavaScript 讀不到這個 cookie** ——就算網站有 XSS(第 09 章),攻擊者的 `document.cookie` 也偷不到 session。
- `Secure`:cookie 只在 HTTPS 傳送,避免明文竊聽(第 17 章)。
- `SameSite=Lax`:限制跨站自動送出,順帶緩解 CSRF(第 10 章)。

### WAF 的定位:補丁,不是替代品

**WAF(Web Application Firewall,網頁應用防火牆)** 擋在應用前面,用規則過濾惡意請求(SQLi payload、XSS payload、掃描特徵)。它有價值,但你必須擺對它的位置:

> **心智模型:WAF 是 OK 繃,不是治療。** WAF 用「特徵比對」擋已知的攻擊字串——但攻擊者變形 payload(第 09 章的大小寫/編碼繞過)、用 WAF 沒見過的手法,一樣能繞過。WAF 的正確定位是**縱深防禦的一層**:它幫你擋掉海量的自動化掃描與腳本小子,替你的程式碼「爭取時間」(例如在你還沒修完某個 CVE 時當虛擬補丁擋一陣子)。但它**永遠不能取代**「程式碼本身就寫對」——把參數化查詢省掉、只靠 WAF 擋 SQLi,是把命運交到別人的規則庫手裡。**先把程式寫對,再拿 WAF 當補強。**

## 19.7 機密管理(Secrets Management):別把鑰匙貼在門上

系統裡到處是「機密(secrets)」:資料庫密碼、API 金鑰、加密金鑰、TLS 私鑰、第三方服務的 token……管好它們,是加固裡極容易被忽略、後果卻極嚴重的一環。

### 頭號大忌:硬編碼進程式與版控

新手最常犯、也最致命的錯:**把密鑰、密碼直接寫死在程式碼裡,然後提交進 git**。

```python
# ❌ 絕對不要這樣 —— 把密鑰硬編碼進程式碼
DB_PASSWORD = "P@ssw0rd_prod_2024"
AWS_SECRET_KEY = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY"
```

為什麼致命?回扣第 17 章(密碼學攻防)——**一旦提交進 git,它就永遠留在版控歷史裡**,就算你下一個 commit 把它刪掉,`git log` / `git show` 還是挖得出來。無數重大外洩事件就是「開發者不小心把 AWS 金鑰推到公開的 GitHub」,而網路上有機器人**專門 24 小時掃 GitHub 上剛推上去的金鑰**,幾分鐘內就會被撿走盜用。

### 正確做法

```
❌ 錯                          ✅ 對
──────────                    ─────────────────────────────
硬編碼進程式碼                  用環境變數 / 設定檔(且設定檔不進版控)
提交進 git                     機密專用的 secrets manager / Vault
所有環境共用一把               不同環境用不同金鑰,並定期輪替
金鑰永不更換                   金鑰洩漏立即撤銷 + 輪替
```

- **環境變數 / 外部設定**:機密從程式碼抽出來,放進環境變數或設定檔,而設定檔(如 `.env`)**務必加進 `.gitignore`**,絕不進版控。
- **Secrets Manager / Vault**:用專門的機密管理系統(HashiCorp **Vault**、AWS Secrets Manager、GCP Secret Manager……)集中保管——它們提供加密儲存、存取稽核、動態產生短期憑證等能力。程式跑起來時「即時去要」機密,而不是把它寫在磁碟上。
- **金鑰輪替(rotation)**:定期更換金鑰,並在懷疑洩漏時**立即撤銷 + 輪替**。金鑰的生命週期越短,被偷後能被濫用的時間窗就越小(這又是「縮小爆炸半徑」)。

> **心智模型:機密是「鑰匙」,不是「程式碼」。** 你不會把家裡的鑰匙用膠帶貼在大門上,更不會把它影印一份寄給所有看過你原始碼的人(這正是硬編碼進公開 repo 的效果)。鑰匙要放進保險箱(Vault)、要能隨時換鎖(輪替)、每把鑰匙只開必要的門(最小權限)。**程式碼是可以公開的,機密永遠不行——這條界線一旦模糊,加固全盤皆輸。**

## 19.8 安全開發生命週期:把安全「左移」(Shift Left)

前面談的多半是「系統上線後怎麼加固」。但最划算的防禦,是讓漏洞**在寫程式的階段就別出現**——這叫**安全左移(Shift Left)**:把安全活動從「上線後才做的滲透測試」往前挪到開發流程的每一步。這套思維叫 **DevSecOps**(把 Security 融進 DevOps),或更廣義的 **SDLC(Secure Software Development Lifecycle,安全開發生命週期)**。

```
需求 ──▶ 設計 ──▶ 開發 ──▶ 測試 ──▶ 部署 ──▶ 維運
 │        │        │        │        │        │
 └威脅    └安全    └SAST/   └DAST    └設定    └監控
  建模     設計     SCA/     動態     加固     (第20章)
          審查     code     掃描     基線
                   review
        ◀───────── 越左邊發現,修起來越便宜 ─────────
```

> **心智模型:漏洞越晚發現,越貴。** 一個漏洞在「設計階段」發現,改個設計文件就好;在「開發階段」發現,改幾行程式碼;上線後被攻擊者發現,代價是資料外洩 + 事件回應(第 21 章)+ 商譽損失,可能貴上千百倍。左移就是「**在最便宜的環節就把它揪出來**」——這和第 00 章 Kill Chain「在最划算的環節攔截」是同一個經濟學。

### 安全左移的具體活動

- **威脅建模(Threat Modeling)**:在設計階段就問「這個功能會被怎麼攻擊?信任邊界在哪?(第 00 章)」——在還沒寫任何一行程式時,就先想清楚攻擊面。
- **程式碼審查(Code Review)**:同儕審查時把安全納入——特別盯那些「把資料放進危險上下文」的地方(SQL 拼接、`innerHTML`、`eval`、反序列化)。
- **自動化掃描三件套**(整合進 CI/CD,每次提交自動跑):

| 工具類型 | 全名 | 怎麼查 | 抓什麼 |
|---------|------|--------|--------|
| **SAST** | Static Application Security Testing | **靜態**分析原始碼(不用執行) | 程式碼裡的注入、硬編碼機密、危險函式 |
| **DAST** | Dynamic Application Security Testing | 對**跑起來**的應用發攻擊測試 | 執行時才顯現的漏洞(類似自動化滲透) |
| **SCA** | Software Composition Analysis | 掃描**你用的第三方套件** | 依賴套件裡的已知 CVE(供應鏈風險) |

### 供應鏈安全:你的漏洞可能不是你寫的

**SCA 特別重要**,因為現代應用有大量程式碼不是你寫的——是你 `npm install` / `pip install` 進來的第三方套件。回扣第 00 章的**漏洞鏈**:一個你依賴的套件有 CVE(最著名的例子就是 Log4Shell / CVE-2021-44228),你的系統就跟著中招,而你可能根本不知道自己「用到了」那個套件(它是依賴的依賴)。

> **關鍵認知**:你的攻擊面**包含你所有的依賴套件**。「我自己的程式碼很乾淨」不代表安全——一個藏在第五層依賴裡的漏洞套件,一樣能讓你被 RCE。SCA(依賴掃描)+ 鎖定版本 + 及時更新有漏洞的依賴,是供應鏈防禦的基本功。這也是為什麼 19.4 的「修補管理」不只管作業系統,也要管**你的依賴清單**。

## 19.9 備份與韌性:最後一道底線

加固做到極致,你還是要假設「萬一全破了呢?」——尤其面對**勒索軟體(ransomware)**:攻擊者不偷你資料,而是**把你的資料全部加密**,再勒索贖金。這時候,你唯一的救命稻草是**備份**。備份是縱深防禦的**最後一道防線**,也是把主動權從攻擊者手裡奪回來的關鍵(第 21 章事件回應時的復原,全靠它)。

### 3-2-1 備份原則

```
3 份資料副本          →  正本 + 兩份備份(單一副本壞了還有備援)
2 種不同儲存媒體      →  例如本地磁碟 + 雲端/磁帶(不會一次全滅)
1 份異地(offsite)   →  一份放在物理上分開的地方(機房火災/水災也不怕)
```

### 對抗勒索:離線 + 不可變備份

3-2-1 還不夠對付勒索軟體——因為現代勒索攻擊會**故意先找到並一起加密/刪除你的備份**,再加密正式資料。所以關鍵是那份備份必須是攻擊者**碰不到、改不掉**的:

- **離線備份(offline / air-gapped)**:備份完就**斷開連線**(拔線、下線的磁帶),攻擊者在網路上摸不到它,自然加密不了。
- **不可變備份(immutable backup)**:用 WORM(Write Once Read Many,寫入一次、只能讀不能改)機制,備份一旦寫入就**在保留期內無法被刪改**——就算攻擊者拿到了備份系統的權限,也刪不掉已經寫進去的備份。(這概念和第 20 章「日誌完整性」用的 WORM 一模一樣。)

> **心智模型:備份的價值,在「還原成功」的那一刻才兌現。** 一份從沒測過能不能還原的備份,只是「你以為你有」的安全感。太多組織出事才發現備份是壞的、加密的、或還原要花三天——那跟沒有備份沒兩樣。**所以備份不是「備份完就結束」,而是要定期演練還原(restore drill)**:真的拿一份備份出來,還原到一台測試機,確認「資料完整、還原時間可接受」。沒演練過的備份,不算數。

## 19.10 靶場練習:對一台 VM 做加固,前後對照

> **授權提醒**:本節所有操作**只在你自己搭建的虛擬機或授權的隔離實驗室**(第 01 章)進行。加固自己的機器完全合法;但若把「加固後再打一遍」的攻擊測試,用在任何未授權的系統上,在台灣一樣觸犯《刑法》第 36 章妨害電腦使用罪(第 00 章)。**攻擊只能打自己的靶機。**

前面十幾章你都在「打」,這一章第一次「守」。最好的驗證方式是**紫隊思維**(第 00 章):先加固,再把前面學過的攻擊打一遍,看擋掉多少。

### 練習拓撲

```
   ┌──────────────┐     加固前先打一遍     ┌──────────────────┐
   │  攻擊機 Kali  │ ───────────────────▶ │  目標 VM          │
   │ (紅隊視角)    │ ◀─── 加固後再打一遍 ── │  乾淨 Ubuntu 或   │
   └──────────────┘                       │  Metasploitable   │
                                           └──────────────────┘
                        (全部在隔離網段,對外不通,第 01 章)
```

### 步驟:量化你的加固成效

**① 加固前:先量基線。** 在目標 VM 上跑 Lynis,記下初始分數與掃描結果:

```bash
sudo lynis audit system         # 記下這個 Hardening index(例如 56/100)當作「加固前」基準
```

同時,從 Kali 對它做一次攻擊者視角的盤點與攻擊(用你前面學的):

```bash
nmap -sV 目標VM_IP              # 第 05 章:看它開了哪些 port、跑什麼服務版本
hydra -l root -P 字典 ssh://目標VM_IP    # 第 11、15 章:試 SSH 密碼暴力破解
```

**② 動手加固。** 依本章清單逐項做,對照 Lynis 給的 `[SUGGESTION]` 和 CIS Benchmark:

- 主機層(19.3):禁 root SSH、改金鑰認證、關掉不用的服務與 port、移除多餘套件。
- 修補(19.4):`apt update && apt upgrade` 把已知 CVE 補掉。
- 網路(19.5):設好 ufw,入向/出向都預設拒絕、只開必要 port。
- Web 層(19.6):若有跑 Web,加上安全標頭、關掉 debug、改掉預設帳密。

**③ 加固後:再量一次,做對照。**

```bash
sudo lynis audit system         # 再看 Hardening index(希望明顯上升,例如 56 → 82)
```

然後**把第 ① 步的攻擊原封不動再打一遍**,對照:

| 加固前 | 加固後(期望) |
|--------|--------------|
| `nmap` 掃到一堆開放 port | 只剩必要 port,其餘掃不到(關服務 + 防火牆) |
| Hydra 慢慢試密碼,理論上會中 | 密碼認證已關,Hydra **直接無效**(金鑰認證) |
| Web 回應沒有安全標頭 | 回應帶上 HSTS/CSP/X-Frame-Options |
| Lynis 56/100 | Lynis 82/100 |

> **心智模型:加固的成效,要「用攻擊來驗證」。** 光看 Lynis 分數上升還不夠——真正有說服力的是「**我親手打過的那些攻擊,加固後打不進去了**」。這就是紫隊(第 00 章)的閉環:你既是打的人、也是守的人,親眼看見「同一招,加固前得手、加固後撞牆」,你對每一條加固措施「到底擋掉了什麼」的理解,會比背一百遍清單都深刻。**沒被擋掉的那些攻擊,就是你加固清單的缺口**——回去補它。

## 19.11 本章小結

- **防禦要成「體系」,不能只靠「補丁」。** 前面十幾章的點狀防禦(參數化查詢、輸出編碼、授權檢查……),要收斂成一套「就算有漏洞也難被利用、被利用了危害也有限」的結構。這才是這門課的目的地——以攻代防、讓系統更安全(第 00 章)。
- **四個核心心法**:①**縱深防禦**(多層獨立防線,打斷 Kill Chain 任一環,第 00、09 章)②**最小權限**(只給剛好夠用的權限,遏制爆炸半徑,第 12、16 章)③**零信任**(不因「在內網」就信任,每次都驗證,打穿第 10 章 SSRF 的假設)④**縮小攻擊面**(最安全的門是不存在的門,第 00、05 章)。
- **主機加固 = 拆門、關門、鎖門**:關掉不用的服務與 port、移除預設帳號/改預設密碼、最小安裝、收緊檔案權限、SSH 加固(禁 root、金鑰認證、白名單)。核心原則:**預設拒絕、明列放行**。
- **修補是投報率最高的防禦**:多數真實入侵打的是「已修補但沒裝」的已知 CVE(第 14 章),不是 0-day。搭配 CIS Benchmark + Lynis/OpenSCAP,把加固變成可量化的工程。
- **網路防禦**:防火牆入向/**出向(egress)都要管**——出向鎖死能擋 C2 外連、緩解 SSRF(第 10 章);網路分段/DMZ 切斷横向移動(第 16 章);VPN + 收斂對外暴露,把攻擊面縮到最小。
- **Web 應用防禦收成清單**:參數化查詢(第 07)、輸出編碼(第 09)、授權檢查(第 12)、安全標頭(HSTS/CSP/X-Frame-Options/X-Content-Type-Options)、安全 cookie(HttpOnly/Secure/SameSite)、CSRF token。**WAF 是補丁不是替代品——先把程式寫對。**
- **機密管理**:別硬編碼、別進版控(第 17 章);用環境變數/Secrets Manager/Vault;定期輪替、洩漏立即撤銷。機密是鑰匙,不是程式碼。
- **安全左移(DevSecOps)**:威脅建模、code review、SAST/DAST/SCA 整合進 CI/CD;**SCA 管供應鏈依賴的 CVE**——你的攻擊面包含你所有依賴套件(第 00 章漏洞鏈、Log4Shell)。漏洞越早發現越便宜。
- **備份是最後一道底線**:3-2-1 原則;對抗勒索要**離線 + 不可變(WORM)**備份;**沒演練過還原的備份不算數**(銜接第 21 章)。

> **心智模型(把整章串起來):加固 = 「把每扇門鎖好、把沒用的門直接拆掉、把院子分成好幾進」。** 這一章做的全部事情,本質就是**縮小並強化攻擊面**——讓攻擊者能敲的門更少、每扇門更難撬、就算撬開一扇也進不了深處。這是防禦的第一階段,也是最重要的一階段。

> **下一章預告**:但——**門鎖得再好,你終究會有一扇沒鎖好,或有一把鑰匙被偷。** 只要攻擊面不是零,被攻破就是機率與時間問題(0-day、內鬼、被釣魚的員工都是加固擋不掉的)。所以加固之後,你必須「**裝監視器**」:假設終究會有人進來,那我要能**看見他**。第 20 章談 **偵測與監控(Log、SIEM、IDS/IPS)**——從最原始的日誌,到把散落事件串成攻擊故事的 SIEM,再到在網路與主機上放哨的 IDS/IPS,並用「紅隊打、藍隊看」的紫隊訓練,親眼看見前面學過的攻擊在監控畫面上長什麼樣子。**加固是「不讓人進」,偵測是「假設他會進,而我要看見」——這是縱深防禦的一體兩面。**
