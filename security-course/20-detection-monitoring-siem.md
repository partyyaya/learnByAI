# 第 20 章:偵測與監控 —— Log、SIEM 與 IDS/IPS

> 上一章(第 19 章)在做「加固」——把每一扇門鎖好、關掉用不到的服務、縮小攻擊面。那是「不讓人進來」。
> 但這一章要先承認一件殘酷的事:**門鎖得再好,你終究會有一扇沒鎖好,或有一把鑰匙被偷。** 只要攻擊面不是零,
> 被攻破就只是機率與時間問題。那怎麼辦?裝監視器。這一章談的不是「怎麼把攻擊擋在門外」,而是「**假設他已經進來了,我怎麼看見他**」——
> 從最原始的 Log(日誌),到把 log 串成攻擊故事的 SIEM,再到在網路與主機上放哨的 IDS/IPS。
> 最後我們會回扣第 00 章的 Kill Chain(在最划算的環節攔截)與 MITRE ATT&CK(藍隊威脅偵測的共通語言),
> 並用「紅隊打、藍隊看」的紫隊訓練,親手驗證:前面十幾章學過的攻擊,到底在監控畫面上長什麼樣子。

## 20.1 心態:Assume Breach —— 「防不住」不等於「輸」

先講一個會顛覆新手直覺的觀念。傳統資安思維是「築高牆」:防火牆、WAF、加固,把壞人擋在外面。這當然要做(第 19 章),但如果你的整套安全**只押在「擋住」這一件事上**,那你其實是在賭「牆永遠不破」——而這場賭注,防守方注定輸,因為:

- 攻擊者只要找到**一個**洞就能進;你卻要守住**每一個**洞。這是根本不對等的賽局。
- 0-day(第 00 章)、供應鏈汙染、內鬼、被釣魚的員工(第 18 章)……有太多路徑是「加固」擋不掉的。
- 人會犯錯:一個沒改的預設密碼、一個忘了關的測試 port,牆就破了。

於是現代防禦的主流心態變成 **Assume Breach(假設已被攻破)**:

> **心智模型:Assume Breach。** 別問「我擋不擋得住?」,要問「**當他進來時,我多久能發現?發現後多快能止血?**」。防禦的勝負不再是「有沒有被攻破」(這幾乎無可避免),而是「**攻破到被逮住之間,他有多少時間為所欲為**」。這段時間,業界叫 **dwell time(潛伏時間)**——業界統計常以「週」甚至「月」為單位,而偵測與回應的全部意義,就是把它壓到「分鐘」。

這正是第 00 章 Kill Chain 的防禦價值所在。攻擊是一條七階段的鏈(偵察→武器化→遞送→利用→安裝→C2→行動),你**不需要擋住全部**,只要在**任何一環看見他、打斷他**,整條鏈就斷了。加固(第 19 章)是想讓他在前幾環就進不來;偵測(本章)則是「就算他過了前幾環,我也要在他『行動』(竊資料、加密勒索)之前抓到」。兩者是**縱深防禦**的一體兩面。

> **關鍵認知**:偵測不是「加固失敗後的補救」,而是縱深防禦裡**平行的一層**。一個成熟的組織會同時投資「擋」(Protect)與「看」(Detect)。只有牆、沒有監視器,等於你家裝了防盜門卻沒裝攝影機——小偷一旦撬開門,就能在你家為所欲為,而你渾然不覺。

Assume Breach 帶來三個實務結論,貫穿本章:

1. **一定要記 log**——沒有紀錄,你連「他來過」都證明不了(20.2)。
2. **log 要送到攻擊者碰不到的地方**——因為他進來第一件事就是想毀屍滅跡(20.3)。
3. **要能把散落的事件串起來看**——單一事件無意義,串成故事才是攻擊(20.5 的 SIEM)。

## 20.2 Log:偵測的原料 —— 要記什麼、從哪來

偵測的一切都建立在 **Log(日誌)** 之上。log 就是系統忠實記下的「誰、在什麼時間、做了什麼」的流水帳。沒有 log,再貴的 SIEM、再厲害的分析師都是巧婦難為無米之炊——**你分析不了你沒記下來的東西**。

### 要記什麼:圍繞「攻擊者一定會碰到的動作」

新手常犯的錯是「什麼都記」或「什麼都不記」。正確做法是圍繞 Kill Chain 想:攻擊者從進來到達成目的,**一定會觸發哪些動作**?那些就是你的必記清單:

| 類別 | 具體事件 | 為什麼要記(對應攻擊) |
|------|----------|----------------------|
| **認證事件** | 登入成功 / 失敗、登出、密碼錯誤、帳號鎖定 | 暴力破解(第 11、15 章)、憑證填充、異常時間/地點登入 |
| **權限與帳號變更** | 新增/刪除帳號、加入管理員群組、`sudo`、權限提升 | 提權與持久化(第 16 章)——攻擊者最愛偷偷開個管理員後門 |
| **程序執行** | 執行了什麼程式、命令列參數、父子程序關係 | 惡意程式、living-off-the-land(用系統內建工具攻擊) |
| **網路連線** | 對外連線的目的 IP/port、DNS 查詢、連線量 | C2 通道(第 00 章)、資料外洩、掃描 |
| **檔案存取** | 敏感檔案的讀寫、設定檔被改、大量檔案被讀取 | 竊資料、勒索加密、改設定檔做持久化 |
| **系統與稽核** | 服務啟停、排程任務(cron)變更、**log 被清除** | 持久化、反鑑識(covering tracks,第 16 章) |

> **心智模型:從攻擊者的必經之路反推監控點。** 攻擊者可以繞過很多東西,但有些動作他**繞不掉**:要進系統就得認證(留下登入紀錄)、要控制就得執行程式(留下程序紀錄)、要偷資料就得對外連線(留下網路紀錄)。把 log 埋在這些「必經之路」上,他走過就會留下腳印。這跟 20.7 的偵測工程是同一個思路。

### Log 從哪來:五大來源

一個完整的監控體系,log 來自五個層次。你要有意識地把它們全部收進來,因為攻擊往往橫跨多層:

```
        ┌─────────────────────────────────────────────┐
        │  ① 作業系統層                                 │
        │     Linux : auditd(稽核)、/var/log/syslog、  │
        │             /var/log/auth.log(認證)          │
        │     Windows: Event Log(Security/System/App)  │
        ├─────────────────────────────────────────────┤
        │  ② Web / 應用伺服器層                          │
        │     Nginx / Apache 的 access log、error log   │
        │     (回扣 Nginx 課程第 09 章 logging-monitoring)│
        ├─────────────────────────────────────────────┤
        │  ③ 應用程式層                                 │
        │     你自己程式碼寫的 log(登入、交易、錯誤)     │
        ├─────────────────────────────────────────────┤
        │  ④ 網路設備層                                 │
        │     防火牆、路由器、IDS/IPS、VPN 的紀錄         │
        ├─────────────────────────────────────────────┤
        │  ⑤ 雲端層                                     │
        │     AWS CloudTrail、GCP Audit Logs、           │
        │     Azure Activity Log(誰對雲端 API 做了什麼)  │
        └─────────────────────────────────────────────┘
```

- **① 作業系統**:Linux 的 `auth.log` 記登入、`auditd` 可以細到「哪個程序讀了哪個檔」;Windows 的 **Event Log** 用「事件 ID」分類(例如 `4624`=登入成功、`4625`=登入失敗、`4720`=新增帳號),這些 ID 是藍隊的基本功。
- **② Web 伺服器**:Nginx/Apache 的 access log 記下每一個 HTTP 請求——這是抓 Web 攻擊(SQLi、XSS、掃描)最直接的原料,Nginx 課程第 09 章專門講過怎麼配置與分析,本章 20.4 會實際讀一段。
- **③ 應用程式**:框架和你的程式碼可以記「業務語意」的事件(誰下了訂單、誰改了 email),這是 OS/Web log 看不到的。
- **④ 網路設備**:防火牆記「哪個 IP 連了哪個 port」,是抓掃描與 C2 外連的關鍵。
- **⑤ 雲端**:雲端環境裡,**API 呼叫就是一切**。CloudTrail 記下「誰用哪把金鑰、對哪個資源、做了什麼 API 動作」——雲端入侵幾乎都能在這裡看到痕跡。

> **新手誤區**:「我開了 log 就安全了。」不。開了 log 只是**有了原料**。如果沒人看、沒集中、沒告警,那些 log 就只是在硬碟裡默默滾動、然後被輪替(rotate)刪掉的垃圾。無數重大資安事件的事後檢討都寫著同一句話:「其實 log 裡早就有跡象,只是沒人在看。」

## 20.3 集中式日誌與日誌完整性 —— 攻擊者第一件事就是清 Log

這一節講一個生死攸關、但新手最常忽略的點:**log 存在哪裡,決定了它值不值得信。**

回想第 16 章(提權與後滲透)的 **covering tracks(清除痕跡)**:一個像樣的攻擊者拿到主機後,**首要動作之一就是清理日誌**——刪掉 `/var/log/auth.log` 裡自己的登入紀錄、清空 shell history、關掉 auditd。對應到 MITRE ATT&CK,這叫 **T1070 Indicator Removal(指標移除)**。

問題來了:如果你的 log 就存在**那台被攻破的主機本地**,那結局是什麼?

```
攻擊者拿到 root
   → log 就在他腳下的 /var/log/
   → rm -rf /var/log/*  或  echo > /var/log/auth.log(清空)
   → 你的「證據」跟著淪陷的主機一起消失了
   → 事後鑑識(第 21 章)時,你面對的是一片空白
```

> **心智模型:證據不能跟犯罪現場放在一起。** 把 log 只存本地,等於把監視器的錄影帶放在被闖空門的那個房間裡——小偷進來第一件事就是把帶子抽走。**log 必須即時送到一個「攻擊者就算拿下這台主機也碰不到」的地方。** 這就是集中式日誌(centralized logging)存在的全部理由。

### 集中式日誌:把 log 即時送走

作法是讓每台主機把 log **即時串流**到一台獨立、加固過、權限嚴格隔離的**中央日誌伺服器**(log server / log collector):

```
  主機 A ─┐
  主機 B ─┼──(遠端 syslog / agent 即時傳送)──▶  中央日誌伺服器
  主機 C ─┘                                        (獨立網段、嚴格權限、
  Web 伺服器 ─────────────────────────────────▶     攻擊者拿下主機 A 也進不來)
```

關鍵設計原則:

1. **即時傳送**:log 一產生就送走,不要等。攻擊者從進來到清 log 往往只有幾秒到幾分鐘的空窗——你要在那之前就把它複製出去。
2. **單向、獨立**:中央伺服器放在獨立網段,對外只收 log、不提供其他服務(縮小它自己的攻擊面),而且被監控的主機**沒有權限回頭刪中央伺服器上的 log**。
3. **WORM(Write Once Read Many,寫入一次、只能讀)**:讓 log 一旦寫入就**不可竄改、不可刪除**,只能追加與讀取。這樣即使攻擊者攻破了中央伺服器,也改不掉已經寫進去的歷史紀錄。
4. **完整性校驗**:對 log 做雜湊鏈或簽章,任何人事後篡改都會被驗出來(呼應第 17 章密碼學的完整性概念)。

Linux 上最基本的一步,就是把本地 syslog 轉發到遠端。以 `rsyslog` 為例:

```bash
# /etc/rsyslog.conf 或 /etc/rsyslog.d/50-remote.conf
# 把所有日誌即時轉發到中央日誌伺服器
# *.*                → 所有 facility、所有等級的日誌都送
# @@                 → 兩個 @ 代表用 TCP(可靠傳輸;單個 @ 是 UDP,可能掉包)
# 10.0.0.50:514      → 中央日誌伺服器的 IP 與 syslog port
*.*    @@10.0.0.50:514
```

> **關鍵認知**:集中式日誌不只是為了「攻擊者刪不掉」,還有兩個附帶好處——(1)**方便關聯分析**:攻擊橫跨多台主機時,你需要把所有 log 攤在同一個地方看(這是 20.5 SIEM 的前提);(2)**時間軸對齊**:所有主機都要用 NTP 對時,否則你把 A 機的 log 和 B 機的 log 併起來,時間戳對不上,就拼不出正確的攻擊順序。**做鑑識(第 21 章)時,一個可信、完整、時間對齊的 log,價值連城。**

## 20.4 讀懂 Log:從一段日誌認出攻擊

有了 log,你得看得懂。這一節用兩段真實格式的 log,示範藍隊怎麼「用肉眼」認出攻擊特徵——這是你在 SIEM 自動化之前,一定要先具備的手感。

### 例一:auth.log —— 認出 SSH 暴力破解

Linux 的 `/var/log/auth.log`(認證日誌)是抓登入攻擊的第一現場。看這一段:

```
# 逐行解讀:同一個來源 IP 在幾秒內狂試不同帳號密碼 —— 典型暴力破解
Jul  3 14:22:01 web01 sshd[2011]: Failed password for root from 203.0.113.66 port 51022 ssh2
Jul  3 14:22:02 web01 sshd[2013]: Failed password for root from 203.0.113.66 port 51044 ssh2
Jul  3 14:22:03 web01 sshd[2015]: Failed password for invalid user admin from 203.0.113.66 port 51066 ssh2
Jul  3 14:22:04 web01 sshd[2017]: Failed password for invalid user oracle from 203.0.113.66 port 51088 ssh2
Jul  3 14:22:59 web01 sshd[2099]: Accepted password for deploy from 203.0.113.66 port 52002 ssh2
```

逐行看門道:

- 前四行都是 `Failed password`,而且來源 IP **全是同一個** `203.0.113.66`,時間戳**每秒一次甚至更密**——正常人不可能一秒試一次密碼。這個「同源、高頻、連續失敗」的模式就是**暴力破解(brute force)** 的簽名(Hydra 這類工具打出來就長這樣,第 11、15 章)。
- `invalid user admin`、`invalid user oracle`:攻擊者在**枚舉常見帳號**(admin、oracle、test……),這些帳號在系統上根本不存在——這是掃描/列舉(第 05 章)的味道。
- 最關鍵的是**最後一行**:`Accepted password for deploy`。前面一連串失敗之後,突然一次**成功**,而且來源 IP 還是同一個 `203.0.113.66`。

> **關鍵認知**:單看前四行「登入失敗」,你可能覺得「反正沒進來,算了」。但把第五行**串起來看**,故事完全變了:**這是一次成功的暴力破解**——攻擊者猜中了 `deploy` 帳號的密碼,已經進來了!這就是為什麼「關聯」如此重要(下一節 SIEM 的核心)。一連串失敗**不可怕**,失敗之後那一次成功才致命。

### 例二:Nginx access log —— 認出掃描與注入嘗試

Web 伺服器的 access log 是抓 Web 攻擊的第一現場(Nginx 課程第 09 章講過格式)。看這一段:

```
# 同一 IP 在 2 秒內對一堆「敏感路徑」和「攻擊 payload」發請求 —— 掃描 + 探漏洞
198.51.100.9 - - [03/Jul/2026:15:01:11] "GET /admin/ HTTP/1.1" 404 153 "-" "sqlmap/1.7"
198.51.100.9 - - [03/Jul/2026:15:01:11] "GET /.env HTTP/1.1" 404 153 "-" "sqlmap/1.7"
198.51.100.9 - - [03/Jul/2026:15:01:12] "GET /wp-login.php HTTP/1.1" 404 153 "-" "sqlmap/1.7"
198.51.100.9 - - [03/Jul/2026:15:01:12] "GET /product?id=1' HTTP/1.1" 500 512 "-" "sqlmap/1.7"
198.51.100.9 - - [03/Jul/2026:15:01:13] "GET /product?id=1 UNION SELECT 1,2,3-- HTTP/1.1" 200 8021 "-" "sqlmap/1.7"
198.51.100.9 - - [03/Jul/2026:15:01:14] "GET /download?f=../../../../etc/passwd HTTP/1.1" 200 2210 "-" "sqlmap/1.7"
```

逐行解讀,每一行都是一個危險訊號:

- **User-Agent 是 `sqlmap/1.7`**:這根本是自動化攻擊工具(第 07 章)的預設名字,大剌剌寫在請求裡。正常瀏覽器不會這樣。(當然,老練的攻擊者會改掉 UA,所以不能只靠這一點,但看到它幾乎可以確定是攻擊。)
- `GET /admin/`、`/.env`、`/wp-login.php`,而且都回 `404`:攻擊者在**盲猜敏感路徑**——後台、環境變數檔(裡面常有資料庫密碼、API 金鑰!)、WordPress 登入頁。連續 404 + 同源 = **目錄掃描/列舉**(第 05 章)。
- `/product?id=1'`(結尾一個單引號)回 `500`:這是在**試 SQL 注入**——用一個單引號破壞 SQL 語法,伺服器回 500 錯誤,等於告訴攻擊者「這裡有注入點」(第 07 章)。
- `/product?id=1 UNION SELECT 1,2,3--` 回 `200` 且回應 8021 bytes:**UNION-based SQLi 成功了**(第 07 章),攻擊者正在撈資料。
- `/download?f=../../../../etc/passwd` 回 `200`:**路徑穿越(path traversal)成功**(第 13 章),攻擊者讀到了系統的 `/etc/passwd`。

> **心智模型:HTTP 狀態碼是攻擊者的體溫計。** 一連串 `404` = 他在盲猜、還沒找到門;突然一個 `500` = 他戳到了會出錯的地方(可能是注入點);由 `500`/`404` 轉為 `200` = **他成功了**。藍隊看 access log,不是看單一請求,而是看**一個 IP 的請求序列**如何從「亂試」演變成「命中」——這個「狀態碼的溫度變化」就是攻擊得手的訊號。

這兩個例子告訴你:**攻擊在 log 裡是有形狀的**。而人力逐行讀 log 顯然不可能規模化——每天幾百萬行 log,你不可能用肉眼盯。所以我們需要一個工具,把「你剛剛用肉眼做的判斷」自動化、規模化——那就是 SIEM。

## 20.5 SIEM:把散落的 Log 串成一個攻擊故事

**SIEM(Security Information and Event Management,安全資訊與事件管理)** 是藍隊的中樞神經。一句話定義它做的事:

> **SIEM = 把所有來源的 log 集中蒐集 → 正規化 → 關聯分析 → 產生告警。**

拆成四個步驟看:

```
① 蒐集 Collect      各主機/設備/雲端的 log 全部匯進來(20.2 的五大來源)
        ↓
② 正規化 Normalize   把格式各異的 log 轉成統一結構
                     (Nginx 的時間格式 ≠ Windows Event ≠ CloudTrail,
                      要統一成「時間、來源IP、使用者、動作、結果」才能比對)
        ↓
③ 關聯 Correlate     跨來源、跨時間把相關事件「串起來」看
                     (這是 SIEM 的靈魂,單看一條 log 看不出的攻擊,串起來就現形)
        ↓
④ 告警 Alert         符合規則就通知分析師 / 觸發自動回應
```

### 為什麼「關聯」才是重點

前四步裡,**關聯(correlation)是 SIEM 真正的價值**。因為:

> **心智模型:單一事件是雜訊,串起來才是攻擊。** 「一次登入失敗」——雜訊,誰都會打錯密碼。「一次登入成功」——正常。但「**同一 IP 在 60 秒內 200 次登入失敗、緊接著一次成功**」——這就是 20.4 例一那個故事:一次成功的暴力破解。關聯做的事,就是把 20.4 你用肉眼串起來的判斷,寫成規則、自動化、7×24 不睡覺地跑。

舉兩條實用的關聯規則,你會發現它們正是把前面的手感規則化:

**規則一:偵測暴力破解成功**

```
若「同一來源 IP」在「60 秒內」產生「≥ 20 次登入失敗(4625 / Failed password)」
   接著「同一 IP」出現「1 次登入成功(4624 / Accepted)」
→ 觸發高危告警:「疑似暴力破解成功」
```

**規則二:偵測疑似資料外洩(多事件關聯)**

```
若「管理員帳號」在「非上班時間(如凌晨 3 點)」登入
   且 同一 session 內「對資料庫/檔案伺服器的下載量」遠超基線(如 > 平時的 50 倍)
→ 觸發高危告警:「疑似資料外洩」
```

規則二特別能體現關聯的威力:「管理員登入」單看正常、「下載資料」單看正常、「凌晨 3 點」單看只是晚睡——但**三者疊在一起**,就是一幅資料外洩的典型畫面。這種「多個各自無害的事件疊起來才可疑」的偵測,正是人力做不到、非得靠 SIEM 的地方。

### 常見 SIEM 工具對照

| 工具 | 授權 | 定位與特點 | 適合誰 |
|------|------|-----------|--------|
| **Splunk** | 商業(貴) | 業界老牌霸主,SPL 查詢語言強大、生態完整 | 預算充足的大型企業 |
| **ELK / Elastic Stack** | 開源(有商業版) | Elasticsearch + Logstash + Kibana,彈性高、自由度大,但要自己組裝調校 | 想自建、有工程能力的團隊 |
| **Wazuh** | 開源(免費) | 基於 OSSEC,**內建 HIDS + SIEM**,開箱有規則與 ATT&CK 對應 | 學習、實驗室、中小企業(本章 20.8 就用它) |
| **Microsoft Sentinel** | 商業(雲端) | Azure 上的雲端原生 SIEM,和 M365/雲端整合深 | 重度使用微軟/雲端生態的組織 |

### SIEM 不是萬靈丹:tuning 與告警疲勞

新手買了 SIEM 常以為「裝上就自動抓壞人」,結果踩進最經典的坑。你必須認清 SIEM 的三個殘酷現實:

1. **要調校(tuning)**:預設規則對你的環境一定不合身。太寬 → 漏掉真攻擊(**false negative,漏報**);太嚴 → 一堆正常行為被當攻擊(**false positive,誤報**)。調校就是不斷在這兩者間找平衡,是一項**持續的工作**,不是一次性設定。

2. **告警疲勞(alert fatigue)**:這是 SIEM 的頭號殺手。如果規則調得太敏感,SIEM 每天噴出幾千條告警,分析師根本看不完,久了就**麻木、乾脆全部忽略**——於是真正的攻擊淹沒在雜訊裡被放過。**史上多起重大外洩事件,SIEM 其實有告警,但被淹沒在告警海裡沒人理。**

3. **False Positive / False Negative 的取捨**:這是所有偵測系統的永恆兩難,一定要理解:

| | 判定為攻擊 | 判定為正常 |
|------|-----------|-----------|
| **實際是攻擊** | ✅ True Positive(正確抓到) | ❌ **False Negative(漏報)** —— 真攻擊被放過,最危險 |
| **實際是正常** | ❌ **False Positive(誤報)** —— 造成告警疲勞 | ✅ True Negative(正確放行) |

> **心智模型:偵測的藝術,是在漏報與誤報之間走鋼索。** 你不可能同時把兩者都降到零——把門檻調嚴,漏報少了但誤報爆增(告警疲勞);調鬆,誤報少了但漏報變多(放走真攻擊)。好的偵測工程(20.7)追求的不是「零誤報」的幻想,而是「**在可接受的誤報量下,盡量不漏掉高危攻擊**」,並把有限的分析師注意力,集中在最高價值的告警上。

## 20.6 IDS / IPS:在網路與主機上放哨

SIEM 是「事後分析 log」;**IDS/IPS 則是「即時盯著流量與行為」的哨兵**。兩者互補:哨兵發現的異常,也會變成 log 送進 SIEM。

### IDS vs IPS:看見 vs 出手

| | **IDS(Intrusion Detection System 入侵偵測系統)** | **IPS(Intrusion Prevention System 入侵防禦系統)** |
|------|-------------------------------------------------|--------------------------------------------------|
| **做什麼** | 偵測到攻擊 → **告警**,但不擋 | 偵測到攻擊 → **主動阻擋**(丟包、斷連線) |
| **部署位置** | 旁路(監聽流量副本),不擋在路徑上 | 串接(in-line),流量必須穿過它 |
| **像什麼** | **監視器 + 保全按鈴通報** | **會自己把門關上的保全** |
| **風險** | 看到了但擋不住,要靠人反應 | **誤判(false positive)會擋掉正常流量**,影響營運 |
| **取捨** | 安全,不影響流量,但被動 | 主動,但要極謹慎調校,否則自己 DoS 自己 |

> **心智模型:IDS 是「看見」,IPS 是「出手」。** 差別就在「要不要讓它自動動手擋」。IPS 聽起來更強,但它有個致命風險:一旦誤報,它會**擋掉合法流量**——想像它誤判你的正常客戶是攻擊者,直接切斷連線,那就是你自己造成的服務中斷。所以很多組織的實務是:**新規則先以 IDS 模式(只告警)跑一段時間、確認幾乎不誤報,再切成 IPS(自動阻擋)**。這又回到 20.5 的漏報/誤報取捨。

### NIDS vs HIDS:網路型 vs 主機型

依「裝在哪、看什麼」,又分兩類,兩者也是互補的:

| | **NIDS(網路型)** | **HIDS(主機型)** |
|------|------------------|------------------|
| **看什麼** | 網路流量(封包) | 單台主機內部:log、檔案完整性、程序、登入 |
| **代表工具** | **Snort、Suricata、Zeek** | **Wazuh、OSSEC、auditd** |
| **優勢** | 一個點看全網段流量、看得到掃描與 C2 外連 | 看得到「主機內部」發生什麼(誰改了設定檔、誰提權) |
| **盲點** | **加密流量(HTTPS)看不到內容**、看不到主機內部行為 | 只看自己這台,看不到網路全貌;主機被攻破後 agent 可能被關 |

實務上兩者都要:NIDS 看「網路層的門口」,HIDS 看「每個房間裡發生什麼」。這也呼應 20.2——網路 log 和主機 log 缺一不可。

### 偵測方法:Signature-based vs Anomaly-based

不論 NIDS 還是 HIDS,底層偵測邏輯不外乎兩種,這是**整個偵測領域最核心的分野**,務必吃透:

| | **Signature-based(特徵比對)** | **Anomaly-based(異常偵測)** |
|------|-------------------------------|------------------------------|
| **原理** | 比對「已知攻擊的特徵/指紋」,像防毒軟體 | 先學習「正常」的基線,凡是偏離基線的就報 |
| **抓得到** | 已知攻擊(有人寫過規則的) | 未知攻擊、0-day、內部異常行為 |
| **抓不到** | ❌ **0-day / 從沒見過的新攻擊**(沒有特徵可比對) | —— |
| **主要缺點** | 規則要不斷更新;稍微變形就繞過 | ❌ **誤報多**(正常行為的變化容易被當異常);基線難建、易被「溫水煮青蛙」 |
| **像什麼** | 通緝犯照片比對(有照片才抓得到) | 「這個人今天行為好反常」的直覺 |

> **心智模型:一個靠記憶,一個靠直覺。** Signature-based 靠「記得所有壞人長相」——問題是**沒見過的新壞人(0-day)它認不出**。Anomaly-based 靠「這不對勁」的直覺——問題是**它太容易大驚小怪(誤報)**,而且聰明的攻擊者會「慢慢來」,一點一點把異常行為「養進」基線裡(讓 anomaly 系統誤以為那是正常)。**現代方案兩者並用**:signature 快狠準地擋掉海量已知攻擊,anomaly 補上「沒見過的」那一塊——又是縱深防禦。

### 一條 Suricata/Snort 規則,逐欄位解剖

NIDS 的 signature 長什麼樣?看一條偵測 SSH 暴力破解的規則(Snort/Suricata 語法相容):

```
alert tcp $EXTERNAL_NET any -> $HOME_NET 22 (msg:"Possible SSH Brute Force"; flow:to_server; flags:S; threshold:type threshold, track by_src, count 5, seconds 30; sid:1000001; rev:1;)
```

逐欄位拆解:

```
alert              ← 動作:符合就「告警」(其他選項:drop=丟包擋下[IPS 模式]、log、pass)
tcp                ← 協定:TCP(也可 udp / icmp / http…)
$EXTERNAL_NET any  ← 來源:外部網段的「任何」來源 port($XXX 是可設定的變數)
->                 ← 方向:從來源流向目的
$HOME_NET 22       ← 目的:內部網段的 22 port(SSH)
─────── 以下括號內是「規則選項」,描述要比對什麼、怎麼告警 ───────
msg:"..."          ← 告警訊息:命中時顯示的說明,方便分析師看懂
flow:to_server     ← 只比對「流向伺服器」方向的封包(過濾掉回應方向)
flags:S            ← 比對 TCP 的 SYN 旗標 = 每一個「新連線的建立」
threshold:...      ← 門檻:track by_src(依來源 IP 計數)、
                     count 5 / seconds 30 = 同一來源 30 秒內 ≥ 5 次新連線才觸發
                     (這就是把「暴力破解=短時間大量連線」寫成規則!)
sid:1000001        ← 規則的唯一編號(signature ID;本地自訂規則慣例用 ≥ 1000000)
rev:1              ← 版本號:規則改一次就 +1,方便追蹤
```

> **關鍵認知**:讀懂這條規則,你就懂了 signature-based 偵測的全部精神——**它把「攻擊在網路上的形狀」(30 秒內同源 5 次 SSH 新連線)翻譯成一條機器能比對的規則。** 這和 20.4 你用肉眼認暴力破解、20.5 的 SIEM 關聯規則,是**同一件事在不同層次的實現**。你也看到它的天生弱點:攻擊者只要把速度放慢到「30 秒 4 次」,就繞過了這條規則——這就是為什麼要搭配 anomaly-based,以及不斷調校門檻。

## 20.7 進階:MITRE ATT&CK 與偵測工程

前面談的都是「怎麼偵測」的機制。這一節談更高階的問題:**我到底該偵測「什麼」?** 這門學問叫**偵測工程(Detection Engineering)**,而它的共通語言,就是第 00 章提過的 **MITRE ATT&CK**。

### 用 ATT&CK 反推「該偵測什麼」

Kill Chain(第 00 章)給了攻擊的**七個宏觀階段**;**MITRE ATT&CK** 則把它細化成一張龐大的矩陣——把攻擊者的 **戰術(Tactic,想達成什麼目標)** 與 **技術(Technique,具體怎麼做)** 全部編號、分類、記錄。這套 **TTP(Tactics, Techniques, and Procedures)** 是全球紅藍隊溝通的標準詞彙。

偵測工程的核心方法論,是**從「攻擊者會做什麼」反推「我該偵測什麼」**:

```
攻擊者的戰術/技術(ATT&CK)     →  會留下什麼痕跡(資料源)  →  我寫什麼偵測規則
────────────────────────────      ─────────────────────      ──────────────────
Credential Access / 暴力破解         auth.log 大量失敗登入        20.4 例一 / 20.5 規則一
  (T1110 Brute Force)
Discovery / 網路服務掃描             防火牆/IDS 短時間大量           Suricata 掃描規則
  (T1046 Network Service Scanning)   不同 port 連線
Persistence / 建立帳號               Windows 4720 / auth.log       「非預期新增帳號」告警
  (T1136 Create Account)             新增使用者事件
Defense Evasion / 清除日誌           log 突然中斷 / 清空事件         「log 被清除」= 高危告警
  (T1070 Indicator Removal)          (回扣第 16 章 covering tracks)
Exfiltration / 資料外洩              對外連線量暴增 / 大量下載       20.5 規則二
  (T1041 Exfiltration over C2)
```

> **心智模型:防守方也要用攻擊者的地圖。** 與其漫無目的地「記所有 log、寫一堆規則」,不如打開 ATT&CK 矩陣,**針對你最在意的攻擊技術,逐一問「這招會在我的哪個 log 留下什麼痕跡?我有沒有對應的偵測規則?」**——把矩陣當成 checklist,你就能系統性地量化「我的偵測覆蓋率有多少格」,而不是憑感覺。這正是偵測工程的日常。特別注意 **T1070(清除日誌)**:當 log 突然斷掉或被清空,本身就是最強烈的攻擊訊號——所以 20.3 的集中式日誌不只保存了證據,「log 中斷」這件事還直接變成一條偵測規則。

### IoC vs IoA:抓「東西」還是抓「行為」

偵測時,你追的線索分兩種,這個區分很重要:

| | **IoC(Indicator of Compromise 入侵指標)** | **IoA(Indicator of Attack 攻擊指標)** |
|------|------------------------------------------|----------------------------------------|
| **抓什麼** | 具體的「壞東西」:惡意 IP、惡意檔案雜湊、惡意網域 | 「攻擊行為的模式」:一連串動作構成的意圖 |
| **例子** | 「連到 `evil.com` / 檔案 hash = abc123」 | 「開了 Office → 生出 PowerShell → 對外連線」這串行為 |
| **時態** | 偏**事後**(這些指標是別人被打過才總結出來的) | 偏**當下/事前**(行為正在發生時就抓) |
| **弱點** | 攻擊者換個 IP/改個檔案就失效(易變) | 較難繞過(意圖模式難改),但較難定義 |

> **心智模型:IoC 抓「已知的壞東西」,IoA 抓「壞的意圖」。** IoC 像通緝犯的照片與指紋(具體但一換就失效);IoA 像「這個人鬼鬼祟祟在試每一扇門」的行為判斷(即使你不認得他是誰,行為本身就暴露了意圖)。這其實就是 20.6 的 signature(≈IoC)vs anomaly(≈IoA)在偵測工程層次的翻版。成熟的偵測**兩者都要**。

### Threat Hunting、SOC、EDR/XDR

三個現代藍隊必懂的概念,收尾這一節:

- **Threat Hunting(主動獵捕)**:不等告警,而是**主動假設「攻擊者可能已經在裡面了」,帶著假設去 log 與端點裡翻找蛛絲馬跡**。這是 Assume Breach(20.1)心態的極致展現——「與其等監視器響,不如自己拿手電筒進屋巡」。獵捕靠的往往是 IoA(行為),因為 IoC 那種被動比對交給自動化就好。

- **SOC(Security Operations Center,資安維運中心)**:企業裡 **7×24 監控、分析、回應資安事件的團隊與作業中心**。SIEM、IDS/IPS 的告警最終都匯到 SOC,由分析師分級處理(Tier 1 初判、Tier 2 深入、Tier 3 獵捕與應變)。SOC 是把本章所有工具「養活、用起來」的組織。

- **EDR / XDR(端點偵測與回應)**:
  - **EDR(Endpoint Detection and Response)**:裝在「端點」(電腦、伺服器)上的進階 agent,可以說是 HIDS 的強化版——它**持續記錄端點上的細部行為**(程序樹、命令列、檔案與登錄檔變動、網路連線),不只偵測,還能**回應**(隔離主機、砍掉惡意程序、回溯攻擊路徑)。它特別擅長抓 IoA 那種「行為鏈」。
  - **XDR(Extended Detection and Response)**:把 EDR 的視野**擴展**到端點以外——整合網路、郵件、雲端、身分等多來源,做跨層的關聯與回應。可以理解成「打通各種偵測孤島、以偵測與回應為核心的下一代整合平台」。

> **關鍵認知**:從 log → SIEM → IDS/IPS → EDR/XDR,你會發現一條清晰的演進脈絡:**偵測的顆粒度越來越細、關聯的範圍越來越廣、從『只偵測』走向『偵測 + 自動回應』。** 但萬變不離其宗——它們全都建立在 20.1「Assume Breach」的心態,和 20.2「忠實記錄攻擊者必經之路」的原料之上。工具會換代,這兩個地基不變。

## 20.8 靶場練習:紅隊打、藍隊看 —— 紫隊訓練

> **授權提醒(這一章尤其要強調)**:以下練習**只能在你自己搭建的隔離實驗室**(第 01 章)進行——攻擊機、靶機、監控機全都是你自己的虛擬機,在隔離網段裡。對任何未授權的系統做本節的攻擊或監控,在台灣觸犯《刑法》第 36 章妨害電腦使用罪(第 00 章)。監控自己不擁有的系統流量,同樣可能違法。**把這條紅線刻在心裡再動手。**

前面十幾章你都在扮紅隊(攻擊);這一章你第一次坐到藍隊的位子。而最好的學法,是**紅藍一起玩**——這正是第 00 章講的**紫隊(Purple Team)**:紅隊打、藍隊看,打完立刻對照「我這一招,在監控畫面上長什麼樣?被抓到了嗎?」。

### 實驗室拓撲

```
   ┌──────────────┐        攻擊         ┌──────────────────┐
   │  攻擊機 Kali  │ ─────────────────▶ │  靶機             │
   │ (紅隊視角)    │                    │  Metasploitable   │
   └──────────────┘                    │  (故意很脆弱)      │
                                        └────────┬─────────┘
                                                 │ 送 log / agent 回報
                                                 ▼
                                        ┌──────────────────┐
                                        │  監控機           │
                                        │  Wazuh 或 ELK     │  ◀── 藍隊在這裡看
                                        │  (SIEM + HIDS)    │
                                        └──────────────────┘
                    (全部在隔離網段,對外不通)
```

### 步驟:打三招、看三招

在監控機裝好 **Wazuh**(推薦,開箱即用、內建 HIDS 與 ATT&CK 對應)或 ELK,把靶機的 log/agent 接進來,然後依序打前面章節學過的攻擊,每打完一招,就切到 Wazuh 儀表板看能不能偵測到:

| 紅隊出招(前面章節) | 對應 ATT&CK | 藍隊該在哪看到、看到什麼 |
|---------------------|-------------|------------------------|
| **Nmap 掃描**(第 05 章)`nmap -sV 靶機IP` | T1046 掃描 | Wazuh/防火牆 log:短時間單一來源大量不同 port 連線 → 掃描告警 |
| **Hydra 暴力破解**(第 11、15 章)對 SSH 狂猜密碼 | T1110 暴力破解 | HIDS 讀 auth.log:大量 `Failed password` 同源 → 觸發 20.4/20.5 那條規則,若猜中還會看到接續的 `Accepted` |
| **SQL 注入**(第 07 章)對靶機 Web app 打 sqlmap | T1190 利用對外應用 | Web access log 進 SIEM:`UNION SELECT`、`' OR 1=1`、`sqlmap` UA、狀態碼異常 → 注入告警 |

**這個練習的價值**,不在於「學會用 Wazuh」,而在於建立一個**閉環的直覺**:

> **心智模型:攻完,一定要回頭看監控。** 當你親手打一次 Hydra,再親眼看到它在 Wazuh 儀表板上化成一條刺眼的紅色告警,你對「攻擊在防守方眼裡長什麼樣」的理解會脫胎換骨。更重要的是**反過來想**:哪些招被漂亮地抓到了?哪些招悄無聲息地過了?**沒被抓到的那些,就是你的偵測缺口(detection gap)**——這正是偵測工程(20.7)要補的洞。紅隊教會藍隊「該防什麼」,藍隊的缺口又反過來告訴紅隊「哪裡還能鑽」。這個紅藍互餵的循環,就是紫隊的精髓,也是一個組織真正變強的方式。

實務上,成熟團隊會用 **Atomic Red Team**、**Caldera** 這類工具,把 ATT&CK 的各項技術做成可重複執行的「原子測試」,系統性地驗證「我的偵測到底覆蓋了矩陣裡的哪幾格」——但概念和你在實驗室手動打三招、看三招,一模一樣。

## 20.9 本章小結

- **心態先於工具:Assume Breach。** 別賭「牆永遠不破」——攻擊者只要一個洞,你要守全部。勝負不在「有沒有被攻破」,而在「**多久發現、多快止血**」(壓低 dwell time)。偵測是縱深防禦裡與「加固」平行的一層,對應 Kill Chain「打斷任一環」。
- **Log 是偵測的原料。** 圍繞攻擊者的必經之路記:認證、權限變更、程序執行、網路連線、檔案存取、log 清除。來源涵蓋 OS(auditd/Event Log)、Web(Nginx/Apache)、應用、網路設備、雲端(CloudTrail)。**沒記下來的,你分析不了。**
- **Log 必須集中、必須完整。** 攻擊者進來第一件事就是清 log(T1070,第 16 章 covering tracks),所以要**即時**送到攻擊者碰不到的中央日誌伺服器,用 WORM/遠端 syslog 保完整性,並全網 NTP 對時。「證據不能跟犯罪現場放一起。」
- **讀懂 log 是基本功。** 暴力破解 = 同源高頻失敗 +「接著一次成功」;Web 攻擊 = 狀態碼從 404/500 溫度變化到 200。**單一事件是雜訊,串起來才是攻擊。**
- **SIEM = 蒐集 → 正規化 → 關聯 → 告警**,靈魂在「關聯」(把散落事件串成攻擊故事)。但它**不是萬靈丹**:要持續 tuning,要對抗告警疲勞,並在 **false positive(誤報)↔ false negative(漏報)** 之間走鋼索。工具:Splunk、ELK、Wazuh、Sentinel。
- **IDS(看見/告警)vs IPS(出手/阻擋)**;**NIDS(網路型:Snort/Suricata)vs HIDS(主機型:Wazuh/OSSEC/auditd)**;偵測方法 **signature(比已知,抓不到 0-day)vs anomaly(抓異常,誤報多)**——現代全都並用,又是縱深防禦。
- **偵測工程用 MITRE ATT&CK 反推「該偵測什麼」**:從 TTP → 資料源 → 偵測規則。**IoC(抓已知壞東西)vs IoA(抓壞的意圖)**;再進到 Threat Hunting(主動獵捕)、SOC(7×24 維運)、EDR/XDR(端點偵測回應)。
- **紫隊練習**:在隔離實驗室用 Wazuh/ELK 建監控,對 Metasploitable 打 Nmap/Hydra/sqlmap,回頭看 SIEM 抓到沒——沒抓到的就是你的偵測缺口。**攻完一定要回頭看監控。**

> **下一章預告**:本章解決了「**看見**」——你已經能在監控畫面上發現攻擊者的身影了。但發現之後呢?警報響起的那一刻,是慌亂地拔網路線、還是有條不紊地應變?第 21 章談 **事件回應(Incident Response)與數位鑑識(Digital Forensics)**:一套標準的 IR 流程(準備→偵測→圍堵→根除→復原→檢討),如何在不破壞證據的前提下圍堵止血,如何做記憶體與磁碟鑑識、還原攻擊時間軸、追出「他怎麼進來、拿走了什麼、還留了什麼後門」。偵測告訴你「出事了」,回應與鑑識告訴你「發生了什麼、怎麼收拾、下次怎麼防」——藍隊防禦篇的最後一塊拼圖。
