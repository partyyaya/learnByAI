# 第 04 章:被動情報蒐集 OSINT

> 電影裡的駭客總是一坐下就開始瘋狂敲鍵盤攻擊系統。真實世界不是這樣。
> 一次專業的滲透測試,超過一半的時間花在「還沒碰到目標」的階段——蒐集情報、畫攻擊面地圖、找出哪扇門最可能沒鎖。
> 這一章講的是「偵察」的第一步:**被動情報蒐集(OSINT)**。它的美妙之處在於——你完全不碰目標的伺服器,只翻公開資料,
> 就能拼湊出對方的組織結構、對外服務、技術棧、甚至員工帳號。攻擊者靠它決定「打哪裡」,防禦者靠它知道「自己漏了什麼」。
> 老規矩,先把第 00 章的紅線刻在心裡:**本章所有技巧只能用在你有授權的目標,或盤點你自己的資產。**

---

## 4.1 什麼是偵察(Reconnaissance)?被動 vs 主動

還記得第 00 章的 Cyber Kill Chain 嗎?七個階段的**第一個**就是「偵察(Reconnaissance)」。它不是熱身,而是整場攻擊的地基。

**偵察 = 在動手攻擊前,盡可能蒐集目標的一切情報。** 目標長什麼樣?對外開了哪些服務?用什麼技術?有哪些員工?這些答案決定你後面每一步怎麼走。

偵察分兩種,差別在「你有沒有直接碰到目標的系統」:

| 類型 | 定義 | 會不會留痕跡 | 舉例 | 對應章節 |
|------|------|------------|------|---------|
| **被動偵察(Passive Recon)** | **完全不直接與目標系統互動**,只從第三方公開來源蒐集情報 | 幾乎不留痕跡(你打的是 Google、公開資料庫,不是目標伺服器) | Google 搜尋、查 whois、看憑證紀錄、翻 LinkedIn | **本章(04)** |
| **主動偵察(Active Recon)** | **直接對目標系統發送封包/請求**來探測 | 會留 log(目標的防火牆、伺服器日誌看得到你的 IP) | port 掃描、banner grabbing、目錄爆破 | 第 05 章 |

用一個比喻:

> **心智模型**:被動偵察像是「站在街對面觀察一棟房子」——你看它幾層樓、幾扇窗、門牌號碼、信箱塞了哪些帳單,但你從沒踏進院子。主動偵察則是「走上前去,一扇扇轉門把、敲窗戶」——你確實得到更精確的資訊(哪扇門沒鎖),但屋主的監視器也錄下了你的臉。

這個差別在實務上非常重要:

- **被動偵察隱蔽性極高。** 因為你查的是 Google、憑證資料庫、社群網站,目標的防禦系統(IDS、防火牆)**根本看不到你在偵察它**。從法律角度,單純瀏覽公開資訊風險也最低(但注意:蒐集到的情報怎麼「使用」才是關鍵,見下方提醒)。
- **主動偵察更精確但會曝光。** 你一旦對目標發封包,對方的日誌就有你的 IP,警覺的藍隊會注意到「有人在掃我們」。

專業的攻擊者(和滲透測試員)一定是**先把被動偵察做到極致,把主動掃描的範圍縮到最小**——因為每一次主動接觸都是暴露自己的機會。

> **一句話原則(呼應第 00 章)**:被動偵察「不碰目標」不代表可以「隨便對誰做」。蒐集競爭對手員工個資、把外洩帳密拿去嘗試登入,這些行為一樣違法。**本章只用於:你有書面授權的滲透測試目標、你自己的組織資產盤點、或官方授權靶場。**

## 4.2 為什麼偵察決定成敗

新手常犯的錯是「急著開打」——裝好 Kali、看到目標就 `nmap` 一把梭。但你去問任何一個資深滲透測試員,他會告訴你:**偵察做得好不好,直接決定這次滲透的成敗。**

### 情報量 = 攻擊面清晰度

回想第 00 章的「攻擊面思維」:把系統想成一棟有很多門的房子,攻擊者的工作是「列舉出所有的門,再逐一試哪扇沒鎖」。偵察就是在**畫這張門的地圖**。

- 你只知道 `example.com` 一個網域 → 你只看到「一扇門」。
- 你透過偵察挖出 `mail.example.com`、`vpn.example.com`、`dev-old.example.com`、`admin.example.com`… → 你突然看到「一整排門」,而且那個 `dev-old`(開發用的舊站)聽起來就很可疑。

**情報越多,攻擊面越清楚,你就越知道該把力氣花在哪。** 往往真正被攻破的入口,不是那個防護嚴密的主網站,而是某個被遺忘的、沒人維護的子網域。

### 偵察也影響後面每一個階段

情報不只用在「找入口」,它貫穿整條 Kill Chain:

```
偵察挖到的情報          → 後續怎麼用
────────────────────────────────────────────────
對方用 WordPress 5.2   → 去查這版本有哪些已知漏洞(武器化)
員工 email 格式是      → 推算出所有人的信箱,準備釣魚(第 18 章)
  名.姓@example.com
GitHub 上洩漏的 API 金鑰 → 直接拿來存取雲端資源(可能免攻擊)
招募啟事寫「熟悉 Jenkins」→ 對方內網很可能有 Jenkins,列入目標
```

> **心智模型:偵察是拼圖。** 每一片碎片單獨看都無害——一個員工姓名、一個子網域、一個軟體版本號,誰在乎?但當你把幾十片碎片拼在一起,就浮現出一張完整的地圖:對方的組織、系統、弱點一覽無遺。**攻擊者的功力,很大程度就是「把無害的碎片拼成致命地圖」的能力。** 這也是為什麼防禦者要在意「每一片碎片」——見 4.11。

### 對防禦者的意義

如果你是藍隊,這一章你要反過來讀:**攻擊者能查到的,你自己也查得到。** 定期用這些技巧「偵察自己」,你才知道對外洩漏了什麼、哪個被遺忘的子網域該關掉。這叫「攻擊面盤點」,是主動防禦的第一步。

## 4.3 OSINT(開源情報)是什麼

**OSINT = Open Source Intelligence,開源情報。** 這裡的「開源」不是指開源軟體,而是「**公開來源**」——任何人都能合法取得的公開資訊。

OSINT 是被動偵察的主力。它的核心概念是:**你要的情報,大多早就散落在公開的網路各處,只是沒人幫你彙整。** 攻擊者(和調查記者、徵信、執法單位)做的事,就是系統性地把這些公開碎片蒐集、關聯起來。

情報可能來自哪些公開來源?

| 來源類別 | 具體管道 | 能挖到什麼 |
|---------|---------|-----------|
| **搜尋引擎** | Google、Bing(進階語法) | 暴露的檔案、登入頁、錯誤訊息、設定檔(4.4) |
| **網域/IP 資料庫** | whois、DNS 紀錄、BGP | 誰擁有這網域、IP 範圍、郵件伺服器(4.5) |
| **憑證透明度** | crt.sh、censys | 從 SSL 憑證挖子網域(4.7) |
| **程式碼平台** | GitHub、GitLab、Pastebin | 誤上傳的金鑰、設定檔、內部程式(4.10) |
| **社群/職業網站** | LinkedIn、Facebook、X | 員工名單、職稱、技術棧、組織結構(4.9) |
| **文件與檔案** | 公司公開的 PDF/Office/圖片 | 作者、軟體版本、內部路徑、地理位置(4.8) |
| **外洩資料庫** | HaveIBeenPwned | 哪些員工帳密曾在資料外洩事件中出現(4.10) |
| **公開紀錄** | 招募網站、財報、新聞、專利 | 技術棧線索、組織規模、供應商 |

這一章接下來會逐一走過這些管道。你會發現一個共同主題:**每一個管道單獨看都很「無害」,但攻擊者要的是把它們串起來。**

> **給防禦者的提醒**:你沒辦法把「公開資訊」變成「不公開」——DNS 本來就要公開、憑證透明度是安全機制的一部分。防禦的重點不是「藏起來」(通常做不到),而是「**不要洩漏本來就不該公開的東西**」(內部檔案、金鑰、過期系統),以及「**知道自己洩漏了什麼**」。

## 4.4 Google Dorking:把搜尋引擎變成偵察工具

Google 不只是拿來搜食譜的。它的爬蟲索引了整個網際網路,包括**很多網站管理員以為沒人會看到的東西**——沒設好權限的備份檔、暴露的後台登入頁、含密碼的設定檔。用進階搜尋語法精準地把這些挖出來,就叫 **Google Dorking**(或 Google Hacking)。

> **為什麼攻擊者愛用**:這完全是被動的——你打的是 Google,不是目標。目標的伺服器不會知道有人透過 Google 找到了它的暴露檔案。而且 Google 早就幫你爬好、索引好了,你只是下對關鍵字。

### 核心進階語法

| 語法 | 作用 | 範例 |
|------|------|------|
| `site:` | 限定只搜某網域(含子網域) | `site:example.com` |
| `filetype:` | 限定檔案類型 | `filetype:pdf`、`filetype:sql` |
| `intitle:` | 網頁標題含某字 | `intitle:"index of"` |
| `inurl:` | 網址含某字 | `inurl:admin` |
| `-`(減號) | **排除**含某字的結果 | `-www`(排除主站) |
| `"..."` | 精確片語(整串一起) | `"SQL syntax error"` |
| `cache:` | 看 Google 的**網頁快取**(即使原頁已被刪) | `cache:example.com` |

### 實用組合(僅用於授權目標 / 自家資產盤點)

以下每一條都附「攻擊者想找什麼」,你也可以把 `example.com` 換成**你自己的網域**,做一次自我體檢。

```
# ① 盤點某組織「所有被 Google 索引到的頁面」——先看攻擊面全貌
site:example.com
# 攻擊者的意圖:一眼看出對方有哪些頁面、哪些子網域被索引

# ② 找「開放目錄列表」——伺服器沒關掉目錄瀏覽,整個資料夾攤開給你看
intitle:"index of" site:example.com
# 常常能翻到備份檔、log、上傳目錄——這是設定疏失的典型徵兆

# ③ 找暴露的設定檔與備份(常含資料庫連線字串、密碼)
site:example.com filetype:env | filetype:config | filetype:bak | filetype:sql
# .env / .config / .bak / .sql 這類檔案本來絕對不該對外——找到就是重大洩漏

# ④ 找登入頁與後台(攻擊者的下一步就是對這些頁面試帳密)
site:example.com inurl:admin | inurl:login | intitle:"admin panel"
# 找出所有「入口」,列為認證攻擊(第 11 章)的目標

# ⑤ 找洩漏的錯誤訊息(錯誤訊息常吐出技術棧、路徑、甚至 SQL 語法)
site:example.com intext:"SQL syntax" | intext:"Warning: mysql"
# 資料庫錯誤外洩 = 這頁可能有 SQL Injection(第 07 章)的線索

# ⑥ 排除主站,專找「不起眼的子網域」——被遺忘的舊站最脆弱
site:example.com -www -shop
# 把最常見的正式站排除,剩下的常是測試站、舊系統
```

> **心智模型**:Google Dorking 就像「用超精準的關鍵字,把整個網際網路當成一個大資料庫來下 query」。管理員以為「沒有連結指到那個備份檔就沒人找得到」——錯了,只要爬蟲爬過一次,它就永遠在索引裡。

### 防禦者怎麼做

- **正確使用 `robots.txt`**:告訴爬蟲別索引敏感路徑。但注意——`robots.txt` 本身是公開的,而且**攻擊者會故意去讀它來找「你想藏什麼」**。它能擋守規矩的 Google 爬蟲,擋不了直接來探測的攻擊者。所以它是「別讓東西被 Google 索引」的工具,**不是存取控制**。
- **敏感檔案根本不要放在 web 目錄下**:`.env`、備份檔、`.git` 目錄不該出現在網站根目錄。這是根因。
- **關掉目錄列表(directory listing)**:Nginx/Apache 預設或設定不當會攤開整個資料夾(參考本倉庫 Nginx 課程)。
- **定期 Google Dork 自己**:把上面的 query 換成自家網域跑一遍,看 Google 索引到了什麼不該有的東西,主動要求移除。

## 4.5 域名與 IP 情報:whois、DNS、反向 DNS

網域名稱和 IP 是網際網路的「地址系統」,而查詢這些地址的機制**天生就是公開的**。攻擊者靠它建立目標的「基礎設施地圖」。

### whois:誰擁有這個網域

`whois` 查詢網域的註冊資訊——誰註冊的、什麼時候、註冊商是誰、DNS 伺服器在哪。

```bash
# 查詢某網域的註冊資訊
whois example.com
# 攻擊者關心的欄位:
#   Registrant(註冊人):可能是公司名、負責人、email、電話 → 社會工程素材(第 18 章)
#   Name Server(名稱伺服器):用哪家 DNS 服務 → 基礎設施線索
#   Creation/Expiry Date(建立/到期日):網域多老、快不快到期
```

> **現況提醒**:因為隱私法規(如 GDPR),現在很多網域的註冊人資訊會被「隱私保護服務」遮蔽,顯示的是代理商而非真人。所以 whois 現在挖到真實個資的機率降低了,但**名稱伺服器、建立日期、基礎設施線索仍然有用**。

### DNS 查詢:dig 與 nslookup

DNS(網域名稱系統)把人類看得懂的網域名,翻譯成機器用的 IP。查 DNS 紀錄能揭露一個組織的網路基礎設施。兩個常用工具:`dig`(功能強、Linux/Mac 常用)和 `nslookup`(跨平台、Windows 也有)。

```bash
# dig 查 A 記錄(網域對應到哪個 IPv4 位址)
dig example.com A
# A 記錄 = 這網域指向哪台伺服器的 IP → 攻擊者知道「要打的機器在哪」

# 查 MX 記錄(郵件伺服器)
dig example.com MX
# MX = Mail Exchange,收信的伺服器 → 釣魚攻擊、郵件系統偵察的目標(第 18 章)

# 查 TXT 記錄(文字紀錄,常放 SPF/DKIM/驗證字串)
dig example.com TXT
# TXT 常洩漏:用哪家郵件服務(Google Workspace/O365)、哪些第三方服務(驗證碼)
#            SPF 紀錄還會列出「哪些伺服器可以幫這網域寄信」→ 基礎設施地圖

# 查 NS 記錄(這網域由哪些名稱伺服器管理)
dig example.com NS
# NS = Name Server → 用自架 DNS 還是 Cloudflare/AWS?透露託管架構

# 一次查全部(ANY)並顯示簡潔結果
dig example.com ANY +short
# +short 只印答案、不印一堆標頭,適合快速看
```

用 `nslookup` 做等效查詢(語法給習慣 Windows 的人):

```bash
nslookup -type=MX example.com    # 查郵件伺服器
nslookup -type=TXT example.com   # 查 TXT 紀錄
```

各記錄類型代表什麼、攻擊者為何在意,整理成表:

| 記錄類型 | 全名 | 內容 | 攻擊者為什麼在意 |
|---------|------|------|----------------|
| **A / AAAA** | Address | 網域 → IPv4 / IPv6 | 知道目標伺服器的實際 IP,才能進一步(主動)掃描(第 05 章) |
| **MX** | Mail Exchange | 郵件伺服器 | 釣魚、郵件基礎設施偵察的入口(第 18 章) |
| **TXT** | Text | SPF、DKIM、各種驗證字串 | 洩漏用哪些雲端/第三方服務、寄信來源清單 |
| **NS** | Name Server | 管理此網域的 DNS 伺服器 | 判斷 DNS 託管方式、有沒有可劫持的設定 |
| **CNAME** | Canonical Name | 別名指向另一個網域 | 找出背後真正的服務(有時能發現「懸空 CNAME」可被接管) |

### 反向 DNS(Reverse DNS):從 IP 反查網域

正向 DNS 是「網域 → IP」,反向 DNS 是「IP → 網域」。攻擊者拿到一個 IP,想知道「這台機器上還跑了什麼」,就會反查。

```bash
# 用 dig 做反向查詢(查 IP 對應的 PTR 記錄)
dig -x 93.184.216.34
# -x = 反向查詢。回傳的 PTR 記錄告訴你這 IP 綁定的主機名
# 攻擊者的意圖:一個 IP 上常常掛好幾個網站/服務,反查能發現「鄰居」
```

> **心智模型**:DNS 紀錄就像一個組織的「對外通訊錄」。它本來就得公開(不然別人怎麼連到你),但把 A、MX、TXT、NS 全部拼起來,攻擊者就畫出了你的「網路基礎設施地圖」:主站在哪、信箱在哪、用了哪些雲服務。

### 防禦者怎麼做

- **whois 開啟隱私保護**:別讓註冊人 email、電話直接曝光成社工素材。
- **TXT / SPF 紀錄別過度洩漏**:SPF 沒必要列出的內部主機就別放;內部驗證用的 TXT 記錄用完就清。
- **清理懸空 DNS 紀錄(dangling DNS)**:指向已刪除雲端資源的 CNAME 可能被攻擊者「接管」(subdomain takeover),定期盤點。
- **心態調整**:DNS 資訊擋不住,重點是「別在 DNS 裡放不該放的線索」,並知道攻擊者看得到這些。

## 4.6 子網域枚舉:每個子網域都是一扇門

一個組織通常不只有 `example.com`,還有一大堆子網域:`mail.example.com`、`blog.example.com`、`api.example.com`、`vpn.example.com`、`staging.example.com`…

**為什麼子網域這麼重要?** 因為:

> **每一個子網域,都是一個獨立的攻擊面(一扇門)。**

主站 `www.example.com` 可能防護得滴水不漏,但那個三年前建的 `test.example.com`、或某個外包做完就沒人管的 `promo2019.example.com`,很可能:

- 跑著過時、有已知漏洞的軟體。
- 沒有上 WAF、沒有監控。
- 開著本該關掉的功能(debug 模式、後台)。

攻擊者的邏輯很簡單:**不打最硬的門,找最鬆的那扇。** 而子網域枚舉,就是把所有的門先列出來。

### 被動 vs 主動枚舉

子網域枚舉也分被動和主動:

- **被動枚舉(本章)**:從第三方公開資料(憑證紀錄、DNS 資料庫、搜尋引擎、被動 DNS)蒐集已知的子網域。**不碰目標**。
- **主動枚舉(第 05 章)**:自己拿字典去「猜」子網域(DNS brute force),對目標 DNS 發大量查詢——會留痕跡。

這一章專注被動。常用工具:

```bash
# subfinder:專門做被動子網域枚舉,速度快、整合大量公開資料源
subfinder -d example.com -silent
# -d 指定目標網域;-silent 只輸出結果(乾淨、好接管線)
# subfinder 預設就是被動的:它去問一堆公開 API(憑證紀錄、被動 DNS 等),不直接掃目標

# amass 的被動模式(功能更全,也整合更多來源)
amass enum -passive -d example.com
# enum = 枚舉子命令;-passive 明確限定「只用被動來源,不主動探測」
# 注意:amass 不加 -passive 會做主動查詢,那就屬於第 05 章的範疇了——用錯模式會暴露自己
```

> **關鍵提醒**:這些工具「被動 vs 主動」的分野,取決於你下的參數。`subfinder` 預設被動,但 `amass enum` 不加 `-passive` 就會主動探測。**動手前務必確認自己在哪個模式**——這既關乎隱蔽性,也關乎你有沒有超出授權範圍(第 00 章的 scope)。

拿到一堆子網域後,攻擊者接著會(在授權範圍內)用主動手段確認「哪些還活著」、各自跑什麼服務——那是第 05 章的事。被動階段的產出,就是這份「候選門清單」。

### 防禦者怎麼做

- **盤點自己的子網域**:用同樣的工具對自家網域跑一遍,你很可能會嚇一跳——找到一堆自己都忘了的子網域。
- **關掉 / 下線用不到的子網域**:每個活著的子網域都是攻擊面,不需要的就收掉(縮小攻擊面,呼應第 00 章)。
- **測試/開發環境別掛在公開網域上**:`staging`、`dev`、`test` 這類環境要嘛內網化、要嘛加存取控制,別讓它裸奔在網際網路上。
- **統一管理與監控**:新開子網域要走流程、上監控,別讓「臨時活動頁」變成永久的破口。

## 4.7 憑證透明度:從 SSL 憑證挖出子網域

這是被動子網域枚舉裡最漂亮、也最反直覺的一招:**你可以從 SSL/TLS 憑證的公開紀錄,挖出一個組織的大量子網域——包括那些他們以為沒公開的。**

### 原理:安全機制反而洩漏了資訊

先講背景。網站要用 HTTPS,就得申請 SSL/TLS 憑證。過去有個問題:憑證頒發機構(CA)如果被入侵或出錯,可能會頒發「偽造的」憑證(例如幫攻擊者頒發一張 `google.com` 的憑證),而沒人會發現。

為了解決這個信任問題,業界推出了 **Certificate Transparency(憑證透明度,CT)**:

> **每一張被頒發的 SSL 憑證,都必須被登記到「公開、可稽核、任何人都能查」的 CT Log(憑證透明度日誌)裡。**

這樣一來,如果有人偷偷幫你的網域申請了憑證,你能在 CT Log 裡發現;瀏覽器也會拒絕沒登記在 CT Log 的憑證。這是個**很好的安全機制**——但它有個副作用:

**因為每張憑證都公開登記,而憑證裡寫著它保護的網域名(包括子網域),所以 CT Log 等於一份「這個組織申請過憑證的所有網域清單」。**

當一個組織幫 `secret-admin.example.com` 申請憑證時,他們可能以為「這網址沒對外公布,沒人知道」——但那張憑證早就被登記進公開的 CT Log 了。

### 用 crt.sh 查詢

`crt.sh` 是一個免費查詢 CT Log 的網站/服務。你可以直接在瀏覽器開 `https://crt.sh/?q=%.example.com`,或用命令列:

```bash
# 用 crt.sh 的 JSON API 查某網域的所有憑證紀錄,並抽出子網域
curl -s "https://crt.sh/?q=%25.example.com&output=json" | jq -r '.[].name_value' | sort -u
# 拆解:
#   %25 是 URL 編碼的 '%',在這裡當萬用字元 → 查「所有 *.example.com」
#   output=json 要求回傳 JSON 格式
#   jq -r '.[].name_value' 抽出每筆憑證裡「保護的網域名」欄位
#   sort -u 排序並去重,得到乾淨的子網域清單
```

跑完你會得到一份子網域清單,常常包含 subfinder 都沒抓到的「內部味」網域,例如 `jenkins.example.com`、`vpn-test.example.com`、`git.internal.example.com`。這些對攻擊者是黃金線索。

> **心智模型**:CT 是一個為了「防止憑證造假」而生的透明機制——但透明本身就是雙面刃。它讓防禦者能監控偽造憑證,也讓攻擊者能免費、被動地列舉你的子網域。**你沒辦法「退出」CT(退出等於你的 HTTPS 不被瀏覽器信任),所以只能接受「我申請過憑證的網域都是公開的」這個現實,並據此規劃。**

### 防禦者怎麼做

- **接受現實,別把「網址保密」當防線**:任何你發過 HTTPS 憑證的網域,都會出現在 CT Log。**絕對不要靠「這個網址沒人知道」來保護敏感系統**(這叫 security through obscurity,靠隱藏來安全,是不可靠的)。內部系統該做的是存取控制、VPN、IP 白名單。
- **反過來善用 CT 做監控**:你也能監控 CT Log(用 crt.sh、CertSpotter 等),一旦有人幫「長得像你公司」的網域申請憑證(釣魚網站前兆),你能第一時間發現。這是把攻擊者的工具變成防禦雷達。
- **考慮萬用字元憑證**:用 `*.example.com` 萬用字元憑證,能避免每個子網域名都個別登記進 CT Log(但萬用字元憑證有自己的風險權衡,私鑰一旦外洩影響範圍更大)。

## 4.8 metadata 洩漏:檔案裡藏著的秘密

一份看起來人畜無害的 PDF、一張官網的照片、一個公開的 Word 文件——它們**內部藏著的「metadata(中繼資料 / 詮釋資料)」**,常常洩漏遠超製作者想像的資訊。

**什麼是 metadata?** 就是「關於資料的資料」。你拍一張照片,照片本身是資料,但檔案裡還記錄了「用哪台相機、什麼時候拍、GPS 座標」——這些就是 metadata。

### 三類常見的 metadata 洩漏

**① 圖片 EXIF:地理位置與裝置資訊**

數位照片(尤其手機拍的)內嵌 **EXIF** 資料,可能包含:

- **GPS 座標**:拍照地點的經緯度——直接暴露「這張照片在哪裡拍的」。想像員工在辦公室拍照發社群,GPS 直接標出公司(甚至機房)位置。
- **裝置型號、拍攝時間、軟體版本**。

```bash
# exiftool 是讀取檔案 metadata 的瑞士刀,幾乎吃所有格式
exiftool photo.jpg
# 輸出裡攻擊者會盯著看的:
#   GPS Latitude / Longitude → 拍攝地點座標(貼到地圖直接定位)
#   Camera Model / Make      → 什麼裝置拍的
#   Create Date              → 拍攝時間(建立行為時間線)
```

**② PDF / Office 文件:作者、軟體版本、內部路徑**

公司對外發布的簡報、報價單、白皮書,製作時會留下:

- **作者姓名 / 使用者帳號**:常常就是內部帳號命名格式的線索(接 4.9)。
- **軟體與版本**:例如「Microsoft Word 2016」「用某某 PDF 產生器」——洩漏對方的軟體環境,攻擊者可對照該版本的已知漏洞。
- **內部檔案路徑**:有時 metadata 或內嵌資訊會露出 `C:\Users\john.chen\Documents\...`,直接洩漏員工帳號名和目錄結構。

```bash
# 對一份公開下載的 PDF 讀 metadata
exiftool company-report.pdf
# 攻擊者盯著:
#   Author / Creator     → 製作者姓名或帳號 → 推斷帳號命名規則(4.9)
#   Producer             → 用哪套軟體產生的(版本 → 已知漏洞比對)
#   Create/Modify Date   → 建立時間線
```

**③ 批次收割:FOCA / metagoofil 的概念**

攻擊者不會一份一份手動看。有專門工具(如 FOCA、`metagoofil`)會**自動去 Google 上把某網域的所有公開文件(PDF/DOC/XLS)抓下來,批次抽取 metadata**,再彙整出「這家公司有哪些員工名、用哪些軟體、內部路徑長怎樣」。這又是「把碎片拼成地圖」的典型。

> **心智模型**:每個檔案都像一封「隱形的自我介紹信」。使用者看到的是內容,但檔案背面用隱形墨水寫著「我是誰做的、用什麼工具、在哪裡、什麼時候」。攻擊者專門讀這面隱形墨水。

### 防禦者怎麼做

- **發布前清除 metadata**:對外發布的文件、圖片一律過一道「清洗」。可以用 `exiftool -all= file.jpg`(清除所有 metadata),或用作業系統/辦公軟體內建的「移除文件屬性和個人資訊」功能。
- **社群發文關掉照片定位**:提醒員工手機關閉照片 GPS,或上傳前去除位置資訊(多數平台會自動去除,但別依賴)。
- **建立發布流程**:把「metadata 清洗」納入對外文件的發布 SOP,而不是靠個人記得。
- **教育員工**:很多洩漏來自員工個人社群(在辦公室打卡、拍工牌、拍白板)。意識教育比技術管制更根本(第 18 章社會工程會深入)。

## 4.9 人員與組織情報:攻擊「人」的前置作業

技術系統可能固若金湯,但組織是由「人」組成的,而人是攻擊面裡最軟的一環。針對人的攻擊(釣魚、社會工程)會在第 18 章深入,這一節先做**被動的人員情報蒐集**——為那一章鋪路。

### LinkedIn 與社群:組織的活地圖

**LinkedIn** 是攻擊者的寶庫。上面公開的資訊能讓你拼出:

- **員工名單與職稱**:誰是 IT 主管、誰是財務、誰是新人(新人常是釣魚的好目標,還不熟公司流程)。
- **組織結構**:誰向誰報告,幫助設計「假冒上司」的釣魚劇本(第 18 章的 pretexting)。
- **技術棧線索**:工程師個人檔案常寫「熟悉 AWS / Kubernetes / Java Spring」——這直接洩漏公司內部用什麼技術。

其他社群(Facebook、X、GitHub、公司部落格)同理,都能補上碎片。

### email 命名規則推斷

這招極其實用,是連結「人員情報」和「攻擊」的橋樑。

大多數公司的 email 有固定格式。只要你透過任何管道(官網聯絡信箱、文件 metadata 的作者欄、新聞稿)拿到**一兩個真實信箱**,就能推斷出**全公司所有人的信箱**。

```
假設你從官網看到一個聯絡信箱:  john.chen@example.com
再從一份 PDF 的作者欄看到:      mary.lin
你就能合理推斷格式是「名.姓@example.com」:

  LinkedIn 上看到有位員工叫 David Wang
        ↓ 套用格式
  推斷他的信箱是:david.wang@example.com
```

有了全公司的信箱清單,攻擊者就能:

- **發動釣魚郵件**(第 18 章)。
- **拿去 HaveIBeenPwned 查有沒有在資料外洩中出現過**(4.10)。
- **對登入系統做帳號枚舉 / 撞庫**(需授權,屬主動,第 11 章)。

> **心智模型:一個信箱,推出全部。** email 命名規則是「一以貫之」的組織慣例——這種一致性對管理很方便,但對攻擊者更方便:破解一個,就破解了全部的命名邏輯。

### 招募啟事:免費的技術棧情報

這是最常被忽略、卻極有價值的一招。**去看目標公司的徵才頁面。** 一則工程師職缺會寫:

> 「需求:熟悉 **Java Spring Boot**、**PostgreSQL**、**Jenkins** CI/CD、**AWS** 環境,有 **Kubernetes** 經驗尤佳。」

這段話翻譯成攻擊者的語言就是:

- 對方後端跑 **Java Spring**(去查 Spring 相關漏洞,如 Spring4Shell)。
- 資料庫是 **PostgreSQL**(SQL Injection 時 payload 要用 PostgreSQL 語法,第 07 章)。
- 內網有 **Jenkins**(Jenkins 是後滲透橫向移動的經典目標)。
- 跑在 **AWS**、用 **Kubernetes**(雲端與容器攻擊面)。

公司為了徵到人,會誠實列出技術棧——等於**免費、合法、公開地把內部架構告訴你**。

> **給防禦者的提醒**:徵才頁不可能不寫技術需求(不然徵不到人)。你能做的是**別過度具體**:寫「熟悉主流 CI/CD 工具」而非「我們用 Jenkins 2.x 跑在這個架構上」;別把內部系統名、版本號寫進職缺。在「徵才吸引力」和「洩漏最小化」之間拿捏。

### 防禦者怎麼做(綜合)

- **員工資安意識培訓**:讓員工知道「你在社群公開的職務、技術棧、打卡地點,都是攻擊者的素材」。
- **email 格式的權衡**:命名規則很難改(也不必為此犧牲可用性),重點放在「就算信箱被推出來,認證也要夠強」——強密碼政策、多因素驗證(MFA),讓「知道信箱」無法直接變成「登入成功」(第 11 章)。
- **職缺描述審查**:技術需求寫得夠用就好,別把內部架構當技術炫耀。

## 4.10 憑證與程式碼洩漏:別人幫你把門打開了

有時攻擊者根本不用「攻擊」——因為帳密和金鑰早就洩漏在公開的網路上,等著人撿。這一節講兩個最常見的來源。

### 帳密外洩:HaveIBeenPwned 的概念

過去十幾年,無數網站發生過大規模資料外洩(LinkedIn、Adobe、各種論壇…),數十億組「email + 密碼」被公開流傳。**HaveIBeenPwned(HIBP)** 是一個彙整了這些公開外洩資料的服務,你可以查詢「某個 email 有沒有出現在已知的資料外洩事件中」。

攻擊者的邏輯(呼應「碎片拼圖」):

```
① 用 4.9 的方法,推出目標員工的信箱 david.wang@example.com
② 到 HIBP 查:這信箱有沒有在某次外洩中出現過?
③ 如果有 → 這個人的某組舊密碼可能已經流出
④ 由於很多人「到處用同一組密碼」(密碼重用),攻擊者拿這組密碼
   去試登入公司系統 → 這叫「撞庫攻擊(credential stuffing)」(第 11 章、第 15 章)
```

> **重要的法律與倫理界線(呼應第 00 章)**:查詢「自己的信箱有沒有外洩」是正當的資安衛生。但**拿別人的外洩帳密去嘗試登入任何系統,就是未授權存取,是犯罪**——即使密碼是「撿來的」。被動偵察合法,不代表你能拿偵察結果去做非法的事。在授權滲透測試中,這類操作必須明確寫進 scope。

### GitHub 上的秘密:誤上傳的金鑰與設定

開發者是人,人會犯錯。最常見的錯誤之一:**把含有密鑰、密碼、API token 的檔案不小心 commit 到公開的 GitHub 儲存庫。**

典型情境:

- 開發時把 AWS 金鑰寫死在程式裡測試,忘了刪就 push。
- `.env`(環境變數檔,裝滿資料庫密碼、API key)沒加進 `.gitignore`,整個上傳。
- 私人 repo 設成公開了,或員工用個人帳號 fork 了公司程式。
- **即使後來刪掉了,Git 歷史裡還留著**——`git log` 翻得出來。

攻擊者會用 GitHub 的搜尋,配合關鍵字組合去撈:

```
# 在 GitHub 搜尋框可用的偵察查詢(概念示意)
org:target-company password        # 某組織的 repo 裡出現 "password" 的地方
"example.com" AWS_SECRET_ACCESS_KEY  # 找綁定目標網域的 AWS 金鑰
filename:.env DB_PASSWORD           # 找誤上傳的 .env 且含資料庫密碼
```

也有自動化工具(如 `trufflehog`、`gitleaks`)專門掃描 Git 儲存庫(含完整歷史)裡「長得像金鑰/密碼」的字串:

```bash
# gitleaks:掃描一個 repo 的整段歷史,找洩漏的密鑰/憑證
gitleaks detect --source ./your-repo -v
# detect 掃描模式;--source 指定要掃的 repo;-v 顯示詳細命中結果
# 防禦者用它掃「自己的」repo,趕在攻擊者之前發現洩漏
```

> **心智模型**:公開的程式碼儲存庫是攻擊者的「失物招領處」——不斷有人把鑰匙掉在這裡。而且 Git 有記憶:你以為「刪掉再 commit 一次」就沒事,但完整歷史還在,鑰匙還躺在那。

### 防禦者怎麼做

- **絕不把密鑰寫進程式碼**:用環境變數、密鑰管理服務(如 AWS Secrets Manager、Vault),`.env` 一定要進 `.gitignore`。
- **上 pre-commit 掃描**:用 `gitleaks`、`trufflehog` 做 commit 前 / CI 階段的自動掃描,把洩漏擋在 push 之前。
- **金鑰一旦外洩,立刻「輪替(rotate)」而非只是刪除**:因為它可能早被爬走了。刪 commit 沒用,唯一正解是「作廢舊金鑰、換新的」。
- **定期掃自家 GitHub / 組織**:主動搜尋自家網域、組織名相關的洩漏,把攻擊者的偵察反過來用在自己身上。
- **員工帳密外洩監控**:讓公司網域的信箱納入外洩監控(HIBP 有企業版 Domain Search),外洩就強制改密碼 + 上 MFA。

## 4.11 防禦視角:縮小你的資訊足跡

前面每一節都附了「防禦者怎麼做」,這一節把它們收斂成一套系統性的思維:**攻擊面縮減(Attack Surface Reduction)**,聚焦在「資訊層面」的攻擊面。

核心觀念只有一句:

> **攻擊者能查到的,你自己先查一遍。定期「偵察自己」,才知道對外洩漏了什麼。**

這叫「攻擊者視角的自我盤點」。把本章當成一份 checklist,對自家組織跑一遍:

### 自我偵察 checklist(防禦版)

| 面向 | 動作 | 對應小節 |
|------|------|---------|
| **搜尋引擎暴露** | 用 Google Dork 搜自家網域,看有沒有暴露的檔案、後台、錯誤訊息;要求 Google 移除敏感索引 | 4.4 |
| **DNS / whois** | 檢查 whois 隱私、清理懸空 DNS、SPF/TXT 別過度洩漏 | 4.5 |
| **子網域盤點** | 用 subfinder / crt.sh 列出自家所有子網域,關掉用不到的、把測試環境內網化 | 4.6、4.7 |
| **憑證透明度監控** | 監控 CT Log,一旦有人申請「像你公司」的憑證(釣魚前兆)立刻警覺 | 4.7 |
| **metadata 清洗** | 對外文件/圖片發布前一律清除 metadata,納入發布流程 | 4.8 |
| **人員資訊** | 資安意識培訓;審查職缺別過度洩漏技術棧;強密碼 + MFA | 4.9 |
| **程式碼 / 帳密洩漏** | pre-commit / CI 掃 secret;金鑰外洩立刻輪替;員工帳密外洩監控 | 4.10 |

### 貫穿全章的防禦心法

**① 你無法把公開資訊變不公開,但能控制「哪些東西被公開」。**
DNS、CT Log、whois 天生公開,擋不住。但 `.env` 洩漏、後台裸奔、金鑰上 GitHub、metadata 沒清——這些是「不該公開卻公開了」,這才是你該全力堵住的。

**② 絕不依賴「隱藏」當安全防線(No security through obscurity)。**
「這個網址沒人知道」「這個後台藏得很深」——CT Log、Google 爬蟲、子網域枚舉會把它們全挖出來。**真正的防線是存取控制、認證、加密,不是隱藏。** 隱藏頂多是延緩,不是防護。

**③ 把攻擊者的工具,變成你的雷達。**
攻擊者用 crt.sh 找你子網域?你就用它監控偽造憑證。攻擊者用 gitleaks 找你的金鑰?你就先用它掃自己。**同一套 OSINT 技術,攻擊者用來找破口,防禦者用來補破口——差別只在誰先做。**

> **心智模型(防禦版)**:回到 4.2 的拼圖比喻。你擋不住攻擊者撿碎片(公開資訊撿不完),但你能做兩件事:**① 別讓「致命的碎片」流出去**(金鑰、內部路徑、暴露檔案)——那些單獨就足以致命;**② 自己先把拼圖拼一遍**,看看攻擊者會拼出什麼,再針對最危險的那塊補起來。

## 4.12 本章小結

- **偵察是 Kill Chain 的第一步,決定整場成敗。** 專業攻擊超過一半時間在偵察——情報越多,攻擊面越清楚。
- **被動 vs 主動**:被動偵察(本章)不直接碰目標、幾乎不留痕跡(查的是 Google、公開資料庫);主動偵察(第 05 章)會對目標發封包、會留 log。專業做法是「被動做到極致,主動範圍縮到最小」。
- **OSINT(開源情報)** 是被動偵察主力:情報散落在搜尋引擎、DNS、憑證紀錄、程式碼平台、社群、公開文件裡,攻擊者把碎片拼成地圖。
- **Google Dorking**:用 `site:`、`filetype:`、`intitle:`、`inurl:`、`-`、`cache:` 精準挖暴露檔案/登入頁/設定檔。
- **域名與 IP 情報**:whois(誰擁有)、DNS(A/MX/TXT/NS 各代表對外服務地圖)、反向 DNS(從 IP 找鄰居)。
- **子網域枚舉**:每個子網域都是一扇門,被遺忘的舊站最脆弱;subfinder(預設被動)、amass `-passive` 從公開來源撈。
- **憑證透明度(CT)**:一個防造假的安全機制,副作用是「每張憑證都公開」,用 crt.sh 就能挖出大量子網域——不能靠網址保密當防線。
- **metadata 洩漏**:圖片 EXIF(GPS、裝置)、PDF/Office(作者、軟體版本、內部路徑),發布前務必用 exiftool 清洗。
- **人員與組織情報**:LinkedIn 拼組織圖、email 命名規則「一個推全部」、招募啟事免費洩漏技術棧——都是社會工程(第 18 章)的前置。
- **憑證與程式碼洩漏**:HaveIBeenPwned 查帳密外洩、GitHub 撿誤上傳的金鑰;**撿到不代表能用——拿外洩帳密登入他人系統是犯罪**。
- **防禦核心**:攻擊面縮減 = 定期「偵察自己」、別洩漏不該公開的東西、絕不靠隱藏當防線、把攻擊者的工具變成雷達。
- **紅線再提醒(第 00 章)**:被動偵察隱蔽 ≠ 可以隨便對任何人做。只對「有授權的目標 / 自家資產 / 官方靶場」施作,且偵察結果不得拿去做未授權的事。

> **下一章預告**:偵察畫好了「攻擊面地圖」,但被動情報有極限——它只告訴你「有哪些門」,沒告訴你「哪扇沒鎖、後面是什麼」。第 05 章進入**主動掃描與列舉**:用 `nmap` 掃 port、辨識服務與版本、抓 banner、列舉目錄與服務細節。這一步開始會**直接碰觸目標、留下 log**,所以第 05 章一開頭會再次強調 scope 與授權——被動偵察的低風險甜蜜期,到此為止。
