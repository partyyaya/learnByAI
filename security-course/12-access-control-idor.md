# 第 12 章:存取控制與業務邏輯漏洞(Broken Access Control、IDOR、越權)

> 上一章(第 11 章)我們解決了「**你是誰**」——登入、session、JWT,把身分驗證清楚。但驗證身分只是第一步。
> 真正決定安全的是下一個問題:「**你是這個身分,那你能不能碰這個東西?**」。你確實是登入的張三,沒錯,
> 可是 `/order?id=1002` 是李四的訂單,你憑什麼看?`/admin` 是管理後台,你一個普通會員憑什麼進?
> 這一章打的就是「授權(存取控制)」這一層。而且要先給你一個震撼數字:OWASP Top 10 2021 把
> **Broken Access Control(失效的存取控制)排在第一名 A01**——它從 2017 的第五名一路爬到榜首。
> 更棘手的是:這類漏洞**掃描器幾乎抓不到**,因為機器不懂「這筆資料到底該屬於誰」。它最靠的,是人腦。

## 12.1 認證 vs 授權:「你是誰」之後的「你能不能」

先把兩個最容易被混為一談的詞徹底分開。它們英文都是 au 開頭,常被簡寫成 **AuthN** 和 **AuthZ**,一字之差,管的事完全不同:

| 面向 | 認證 Authentication(AuthN) | 授權 Authorization(AuthZ) |
|------|---------------------------|--------------------------|
| **回答的問題** | 你是誰? | 你(這個已知身分)能做什麼? |
| **發生時機** | 進門時驗身分 | 進門後,每次要碰資源時 |
| **失敗的後果** | 假冒別人登入(第 11 章) | 越權:碰到不該碰的資料/功能(本章) |
| **類比** | 機場出示護照,證明你是本人 | 你的登機證只准你登「這一班、這個座位」 |
| **檢查一次夠嗎** | 登入時驗一次,發 session | **每一個請求都要重驗**(這是重點) |

> **心智模型**:認證是「查驗證件」,授權是「查權限」。你可以是一個貨真價實、通過認證的合法使用者——這一點攻擊者也做得到,他就是拿自己的正牌帳號登入——但**合法登入不等於什麼都能碰**。存取控制漏洞的可怕之處正在這裡:攻擊者**不需要駭進系統、不需要偷別人的密碼**,他用自己的帳號正大光明登入,然後把請求裡的一個 id 改掉,就看到了別人的資料。整個過程對系統來說,「認證」是通過的,壞就壞在「授權」沒做。

這也解釋了為什麼第 11 章做得再好都救不了本章的漏洞。你的登入機制固若金湯、JWT 簽章無懈可擊、密碼用 Argon2 雜湊——這些全部只證明了「請求的人確實是張三」。但如果後端在張三索取 `id=1002` 的訂單時,只查「這筆訂單存在嗎」而不查「這筆訂單屬於張三嗎」,那再強的認證都是白搭。

> **關鍵認知**:認證和授權是**兩道獨立的牆**,不能用一道代替另一道。「他能登入」推不出「他能存取這筆資料」。本章要反覆敲進你腦裡的一句話是:**每一個請求,都要在伺服器端重新問一次「這個身分有沒有權限碰這個具體物件/功能」。**

## 12.2 存取控制模型:RBAC、ABAC、與 deny by default

在動手打之前,先建立防守方的詞彙。存取控制不是「寫一堆 if 判斷」就完事,業界有成熟的模型,理解它們才知道漏洞出在哪一環。

### 三種常見模型

**① RBAC(Role-Based Access Control,角色型存取控制)**——最普及。把權限綁在「角色」上,使用者被指派角色,角色決定能做什麼:

```
使用者 張三  → 角色 [一般會員]      → 能:看自己的訂單、下單
使用者 李四  → 角色 [客服]          → 能:看所有訂單、改訂單狀態
使用者 王五  → 角色 [管理員 admin]  → 能:上述全部 + 管理使用者、看報表
```

RBAC 的好處是好管理(改角色權限,一票人一起變),但它天生**只管「能不能用這個功能」,不管「能不能碰這一筆具體資料」**。客服角色「能看訂單」——但能看**哪一筆**?RBAC 本身沒說。這個縫隙,正是 IDOR(12.3)的溫床。

**② ABAC(Attribute-Based Access Control,屬性型存取控制)**——更細緻。權限由「屬性」動態決定:使用者的屬性(部門、等級)、資源的屬性(擁有者、機密等級)、環境的屬性(時間、IP)。規則長這樣:

```
允許存取,若  (資源.擁有者 == 請求者.id)          ← 這條就能擋住 IDOR
         或  (請求者.角色 == "admin")
         且  (請求時間 在 上班時間內)
```

ABAC 能表達「這筆資料屬於你才給看」這種**物件層級**的規則,正好補上 RBAC 的縫。實務上常是 RBAC + ABAC 混用:用 RBAC 管功能大分類,用 ABAC(或直接寫歸屬檢查)管單筆資料。

**③ 其他**:還有 DAC(Discretionary,擁有者自己決定分享給誰,如 Google Docs 的分享)、MAC(Mandatory,強制式,軍方那種機密分級)。入門先掌握 RBAC 和 ABAC 的分工即可。

### 一切的地基:Deny by Default(預設拒絕)

比選哪個模型更重要的,是一個**設計原則**:

> **心智模型:Deny by Default(預設拒絕 / 最小權限)。** 存取控制的正確預設值是「**拒絕**」——除非有一條規則明確說「這個人可以」,否則一律不准。這對應第 00 章的信任邊界思維:牆內的資源預設對牆外關閉,要一扇一扇明確開門。

反過來的「預設允許(allow by default)」是災難的根源:系統預設放行,靠工程師記得在每個敏感端點「補上」檢查。人一定會漏——漏掉那一個沒補檢查的端點,就是一個越權漏洞。

```
❌ 預設允許:新加一個 /api/reports 端點,工程師忘了加權限檢查 → 全世界都能看報表
✅ 預設拒絕:新端點預設就進不去,必須明確宣告「這個端點需要 admin 角色」才開放
             → 忘了宣告 = 沒人進得去(頂多是功能壞掉,不是資安破口)
```

「忘記」在兩種預設下的後果天差地遠:預設允許時「忘記」=開了個洞;預設拒絕時「忘記」=功能不能用。**你要讓失誤倒向安全的那一邊。** 這就是為什麼框架的路由權限、雲端的 IAM policy,都該以「白名單、預設拒絕」來設計。

## 12.3 IDOR:改一個 id,就看到別人的訂單

現在進入本章的主角。**IDOR(Insecure Direct Object Reference,不安全的直接物件參照)** 是存取控制漏洞裡最經典、最好懂、也最常見的一種。我們直接把第 00 章 0.3 節那個埋下的伏筆挖出來:

```
網址是 /order?id=1001(我的訂單)?那 /order?id=1002 是不是別人的?
```

這一句話,就是 IDOR 的全部精髓。

### 漏洞怎麼發生的:逐步拆解

假設你是某購物網站的會員,登入後點進「我的訂單」,網址是:

```
https://shop.example.com/order?id=1001
```

你看到自己訂單 1001 的內容:買了什麼、收件地址、電話、金額。一切正常。但作為有攻擊者思維的人(第 00 章思維二:找設計者沒預期的用法),你會立刻注意到三件事:

**第一,這個 id 是「可預測的」。** 它是 `1001`,一個連續遞增的整數。那 `1000`、`1002`、`1003`……幾乎一定是別人的訂單。攻擊者根本不用猜,直接從 1 數到 99999 就能把全站訂單掃一遍(這叫**列舉 enumeration**)。

**第二,id 是「使用者可控」的。** 它就明晃晃地掛在網址上,你想改成什麼都行。這正是第 00 章的信任邊界:任何從外部進來、使用者能改的東西都不可信,而這個 `id` 就是使用者說了算。

**第三,關鍵在後端「用這個 id 做了什麼查詢」。** 我們把有漏洞的後端攤開來看:

```php
<?php
// order.php —— 一個典型的、有 IDOR 漏洞的訂單查詢
session_start();
$currentUser = $_SESSION['user_id'];   // ① 認證是有的:知道現在是誰(假設是 42 號使用者)
$orderId = $_GET['id'];                // ② 直接拿 URL 的 id(使用者可控、不可信!)

// ③ 致命的一行:只查「這筆訂單存在嗎」,完全沒查「它屬不屬於當前使用者」
$order = db_query("SELECT * FROM orders WHERE id = ?", [$orderId]);

echo render_order($order);             // ④ 查到就直接吐出來
?>
```

看出來了嗎?**認證做了(第 ① 行知道你是 42 號),但授權沒做。** 第 ③ 行的 SQL 只有 `WHERE id = ?`,它問的是「1002 這筆訂單在不在」,而不是「1002 這筆訂單是不是 42 號的」。所以你把網址改成 `?id=1002`,後端查到 1002 存在、吐給你——即使那是別人的訂單。

> **心智模型**:IDOR 的病根不是「id 掛在網址上」,也不是「id 太好猜」。病根是**後端只驗證了「物件存在」,卻沒驗證「物件歸屬」**。它信任了「既然你送得出這個 id,你大概有權看吧」——這是把「使用者可控的輸入」當成了「授權憑證」,經典的信任錯置。

### 攻擊怎麼進行

實務上 IDOR 藏在各種地方,不只網址參數:

```
① URL 查詢參數:   /order?id=1002
② URL 路徑:       /api/users/1002/profile
③ 表單隱藏欄位:   <input type="hidden" name="account_id" value="1001">
④ JSON 請求 body:  { "invoiceId": 1002 }
⑤ Cookie 裡的 id:  Cookie: current_account=1001
```

攻擊者用 Burp Suite(第 06 章)攔下請求,把 id 改掉重送即可。更進一步,用 Burp Intruder 或簡單腳本**批次列舉**:

```bash
# 概念示意:帶著自己的 session cookie,把 id 從 1000 掃到 2000
for id in $(seq 1000 2000); do
  curl -s -b "session=我自己的合法session" \
       "https://shop.example.com/order?id=$id" -o "order_$id.html"
done
# 跑完,別人的訂單全在你硬碟裡了——你全程都用自己的合法帳號
```

這就是 IDOR 恐怖的地方:**沒有任何一步是「非法入侵」**。你用自己的帳號登入(認證合法)、發正常格式的請求(沒有畸形 payload)、伺服器正常回應(沒有錯誤)。從流量上看,和一個正常使用者瘋狂看訂單沒兩樣。WAF、掃描器都難以判斷——因為只有業務端才知道「42 號不該看 1002」。這也是 IDOR 長年霸榜、又特別依賴人工測試的原因。

### 修正:補上「歸屬檢查」

根治只需要在查詢裡把「當前使用者」也綁進去:

```php
<?php
session_start();
$currentUser = $_SESSION['user_id'];   // 42 號
$orderId = $_GET['id'];

// ✅ 修正核心:WHERE 同時綁 id 「和」 owner。查的是「這筆是不是『我的』」
$order = db_query(
    "SELECT * FROM orders WHERE id = ? AND user_id = ?",
    [$orderId, $currentUser]           // 訂單 id + 當前使用者 id 一起當條件
);

if (!$order) {
    // 查不到 → 可能不存在,也可能是別人的。一律回 404,不透露「其實存在但你沒權限」
    http_response_code(404);
    exit("找不到訂單");
}
echo render_order($order);
?>
```

兩個要點:

1. **把歸屬條件寫進查詢**(`AND user_id = ?`)。這是最直接的做法:讓資料庫層面就查不出「不屬於我的資料」。等價寫法是先查出來、再在程式裡 `if ($order->user_id !== $currentUser) 拒絕`——效果一樣,重點是**那個歸屬判斷一定要有**。
2. **拒絕時回 404 而非 403**。403(Forbidden)等於告訴攻擊者「這筆存在,只是你沒權限」——反而幫他確認了 id 有效,方便列舉。統一回 404(Not Found)讓「不存在」和「存在但無權」無法區分。(這是縱深防禦的細節,不是主防線,別本末倒置——主防線永遠是那個歸屬檢查。)

> **新手誤區**:「那我把 id 改成隨機難猜的 UUID 不就好了?」——這只是**減緩,不是根治**(12.8 會詳談)。UUID 讓「盲猜列舉」變難,但只要 id 從任何管道洩漏(分享連結、API 回應、被爬蟲抓到、朋友轉傳),沒有歸屬檢查的後端照樣把資料吐出來。**根治永遠是「查歸屬」,換難猜的 id 只是給根治上再加一層,不能取代它。**

## 12.4 垂直越權 vs 水平越權

「越權(privilege escalation / broken access control 的具體表現)」依「往哪個方向越」分兩種,務必分清楚,因為它們的攻擊目標和防禦重點不同:

| 面向 | 水平越權 Horizontal | 垂直越權 Vertical |
|------|--------------------|--------------------|
| **方向** | 同一階層,A 使用者 → B 使用者 | 往上跨階層,一般使用者 → 管理員 |
| **想拿到的** | 別人的**資料/操作**(同權限等級) | 更**高的權限/功能**(管理員能做的事) |
| **經典例子** | 改 `id=1001→1002` 看別人訂單(IDOR) | 打 `/admin`、把自己 `role` 改成 admin |
| **本質** | RBAC 角色對,但碰了不該碰的**那一筆** | 角色根本不該有這個功能,卻用到了 |
| **對應本章** | 12.3 IDOR | 12.5 功能級控制缺失、12.6 Mass Assignment |
| **危害** | 大量個資外洩、竄改他人資料 | 直接接管系統(最嚴重) |

用一句話記:

> **心智模型**:**水平越權是「同一層樓,走進隔壁的房間」——你是會員,去看別的會員的資料;垂直越權是「搭電梯上頂樓」——你是會員,卻用到了只有管理員該有的功能。** 水平的危害是「橫向」洩漏(受害者是其他使用者);垂直的危害是「縱向」提權(受害者是整個系統)。實戰中兩者常串起來:先水平越權摸到一個客服帳號的資料,再從中找垂直越權的破口打到 admin(第 00 章的漏洞鏈)。

兩者的防禦落點也不同:

- **水平越權**要靠「**物件層級授權**(object-level authorization)」——每筆資料都檢查「這是不是請求者的」。這正是 12.3 那個 `AND user_id = ?`。
- **垂直越權**要靠「**功能層級授權**(function-level authorization)」——每個敏感功能都檢查「請求者的角色夠不夠格」。這是 12.5 的主題。

## 12.5 功能級存取控制缺失:`/admin` 只靠「前端不顯示」是假防禦

**功能級存取控制缺失(Missing Function-Level Access Control)** 是垂直越權最常見的成因。它的典型長相,直接回扣第 00 章那句「所有前端驗證都只是使用者體驗,不是安全防線」。

### 經典翻車現場

後端有一個管理頁面 `/admin/users`,可以看全站使用者、刪帳號。前端這樣「保護」它:

```jsx
// 前端:根據角色決定「要不要顯示這個連結」
function Navbar({ user }) {
  return (
    <nav>
      <a href="/dashboard">首頁</a>
      <a href="/order">我的訂單</a>
      {/* ⚠️ 只有 admin 才「看得到」這個連結 */}
      {user.role === "admin" && <a href="/admin/users">使用者管理</a>}
    </nav>
  );
}
```

普通會員登入,看不到「使用者管理」這個連結。開發者覺得「他看不到就進不去」,收工。

**但連結看不到 ≠ 頁面進不去。** 攻擊者根本不看你的導覽列——他直接在網址列敲:

```
https://shop.example.com/admin/users
```

如果後端的 `/admin/users` 端點**沒有自己做角色檢查**,它就會乖乖把使用者管理頁吐給這個普通會員。前端那個 `user.role === "admin"` 判斷,對「不透過你的網頁、直接打 URL 的攻擊者」形同虛設——它只是決定了「要不要畫這個連結」,從來就不是一道安全檢查。

這種「直接猜/打出沒被連結出來的 URL」的手法,有個名字叫**強制瀏覽(Forced Browsing)**:攻擊者主動去戳那些「你以為沒人知道」的路徑。常見目標:

```
/admin           /admin/            /admin.php
/api/admin/users  /internal/config   /debug
/user/1/delete    /export/all-orders.csv
```

配合第 05 章的目錄爆破工具(如 gobuster、ffuf)拿字典去掃,這些「藏起來」的端點很快就現形。**「沒有連結」從來不是保護,那叫「隱藏式安全(security through obscurity)」,不是安全。**

### 修正:每個敏感端點,後端自己強制授權

```php
<?php
// admin/users.php —— 正確做法:後端自己檢查,不信任前端
session_start();
$user = get_current_user_from_session();

// ✅ 進入任何 admin 功能前,伺服器端強制檢查角色。不符 → 直接擋
if ($user === null || $user['role'] !== 'admin') {
    http_response_code(403);
    exit("拒絕存取");
}

// 通過檢查,才是真正的功能
render_admin_user_list();
?>
```

更好的做法是**集中式**授權(12.8 詳談):不要在每個 admin 檔案裡各自 copy 一段檢查(總有一個會漏),而是用中介層(middleware)統一攔截整個 `/admin/*` 路由:

```js
// Express 範例:整個 /admin 路由群組,先過這道 middleware
function requireAdmin(req, res, next) {
  if (!req.user || req.user.role !== "admin") {
    return res.status(403).send("拒絕存取");   // 不是 admin,一律擋在這
  }
  next();                                        // 是 admin 才放行到後面的路由
}

app.use("/admin", requireAdmin);   // ⭐ 一行,罩住 /admin 底下所有端點(deny by default 的體現)
```

> **關鍵認知**:前端隱藏連結、灰掉按鈕、`disabled` 屬性——這些**全部**只是 UX(使用者體驗),讓正常使用者不誤觸。安全檢查**只有在伺服器端做的那一次才算數**。你可以在前端也做一份(改善體驗),但前端那份永遠是「錦上添花」,後端那份才是「命根子」。少了後端這份,前端做得再漂亮都是裸奔。

## 12.6 Mass Assignment:表單偷塞一個 `role=admin` 就提權

**Mass Assignment(批量賦值,也叫 Autobinding / Object Injection)** 是垂直越權的另一條捷徑,特別容易在用了 ORM、又圖方便的現代框架裡出現。

### 漏洞怎麼發生的

現代框架為了方便,常提供「把整包請求參數一次塞進物件」的功能。例如註冊功能:

```js
// 有漏洞的註冊 —— 圖方便,把整包 req.body 直接餵給模型
app.post("/api/register", async (req, res) => {
  // ⚠️ 致命:req.body 是使用者完全可控的,這裡照單全收
  const user = await User.create(req.body);
  res.json(user);
});
```

前端「正常」送的是:

```json
{ "username": "attacker", "password": "p@ss123", "email": "a@evil.com" }
```

但攻擊者不透過你的表單,他用 Burp 或 curl **多塞一個欄位**:

```json
{
  "username": "attacker",
  "password": "p@ss123",
  "email": "a@evil.com",
  "role": "admin",        ← 攻擊者手動加的,你的前端表單根本沒這個欄位
  "isAdmin": true,        ← 順便試試這個常見命名
  "credit": 999999        ← 甚至偷改餘額
}
```

如果 `User` 模型的 `role`、`isAdmin`、`credit` 欄位沒有保護,`User.create(req.body)` 會**把這些欄位一起寫進去**——攻擊者一註冊就是管理員,順便帳戶裡有一百萬。這就是 Mass Assignment:**開發者以為使用者只會送「表單上有的欄位」,但攻擊者能送「資料庫裡有的任何欄位」。**

> **心智模型**:Mass Assignment 的病根,和 IDOR 是同一個家族——**把「使用者可控的輸入」和「內部信任的資料」混在一起處理**。`role`、`isAdmin`、`balance` 這些是「系統該控制的欄位」,絕不能讓它們跟「使用者填的欄位」走同一條「照單全收」的路。信任邊界又一次被跨越了。

### 修正:白名單欄位 / DTO

防禦核心是**永遠明確列出「允許使用者填的欄位」,其餘一律忽略**——又是 deny by default:

```js
// ✅ 做法一:白名單(pick / allowlist),只取這幾個欄位,其他全丟掉
app.post("/api/register", async (req, res) => {
  const safe = {
    username: req.body.username,
    password: req.body.password,
    email: req.body.email,
    // role / isAdmin / credit 根本不在名單裡 → 攻擊者塞了也進不來
  };
  const user = await User.create({ ...safe, role: "user" }); // 角色由後端強制指定
  res.json({ id: user.id, username: user.username });         // 回應也別把敏感欄位吐出去
});
```

其他語言的等價武器:

- **DTO(Data Transfer Object)**:定義一個只含「可接受欄位」的類別,請求先綁到 DTO,再由後端把 DTO 的值搬到真正的實體。危險欄位不在 DTO 裡,天然進不來。(Java Spring、C# 常見做法。)
- **框架的欄位保護**:Rails 的 `strong parameters`(`params.require(:user).permit(:username, :email)`)、Laravel 的 `$fillable`(白名單)/ `$guarded`(黑名單,較不推薦)、Sequelize/Mongoose 指定可寫欄位。**優先用白名單(`permit` / `$fillable`),別用黑名單**——黑名單漏列一個就破功,道理跟 XSS 黑名單必敗(第 09 章)一模一樣。

## 12.7 業務邏輯漏洞:機器抓不到,只能靠人腦

前面的 IDOR、越權還算「有明確模式」。真正讓自動化掃描器束手無策的,是**業務邏輯漏洞(Business Logic Vulnerability)**——這裡沒有畸形 payload、沒有注入字元,每個請求單獨看都「合法」,錯的是**它們組合起來違反了業務規則**。掃描器不懂「一張折價券只能用一次」「數量不能是負數」這種業務常識,所以這類漏洞**幾乎只能靠人腦去想**「這個流程能不能被玩壞」。看四種經典型態:

### ① 競態條件(Race Condition / TOCTOU):同一瞬間做兩次

**TOCTOU(Time-Of-Check To Time-Of-Use,檢查時到使用時的時間差)** 是競態條件的核心。系統「先檢查、後使用」,如果這兩步之間有空隙,攻擊者就同時發很多請求,搶在「檢查」都通過、「使用」都還沒扣減的瞬間插隊。

情境:一張 100 元折價券,規則「每人限用一次」。有漏洞的流程:

```
① 檢查:這張券這個人用過了嗎? → 沒有,通過
② 使用:折 100 元 + 標記為「已使用」
```

正常人一次點一下沒問題。但攻擊者**同時併發送出 50 個「使用折價券」請求**:

```
時間軸(50 個請求幾乎同時到達):
  請求1: 檢查→沒用過✓ ┐
  請求2: 檢查→沒用過✓ ├─ 50 個請求都在「標記已使用」之前完成了檢查
  ...                  │   因為此刻資料庫裡還是「未使用」
  請求50:檢查→沒用過✓ ┘
  → 結果:一張券被折了 50 次,現折 5000 元
```

同樣的模式能打:提領同一筆餘額多次、把限量商品搶超過庫存、把邀請碼用爆。

**防禦**:消除「檢查」和「使用」之間的空隙,讓這一整組操作**不可分割(atomic)**:

```sql
-- ✅ 用資料庫的原子操作 + 條件更新:把「檢查」和「扣減」合成一步
-- 只有「還沒被用過(used=0)」時才更新成功;WHERE 沒中就是別人先扣了
UPDATE coupons SET used = 1, used_by = ?
WHERE code = ? AND used = 0;
-- 檢查「受影響列數」:更新到 1 列 = 我搶到了;更新到 0 列 = 已被用掉,拒絕
```

其他武器:**資料庫交易(transaction)+ 適當的鎖(如 `SELECT ... FOR UPDATE` 悲觀鎖)**、**冪等鍵(idempotency key)**(讓同一個操作即使收到多次也只生效一次,金流 API 常用)、樂觀鎖(version 欄位)。核心觀念是:**任何「檢查完才動作」的敏感操作,都要假設會被併發攻擊。**

### ② 負數 / 超大數量:買 -1 件變退款

系統驗了「數量是不是數字」,卻忘了驗「數量合不合理」。攻擊者把數量改成負數或天文數字:

```json
{ "productId": 42, "quantity": -1, "price": 500 }
```

如果後端算總價是 `quantity * price`,`-1 * 500 = -500`——結帳「總額 -500」,系統不但沒收錢,還可能**退你 500 元**。或者超大數量觸發整數溢位(第 14 章)、或用負數繞過「庫存不足」檢查。

**防禦**:對所有數值做**業務範圍驗證**——數量必須是 `>= 1` 的整數且有合理上限,金額不能為負。**別只驗「型別」,要驗「業務上的合法範圍」。** 這是 deny by default 用在數值上:只接受明確合理的值。

### ③ 工作流程繞過:略過付款,直接跳「訂單完成」

多步驟流程(選購 → 填地址 → **付款** → 完成)如果每一步是獨立端點、又沒檢查「前一步做完了嗎」,攻擊者就**直接跳到最後一步**:

```
正常流程:  /cart → /checkout → /payment(付錢)→ /order/complete
攻擊者:     直接打 /order/complete?orderId=123
            略過 /payment 那一步 → 訂單狀態變「已完成」,但根本沒付款
```

同類還有:略過「驗證 email」直接啟用帳號、略過「輸入舊密碼」直接改密碼、註冊流程跳過付費牆。

**防禦**:在伺服器端維護**流程狀態機(state machine)**,每一步都檢查「目前狀態允不允許進入下一步」。要進 `complete`,先確認這筆訂單的伺服器端狀態是 `paid`。**流程的每一步都是一道授權檢查**——狀態不對,就拒絕。狀態存在伺服器,絕不信任前端說「我付過了」。

### ④ 竄改客戶端傳來的價格 / 金額

最經典、也最不該犯的錯:**把價格交給前端送**。

```json
POST /api/checkout
{ "productId": 42, "quantity": 1, "price": 39900 }   ← 攻擊者把 39900 改成 1
```

如果後端**信任請求裡的 `price`** 來算錢,攻擊者把 39900 改成 1,一台手機一塊錢帶走。同理可竄改的還有:運費、折扣率、幣別、紅利點數。

**防禦**:**價格、折扣、任何跟錢有關的關鍵資料,一律以伺服器端為準。** 前端只能送「你要買哪個商品(productId)、幾件」,後端**自己**去資料庫查這個商品現在的價格來算總額——**永遠不要相信客戶端送來的金額**。

> **心智模型:業務邏輯漏洞 = 「規則在你腦中,但沒寫進程式碼」。** 你知道「一件商品要付對應價格、券只能用一次、要先付款才算完成」,但如果這些規則沒有在伺服器端被**強制檢查**,它們就只是「你的期待」,不是「系統的約束」。攻擊者專門找「開發者假設使用者會照規矩走」的地方。防禦的通則:**把每一條業務規則,都變成伺服器端一道明確的、無法繞過的檢查。**

## 12.8 【重點】防禦:每個請求都做「物件層級授權」

防禦要寫得跟攻擊一樣詳盡。存取控制的防禦沒有一顆銀彈,但有一個**壓倒性的核心原則**,加上一圈配套。先把核心原則刻進骨頭:

> **心智模型(本章最重要的一句)**:**對每一個進來的請求,在伺服器端問一次——「這個已認證的身分,有沒有權限操作『這個具體的物件 / 這個具體的功能』?」** 水平越權靠「物件歸屬檢查」擋,垂直越權靠「功能角色檢查」擋。這個檢查**不能省、不能只做在前端、不能只做一次**。

### 七道防線總覽

| # | 防禦手段 | 對付什麼 | 定位 |
|---|---------|---------|------|
| ① | **物件層級授權**:每筆資料查「這是不是請求者的」 | IDOR、水平越權 | **根治核心** |
| ② | **Deny by Default**:預設拒絕,明確才放行 | 忘記加檢查的端點 | 設計地基 |
| ③ | **集中式授權**:檢查邏輯統一在中介層,別散落各處 | 漏掉某個端點的檢查 | 架構 |
| ④ | **功能層級授權**:敏感功能強制查角色 | 垂直越權、`/admin` | 根治核心 |
| ⑤ | **不可預測 / 間接參照**:UUID 或每使用者的間接 map | 降低列舉難度 | **減緩(非根治)** |
| ⑥ | **關鍵金額 / 狀態一律伺服器端為準** | 改價、流程繞過 | 業務邏輯根治 |
| ⑦ | **併發用鎖 / 交易 / 冪等鍵;管理功能獨立強制授權** | 競態、提權 | 業務邏輯 + 提權 |

逐條展開重點:

**① 物件層級授權(object-level authorization)——最重要。** 就是 12.3 那個 `AND user_id = ?`。任何「用一個 id 去取單筆資料」的地方,都要把「當前使用者」綁進查詢或加一道歸屬判斷。這是擋 IDOR 的唯一根治法,沒有之一。

**② Deny by Default。** 承 12.2:框架路由、雲端 IAM、資料庫權限,全部以「預設拒絕、白名單開放」設計。讓「忘記加規則」的後果是「功能不能用」,而不是「破口大開」。

**③ 集中式授權(centralized authorization)。** 別在 200 個 controller 裡各自 copy-paste 權限檢查——你只要漏一個就是漏洞,而且很難稽核。把授權集中到**中介層 / 過濾器 / policy 層**(如 12.5 的 `app.use("/admin", requireAdmin)`、Rails 的 Pundit/CanCanCan、Spring Security 的 method security)。一處定義、全域套用、統一稽核。

**④ 功能層級授權。** 承 12.5:每個敏感功能(尤其管理功能)都要在後端強制查角色,前端隱藏連結不算數。

**⑤ 不可預測 / 間接物件參照——重點澄清定位。** 兩種做法:(a) 用 **UUID**(如 `a3f8...` 而非 `1002`)當 id,讓盲猜列舉幾乎不可能;(b) 用**每使用者的間接參照 map**——前端只看到 `1、2、3`(你自己資源的序號),後端維護一張「這個使用者的 3 號 = 資料庫 1002 號」的對照表,別人的 id 你根本引用不到。

> **關鍵認知(最容易被誤解的一點)**:換難猜的 id 或間接參照,**是減緩,不是根治**。它把「盲猜列舉」的門檻拉高,但只要 id 從任何管道洩漏(分享網址、API 回應夾帶、Referer 洩漏、內部人員),一個「沒做歸屬檢查」的後端照樣把資料吐出去。**唯一的根治永遠是 ① 的歸屬檢查。** 把 UUID 當成「加了這個就安全」是危險的錯覺——它只是縱深防禦裡的一層,疊在歸屬檢查之上,不能取代它。

**⑥ 關鍵金額 / 狀態,伺服器端說了算。** 承 12.7:價格、折扣、餘額、訂單狀態、權限等級——所有「有價值、有安全意義」的資料,一律以伺服器端資料庫為準,絕不信任客戶端送來的值。前端只能送「意圖(要買哪個、幾件)」,不能送「結論(總價多少、狀態是完成)」。

**⑦ 併發防護 + 管理功能隔離。** 承 12.7①:敏感的「檢查後動作」用資料庫交易、鎖、原子更新、冪等鍵防競態。管理功能(admin)最好**獨立部署 / 獨立授權 / 加上二次驗證**,並全程稽核記錄(誰在什麼時候動了什麼,對接第 20 章的日誌與 SIEM),因為它一旦被越權,就是全系統淪陷。

### 一張圖收束:一個請求該過幾關

```
使用者請求 GET /api/orders/1002
        │
        ▼
① 認證(第 11 章):session/JWT 有效嗎?你是誰? ──否──► 401 未認證
        │ 是(你是 42 號)
        ▼
② 功能授權(RBAC):42 號的角色能用「看訂單」這功能嗎? ──否──► 403
        │ 能
        ▼
③ 物件授權(本章核心):1002 這筆訂單屬於 42 號嗎? ──否──► 404
        │ 屬於
        ▼
   回傳訂單資料 ✓
```

第 ① 關是第 11 章的事,第 ②③ 關才是本章的核心。**大多數 IDOR / 越權漏洞,都是第 ③ 關(甚至第 ②③ 關一起)整個沒做。** 記住這張圖,寫任何取單筆資源的端點時,自問「這三關我都過了嗎」。

## 12.9 靶場練習:在授權環境動手

> **再次強調**(第 00、01 章):以下練習**只在你自己搭的靶場或官方授權平台**進行。存取控制漏洞特別要提醒——因為它「不像入侵」:你只是改個 id、打個沒連結的 URL,手法極其「無害」,最容易讓人心存僥倖跑去戳真實網站。但別忘了:**在未授權的網站上改 id 去看別人的資料,即使你什麼都沒破壞,在台灣一樣構成《刑法》§358 入侵 / §359 破壞電磁紀錄罪(第 00 章)。** 「進去了」本身就成立,不用偷東西。存取控制漏洞尤其如此。

### OWASP Juice Shop(首選,存取控制關卡最豐富)

Juice Shop(現代 Angular + Node 架構)有**大量**存取控制 / IDOR 關卡,是練本章的最佳靶場:

| 關卡類型 | 對應本章 | 練習重點 |
|---------|---------|---------|
| **View Basket(看別人的購物籃)** | 12.3 IDOR / 水平越權 | 改 basket id,看到別人的購物籃 |
| **View another user's shopping basket** | 12.3 | 用 Burp 攔請求改 id 列舉 |
| **Access the administration section** | 12.5 強制瀏覽 | 找出並直接打管理端點 |
| **Forged Feedback / Forged Review** | 12.3 IDOR | 冒用別人 id 送出內容 |
| **管理員 / 提權相關關卡** | 12.4 / 12.6 | 越權到管理功能 |

**建議練法**:全程開著 Burp Suite(第 06 章)看每個請求帶了哪些 id,養成「看到 id 就想改改看」的直覺。解出來計分板會記點,適合按部就班闖關。

### PortSwigger Web Security Academy(Access control labs,最系統)

PortSwigger 官方的 **Access Control** 實驗室是最有系統的一組,一題一個主題,循序漸進,而且完全免費、官方明確授權:

- **Unprotected admin functionality**:對應 12.5,直接打沒保護的 admin 端點。
- **IDOR(insecure direct object references)**:對應 12.3,改 id 看別人資料。
- **User role controlled by request parameter / User ID controlled by request**:對應 12.6,竄改參數提權。
- **Horizontal / Vertical privilege escalation** 系列:對應 12.4,兩種越權分開練。
- **Multi-step process with no access control on one step**:對應 12.7③,工作流程繞過。

這組 lab 幾乎就是本章的實作版,強烈建議照順序打完。

### DVWA(入門暖身)

DVWA(第 01 章搭建)的難度分級適合入門:

- 相關模組能練基本的越權與強制瀏覽概念。
- 一樣的練法:Low 打通後把難度調到 High,開 View Source 看它加了什麼檢查(通常就是 12.8 的歸屬 / 角色檢查)——這是「攻完想防」最直接的訓練(第 00 章學習建議)。

搭建最省事的是 Docker(可搭配本倉庫 Docker 課程),`docker run` 起一個容器就有靶場,打壞了砍掉重來、完全隔離(第 01 章)。

## 12.10 本章小結

- **認證 ≠ 授權**:認證(第 11 章)回答「你是誰」,授權(本章)回答「你能不能碰這個東西」。攻擊者常常是**合法登入的正牌使用者**,壞就壞在後端沒做授權檢查。這也是為什麼 **Broken Access Control 高居 OWASP Top 10 2021 第一名(A01)**,且掃描器難自動抓、最靠人腦。
- **存取控制模型**:RBAC(角色型,管「能不能用這功能」)、ABAC(屬性型,能管「能不能碰這一筆」)、地基是 **deny by default(預設拒絕)**——讓「忘記加檢查」的後果倒向安全。
- **IDOR** 的病根不是「id 好猜」,而是**後端只查「物件存在」沒查「物件歸屬」**。根治是把當前使用者綁進查詢(`AND user_id = ?`)。改 id 就能列舉別人的資料,全程用自己的合法帳號,所以特別隱蔽。
- **越權分兩種**:水平(A→B 同級使用者的資料,靠物件層級授權擋)、垂直(一般使用者→管理員,靠功能層級授權擋)。
- **功能級控制缺失**:`/admin` 只靠「前端不顯示連結」是假防禦,直接打 URL(強制瀏覽)就進去了——**前端驗證永遠只是 UX,安全檢查只算後端做的那一次**(第 00 章)。
- **Mass Assignment**:表單偷塞 `role=admin`、`isAdmin=true`,ORM 照單全收就提權。防禦是**白名單欄位 / DTO**,別用黑名單。
- **業務邏輯漏洞**(掃描器抓不到,靠人腦):①競態 / TOCTOU(併發用鎖、交易、冪等鍵)②負數 / 超大數量(驗業務範圍)③工作流程繞過(伺服器端狀態機)④竄改客戶端價格(金額一律伺服器端為準)。
- **防禦七道防線**,核心一句:**每個請求都在伺服器端做「物件層級 + 功能層級」授權檢查**。UUID / 間接參照只是**減緩**列舉,**根治永遠是查歸屬**。

> **下一章預告**:本章我們讓攻擊者「越權讀寫了不該碰的**資料**」——但資料終究還是資料。第 13 章要更進一步:**檔案上傳、路徑穿越(Path Traversal)、反序列化(Deserialization)**,讓攻擊者從「越權碰資料」升級到「**讓伺服器替你執行程式碼、讀寫任意檔案**」。上傳一個偽裝成圖片的 webshell、用 `../../../etc/passwd` 跳出目錄讀系統檔、把惡意的序列化物件餵給後端觸發 RCE(第 00 章詞彙表裡最嚴重的那一類)。從「讀資料」到「控主機」,危害等級再上一層。
