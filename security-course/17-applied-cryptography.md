## 17.1 密碼學要達成的四個目標:先搞清楚你要什麼

新手學密碼學常常一頭栽進「AES 好還是 RSA 好」,卻答不出「你到底要保護什麼」。這是本末倒置。**先問目標,再挑工具。** 密碼學要達成的其實只有四件事:

| 目標 | 白話 | 要回答的問題 | 對應工具 |
|------|------|------------|---------|
| **機密性(Confidentiality)** | 別人看不到內容 | 「這段資料被竊聽了會不會外洩?」 | 加密(對稱 AES / 非對稱 RSA、ECC) |
| **完整性(Integrity)** | 內容沒被竄改 | 「這段資料在傳輸/儲存中被改過嗎?」 | 雜湊(hash)、MAC / HMAC |
| **鑑別性(Authenticity)** | 確認來源是誰 | 「這真的是他發的,不是別人冒名?」 | HMAC、數位簽章(digital signature) |
| **不可否認性(Non-repudiation)** | 事後賴不掉 | 「他能不能否認這是他簽的?」 | 數位簽章(私鑰只有他有) |

這張表要刻進腦子,因為**選錯目標,再強的演算法都白搭**:

- 只做了加密(機密性),沒做完整性——攻擊者看不懂內容,但可以**盲改密文**讓你解出被竄改的明文(這正是 17.5 padding oracle、以及 CBC 位元翻轉攻擊的根)。
- 只做了雜湊(完整性),沒有密鑰——攻擊者改了資料後**把雜湊也一起重算**,你根本驗不出來(所以要用帶密鑰的 HMAC,見 17.2)。

> **心智模型**:機密性和完整性是**兩件不同的事**,不會互相涵蓋。「加密了」不代表「沒被改」。現代做法是用同時提供這兩者的 **AEAD**(Authenticated Encryption with Associated Data,認證加密),一個 API 把「加密 + 完整性 + 鑑別」一次做完——這是 17.9 防禦的核心建議,先記住這個詞。

**鑑別性 vs 不可否認性差在哪?** 兩者都在「確認來源」,但 HMAC 用的是**雙方共享的同一把密鑰**——所以你能驗「這是知道密鑰的人發的」,卻**不能對第三方證明是對方而非自己發的**(因為你也有密鑰,你自己也能偽造)。數位簽章用**簽名者獨有的私鑰**,只有他簽得出、全世界都能用他的公鑰驗——所以他事後**賴不掉**,這才叫不可否認。這個差別在金流、合約、程式碼簽章場景至關重要。

## 17.2 三大原語:對稱、非對稱、雜湊(別搞混)

密碼學的積木其實就三塊。搞懂「各自能幹嘛、別拿來幹不該幹的事」,你就贏過八成的開發者了。

### 一、對稱加密(Symmetric):同一把鑰匙,快

代表是 **AES(Advanced Encryption Standard)**。加密和解密**用同一把金鑰**,像一把實體鑰匙——鎖門開門是同一把。

- **優點**:快。硬體有 AES 指令集,加密幾 GB 資料眨眼就好。適合加密「大量資料」(檔案、資料庫欄位、TLS 連線裡的實際流量)。
- **罩門**:**金鑰交換問題**。你要跟對方通訊,得先讓對方拿到同一把金鑰——但你怎麼「安全地」把金鑰送過去?用明文送就被竊聽了。這個「先有雞還是先有蛋」的問題,正是非對稱加密要解的。

### 二、非對稱加密(Asymmetric / 公鑰密碼):一對鑰匙,慢

代表是 **RSA** 與 **ECC(Elliptic Curve Cryptography,橢圓曲線)**。每個人有**一對**金鑰:**公鑰(public key)可以公開,私鑰(private key)自己藏好**。兩者數學上配對,但**由公鑰推不出私鑰**。它有兩種完全相反的用法,新手最常搞反:

```
用法一(加密):公鑰「加密」 → 私鑰「解密」
  任何人都能用你的公鑰加密訊息給你,但只有握有私鑰的你解得開 → 達成「機密性」

用法二(簽章):私鑰「簽名」 → 公鑰「驗證」
  只有你能用私鑰簽,所有人都能用你的公鑰驗這是你簽的 → 達成「鑑別性 + 不可否認性」
```

- **優點**:解決了金鑰交換——公鑰隨便公開沒差。
- **罩門**:**慢**,而且能加密的資料量很小(RSA 只能加密比金鑰短的資料)。

> **關鍵認知**:非對稱加密**不是拿來加密大檔案的**。真實系統的標準玩法是**混合加密(hybrid)**:用非對稱加密去「安全地交換一把對稱金鑰」,之後真正的大量資料用又快又好的對稱加密(AES)來加。**TLS 就是這樣運作的**(17.8)——非對稱負責握手交鑰,對稱負責跑流量。

### 三、雜湊、HMAC、數位簽章:別把它們混為一談

這三個常被新手混用,分清楚:

| 原語 | 是什麼 | 有密鑰嗎 | 能做什麼 | 不能做什麼 |
|------|--------|---------|---------|-----------|
| **雜湊(Hash,如 SHA-256)** | 單向壓縮成固定長度指紋 | 無 | 完整性(比對指紋)、去重 | **不能**驗來源(任何人都算得出)、**不可逆**(不是加密) |
| **HMAC** | 雜湊 + 一把共享密鑰 | 有(共享) | 完整性 **+** 鑑別性 | 不可否認(雙方都有密鑰) |
| **數位簽章** | 用私鑰對雜湊簽名 | 有(私鑰/公鑰對) | 完整性 + 鑑別性 **+** 不可否認 | — |

雜湊(SHA-256)的三大性質決定了它的用途:**單向**(算得出指紋、還原不了原文)、**定長**(任何大小的輸入都輸出固定長度)、**抗碰撞**(找不到兩個不同輸入產生相同指紋——這點 MD5/SHA-1 已經破功,見 17.6)。

> **新手誤區**:「我把資料 SHA-256 一下,別人就改不了了。」——錯。雜湊**沒有密鑰**,攻擊者改了資料後把 SHA-256 **重算一次**附上去,你完全驗不出。要防竄改必須用**帶密鑰的 HMAC**(攻擊者沒有密鑰,算不出對的 MAC),或用數位簽章。這也是 JWT(第 11 章)為什麼用 `HS256`(HMAC)或 `RS256`(RSA 簽章)而不是裸 SHA-256 的原因。

## 17.3 編碼 ≠ 加密 ≠ 雜湊:新手第一大誤區

這一節單獨拉出來講,因為它是**工程師最常犯、也最致命的認知錯誤**,而且直接呼應第 15 章(密碼儲存)。看到一串看不懂的字元,很多人就以為「安全了」。大錯特錯。先把三者釘死:

| | 編碼(Encoding) | 加密(Encryption) | 雜湊(Hashing) |
|--|------------------|--------------------|-----------------|
| **目的** | 換一種表示法(方便傳輸/儲存) | 保密(機密性) | 產生指紋(完整性) |
| **需要密鑰嗎** | **不需要** | 需要 | 不需要 |
| **可逆嗎** | **可逆,而且人人可逆** | 可逆(需密鑰) | **不可逆** |
| **例子** | Base64、URL encode、Hex | AES、RSA | SHA-256、bcrypt |
| **能保護資料嗎** | **完全不能!** | 能 | 不能還原,但能比對 |

**核心真言:Base64 不是加密,它是換衣服,不是上鎖。** Base64 的唯一目的是把二進位資料用可列印字元表示(方便塞進 URL、JSON、email),它**不需要任何密鑰**,任何人拿到就能還原。看實例點破:

```bash
# 有人跟你說「這個 token 我 Base64 過了,很安全」——我們來拆穿
$ echo "user=admin&role=superadmin" | base64
dXNlcj1hZG1pbiZyb2xlPXN1cGVyYWRtaW4K            # ← 看起來像亂碼,新手就安心了

$ echo "dXNlcj1hZG1pbiZyb2xlPXN1cGVyYWRtaW4K" | base64 -d
user=admin&role=superadmin                       # ← 一行指令原形畢露,還能改了再編回去!
```

- 攻擊者做的事:`base64 -d` 解開 → 把 `role=superadmin` 改成你要的 → `base64` 編回去 → 送出。**沒有密鑰、沒有阻礙。** 這在 JWT 攻擊(第 11 章)裡是基本功——JWT 的 header 和 payload 就只是 Base64URL 編碼,**任何人都讀得到、改得動**,真正的保護是最後那段**簽章**。

**怎麼一眼認出是哪一種?**(滲透測試看到可疑字串的判斷法)

```
只由 A-Z a-z 0-9 + / 組成、常以 = 結尾、長度是 4 的倍數  → 很可能是 Base64(可直接解)
只由 0-9 a-f 組成、長度是 32/40/64 個字元              → 很可能是 Hex 的雜湊
  32 hex = MD5(128 bit)、40 hex = SHA-1、64 hex = SHA-256
有兩三段用 . 分隔、每段是 Base64URL                    → 幾乎確定是 JWT(第 11 章)
以 $2b$ / $argon2id$ / $6$ 開頭                         → 密碼雜湊(bcrypt / Argon2 / crypt,第 15 章)
```

> **關鍵認知**:「看不懂」不等於「安全」。判斷資料有沒有被真正保護,唯一的標準是「**還原它需不需要一把攻擊者拿不到的密鑰**」。編碼不需要 → 不算保護;雜湊不可逆但**能被比對/被彩虹表反查**(第 15 章)→ 只保護完整性不保護機密性;只有帶密鑰的加密,才真正保護機密性。

## 17.4 加密怎麼被用錯(一):ECB 模式與 IV/nonce 重用

演算法選對了(AES),還是能死得很難看——因為**「模式(mode)」和「參數」用錯**。這是密碼學誤用的重災區。

### 著名的企鵝圖:ECB 模式洩漏結構

AES 一次只加密固定大小的一個「區塊(block,16 bytes)」。資料比一個區塊長怎麼辦?要用**分組模式(mode of operation)**把區塊串起來。最天真的模式叫 **ECB(Electronic Codebook)**:把資料切成區塊,**每塊各自獨立加密**。

問題來了——**相同的明文區塊,永遠產生相同的密文區塊**。

```
明文:  [區塊A][區塊A][區塊B][區塊A]
              ↓ ECB(每塊獨立加密,同塊同結果)
密文:  [ 密文X ][ 密文X ][ 密文Y ][ 密文X ]
              ↑ 明文的「重複結構」原封不動洩漏到密文!攻擊者不用解密就看出圖案
```

- **為什麼錯**:雖然攻擊者解不出區塊內容,但資料的**巨觀結構整個外洩**。經典示範就是「ECB 企鵝圖」——把一張 Linux 吉祥物 Tux 企鵝的圖用 AES-ECB 加密,加密後**你還是清楚看得出那是一隻企鵝**,因為圖中大片相同顏色的區域產生了大片相同的密文。這張圖是密碼學課永遠的迷因,一看就懂 ECB 有多爛。
- **怎麼被打**:結構洩漏之外,ECB 還能被「**剪貼攻擊(cut-and-paste)**」——因為區塊獨立,攻擊者能把密文區塊重排、拼接,組出對他有利的明文(cryptopals 有一整題就在打這個,17.10)。
- **怎麼修**:**別用 ECB**。用會把區塊「鏈起來」的模式,讓相同明文因為前後文不同而產生不同密文。首選 **GCM**(AES-GCM,同時給你完整性,是 AEAD),或至少 CBC(但 CBC 沒有內建完整性,見 17.5 的 padding oracle)。

### IV / nonce 重用:一次重用,滿盤皆輸

為了讓「相同明文每次加密都不一樣」,現代模式需要一個**每次都不同**的隨機值:CBC 模式叫 **IV(Initialization Vector,初始化向量)**,CTR/GCM 模式叫 **nonce(number used once,用過即棄的數)**。名字不同,鐵律一樣:

> **鐵律**:IV/nonce **絕不能重用**,而且(對 GCM/CTR 而言)**在同一把金鑰下重用一次就是災難**。

看 CTR/GCM 為什麼重用 nonce 這麼致命(這是 stream cipher 家族的通病):

```
CTR/GCM 本質:用 (金鑰 + nonce + 計數器) 生出一段「金鑰流(keystream)」,
             再拿金鑰流去 XOR 明文得到密文。   密文 = 明文 ⊕ 金鑰流

若兩則訊息用了「相同金鑰 + 相同 nonce」→ 兩者的金鑰流一模一樣:
   密文1 = 明文1 ⊕ 金鑰流
   密文2 = 明文2 ⊕ 金鑰流
攻擊者把兩段密文 XOR:
   密文1 ⊕ 密文2 = 明文1 ⊕ 明文2      ← 金鑰流被消掉了!
   → 金鑰完全沒被破,但兩則明文的關係整個外洩,常足以還原內容
```

- **為什麼錯**:nonce 重用**直接抵銷了加密的隨機性**,金鑰流被抵消,明文外洩。對 **AES-GCM 更慘**:重用 nonce 不只洩漏明文,還會**洩漏用來算完整性標籤的認證金鑰**,讓攻擊者能**偽造任意訊息的合法標籤**——完整性防護整個崩掉。這是有名的 "forbidden attack"。
- **怎麼被打**:歷史上 WEP(早期 Wi-Fi 加密)就是 IV 太短、很快重複,被完整破解;許多自幹加密的 App 把 nonce 寫死成固定值或 `0`,一測就破。
- **怎麼修**:**GCM 的 nonce 用 CSPRNG 隨機產生(96-bit),或用嚴格遞增的計數器,總之保證同一把金鑰下永不重複**;需要加密海量訊息時考慮 XChaCha20(nonce 夠長,隨機碰撞機率可忽略)。**永遠不要把 IV/nonce 寫死。**

## 17.5 加密怎麼被用錯(二):金鑰管理、弱亂數與進階攻擊

演算法和模式都對了,還有兩個更接地氣的坑:**金鑰放哪**、**隨機從哪來**。這兩個是滲透測試裡「翻一翻就撿到」的高頻戰果。

### 硬編碼金鑰 / 金鑰進版控

再強的 AES,金鑰被撿走就等於沒加密。最常見的犯罪現場:

```python
# 反面教材:金鑰直接寫在原始碼裡,還跟著程式碼進了 Git
SECRET_KEY = "aes-key-1234567890abcdef"          # ← 硬編碼!任何拿到原始碼的人都有金鑰
cipher = AES.new(SECRET_KEY.encode(), AES.MODE_GCM)
```

- **怎麼被打**(回扣第 13 章讀檔、第 16 章後滲透撈設定檔):攻擊者拿到 shell 後,第一件事就是翻設定檔、翻原始碼、翻環境變數找金鑰。更常見的是**金鑰早就在公開的 Git 歷史裡**——就算你「後來刪掉了」,`git log`/`git show` 仍能挖出舊 commit 的金鑰。GitHub 上被自動掃出的 AWS 金鑰、API token 多到 GitHub 專門做了 secret scanning。
- **怎麼修**:金鑰**永不進版控**。放環境變數、`.env`(且 `.gitignore` 排除)、或正規的 **secrets manager / KMS**(17.9 詳述);已經外洩的金鑰**當作已洩漏,立刻輪替(rotate)**,不是「把 commit 刪掉」就沒事——它可能早被爬走了。

### 弱亂數:用可預測的 RNG 產金鑰/token/session id

密碼學的安全性**建立在「攻擊者猜不到隨機值」之上**——金鑰、IV/nonce、session id、密碼重設 token、CSRF token(第 10 章)……全靠亂數。**用錯亂數來源,等於把這些值攤在陽光下。**

```javascript
// 反面教材:用「一般用途」的亂數產密碼重設 token
const token = Math.random().toString(36).slice(2);   // ← Math.random 不是密碼學安全的!
// Math.random 用的是可預測的 PRNG,攻擊者觀察幾個輸出就能推算內部狀態、預測後續 token

// 正確:用 CSPRNG(Cryptographically Secure PRNG)
const crypto = require('crypto');
const token = crypto.randomBytes(32).toString('hex'); // ← 32 bytes 高熵、不可預測
```

- **為什麼錯**:一般的 PRNG(如 `Math.random()`、C 的 `rand()`、Java 的 `java.util.Random`)是為「統計上夠隨機、跑得快」設計的,**不是為了不可預測**——它們的內部狀態能從少量輸出反推,進而預測未來所有輸出。拿它產密碼重設 token,攻擊者就能**預測別人的 token 直接接管帳號**。
- **怎麼修**:所有「安全相關」的隨機值一律用 **CSPRNG**:Node 的 `crypto.randomBytes`、Python 的 `secrets` 模組(不是 `random`!)、Java 的 `SecureRandom`、Linux 的 `/dev/urandom`、瀏覽器的 `crypto.getRandomValues`。**心法:只要這個隨機值「被猜到會出事」,就必須用 CSPRNG。**

### Padding Oracle:只做加密不做完整性的經典報應

前面 17.1 說過「加密不等於防竄改」,padding oracle 就是最經典的懲罰。CBC 模式解密時需要檢查「填充(padding)」格式對不對,如果系統**因為 padding 對不對而回傳不同的錯誤/行為**(一個會「洩漏 padding 是否正確」的預言機,oracle),攻擊者就能:

```
攻擊者不知道金鑰,但反覆送「竄改過的密文」給伺服器,觀察回應:
  padding 錯 → 伺服器回「格式錯誤」    (oracle 說:錯)
  padding 對 → 伺服器回「解密成功/其他」(oracle 說:對)
一個 byte 一個 byte 試,靠這個「對/錯」訊號,最終能「不知道金鑰就解出整段明文」,
甚至反過來加密出任意明文。歷史上 POODLE、以及多起 CBC 實作都栽在這。
```

- **為什麼錯**:根因是**只做了機密性(CBC 加密),沒做完整性**——伺服器願意去「解密並剖析」攻擊者亂改的密文,還把結果差異洩漏出去。
- **怎麼修**:**用 AEAD(AES-GCM / ChaCha20-Poly1305)**。AEAD 在解密前先驗完整性標籤,標籤不對**直接拒絕、根本不解密**,oracle 無從問起。或至少遵守 "Encrypt-then-MAC":先加密、再對密文算 MAC,驗 MAC 失敗就不解密。**這再次證明 17.1 那句話:機密性和完整性要一起做。**

### 降級攻擊(Downgrade)

系統為了相容常「同時支援新舊演算法/協定」,攻擊者(尤其中間人)就**強迫雙方協商到最弱的那個**再打它。TLS 的 POODLE、FREAK、Logjam 都是逼降到弱協定/弱金鑰;JWT 的 `alg: none`(第 11 章)也是一種「降級成不驗簽」。**怎麼修**:**伺服器端硬性關掉舊協定/弱演算法**(17.8 的 `ssl_protocols` 只留 1.2/1.3)、驗簽時**寫死允許的演算法白名單**、上 HSTS 防 HTTPS 被降回 HTTP。

## 17.6 雜湊怎麼被用錯:快雜湊存密碼、MD5/SHA-1 碰撞、自創加密

### 用「快雜湊」存密碼(回扣第 15 章)

這是第 15 章的核心,這裡從密碼學角度再釘一次。很多人拿 `SHA-256(password)` 存密碼,自以為安全——**大錯**:

- SHA-256 是為「**快**」設計的(每秒可算數十億次)。這對驗檔案完整性是優點,對存密碼是**致命缺點**:資料庫一旦外洩,攻擊者用 GPU 一秒試幾十億個候選密碼做離線爆破(第 15 章),快雜湊等於門戶大開。
- 加 salt 只能防「彩虹表/預算表」和「相同密碼撞出相同雜湊」,**擋不住針對單一帳號的暴力破解**——因為快雜湊本身太快。
- **怎麼修**:密碼要用**慢、且可調成本**的專用密碼雜湊:**Argon2(首選,尤其 Argon2id)** 或 **bcrypt**、scrypt。它們刻意「慢」且吃記憶體,把攻擊者每秒能試的次數壓到極低。細節見第 15 章;這裡的重點是:**「雜湊」不是只有一種,存密碼要用『慢雜湊』,不是 SHA-256。**

### MD5 / SHA-1:碰撞已破,別再用在需要抗碰撞的地方

雜湊的「抗碰撞性」是指「找不到兩個不同輸入產生相同雜湊」。**MD5 早已被完全攻破,SHA-1 也在 2017 年被 Google 實際做出碰撞(SHAttered)。**

- **怎麼被打**:攻擊者能構造**兩份雜湊值相同、但內容不同的檔案**——例如一份無害的合約 PDF 和一份惡意版本雜湊一樣;或一張你信任的憑證和一張偽造憑證雜湊一樣(歷史上 Flame 惡意程式就用 MD5 碰撞偽造微軟簽章)。凡是靠雜湊「認身分/認內容」的場景(數位簽章、憑證、檔案完整性、Git object)用了 MD5/SHA-1,就可能被偷天換日。
- **怎麼修**:需要抗碰撞的場景一律用 **SHA-256 及以上(SHA-2 / SHA-3 家族)**。(注意:MD5/SHA-1 拿來做「非安全用途」的 checksum、快取 key 還行,但**別碰任何安全判斷**。)

### 自己 XOR / 自創加密:「別自己造密碼學」

滲透測試常遇到 App 自己刻的「加密」:把資料跟一個固定字串 XOR、或字元位移、或幾個步驟拼一拼,美其名曰「我們自研的加密演算法」。

```python
# 反面教材:自研「加密」= 拿固定 key 做 XOR
def my_encrypt(data, key="secret"):
    return bytes(b ^ ord(key[i % len(key)]) for i, b in enumerate(data.encode()))
    # 固定短 key 的 XOR:已知/猜到一段明文就能還原 key,或用頻率分析直接破,毫無安全性可言
```

- **為什麼錯**:密碼學經過**幾十年全世界密碼學家公開攻擊、檢驗**才敢說「暫時安全」。你一個人閉門造出來的東西,只是「**你自己還沒想到怎麼破**」,不代表別人破不了。cryptopals(17.10)前幾題就在教你**幾分鐘破掉各種自幹 XOR/位移加密**,做完你就再也不敢自己造了。
- **怎麼修**:**別自己造密碼學(Don't roll your own crypto)。** 用經過驗證的標準演算法、經過驗證的函式庫的**高階 API**(17.9)。你的創意應該花在業務,不是重新發明一個爛掉的 AES。

> **心智模型**:密碼學跟開鎖不一樣——鎖看得到構造,但一個「你破不了的加密」不代表「沒人破得了」。**安全性不能靠隱藏演算法(security by obscurity)**,要靠「就算演算法完全公開,沒有金鑰還是破不了」(這叫 Kerckhoffs 原則)。你自研的東西之所以「看起來安全」,往往只是因為還沒人認真看它。

## 17.7 TLS / HTTPS 攻防:中間人的門戶

前面談的都是「你的程式怎麼用密碼學」,現在談**傳輸中**的密碼學——**TLS(Transport Layer Security)**,也就是 HTTPS 的 S。它是混合加密(17.2)最成功的實戰應用,也是本倉庫 Nginx 課程(`../nginx/06-ssl-https.md`)、common 課程(`../common/01-http-https.md`、`02-ssl-certificates.md`)的主題,這裡從攻防角度串起來。

### TLS 一次做齊三件事

TLS 不只是「加密」,它在一次握手裡同時達成 17.1 的三個目標:

```
① 驗身分(鑑別性):伺服器出示「憑證(certificate)」,由受信任的 CA 簽發,
                  用非對稱簽章證明「我真的是 bank.com」——這步防的就是冒名頂替
② 交金鑰(機密性):用非對稱(RSA/ECDHE)安全協商出一把「本次連線專用的對稱金鑰」
                  (ECDHE 還提供前向保密:就算私鑰未來外洩,過去錄的流量也解不開)
③ 跑流量 + 驗完整性:之後所有資料用那把對稱金鑰(AES-GCM)加密傳輸,並帶完整性標籤
                  → 一次滿足機密性 + 完整性 + 鑑別性
```

### 憑證驗證:不驗憑證 = 中間人門戶大開

TLS 的**整個安全性,建立在「客戶端真的去驗伺服器的憑證」**。一旦不驗,加密再強都白搭——因為你可能**正在跟攻擊者建立一條「加密良好」的連線**。

> **心智模型**:加密只保證「這條管子裡的內容別人偷看不到」,但**沒告訴你管子的另一頭是誰**。憑證驗證就是在確認「另一頭真的是我要找的人」。少了它,你可能跟中間人(MITM)建了一條加密管——內容對他全公開,因為他就是你連線的對象。

**中間人攻擊(Man-in-the-Middle,MITM)** 就是攻擊者卡在你和伺服器中間,分別跟兩邊各建一條連線、居中轉發並竊聽/竄改。**能不能得逞的關鍵,就在客戶端有沒有嚴格驗憑證**:

```python
# 反面教材:程式呼叫 HTTPS API 時關掉憑證驗證(現場超常見的災難)
import requests
requests.get("https://api.internal/", verify=False)   # ← verify=False 等於「隨便誰冒充我都信」
# 開發時為了跳過自簽憑證錯誤而加,結果忘了拿掉帶上線 → MITM 門戶大開
# 正確:憑證要驗;內部/自簽環境請把「自己的 CA」加進信任庫,而不是整個關掉驗證
```

- **sslstrip / HTTPS 降級**:另一類 MITM 手法。攻擊者在中間**把使用者對外的 HTTPS 悄悄降回 HTTP**(使用者一開始常是打 `http://` 再被導向 https),讓流量以明文經過自己。**對策就是 HSTS**(見下)——強制瀏覽器「這個網域只准用 HTTPS」,沒得降級。

### 現代 TLS 設定要點(藍隊必做,對應 Nginx 課程)

```nginx
# 對應 ../nginx/06-ssl-https.md,以攻防視角標註「為什麼」
ssl_protocols TLSv1.2 TLSv1.3;              # 只留安全版本;TLS 1.0/1.1(及更舊的 SSLv3)已被攻破,關掉防降級攻擊
ssl_prefer_server_ciphers on;               # 握手以伺服器的套件順序為準,不讓客戶端挑到弱套件
ssl_ciphers 'ECDHE-...-AES128-GCM-SHA256:...';  # 只留 ECDHE(前向保密)+ GCM(AEAD)的強套件
# 加上 HSTS:強制瀏覽器只用 HTTPS,直接封死 sslstrip 這類降級
add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
```

- **棄用舊協定**:TLS 1.0/1.1、SSLv3 一律關掉(POODLE、BEAST 等都打舊協定)。
- **強套件 + 前向保密**:只留 ECDHE + AEAD(GCM/ChaCha20-Poly1305)套件。
- **HSTS**:如上,防降級。`preload` 收錄後幾乎無法撤回,確定永不回 HTTP 再加(Nginx 課程有提醒)。
- **驗收工具**:`nmap --script ssl-enum-ciphers -p 443 <host>` 或線上的 SSL Labs 掃一遍,舊協定不該出現、評級應為 A。(這也是藍隊/紅隊都會做的一步:紅隊找弱協定當降級入口,藍隊掃出來關掉。)

## 17.8 【重點】防禦:密碼學的正確用法

防禦要寫得跟攻擊一樣詳盡。密碼學的防禦有個好消息:**九成的正確做法可以濃縮成幾條鐵律**,照做就避開了本章所有攻擊。

### ① 第一鐵律:別自己造密碼學,用高階 API

- **別自己造演算法**(17.6),也**別自己拼裝原語**(自己組 AES + IV + MAC 極易出錯——padding oracle、nonce 重用都是這樣來的)。
- 用**經過驗證的函式庫的高階 API**:如 libsodium / NaCl(`crypto_secretbox`、`crypto_box`)、Python 的 `cryptography` 的 Fernet、Go 的 `crypto/*`。這些 API **幫你把模式、IV、MAC 都處理好了**,你只管丟資料進去。**能用「一個函式做完加密+完整性」的,就別自己碰 mode 和 IV。**

### ② 優先用 AEAD(把 17.1、17.4、17.5 一次解決)

- 需要對稱加密時,**一律優先 AES-GCM 或 ChaCha20-Poly1305(AEAD)**。它們**同時提供機密性 + 完整性 + 鑑別**,天生免疫 padding oracle(17.5),也不會讓你「只加密沒防竄改」。
- **唯一要小心的就是 nonce 不能重用**(17.4)——用 CSPRNG 產生或嚴格遞增計數器保證唯一。
- 選型:有硬體 AES 加速就用 AES-GCM;純軟體/行動裝置環境 ChaCha20-Poly1305 更快更穩(沒有 timing 側信道問題)。

### ③ 金鑰管理:全生命週期都要顧

| 環節 | 正確做法 |
|------|---------|
| **產生** | 用 CSPRNG 產生;金鑰長度足夠(AES-256、RSA ≥ 2048/3072、ECC 用 P-256 以上) |
| **儲存** | **永不進版控、永不硬編碼**;用 **KMS(AWS KMS / GCP KMS / Azure Key Vault)** 或 secrets manager(Vault、AWS Secrets Manager);最高等級用 HSM |
| **傳遞** | 用 KMS 的「envelope encryption」——資料金鑰用主金鑰包起來,主金鑰永不離開 KMS |
| **輪替(rotation)** | 定期輪替;金鑰疑似外洩**立刻輪替並視同已洩漏**(17.5) |
| **權限** | 最小權限(第 00 章):只有真正需要的服務能取用金鑰,並留存取稽核 log(第 20 章) |

### ④ 密碼儲存:Argon2 / bcrypt(第 15 章)

- 存密碼**只用慢雜湊**:**Argon2id(首選)** 或 bcrypt/scrypt,搭配唯一 salt,成本參數調到「登入可接受、爆破很痛」。**絕不用 SHA-256/MD5 這類快雜湊存密碼**(17.6)。細節見第 15 章。

### ⑤ 亂數:安全相關一律 CSPRNG

- token、session id、金鑰、IV/nonce、重設連結……只要「被猜到會出事」,就用 CSPRNG(`secrets`、`crypto.randomBytes`、`SecureRandom`、`/dev/urandom`),**絕不用 `Math.random()`/`rand()`**(17.5)。

### ⑥ 完整性 / 鑑別:該簽的要簽、該 MAC 的要 MAC

- 傳輸中信任的資料(webhook、下發到客戶端又收回的狀態、JWT)要用 **HMAC 或數位簽章**驗完整性與來源(第 11 章)。**別只靠雜湊**(17.2 新手誤區)。
- 驗簽時**寫死允許的演算法白名單**,防 `alg: none` 與降級(17.5、第 11 章)。

### ⑦ 側信道:定時比較(呼應第 10 章 CSRF token)

比對「祕密值」(MAC、token、簽章、API key)時,**不能用一般的 `==`**——因為多數 `==` 是「逐字元比,遇到第一個不同就提早返回」,攻擊者能靠**回應時間的細微差異**一個一個字元猜出正確值(timing attack,時序側信道)。要用**定時比較(constant-time compare)**:

```php
// 反面教材:遇到第一個不同 byte 就 return,比對耗時「洩漏」了正確前綴長度
if ($user_token == $real_token) { ... }               // ← 可被 timing attack

// 正確:定時比較,無論哪裡不同都花一樣的時間
if (hash_equals($real_token, $user_token)) { ... }     // PHP:hash_equals
// 其他語言:Python secrets.compare_digest、Node crypto.timingSafeEqual、Go subtle.ConstantTimeCompare
```

這正是第 10 章講 CSRF token 比對時提到「用 `hash_equals` 別用 `==`」的原因——**任何祕密值的比對都適用這條**。

### ⑧ TLS 用現代設定(17.7)

- 只開 TLS 1.2/1.3、強套件 + 前向保密、上 HSTS;客戶端**務必驗憑證**(別 `verify=False`),內部環境用自己的 CA 而不是關掉驗證。

> **心智模型:縱深防禦(第 00 章)套在密碼學上**——別自己造(用對工具)→ 用 AEAD(一次做齊機密+完整)→ 金鑰管好(進 KMS、會輪替)→ 亂數用 CSPRNG → 比對用定時 → 傳輸用現代 TLS。每一層都獨立擋住一類攻擊,疊起來就很難被打穿。

## 17.10 本章小結

- **先定目標再挑工具**:密碼學要達成四件事——**機密性**(加密)、**完整性**(雜湊/HMAC)、**鑑別性**(HMAC/簽章)、**不可否認性**(數位簽章)。機密性和完整性是**兩件事**,現代用 **AEAD** 一次做齊。
- **三大原語別搞混**:對稱(AES,快,有金鑰交換問題)、非對稱(RSA/ECC,慢,拿來交換對稱金鑰與簽章)、雜湊/HMAC/簽章(單向指紋;裸雜湊沒密鑰擋不了竄改,要 HMAC 或簽章)。
- **編碼 ≠ 加密 ≠ 雜湊**:**Base64 不是加密**,不需密鑰、人人可逆。判斷資料有沒有被保護,只看「還原需不需要一把攻擊者拿不到的密鑰」。
- **加密誤用重災區**:ECB 洩漏結構(企鵝圖)→ 用 GCM;**IV/nonce 重用**(GCM/CTR 重用一次就災難)→ CSPRNG 保證唯一;硬編碼金鑰/金鑰進版控(第 13、16 章撿現成)→ KMS + 永不進版控 + 輪替;**弱亂數**(`Math.random`)→ CSPRNG;padding oracle(只加密不做完整性)→ AEAD;降級攻擊 → 關舊協定 + 演算法白名單。
- **雜湊誤用**:快雜湊存密碼(第 15 章)→ Argon2/bcrypt;MD5/SHA-1 碰撞已破 → SHA-256 以上;自創加密 → **別自己造密碼學**。
- **TLS = 加密 + 驗身分 + 完整性**:核心是**驗憑證**(不驗 = MITM 門戶大開,別 `verify=False`);現代設定棄用舊協定、用強套件 + 前向保密、上 HSTS 防 sslstrip 降級。
- **正確用法八條**:別自己造(用高階 API)、優先 AEAD、金鑰進 KMS 且會輪替、密碼用 Argon2/bcrypt、亂數用 CSPRNG、完整性用 HMAC/簽章、比對用**定時比較(`hash_equals`)** 防側信道、TLS 用現代設定。

> **下一章預告**:這一章你看到——**演算法本身幾乎打不動,倒是「用它的人」天天出包**。第 18 章要把這個道理推到極致:**社會工程與釣魚(Social Engineering & Phishing)**。你把 TLS 設到 A+、AES-GCM 用到滴水不漏,只要有一個員工被一封「IT 部門請重設密碼」的假信騙走帳密,再強的密碼學都直接繞過。**人,是整個系統最脆弱、也最難打補丁的一環。** 下一章我們進到這個環節——攻擊者怎麼操弄信任與情緒,以及(重點放在防禦)組織與個人怎麼建立「人的防火牆」。這一章倫理提醒會更重、更前置,因為社會工程直接對「人」動手。
