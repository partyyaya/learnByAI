# 第 02 章:瀏覽器原生 ESM 與 No-bundle Dev Server

> 這是整門課的技術核心。第 00 章我說「Vite dev 不打包」,第 01 章你看到了「秒啟動」。
> 這一章我們要把這件事**拆到最底**:為什麼能不打包?瀏覽器到底做了什麼?Vite 伺服器又做了什麼?
> 我們會打開瀏覽器 Network 面板**親眼驗證**,也會誠實討論「不打包」帶來的代價(那正是第 03 章的引子)。

---

## 2.1 先複習:瀏覽器原生 ESM 是什麼

第 00 章講過,現代瀏覽器原生支援 ES Modules。我們把這件事再具體化一次,因為 Vite 的一切都建立在它之上。

假設你有兩個檔案,完全不經任何工具,直接放到一個靜態伺服器上:

```js
// math.js
export function add(a, b) {
  return a + b
}
```

```html
<!-- index.html -->
<script type="module">
  // 注意 type="module"
  import { add } from './math.js'
  console.log(add(1, 2))   // 3
</script>
```

當瀏覽器載入這個頁面:

1. 看到 `<script type="module">`,進入 **ESM 模式**。
2. 執行到 `import { add } from './math.js'`,瀏覽器**自己發出一個 HTTP 請求**去抓 `./math.js`。
3. 抓回來、執行,拿到 `add`,印出 `3`。

**關鍵洞察**:沒有任何打包工具參與。瀏覽器**自己**就會「順著 `import` 往下抓檔案」。這個能力,就是 Vite 不打包也能跑的根本原因。

> **心智模型**:`import` 在瀏覽器眼裡,就是「一個會去抓檔案的指令」。一個 `import` = 一個 HTTP 請求。整個應用就是「從 HTML 出發,順著一個個 import 展開的依賴樹」,瀏覽器自己會把這棵樹爬完。

## 2.2 那為什麼不能「直接這樣裸寫」就好,還需要 Vite?

如果瀏覽器自己就會爬,那 Vite 在中間幹嘛?這是個好問題。答案是:**裸寫原生 ESM 有三個現實障礙,Vite 就是來補這三個洞的**。我們一個一個看,因為這三個洞剛好就是 Vite dev server 的三大職責。

### 障礙 1:瀏覽器只看得懂「標準 JS / CSS」

你寫的是 `.ts`、`.vue`、`.jsx`、`.scss`——瀏覽器全都不認識。`import './App.vue'` 瀏覽器會直接報錯。

**Vite 的解法**:當瀏覽器來要 `App.vue` 時,Vite 伺服器**即時把它轉成標準 JS** 再回傳。瀏覽器永遠只收到它看得懂的東西。(這就是第 04 章「轉換管線」。)

### 障礙 2:「裸模組匯入(bare import)」瀏覽器不會解析

你常這樣寫:

```js
import { createApp } from 'vue'    // 'vue' 不是路徑,是一個套件名
import _ from 'lodash-es'
```

`'vue'` 這種「不是以 `/`、`./`、`../` 開頭」的匯入,叫**裸模組匯入(bare import)**。

**問題**:瀏覽器面對 `import ... from 'vue'`,它不知道 `vue` 在哪!瀏覽器只會發 HTTP 請求去抓「路徑」,它不懂「去 `node_modules` 裡找 `vue` 套件」這種 Node.js 才有的規則。所以瀏覽器看到 `'vue'` 會直接報錯:`Failed to resolve module specifier "vue"`。

**Vite 的解法**:Vite 會把 `'vue'` **改寫(rewrite)**成一個瀏覽器抓得到的真實路徑,例如:

```js
// 你寫的:
import { createApp } from 'vue'

// Vite 改寫成(瀏覽器實際收到的):
import { createApp } from '/node_modules/.vite/deps/vue.js?v=a1b2c3d4'
```

這個改寫動作,牽涉到「找出 `vue` 到底在哪、要不要先預打包」——這就是第 03 章「依賴預打包」的核心工作。**這裡先記住:裸匯入會被 Vite 改寫成真實路徑。**

### 障礙 3:模組太多時,請求數量爆炸

這是「不打包」的天生代價。如果你的應用有 1000 個模組,瀏覽器就要發近 1000 個 HTTP 請求(因為一個 import 一個請求)。

- 對**你自己的原始碼**(`src/` 裡幾百個檔):在現代 HTTP/2(可多路複用)+ 本機 dev server 下,還算可以接受,Vite 也有快取機制(第 04、05 章)。
- 對**第三方依賴**:這就出大事了。像 `lodash-es` 這種套件,內部被拆成**幾百個小模組**互相 import。光一個 lodash 就可能引爆數百個請求,瀏覽器會卡到不行。

**Vite 的解法**:把第三方依賴用 esbuild **預先打包**成少少幾個檔案(這樣 1 個套件可能只剩 1 個請求)。這正是第 03 章「依賴預打包」要解決的另一半問題。

> **把三個障礙與三章對應起來(這是本章最重要的地圖)**:
>
> | 障礙 | Vite 的職責 | 哪一章 |
> |------|-------------|--------|
> | 瀏覽器看不懂 .ts/.vue | 即時轉譯成標準 JS | 第 04 章 |
> | 裸匯入 `'vue'` 無法解析 | 改寫路徑 | 第 02、03 章 |
> | 第三方依賴請求爆炸 | 依賴預打包 | 第 03 章 |
>
> 所以 **Vite dev server = 一個會「即時轉譯 + 改寫匯入路徑 + 預打包依賴」的伺服器**。

## 2.3 Vite dev server 的完整工作流程

把上面三個障礙的解法串起來,一個完整的 dev 請求流程是這樣的。假設使用者打開 `http://localhost:5173`:

```
① 瀏覽器請求 http://localhost:5173/
   → Vite 回傳 index.html

② 瀏覽器解析 HTML,看到 <script type="module" src="/src/main.ts">
   → 發請求要 /src/main.ts

③ Vite 收到對 /src/main.ts 的請求:
   a. 從硬碟讀出 main.ts 原始內容
   b. 用 esbuild 把 TS 語法剝掉,轉成標準 JS(障礙 1)
   c. 掃描這段 JS 裡的所有 import,把裸匯入改寫成真實路徑(障礙 2)
      例如 import 'vue' → import '/node_modules/.vite/deps/vue.js?v=xxx'
      例如 import './counter.ts' → 維持相對路徑(瀏覽器抓得到)
   d. 把轉好的 JS 回傳給瀏覽器

④ 瀏覽器執行 main.ts(的 JS 版),又遇到裡面的 import
   → 對每個 import 再發一次請求,回到步驟 ③

⑤ 重複,直到整棵依賴樹被瀏覽器爬完
```

**請仔細體會步驟 ③ 的精髓**:Vite **每次只處理「瀏覽器當下要的那一個模組」**。瀏覽器沒要的模組,Vite 連碰都不碰。

這就是 **「按需編譯(on-demand compilation)」** 或叫 **「No-bundle」**。

> **對比 Webpack(務必對照記憶)**:
> - **Webpack**:啟動 dev server 前,先把**整棵依賴樹**(3000 個模組全部)打包好。專案越大,啟動越久。
> - **Vite**:啟動時**什麼都不打包**,只是把 server 架起來。瀏覽器要哪個,才即時轉哪個。專案大小幾乎不影響啟動時間。
>
> 這就是為什麼第 01 章你看到 `ready in 312 ms`。Vite 啟動時根本沒在「打包」,只是在「準備好待命」。

## 2.4 親手驗證:打開 Network 面板看真相

理論講完,我們來「眼見為憑」。這一步請務必動手做,它會把前面所有抽象的東西變成你眼前的事實。

1. 把第 01 章建好的專案跑起來:`npm run dev`。
2. 打開瀏覽器,進 `http://localhost:5173`。
3. 按 F12 開 DevTools,切到 **Network** 面板,勾選只看 **JS**,然後**重新整理頁面**。

你會看到類似這樣的請求清單(而不是一個打包好的大檔):

```
Name                          Type        Status
─────────────────────────────────────────────────
localhost  (index.html)       document    200
main.ts                       script      200      ← 你的入口,注意副檔名是 .ts!
counter.ts                    script      200      ← main.ts import 進來的
style.css                     stylesheet  200
vite.svg                      ...
@vite/client                  script      200      ← Vite 注入的!負責 HMR,第 05 章講
```

**逐項解讀,每一行都印證了前面的理論**:

- 看到 **`main.ts`** 直接出現在請求清單裡——這證明了「**沒有打包**」。如果是 Webpack,你只會看到一個 `bundle.js`,看不到個別的 `main.ts`。Vite 是一個一個檔案各自被請求。
- 點開 `main.ts` 看 **Response**(回應內容):你會發現它**已經是純 JS 了**,型別語法被剝掉了。這證明了「**Vite 即時把 TS 轉成 JS**」(障礙 1 的解法)。
- 如果你的程式 import 了某個 npm 套件,Network 裡會看到一個 `/node_modules/.vite/deps/xxx.js?v=...` 的請求——這證明了「**裸匯入被改寫 + 依賴被預打包**」(障礙 2、3 的解法)。
- 那個 **`@vite/client`** 是 Vite 自動注入的一小段程式,負責跟 dev server 建立連線、接收熱更新訊息。第 05 章 HMR 會詳細拆它。

**再做一個關鍵實驗,體會「按需」**:

如果你的專案有某個模組,目前的頁面**還沒用到**(例如一個還沒點進去的路由頁面),你會發現 **Network 裡根本沒有它的請求**。只有當你實際導航到那個頁面、觸發了它的 import,Vite 才會去轉它、瀏覽器才會去抓它。

> 🎯 **這就是「按需編譯」的鐵證**:沒被用到的程式碼,dev 階段完全不會被處理。這也是為什麼大型專案的 Vite dev 依然飛快——它永遠只做「當下螢幕需要」的那一點點工作。

## 2.5 No-bundle 的代價(誠實面對,並引出第 03 章)

我必須誠實:「不打包」不是完美無缺,它有明確的代價。理解這個代價,你才會懂為什麼還需要第 03 章。

### 代價:請求瀑布(request waterfall)與深層依賴

因為一個 import 一個請求,如果你的模組依賴鏈很深:

```
main.ts → A.ts → B.ts → C.ts → D.ts
```

瀏覽器必須:抓 main.ts → 解析發現要 A → 抓 A → 解析發現要 B → 抓 B …… 一層一層**接力**。這叫「請求瀑布」,層數越深、累積延遲越明顯。

- 對**自己的原始碼**:層數通常還好,加上瀏覽器與 Vite 都有快取(第 04 章),體感 OK。
- 對**第三方依賴**:災難。前面說過,`lodash-es` 內部可能有幾百個互相 import 的小模組,變成幾百層的請求瀑布,dev 會卡到無法用。

### 解法預告:對「依賴」打包,對「原始碼」不打包

Vite 的策略很聰明,它把模組分成兩類、區別對待:

| 模組類型 | 例子 | dev 階段策略 | 為什麼 |
|----------|------|-------------|--------|
| **你的原始碼(source)** | `src/` 下的檔案 | **不打包**,按需即時轉譯 | 你常改它,要 HMR、要快;檔案數可控 |
| **第三方依賴(dependencies)** | `node_modules` 下的套件 | **預先打包**(用 esbuild) | 你不會改它;數量巨大、內部模組超多,不打包會請求爆炸 |

**白話翻譯**:你天天改的程式碼(src),Vite 不打包,保持「改一個轉一個」的靈活與速度;你幾乎不會動的第三方套件(node_modules),Vite 在啟動時先用超快的 esbuild 打包成幾個檔,避免請求爆炸。

這個「**對依賴打包、對原始碼不打包**」的混合策略,就是 Vite dev 又快又能用的祕密。而「對依賴打包」這件事,有一個專門的名字,也是下一章的主題——

> **依賴預打包(Dependency Pre-bundling)**。

## 2.6 本章小結與下一步

這一章我們把「dev 不打包」拆到了最底:

- **根本原因**:現代瀏覽器原生支援 ESM,會自己順著 `import` 抓檔。
- **Vite 的三大職責**(補裸寫 ESM 的三個洞):即時轉譯(障礙 1)、改寫裸匯入路徑(障礙 2)、預打包依賴(障礙 3)。
- **核心機制**:按需編譯(No-bundle)——瀏覽器要哪個,Vite 才轉哪個,所以啟動與專案大小無關。
- **親眼驗證**:Network 面板裡看到一個個 `.ts` 被分別請求、內容已轉成 JS,且沒用到的模組根本不會被請求。
- **誠實的代價**:不打包會有請求瀑布問題,對第三方依賴尤其嚴重 → 所以要「依賴預打包」。
