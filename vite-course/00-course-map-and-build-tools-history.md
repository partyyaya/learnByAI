# 第 00 章:課程地圖與建構工具演進史

> 這一章不寫任何 Vite 設定。我們要先回答一個更根本的問題:
> **為什麼前端需要「建構工具」這種東西?它到底在解決什麼痛?**
> 把這個搞懂,你後面看 Vite 的每一個設計都會有「啊,原來是為了解決那個問題」的恍然大悟感。

---

## 0.1 先問:沒有建構工具的世界長怎樣?

回到最原始的前端。我們寫的網頁是這樣的:

```html
<!-- index.html -->
<script src="jquery.js"></script>
<script src="utils.js"></script>
<script src="app.js"></script>
```

瀏覽器從上到下,一個一個 `<script>` 載入、執行。所有的變數、函式都掛在「全域」(`window`)上。

這在小專案沒問題,但專案一變大,痛點就全冒出來了。我們一個一個拆解,因為**每一個痛點,後面都對應到一個建構工具的功能**。

### 痛點 1:全域變數污染

```js
// utils.js
var formatDate = function () { /* ... */ }   // 掛在 window.formatDate

// app.js
var formatDate = function () { /* ... */ }   // 又一個!直接覆蓋掉上面那個
```

兩個檔案都宣告了 `formatDate`,後載入的會**默默覆蓋**前一個,而且完全不報錯。專案一大,這種「名字撞車」幾乎無法避免。

**白話翻譯**:沒有「模組」的概念,所有程式碼都住在同一個房間裡,誰都能改誰的東西。

### 痛點 2:依賴順序要人腦維護

`app.js` 用到了 `utils.js` 的東西,所以 `utils.js` 一定要先載入。這個順序是**靠你手動排 `<script>` 的位置**來保證的。

檔案多到 30 個的時候,你要怎麼記得誰依賴誰?排錯一個順序,就是一個 `xxx is not defined` 的執行期錯誤。

**心智模型**:依賴關係是程式碼裡的事實(`app.js` 真的用了 `utils.js`),但你卻要在「另一個地方」(HTML 的 script 順序)手動同步它。**兩處要手動保持一致 = 一定會出錯。**

### 痛點 3:HTTP 請求數量爆炸

每個 `<script>` 都是一個獨立的 HTTP 請求。100 個模組就是 100 個請求。在 HTTP/1.1 時代,瀏覽器對同一網域的並發請求數有限制(通常 6 個),請求一多,載入就慢得受不了。

**這就是為什麼需要「打包(bundle)」**:把上百個小檔案合併成少數幾個大檔案,減少請求數。

### 痛點 4:瀏覽器看不懂的語法

我們想用更好的工具寫程式:

- **TypeScript**:瀏覽器不認識型別語法。
- **JSX / Vue SFC**:`<div>{count}</div>` 或 `.vue` 檔,瀏覽器根本不知道那是什麼。
- **新語法**:可選鏈 `?.`、ES2022 的新 API,在舊瀏覽器跑不動。
- **Sass / Less**:CSS 的超集,瀏覽器只懂純 CSS。

這些東西都需要先**轉譯(transform / transpile)**成瀏覽器能懂的純 JS / CSS。

### 痛點 5:沒做最佳化

直接把原始碼丟上線:沒壓縮(檔案肥大)、沒移除沒用到的程式碼(dead code)、沒處理快取。使用者下載一堆用不到的東西。

## 0.2 於是,「模組化」與「建構工具」誕生了

上面五個痛點,前端社群花了十幾年慢慢解決。整個故事可以分成兩條主線:

1. **語言層面**:JavaScript 終於有了官方的「模組系統」。
2. **工具層面**:出現了專門做打包、轉譯、最佳化的「建構工具(build tool / bundler)」。

我們先把「模組系統」這條線講清楚,因為它是理解 Vite 的關鍵——**Vite 的整個 dev 設計,就是建立在「現代瀏覽器原生支援 ESM」這個前提上的**。

---

## 0.3 模組系統演進:從 CommonJS 到 ESM

「模組系統」要解決的就是 0.1 的痛點 1、2:**讓每個檔案是獨立的作用域,並能明確宣告「我依賴誰、我提供什麼」**。

歷史上出現過好幾套方案,你一定會在報錯訊息或設定檔裡看到它們的名字,所以一定要認得。

### CommonJS(CJS)—— Node.js 的模組系統

```js
// utils.js
function formatDate() { /* ... */ }
module.exports = { formatDate }     // 用 module.exports 匯出

// app.js
const { formatDate } = require('./utils')   // 用 require 匯入
```

特點:

- **同步載入**:`require` 是一個函式呼叫,執行到那一行才去讀檔、立刻回傳。這在伺服器(檔案在本機硬碟)沒問題。
- **動態**:`require` 可以寫在 `if` 裡、可以用變數當路徑(`require(someVar)`)。
- **問題**:正因為「同步 + 動態」,**它沒辦法直接在瀏覽器跑**(瀏覽器讀檔要走網路,不能同步等),而且**靜態分析困難**(打包工具很難在不執行程式碼的情況下,確定你到底 require 了什麼)。

**記住這點**:CommonJS 的「動態」特性,是後面第 03 章「為什麼要依賴預打包」的核心原因之一。

### ESM(ES Modules)—— JavaScript 官方標準模組

ES2015(ES6)終於把模組系統寫進了語言標準:

```js
// utils.js
export function formatDate() { /* ... */ }      // 用 export 匯出

// app.js
import { formatDate } from './utils.js'         // 用 import 匯入
```

特點(請跟 CommonJS 對照著看,差異就是 Vite 能成立的原因):

- **靜態結構**:`import`/`export` **只能寫在模組最頂層**,不能放在 `if` 裡,路徑也必須是字串字面量。這個限制看似討厭,但好處巨大——**工具不需要執行程式碼,光用「讀」的就能畫出完整的依賴關係圖**。這叫「靜態可分析」。
- **非同步載入**:瀏覽器看到 `import`,可以非同步地去抓那個檔案,不會卡住主執行緒。這正好適合「走網路抓檔」的瀏覽器環境。
- **瀏覽器原生支援**:這是最關鍵的一點。現代瀏覽器**可以直接執行 ESM**,只要這樣寫:

```html
<!-- 加上 type="module",瀏覽器就會把它當 ESM 處理 -->
<script type="module" src="/app.js"></script>
```

此時瀏覽器看到 `app.js` 裡的 `import './utils.js'`,**會自己發一個 HTTP 請求去抓 `utils.js`**。也就是說——**瀏覽器自己就能「順著 import 把整棵依賴樹爬完」**,不需要任何打包工具幫忙合併。

> **這就是 Vite 的命根子。**
> Vite dev server 的核心洞察是:既然瀏覽器自己會順著 `import` 抓檔,那 dev 階段我為什麼還要先把幾千個模組打包成一包?
> 我只要當一個「能即時把 TS/Vue/JSX 轉成瀏覽器看得懂的 ESM」的伺服器就好。
> 這個觀念第 02 章會完整展開,這裡先埋下種子。

### 一張表看懂 CJS vs ESM

| 面向 | CommonJS(CJS) | ES Modules(ESM) |
|------|----------------|-------------------|
| 語法 | `require` / `module.exports` | `import` / `export` |
| 載入時機 | 同步(執行到才載入) | 靜態(編譯期就確定依賴) |
| 能否動態路徑 | 可以(`require(變數)`) | 不行(路徑須為字面量) |
| 瀏覽器原生支援 | ❌ 不行 | ✅ 可以(`<script type="module">`) |
| 靜態分析(Tree shaking) | 困難 | 容易 |
| 主要場景 | Node.js 傳統生態、舊套件 | 現代瀏覽器、現代套件 |

> **為什麼這張表這麼重要?** 因為 npm 上的套件,有的是 CJS、有的是 ESM、有的兩種都附。Vite 處理它們的方式不一樣,這是第 03 章「依賴預打包」要解決的核心矛盾。先有印象。

## 0.4 建構工具的演進史(以及 Vite 站在哪)

理解了模組系統,我們來看「建構工具」這條線是怎麼一路演化到 Vite 的。我會用「它解決了什麼、又留下什麼問題」的角度講,因為**每一代工具都是在補上一代的洞**。

### 第一代:任務執行器 Grunt / Gulp(約 2012~2015)

它們本質上是「自動化任務跑腿」:幫你把「壓縮 CSS」「轉譯 JS」「搬檔案」這些動作串成流程。

- **解決了**:把重複的手動操作自動化。
- **沒解決**:它們不理解「模組依賴」。你還是得自己處理模組之間怎麼合併。它只是個「按順序執行任務」的機器人。

### 第二代:Webpack(2014~,長期霸主)

Webpack 帶來一個革命性的觀念:**「一切皆模組」**。不只 JS,連 CSS、圖片、字型,都能被 `import` 進來,由 Webpack 統一處理。

它的核心工作流程是:

```
從入口檔(entry,例如 src/main.js)開始
   → 解析它的所有 import
   → 遞迴解析每個依賴的 import
   → 建出一張完整的「模組依賴圖(module graph)」
   → 用各種 loader 把非 JS 資源轉成 JS
   → 把整張圖打包(bundle)成幾個 .js 檔
   → 輸出到 dist/
```

- **解決了**:0.1 的全部五個痛點。模組化、依賴自動管理、合併請求、轉譯、最佳化,一套搞定。Webpack 統治了前端整整十年。
- **留下的問題,正是 Vite 的切入點**:

  **問題在「dev(開發)階段」。** Webpack 不管你是要上線、還是只是本機開發,它的模式都是「**先把整張依賴圖打包完,才能啟動 dev server**」。

  ```
  你的專案有 3000 個模組
     → webpack 啟動 dev server 前,要先把這 3000 個全部打包一次
     → 專案越大,啟動越慢(大型專案冷啟動要等 30 秒~幾分鐘)
     → 你改一行程式碼,它要重新計算受影響的 bundle(雖然有快取,還是慢)
  ```

  **這就是工程師每天最痛的點**:啟動慢、改一行等很久。專案越大越痛。

### 第三代:esbuild(2020)—— 速度的降維打擊

esbuild 是用 **Go 語言**寫的打包/轉譯工具。它的賣點只有一個字:**快**,比 Webpack(JS 寫的)快 10~100 倍。

為什麼能快這麼多?

1. **語言**:Go 是編譯成原生機器碼的語言,且天生支援多核心平行處理;而 Webpack/Babel 是 JS,跑在單執行緒的 Node.js 上。
2. **設計**:esbuild 把「解析、轉譯、產生程式碼」高度平行化,並盡量減少資料在不同步驟間的重複轉換。

- **解決了**:轉譯與打包的速度問題。
- **沒完全解決**:esbuild 的**程式碼分割(code splitting)、CSS 處理、外掛生態**在當時還不夠成熟,不適合單獨拿來做複雜專案的「生產建構」。

> **關鍵伏筆**:esbuild 太快了,快到「丟掉它太可惜」。Vite 把 esbuild 用在兩個地方:
> ① dev 階段把 TS/JSX 即時轉成 JS(第 04 章);② 依賴預打包(第 03 章)。
> 但 Vite **生產建構不用 esbuild**,而是用下面要講的 Rollup。為什麼?第 08 章會講。

### 第四代:Vite(2020,尤雨溪/Vue 團隊)

Vite(法文「快」的意思,讀作 /viːt/)把前面的洞察組合成一個全新的架構。它的核心理念是把「開發」和「生產」**徹底分成兩套引擎**:

```
┌─────────────── 開發(dev) ───────────────┐
│  不打包!                                  │
│  起一個 dev server,瀏覽器要哪個模組,      │
│  伺服器才即時用 esbuild 把那一個轉成 ESM 回傳 │
│  → 啟動是「秒級」,跟專案大小幾乎無關        │
└────────────────────────────────────────┘

┌─────────────── 生產(build) ──────────────┐
│  用 Rollup 好好地打包、最佳化、分割         │
│  → 產出體積小、相容性好的正式檔案           │
└────────────────────────────────────────┘
```

**為什麼 dev 不打包就能快?** 因為前面 0.3 講過了:**現代瀏覽器原生支援 ESM**,瀏覽器自己會順著 `import` 抓檔。Vite dev 階段只要扮演一個「即時轉譯伺服器」,而不是「打包機器」。

**為什麼 build 還要打包?** 因為正式上線時,如果不打包,一個頁面可能要發幾百個 HTTP 請求(每個模組一個),反而更慢;而且還需要壓縮、tree shaking、相容舊瀏覽器。所以生產階段交給成熟的 Rollup。

這個「**dev 不打包(用瀏覽器原生 ESM + esbuild 即時轉譯)、build 才打包(用 Rollup)**」的雙引擎設計,就是這門課要拆解的核心。

### 第五代(進行中):Rolldown / Rust 化(2024~)

Vite 目前的兩套引擎(esbuild 和 Rollup)行為上有些不一致(因為是兩個不同的工具)。Vite 團隊正在用 **Rust** 寫一個叫 **Rolldown** 的新打包器,目標是「一個工具同時搞定 dev 與 build」,徹底統一行為、再把速度推上去。同期的競品還有 Vercel 的 **Turbopack**(也是 Rust)。這部分留到第 10 章詳談,這裡你只要知道「Vite 的引擎還在演化中」就好。

### 一張時間軸總結

| 年代 | 工具 | 核心貢獻 | 留下的問題 |
|------|------|----------|------------|
| ~2012 | Grunt / Gulp | 任務自動化 | 不理解模組依賴 |
| 2014~ | Webpack | 一切皆模組、統一打包 | dev 啟動慢、改動慢 |
| 2020 | esbuild | Go 寫的,快 10~100 倍 | 生產建構功能不夠完整 |
| 2020 | **Vite** | dev 不打包 + build 用 Rollup 的雙引擎 | 兩套引擎行為不一致 |
| 2024~ | Rolldown / Turbopack | Rust 化,統一 dev/build | 仍在發展中 |

## 0.5 建立本課程的核心心智模型

整門課,你只要牢牢記住下面這個模型,後面所有細節都掛得上去:

> ### Vite = 「dev 不打包的即時 ESM 伺服器」+「build 才打包的 Rollup」
>
> 1. **dev 階段**:瀏覽器原生支援 ESM,所以 Vite 不打包,只當一個「你要哪個模組,我才即時把它轉成 ESM 回給你」的伺服器。啟動快、改動快。
> 2. **build 階段**:為了體積、請求數、相容性,改用 Rollup 認真打包最佳化。
> 3. **esbuild 的角色**:dev 階段的「即時轉譯器」+「依賴預打包器」,因為它夠快。
> 4. **取捨來源**:dev 和 build 是兩套不同引擎 → 所以才有「為什麼 dev 沒事 build 卻出錯」這類問題(後面章節會遇到)。

下面這張圖把 dev 與 build 兩條路徑攤開,建議你截圖存著,每學一章回來對一次:

```
                          ┌──────────────────────────────┐
                          │        你的原始碼              │
                          │  .ts .tsx .vue .css 圖片...     │
                          └───────────────┬────────────────┘
                                          │
                ┌─────────────────────────┴──────────────────────────┐
                │                                                     │
        ┌───────▼────────┐                                  ┌─────────▼─────────┐
        │   dev(開發)    │                                  │   build(上線)    │
        ├────────────────┤                                  ├───────────────────┤
        │ 不打包          │                                  │ 用 Rollup 打包     │
        │ 瀏覽器原生 ESM  │                                  │ 壓縮 / tree shaking│
        │ esbuild 即時轉譯 │                                  │ code splitting    │
        │ 依賴預打包(esbuild)│                              │ 輸出 dist/         │
        │ HMR 熱更新      │                                  │                   │
        └────────────────┘                                  └───────────────────┘
            ↑ 第 02~05 章                                        ↑ 第 08 章
```

## 0.6 本章小結與下一步

這一章我們刻意一行 Vite 設定都沒寫,因為**建構工具的所有功能,本質都是在補「裸寫 `<script>`」留下的洞**。你現在應該能回答:

- 為什麼前端需要模組系統?(全域污染、依賴順序)
- CommonJS 和 ESM 差在哪?為什麼 ESM 能在瀏覽器原生跑?(靜態可分析 + 瀏覽器支援)
- Webpack 解決了什麼、又留下什麼痛?(統一打包,但 dev 啟動慢)
- Vite 的核心架構是什麼?(dev 不打包 + build 用 Rollup 的雙引擎)

**下一章(01)**,我們會動手把 Vite 跑起來,認識專案結構與 `vite.config.ts`,並親眼看到 dev server「秒啟動」這件事——然後在第 02 章,我們會打開瀏覽器的 Network 面板,**親眼驗證「dev 真的沒打包」**這個本章最重要的論點。
