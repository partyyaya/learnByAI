# 33｜專題規劃：從想法到可執行計畫

> 這章是專題衝刺前最重要的一步。你會把模糊想法變成具體需求、可交付里程碑與驗收標準，避免做到一半迷路。

## 學習目標

- 能選出符合目前能力的專題題目。
- 能把需求拆成可執行任務與里程碑。
- 建立明確 MVP（最小可行產品）與驗收條件。
- 能規劃時程、風險與展示內容。

## 前置條件

- 已完成 A 到 E 區塊，具備基礎到實務能力。

## 專題為什麼常失敗

- 題目太大，無法在時間內完成。
- 缺少明確範圍與驗收標準。
- 只寫功能，沒有測試與文件。
- 沒有分里程碑，最後一週爆量趕工。

## 專題選題原則（務實）

### 原則 1：你能在 4 到 8 週完成 MVP

不要一開始就做大型平台，先完成可用核心。

### 原則 2：能展示你的核心能力

至少覆蓋其中 2 到 3 項：

- API/資料庫
- 自動化/爬蟲
- 資料分析/報告
- 測試與工程品質

### 原則 3：題目最好有真實場景

例如：個人工作流程、團隊報表、內容整理、電商監控。

## 專題類型建議（對應本課）

- **CLI 工具型**：任務管理、批次檔案處理、資料清理器。
- **API 服務型**：待辦事項、訂單系統、會員管理 API。
- **資料分析型**：銷售分析、用戶行為分析、爬蟲 + 報表。

## 專題規格模板（建議照填）

### 1) 題目與一句話描述

例如：`Sales Insight Tool` - 每日自動匯整銷售資料並產生圖表報告。

### 2) 目標使用者

誰會用這個系統？解決什麼痛點？

### 3) MVP 功能清單（3 到 5 項）

只列核心，次要功能放 backlog。

### 4) 非功能需求

- 效能目標（例如 API 回應 < 300ms）
- 穩定性（錯誤重試、日誌）
- 安全性（基本驗證、敏感資料處理）

### 5) 技術棧

Python、FastAPI、SQLite、Pandas、Matplotlib、pytest 等。

### 6) 驗收標準

每個功能都要有「可測試條件」。

## 里程碑切分範例（6 週）

- **W1**：需求定義、資料模型、專案骨架
- **W2**：核心功能 A 完成
- **W3**：核心功能 B 完成
- **W4**：測試補齊、重構、錯誤處理
- **W5**：部署與文件
- **W6**：Demo 彩排與簡報整理

## 任務拆解方法（從大到小）

需求：「使用者可新增任務」

可拆成：

1. 定義資料模型（Todo）
2. 新增 API 端點
3. 輸入驗證
4. 寫測試（成功/失敗）
5. 更新文件

每個任務都可在 0.5 到 1 天完成，管理最穩定。

## 風險管理（提前想）

### 常見風險

- 外部 API 不穩定
- 資料品質差
- 功能超出時程
- 部署卡關

### 對應策略

- 準備 mock 資料
- 保留 fallback 流程
- 先交 MVP，再做加值功能
- 提前做部署驗證，不要最後一週才開始

## 專題產出物清單（最少）

- 可執行程式碼
- `README.md`（安裝、使用、架構）
- 測試（至少核心邏輯）
- Demo 資料或截圖
- 簡報或短報告

## 評分/面試視角的加分點

- 功能完成度 + 穩定性（錯誤處理）
- 程式碼可讀性（模組化、命名、型別註記）
- 測試與品質工具（pytest、ruff、mypy）
- 能說明設計取捨（為何這樣設計）

## 專題提案範例（簡版）

```text
題目：Order Alert API
目標：即時監控訂單異常，提供查詢與告警
MVP：
1. 訂單新增與查詢 API
2. 異常訂單判斷規則
3. 每日異常報表輸出
技術：FastAPI + SQLite + pytest + Docker
驗收：
- 3 個核心 API 通過測試
- 可在本地容器啟動
- 產出異常報表 CSV
```

## 章末練習

- 必做：使用本章模板寫出你的專題規格文件。
- 必做：列出 2 週內可完成的 MVP 任務清單。
- 選做：做一次 5 分鐘提案口頭演練。

## 本章重點回顧

- 專題成功關鍵不在炫技，而在「範圍清楚 + 里程碑可執行」。
- 先交可驗收的 MVP，再逐步擴充。
- 規劃做好，後續實作會快很多、穩很多。
