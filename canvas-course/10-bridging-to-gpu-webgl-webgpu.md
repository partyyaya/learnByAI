# 第 10 章:跨越到 GPU——WebGL / WebGPU 的心智轉換

> **學習目標**:完成從 Canvas 2D 到 GPU 繪圖的**心智轉換**——從「下繪圖命令」(你說畫什麼)到「定義管線 + 丟資料給 GPU 平行處理」(你給程式和資料,GPU 自己算)。理解 GPU 管線、draw call 成本、為什麼大家用庫(PixiJS/three.js),以及 WebGPU 與你 [Browser AI 課](../browserAI/README.md) 的關係。
> **預計時數**:90 分鐘
> 這一章**不是教你寫完整的 WebGL 程式**(那是另一門課),而是搭一座橋:讓你理解 GPU 繪圖的思維跟 Canvas 2D 哪裡根本不同,知道何時該過橋、過橋後世界長怎樣。

---

## 10.1 為什麼需要過橋?Canvas 2D 的邊界

第 09 章結尾說過:2D 優化做滿仍撐不住時,代表你撞到了 Canvas 2D 的設計邊界。典型訊號:

- **數萬以上的圖元每幀都在動**(大規模粒子、海量資料點視覺化)。
- **複雜的即時特效**:逐像素發光、變形、光照、後處理。
- **3D**。

根本原因:**Canvas 2D 的繪圖 API 是「一道一道下命令」的**——底層雖然常有 GPU 加速與自動合批(別誤會成純 CPU、純序列,那正是第 00 章要破除的迷思),但**在 API 語意上你很難表達「一次畫十萬個」這種批次意圖**。而 GPU 的本事正是「**同時處理幾十萬個東西**」,要榨出它,你得換一套「能一次餵一大批資料」的 API。

---

## 10.2 最大的心智轉換:從「下命令」到「定義管線 + 餵資料」

這是全章唯一一個你必須翻轉的觀念,也是 WebGL 勸退新手的真正原因——**不是語法難,是思維變了**。

### Canvas 2D:命令式,你說「畫什麼」

```js
ctx.fillStyle = 'red';
ctx.fillRect(10, 10, 50, 50);   // fillRect(x, y, 寬, 高):在 (10,10) 畫一個 50×50 的紅方塊——你下令,瀏覽器照做
```

你像個導演,一句一句指揮。CPU 收到命令,(通常)轉成 GPU 操作。

### WebGL / WebGPU:你給 GPU「程式 + 資料」,它自己平行算

GPU 繪圖你不能「叫它畫方塊」。你要做的是:

1. **準備一段在 GPU 上跑的程式**(叫 **shader**,用 GLSL / WGSL 寫)。
2. **把一堆資料(頂點座標、顏色…)上傳到 GPU 的記憶體**(buffer)。
3. **下一個 draw call**,叫 GPU「用這段 shader,把這堆資料跑一遍」。
4. GPU 拿到後,**幾千個核心同時處理每個頂點、每個像素**。

```
Canvas 2D:  你 → 「畫紅方塊」 → 瀏覽器畫
WebGL:      你 → 上傳頂點資料 + shader 程式 → 「跑!」 → GPU 幾千核心同時算出所有像素
```

> **心智模型**:Canvas 2D 是「**請人幫你畫**」(你動嘴);WebGL 是「**寫一個程式,描述「給定一個頂點/像素,該算出什麼」,然後讓 GPU 對幾十萬份資料同時跑這個程式**」(你寫的是「規則」,GPU 大規模套用)。從「指揮繪圖」變成「編程一條平行計算流水線」——這就是門檻所在,也是威力所在。

---

## 10.3 GPU 管線:vertex shader → 光柵化 → fragment shader

GPU 繪圖有一條固定的「流水線」,理解它,WebGL/WebGPU 的程式碼就有了骨架:

```
頂點資料(buffer)
   ↓
① Vertex Shader:對「每個頂點」跑一次 —— 算出它在畫面上的最終位置
   ↓
② 光柵化(Rasterization):GPU 自動把三角形「填」成一格格像素(fragment)
   ↓
③ Fragment Shader:對「每個像素」跑一次 —— 算出這個像素是什麼顏色
   ↓
畫到畫布
```

- **Vertex shader**:處理「形狀的角點在哪」(套用變換、投影)。對每個頂點平行跑。
- **Fragment shader**(又叫 pixel shader):處理「每個像素的顏色」(貼圖、光照、特效)。對每個像素平行跑——**你看到的所有炫炮畫面特效,幾乎都是在這裡寫的**。

> **心智模型**:GPU 把「畫一個形狀」拆成兩個平行階段——先算「角在哪」(vertex),GPU 自動填出中間的像素,再算「每個像素什麼色」(fragment)。**三角形是 GPU 唯一真正認得的形狀**——圓、曲線、3D 模型,最終都被拆成大量三角形。這跟 Canvas 2D「直接畫圓畫曲線」是完全不同的世界。

---

## 10.4 draw call 成本:跟 Canvas 2D 相反的直覺

Canvas 2D 你不太需要想「呼叫幾次繪圖」。但在 GPU 世界,**每一次 draw call(叫 GPU 畫一批)都有固定的溝通開銷**(CPU 要設定狀態、通知 GPU)。所以效能直覺翻轉了:

```
❌ GPU 上的錯誤做法:畫 10000 個方塊 = 呼叫 10000 次 draw call
   → 大部分時間花在「CPU 跟 GPU 來回溝通」,GPU 反而閒著

✅ 正確做法:把 10000 個方塊的資料一次打包,一個 draw call 全部畫
   → GPU 一次收到、幾千核心同時算 → 飛快
   (這叫 batching / instancing)
```

| | Canvas 2D | WebGL / WebGPU |
|---|-----------|----------------|
| 效能直覺 | 別畫太多東西、別碰像素回讀 | **別發太多 draw call**,盡量批次 |
| 一次畫一個 vs 一批 | 差別不大 | **天差地遠**(批次是核心優化) |
| 瓶頸常在 | 主執行緒、重畫面積 | draw call 數、shader 複雜度、頻寬 |

> **心智模型**:GPU 像一座超大工廠,開機(每次 draw call)要暖機成本,但一旦運轉能同時處理海量訂單。**所以你要「一次給一大批」,而不是「一個一個遞」**。這也是為什麼 PixiJS 這類庫拼命做「自動批次合併」——把你畫的成千上萬個精靈,偷偷合併成極少的 draw call。

---

## 10.5 為什麼大家用庫(PixiJS / three.js / regl)

原生 WebGL 連「畫一個三角形」都要寫上百行樣板(編譯 shader、建 buffer、綁定屬性、設 uniform…),極度繁瑣且易錯。所以實務上幾乎沒人裸寫 WebGL:

| 庫 | 定位 |
|----|------|
| **PixiJS** | 高效能 **2D** 渲染(GPU 加速的「場景圖」)——你第 08 章手刻的場景圖,它用 WebGL 做到極致 |
| **three.js** | **3D** 的事實標準,封裝相機、光照、材質、模型載入 |
| **regl / twgl** | 薄封裝,去掉 WebGL 樣板但保留底層控制 |
| **PixiJS / Babylon / 各家** | 也逐步支援 WebGPU 後端 |

> **務實建議**:**需要 GPU 效能但做 2D → 直接上 PixiJS**(它的 API 跟你第 08 章的場景圖幾乎同構,學習曲線平緩);**做 3D → three.js**。只有當你要做引擎、研究渲染、或極致優化時,才裸寫 WebGL/WebGPU。你這門課學的「場景圖、相機、命中、批次」觀念,在這些庫裡全部適用——**你不是從零學,是換一個更快的後端**。

---

## 10.6 WebGPU:新一代,以及跟 Browser AI 的關係

**WebGPU** 是繼 WebGL 之後的新一代 GPU API(2023 起在主流瀏覽器落地),相比 WebGL:

- **更現代的 API 設計**(對齊 Vulkan/Metal/D3D12),狀態管理更清晰、更少全域狀態的坑。
- **效能更好**:更低的 CPU 開銷、更好的多執行緒支援。
- **關鍵新能力:Compute Shader**——可以用 GPU 做**通用平行計算**,不只是繪圖。

最後這點,正是 WebGPU 跟你 [Browser AI 課](../browserAI/README.md) 的接點:**瀏覽器裡跑神經網路推論(如 Transformers.js、ONNX Runtime Web),底層就是用 WebGPU 的 compute shader 把矩陣運算丟給 GPU 平行算**。

> **心智模型**:WebGL 的 GPU「只會畫」(繪圖管線);WebGPU 的 GPU「**既會畫,也會算**」(繪圖 + 通用計算)。從本課的角度,WebGPU 是「更好、更通用的過橋目的地」;從 AI 的角度,它是「瀏覽器端模型推論的加速引擎」。這兩條線在 WebGPU 交會——本倉庫的 Canvas 課與 Browser AI 課,在這裡握手。

---

## 10.7 2D 與 GPU 互通:你不用全有或全無

過橋不是「拋棄 Canvas 2D」。它們可以**混用**,因為「一張 canvas」可以當另一張的 `drawImage` 來源(第 04 章):

```js
// 把 WebGL 畫的高效能內容,當成圖層貼到 2D canvas 上,再用 2D 畫 UI/文字
ctx2d.drawImage(webglCanvas, 0, 0);    // drawImage(來源, dx, dy) → 把整張 WebGL 畫布貼到 (0,0);WebGL 畫粒子,2D 畫介面與文字
```

常見混搭策略:**用 GPU(WebGL/PixiJS)畫「海量、會動」的主內容,用 Canvas 2D 畫「文字、UI、座標軸」**(因為 2D 的文字排版方便太多)。Canvas 2D 的文字能力 + WebGL 的渲染量,各取所長。

## 10.8 決策框架:留在 2D,還是過橋?

```
你的 Canvas 2D 跑得順嗎(第 09 章優化做完)?
│
├─ 順 ──────────────────────────────→ 留在 2D。別自找 WebGL 的苦。
│
└─ 不順,且是「圖元數量級/特效/3D」造成的
   │
   ├─ 做 2D,要效能 ───────→ 上 PixiJS(沿用你的場景圖觀念,換 GPU 後端)
   ├─ 做 3D ──────────────→ 上 three.js
   ├─ 要 GPU 通用計算/最新特性 → WebGPU(或經由支援它的庫)
   └─ 要做引擎/研究/極致控制 → 裸寫 WebGL / WebGPU
```

> **最後叮嚀**:GPU 繪圖的開發、除錯成本遠高於 2D(shader 出錯往往只給你一片黑、沒有堆疊追蹤)。**先確定 2D 真的撐不住、且優化已做滿,再過橋。** 很多「我需要 WebGL」的需求,其實第 09 章的分層 + 按需渲染就解決了。工程是「用最低成本達標」,不是「用最炫的技術」。

---

## 10.9 本章小結與下一步

- **何時過橋**:2D 優化做滿仍撐不住(數萬動態圖元、複雜即時特效、3D)。
- **核心心智轉換**:從「下繪圖命令」(說畫什麼)到「定義管線 + 餵資料給 GPU,讓幾千核心平行算」(寫規則,GPU 大規模套用)。
- **GPU 管線**:vertex shader(每個頂點)→ 光柵化(自動填像素)→ fragment shader(每個像素的顏色);三角形是 GPU 唯一認得的形狀。
- **draw call 成本**:直覺翻轉——少發 draw call、盡量批次(batching/instancing);這是 GPU 的核心優化。
- **用庫**:2D 用 PixiJS、3D 用 three.js;你學的場景圖/相機/命中觀念全部適用,只是換更快的後端。
- **WebGPU**:更現代 + compute shader(GPU 通用計算),是瀏覽器端 AI 推論的加速引擎——與 Browser AI 課交會。
- **可混用**:GPU 畫海量內容、2D 畫文字 UI,互貼互通,不必全有或全無。
