# 第 00 章:課程地圖與渲染模型心法

> **學習目標**:建立整門課的核心心智模型——**Canvas 是 immediate mode(畫完即忘)**,並理解這一句話如何推導出 Canvas 的所有難點與設計。
> **預計時數**:60 分鐘
> 這一章不會畫任何一條線。我們要先回答一個更根本的問題:
> **瀏覽器明明已經有 DOM 能畫東西了,為什麼還要 Canvas?它到底是哪一種「畫東西」?**
> 把這個搞懂,你後面看 Canvas 的每一個「為什麼這麼難用」都會有「啊,原來是因為那個前提」的恍然大悟感。

## 0.1 先問:同樣是「在螢幕上畫東西」,為什麼瀏覽器有四套?

你想在網頁上畫一個紅色圓圈。其實有四種完全不同的做法:

```html
<!-- 做法 1:DOM -->
<div style="width:100px;height:100px;border-radius:50%;background:red"></div>

<!-- 做法 2:SVG -->
<svg><circle cx="50" cy="50" r="50" fill="red" /></svg>

<!-- 做法 3:Canvas 2D -->
<canvas id="c"></canvas>
<script>
  const ctx = document.getElementById('c').getContext('2d');
  ctx.fillStyle = 'red';
  ctx.beginPath();
  ctx.arc(50, 50, 50, 0, Math.PI * 2);   // 畫一個圓
  ctx.fill();
</script>

<!-- 做法 4:WebGL(這裡只是示意,真要畫一個圓要寫幾十行 shader) -->
```

畫面結果幾乎一模一樣,都是一個紅圓。**那它們差在哪?為什麼要有四套?**

答案不在「畫出來長怎樣」,而在「**畫完之後,這個圓還存不存在**」。這就帶出整門課最重要的分水嶺。

## 0.2 兩種渲染模型:Retained mode vs Immediate mode

這是電腦繪圖的一個經典分類,也是這門課的**主軸**。請務必讀懂這一節,後面所有章節都掛在它上面。

### Retained mode(保留模式)—— DOM 與 SVG

當你寫一個 `<div>` 或 `<circle>`,你是在「**描述一棵樹**」。你告訴瀏覽器:「這裡有一個圓,半徑 50,紅色。」然後瀏覽器會:

- 把這個圓當成一個**物件**,記在記憶體裡(這棵樹就是 DOM tree / SVG DOM)。
- 你之後可以隨時拿到它:`circle.setAttribute('fill', 'blue')`,瀏覽器會自己重畫。
- 你滑鼠移上去,瀏覽器知道「你正指著那個圓」,自動發 `click`、`mouseover` 事件給它。
- 視窗縮放、滾動,瀏覽器自動幫你重新排版、重繪。

**關鍵詞:瀏覽器「保留(retain)」了你描述的那些物件**,並全權負責後續的重繪、事件、命中測定。你只要改資料,剩下的它包辦。

> **白話翻譯**:retained mode 像是你雇了一個管家。你說「房間角落放一張紅椅子」,管家就記住了。之後你說「把椅子漆成藍色」,他自己去漆;有人碰了椅子,他來通報你。你只動嘴,不動手。

### Immediate mode(立即模式)—— Canvas

當你寫 `ctx.arc(...); ctx.fill();`,你不是在描述一個物件,你是在**下一道命令**:「現在,把這些像素塗成紅色。」瀏覽器照做,然後——

- **它立刻忘記這件事。** 畫布上根本沒有「圓」這個東西,只有一格一格被塗成紅色的**像素**。
- 你想把圓改成藍色?**對不起,沒有「那個圓」可以改**。你只能把那塊區域清掉、重新下一次繪圖命令。
- 你滑鼠移上去?瀏覽器**完全不知道那裡有個圓**,它只看到一塊 canvas 元素。它不會發任何事件給「圓」,因為對它來說圓不存在。

**關鍵詞:你下完繪圖命令,效果「立即(immediate)」反映到像素上,然後系統什麼都不記得。** 畫布只是一塊塗料未乾的牆,你刷了什麼上去,它就只是一面有顏色的牆,牆不知道自己上面有「一個圓」。

> **白話翻譯**:immediate mode 沒有管家。你自己拿著刷子,在牆上刷出一個紅圓。刷完,牆上就是一坨紅色顏料——牆不會記得「這是一個圓」。你想改顏色,得自己把那塊刮掉重刷。有人摸了牆,牆也不會告訴你他摸的是不是圓。**所有事都得你自己來。**

### 一段程式碼,看懂「畫完即忘」

這是整門課最重要的一個示範,請仔細看:

```js
const ctx = canvas.getContext('2d');

// 畫一個紅圓
ctx.fillStyle = 'red';
ctx.beginPath();
ctx.arc(100, 100, 50, 0, Math.PI * 2);
ctx.fill();

// 現在我想把它變藍色。直覺上你會想找「那個圓」然後改它——
// 但根本沒有「那個圓」這個東西可以抓。
// 沒有 circle.fill = 'blue' 這種寫法,因為圓不是物件,它只是一片像素。

// 你唯一能做的是:把整塊清掉,重畫一次。
ctx.clearRect(0, 0, canvas.width, canvas.height);   // 把畫布擦乾淨
ctx.fillStyle = 'blue';                              // 換顏色
ctx.beginPath();
ctx.arc(100, 100, 50, 0, Math.PI * 2);               // 重新下一次繪圖命令
ctx.fill();
```

> **心智模型**:在 Canvas 裡,「畫面上的東西」和「你腦中的物件」是**兩個分開的世界**,而且**Canvas 只認得前者(像素),不認得後者(物件)**。如果你想要有「物件」的概念(這個叫圓、那個叫方塊、可以移動、可以點),那是**你自己要在 JS 裡維護的資料**,Canvas 一概不管。這個落差,就是後面所有工作的來源。

### 兩種模型對照表

| 面向 | Retained mode(DOM / SVG) | Immediate mode(Canvas) |
|------|---------------------------|--------------------------|
| 你在做的事 | 描述一棵物件樹 | 下一連串繪圖命令 |
| 畫完之後 | 物件還在,可隨時修改 | 系統忘光,只剩像素 |
| 改一個圖形 | 改屬性,瀏覽器自動重繪 | 自己清掉、自己重畫 |
| 事件(click 等) | 瀏覽器自動派發給對應物件 | 沒有!canvas 只是一塊 buffer |
| 命中測定(點到誰?) | 瀏覽器內建 | 自己用數學算 |
| 排版 / 重繪 | 瀏覽器負責 | 你負責 |
| 適合的數量級 | 數百~數千個元素就開始卡 | 數萬~數十萬個圖元也能順 |

看到最後一行了嗎?這就引出下一個問題:**既然 immediate mode 這麼麻煩(什麼都自己來),為什麼還要用它?**

## 0.3 「畫完即忘」如何推導出 Canvas 的一切

這一節是這章的精華。我要讓你看到:**Canvas 課程後面那十章,全部都是在補「畫完即忘」留下的洞。** 你不用死記後面有哪些章,你只要從「畫完即忘」這一句話,自己就能推出來。

我們一條一條推:

### 推論 1:沒有物件 → 想讓東西動,就得「清掉 + 重畫」→ 需要動畫迴圈

畫面上的圓不是物件,你沒辦法叫它「往右移 1 像素」。你只能:**擦掉整張畫布 → 在新位置重畫一次**。每秒做 60 次,看起來就是動畫。

```
每一幀(1/60 秒):
   清空畫布 → 更新物件位置(你自己存的資料) → 照新位置重畫
```

→ 這就是 **第 01 章的渲染迴圈** 和 **第 06 章的動畫架構**。

### 推論 2:沒有事件 → 想知道「點到了哪個圖形」→ 得自己做命中測定

使用者點了畫布上 `(120, 130)` 這個座標。瀏覽器只會告訴你「canvas 被點了,座標是 (120,130)」——它**不知道**那個位置有沒有圖形、是哪一個。

要知道「點到了那個圓」,你得自己算:`(120,130)` 到圓心 `(100,100)` 的距離是不是小於半徑 50?這叫**命中測定(hit testing)**。圖形一多,你還得想辦法不要每次都把所有圖形都算一遍(空間索引)。

→ 這就是 **第 07 章:互動與命中測定**。

### 推論 3:想要「場景」的概念 → 得自己建一套物件系統 + 髒區追蹤

你終究會想要「畫面上有 50 個圖形,各有各的位置顏色,我能個別管理」。但 Canvas 不給你這個,你得自己在 JS 裡維護一個陣列(這叫 **scene graph / 場景圖**),每次重繪就遍歷它重畫。

進一步,當畫面很複雜,「每幀全部重畫」太浪費,你會想「只重畫有變動的那塊」——這叫**髒矩形(dirty rectangle)**。這些 retained mode 免費送你的東西,在 Canvas 裡全都要自己蓋。

→ 這就是 **第 08 章:場景圖與架構**——有趣的是,你會發現自己最後是在 **immediate mode 之上,手工蓋出一層 retained mode**。Konva、Fabric 這些庫做的就是這件事。

### 推論 4:全部自己來 → 數量一大就有效能問題 → 需要效能工程

正因為重繪、命中、合成全是你的程式碼在跑,所以效能也全是你的責任。分層畫布、把繪圖丟到 Worker(OffscreenCanvas)、減少狀態切換……這些都是你要學的。

→ 這就是 **第 09 章:效能工程** 和 **第 10 章:跨越到 GPU**。

### 一張表:DOM 免費送你的 vs Canvas 要你自己做的

| 能力 | DOM / SVG | Canvas | 本課對應章節 |
|------|-----------|--------|--------------|
| 物件存在、可修改 | ✅ 內建 | ❌ 自己用 JS 陣列維護 | 08 |
| 移動/動畫 | ✅ 改屬性即可 | ❌ 清掉重畫 + 迴圈 | 01、06 |
| 點擊事件落到正確元素 | ✅ 自動派發 | ❌ 自己做命中測定 | 07 |
| 只重繪變動部分 | ✅ 瀏覽器內部優化 | ❌ 自己做髒矩形 | 08、09 |
| 座標/縮放/旋轉 | ✅ CSS transform | ⚠️ 有 API 但要自己管矩陣 | 03 |
| 無障礙(螢幕報讀) | ✅ 語意結構 | ❌ 像素無語意,要額外處理 | 0.4 會談 |

> **核心洞察**:**用 Canvas,本質上就是放棄瀏覽器幫你做的一切,換取「直接控制每一個像素」的自由與效能。** 這門課,就是教你怎麼把放棄掉的那些東西,一塊一塊用自己的程式碼補回來——而且補得比通用的瀏覽器更貼合你的需求、更快。

## 0.4 四種繪圖技術的光譜:什麼時候才該動用 Canvas?

理解了兩種模型,我們把開頭那四種做法排在一條光譜上。**選錯工具,後面會痛不欲生**,所以這張表你要會用。

| | DOM | SVG | Canvas 2D | WebGL / WebGPU |
|---|-----|-----|-----------|----------------|
| 渲染模型 | Retained | Retained | **Immediate** | Immediate(更底層) |
| 圖像本質 | 盒子模型 | 向量 | 點陣(像素) | 點陣(GPU 管線) |
| 縮放會不會糊 | 不會 | 不會(向量) | 會(點陣) | 看你怎麼畫 |
| 事件/命中 | 內建 | 內建 | 自己做 | 自己做 |
| 無障礙 | 最好 | 好 | 差(要額外補) | 差 |
| 適合數量級 | 數百 | 數百~數千 | 數千~數萬 | 數十萬~數百萬 |
| 典型場景 | 一般網頁 UI | icon、圖表、流程圖 | 遊戲、白板、影像處理、密集視覺化 | 3D、大規模粒子、高效能 2D |
| 學習/維護成本 | 低 | 低~中 | 中 | 高 |

### 決策樹:我到底該用哪個?

```
要畫的東西多嗎?互動複雜嗎?
│
├─ 就是一般 UI、按鈕、卡片 ──────────────→ 用 DOM。別用 Canvas 自找麻煩。
│
├─ 圖示、logo、可縮放的圖表,元素不多(<幾千) ─→ 用 SVG。向量、可被 CSS/JS 操作、有事件。
│
├─ 元素很多(數千~數萬)、要逐像素控制、
│  要做動畫/遊戲/影像處理/白板 ─────────────→ 用 Canvas 2D。(這門課)
│
└─ 數十萬以上圖元、3D、要榨乾 GPU ───────────→ 用 WebGL / WebGPU。(第 10 章帶你過去)
```

> **常見誤用**:有人拿 Canvas 來做整個網頁 UI(因為覺得「酷」或「想自己控制一切」)。結果是——文字無法被選取、搜尋引擎讀不到內容、螢幕報讀器看到一片空白、改個按鈕顏色要重寫繪圖邏輯。**Canvas 不是用來取代 DOM 的,它是用來做 DOM 做不好的事(密集圖形、像素操作、動畫)。** 大多數成熟產品(Figma、Google Docs)都是 **DOM + Canvas 混搭**:UI 用 DOM,畫布內容用 Canvas。

## 0.5 破除一個迷思:immediate mode ≠ 慢、≠ 純 CPU

很多人以為「Canvas 2D 是軟體繪圖、跑在 CPU、所以慢」。**這是錯的,而且這個誤解會害你做出錯誤的優化決策。**

事實是:現代瀏覽器的 Canvas 2D context **通常是 GPU 加速的**——你下的 `fillRect`、`drawImage` 這些命令,底層多半被翻譯成 GPU 操作,畫布內容存在 GPU 的紋理(texture)裡,最後跟頁面其他部分一起由 GPU 合成。

那「immediate mode」這個詞到底指什麼?它指的是**你跟 API 互動的心智模型**,不是效能等級:

- **Immediate** 講的是:你下命令、命令立即作用在畫布上、然後 API 不保留任何物件概念。
- 它**沒有**規定底層是 CPU 還是 GPU 在跑。

> **心智模型**:immediate / retained 是「**API 的語意**」之分(系統記不記得物件),不是「**快慢**」或「**CPU/GPU**」之分。
> - Canvas 2D = immediate API,底層常是 GPU。
> - 你之後會看到的真正效能瓶頸,往往不是「CPU 軟體繪圖」,而是**像素回讀(`getImageData`,GPU→CPU 搬資料,很貴,見第 05 章)**、**過多的狀態切換**、**沒做髒區重繪**。先把這個概念放對,第 09 章才不會優化錯地方。

## 0.6 建立本課程的核心心智模型

整門課,你只要牢牢記住下面這個模型,後面所有細節都掛得上去:

> ### Canvas = 一塊「只會聽繪圖命令、畫完即忘」的像素佈
>
> 1. **它不記得物件**:你畫的圓、方塊,畫完就只是像素。要有「物件」的概念,你得自己在 JS 裡維護資料(第 08 章)。
> 2. **它不會動**:要動畫,就是「清掉 → 重畫」每秒 60 次(第 01、06 章)。
> 3. **它沒有事件**:要知道點到誰,自己用數學算命中(第 07 章)。
> 4. **它什麼都丟給你**:重繪、合成、效能,全是你的責任,但也給你完全的控制權與效能(第 09、10 章)。
>
> **一句話總結:用 Canvas,就是親手把 DOM 免費送你的那台渲染引擎,一塊一塊自己造出來。這門課就是那張造引擎的施工圖。**

這一章我們刻意一條線都沒畫,因為**Canvas 的所有「為什麼這麼麻煩」,本質都源自同一件事:它是 immediate mode,畫完即忘**。你現在應該能回答:

- 後面那十章在幹嘛?(把「畫完即忘」留下的洞——動畫、事件、場景、效能——一塊塊補回來)
- 什麼時候**不該**用 Canvas?(一般 UI 用 DOM;可縮放少量向量用 SVG;超大規模/3D 用 WebGL)
- Canvas 2D 是純 CPU 軟體繪圖嗎?(不是,通常 GPU 加速;immediate 是 API 語意,不是效能等級)
