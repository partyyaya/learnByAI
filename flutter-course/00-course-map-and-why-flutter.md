# 第 00 章：課程地圖與 Flutter 全貌

> 這一章不寫任何安裝設定，也不寫一行 App 程式碼。我們要先回答幾個更根本的問題：
> **跨平台 App 到底難在哪？Flutter 用什麼招數解決？它跟 React Native、原生開發的根本差異是什麼？**
> 把這個搞懂，你後面看 Flutter 的每一個設計（為什麼一切皆 Widget、為什麼畫面這麼順、為什麼 UI 兩平台長得一模一樣）都會有「啊，原來是為了這個」的恍然大悟感。

---

## 0.1 先問：寫一個「能同時上 iOS 和 Android」的 App，難在哪？

假設你要做一個記帳 App，老闆說：「iOS、Android 都要上，預算只有一組人。」你有哪些選擇？

### 選項 A：各寫一份原生（Native）

- iOS 用 **Swift + UIKit/SwiftUI**，Android 用 **Kotlin + Jetpack Compose**。
- **優點**：效能最好、能用到所有系統功能、體驗最「原生」。
- **痛點**：**同一個功能要寫兩次**。登入畫面寫兩遍、API 串接寫兩遍、改一個按鈕顏色要改兩個專案。兩邊還常常進度不同步、bug 不一樣。人力直接 ×2。

**這就是跨平台框架想解決的核心痛點：一套程式碼，跑兩個平台。**

### 選項 B：用網頁包一層（WebView / Hybrid）

- 用 HTML/CSS/JS 寫好網頁，塞進一個 App 殼裡（早期的 Cordova / Ionic 走這條路）。
- **優點**：前端工程師直接上手，一套程式碼到處跑。
- **痛點**：它本質上是「在 App 裡開了一個瀏覽器」。捲動會卡、動畫不順、長得不像原生 App，使用者一滑就感覺得出來「這是網頁假裝的」。

### 選項 C：跨平台框架（React Native / Flutter）

這就是這門課的主角所在的位置。它們的承諾是：**一套程式碼，但跑出來是「真的」原生體驗，不是網頁套殼。**

但 React Native 和 Flutter 達成這件事的**方法完全不同**——這個差異是理解 Flutter 的關鍵，我們下一節專門講。

---

## 0.2 核心分歧：「畫面」到底是誰畫的？

所有跨平台框架，最終都要回答一個問題：**螢幕上那個按鈕，是誰畫出來的？**

### React Native 的做法：指揮原生元件（橋接）

React Native 的思路是：**「我不自己畫，我去命令系統幫我畫。」**

```text
你的 JS 程式碼：「給我一個按鈕」
        │
        ▼
   [ Bridge 橋接層 ]   ← 把指令翻譯給原生
        │
        ▼
iOS 用 UIButton 畫 / Android 用 Button 畫   ← 真正畫畫的是系統
```

- **好處**：按鈕長得 100% 像系統原生（因為它就是系統的按鈕）。
- **代價**：你的程式碼（JS）跟系統元件之間隔了一座「橋」。每次互動都要過橋翻譯，**橋一塞車，畫面就卡**。而且 iOS 的按鈕和 Android 的按鈕行為、外觀不一樣，你常常要寫「如果是 iOS 就…，如果是 Android 就…」。

**心智模型**：React Native 像個「翻譯官」。你說中文，它翻成 iOS 話跟 Android 話，叫各自的系統去做事。翻譯本身會有延遲與落差。

### Flutter 的做法：自己帶畫筆，什麼都自己畫

Flutter 的思路完全相反：**「我不靠系統的元件，我自己畫每一個像素。」**

```text
你的 Dart 程式碼：「給我一個按鈕」
        │
        ▼
  [ Flutter Framework ]  ← 自己決定按鈕長怎樣
        │
        ▼
  [ 渲染引擎 Impeller/Skia ]  ← 直接在畫布上畫出每個像素
        │
        ▼
   系統只提供一塊「空白畫布」(Canvas)
```

Flutter 跟系統要的東西非常少：**「給我一塊畫布，再把使用者的觸控座標告訴我就好，剩下我自己來。」** 按鈕、文字、動畫、陰影，全部是 Flutter 自己用畫筆畫上去的。

- **好處**：
  1. **兩平台長得一模一樣**（因為都是 Flutter 畫的，不依賴系統元件），UI 高度可控。
  2. **效能順**（不需要過橋翻譯，動畫可以穩定跑 60/120fps）。
  3. **設計自由**：你想要的任何造型都畫得出來，不受系統元件限制。
- **代價**：
  1. App 體積會大一點（要把「畫筆」也就是渲染引擎打包進去）。
  2. 預設外觀是 Flutter 自己的（Material Design），想完全融入系統風格要多花一點工。

**心智模型**：Flutter 像個「自帶畫具的畫家」。它不請系統幫忙，自己準備好顏料和畫筆，在系統給的空白畫布上，一筆一筆把整個畫面畫出來。

> ⭐ **這是整門課最重要的一句話**：**Flutter 不使用系統的 UI 元件，它自己畫所有東西。** 你後面學到的「一切皆 Widget」「三棵樹」「重繪機制」，全都是這個前提推導出來的結果。

## 0.3 那 Flutter 是用什麼「畫」的？認識它的技術堆疊

Flutter 由幾層疊起來，由上而下：

```text
┌─────────────────────────────────────────┐
│  你的 App（Dart 寫的 Widget）              │  ← 你大部分時間待在這層
├─────────────────────────────────────────┤
│  Framework 層（Dart）                      │
│  Material / Cupertino（現成的元件）         │
│  Widgets（Widget 基礎類別）                 │
│  Rendering（排版、計算每個東西多大、在哪）   │
│  Animation / Painting / Gestures           │
├─────────────────────────────────────────┤
│  Engine 層（C++）                          │
│  Impeller / Skia（繪圖）、文字排版、Dart VM │
├─────────────────────────────────────────┤
│  Embedder（各平台的殼）                     │
│  iOS / Android / Web / Windows / macOS...  │  ← 跟系統要畫布、收觸控事件
└─────────────────────────────────────────┘
```

幾個你一定要認得的名詞：

- **Dart**：Flutter 用的程式語言（第 02 章專門教）。它有兩種編譯模式，正好對應開發與上線兩種需求：
  - **開發時（JIT，Just-In-Time）**：邊跑邊編譯，所以能支援 **Hot Reload（熱重載）**——改一行程式碼、存檔，畫面 1 秒內就更新，**而且保留你當前的狀態**（不用每次都重新操作到那一頁）。這是 Flutter 開發體驗的殺手鐧。
  - **上線時（AOT，Ahead-Of-Time）**：打包前先全部編譯成原生機器碼，所以**正式版啟動快、執行順**，沒有「邊跑邊編譯」的開銷。
- **Skia / Impeller**：真正的「畫筆」（渲染引擎）。Skia 是 Google 老牌的 2D 繪圖庫（Chrome 也在用）；**Impeller 是 Flutter 新一代引擎**，預先編譯著色器（shader）來消除舊版偶發的「首次動畫卡頓」，現在已是 iOS / Android 的預設。你不用直接操作它，但要知道「畫面是它畫的」。

**白話翻譯**：你寫 Dart → Framework 幫你算好「每個東西多大、放哪、什麼顏色」→ Engine 拿這份「繪圖指令」用 Impeller 在畫布上實際畫出來。你 99% 的時間只待在最上面那層。

## 0.4 Flutter vs React Native vs 原生：一張表看懂取捨

| 面向 | 原生（Swift / Kotlin） | React Native | **Flutter** |
|------|----------------------|--------------|-------------|
| 程式語言 | Swift + Kotlin（兩種） | JavaScript / TypeScript | **Dart（一種）** |
| 畫面誰畫的 | 系統元件 | 系統元件（透過橋接） | **自己畫每個像素** |
| 兩平台一致性 | 各自原生外觀 | 接近原生，但有差異 | **幾乎完全一致** |
| 效能 | 最佳 | 好（橋接偶有瓶頸） | **接近原生（無橋接）** |
| 熱重載 | 較慢/有限 | 支援 | **支援，且保留狀態** |
| 上手門檻 | 高（要學兩套） | 低（會 React 就行） | **中（要學 Dart + Widget）** |
| App 體積 | 最小 | 中 | **略大（含引擎）** |
| 適合場景 | 極致效能/深度系統整合 | 已有 React 團隊 | **UI 要求高、要快速雙平台、設計自由** |

**結論**：沒有「最好」，只有「最適合」。這門課選 Flutter，是因為它的「自己畫」哲學帶來高度一致、流暢、可控的 UI，而且一套 Dart 程式碼就能涵蓋 iOS / Android（甚至 Web / 桌面），對「小團隊要做高品質雙平台 App」是目前最甜的點。

## 0.5 「一切皆 Widget」是什麼意思？先給你一個預告

你一定會聽到這句 Flutter 名言：**Everything is a Widget（一切皆 Widget）**。第 03 章會深入，但先建立直覺：

在 Flutter 裡，**畫面上看得到的東西是 Widget**（按鈕、文字、圖片），**看不到的「排版意圖」也是 Widget**（置中、留白 padding、直排 column、橫排 row），甚至**整個 App 本身也是一個 Widget**。

```dart
// 先看不懂沒關係，感受一下「結構」就好
Center(                          // 「我要置中」← 這也是一個 Widget
  child: Padding(                // 「我要留 16 的內距」← 也是 Widget
    padding: EdgeInsets.all(16),
    child: Text('Hello Flutter'),// 「顯示文字」← 是 Widget
  ),
)
```

逐段看這個結構：

- `Text('Hello Flutter')`：最內層，負責「顯示一段文字」。
- `Padding(...)`：把上面那個文字「包起來」，並在四周加上 16 的內距。**注意：Padding 不是文字的一個屬性，而是一個獨立的 Widget 把文字包在裡面。**
- `Center(...)`：再把整包「置中」。
- `child:`：這是 Flutter 表達「父子關係」的方式——一個 Widget 透過 `child`（或 `children`）裝著另一個 Widget。

**心智模型**：Flutter 的 UI 是用 Widget **層層包裝**出來的，像俄羅斯娃娃。React 開發者可以類比成 JSX 的巢狀結構；後端工程師可以想成「一棵物件樹」。這種「組合（composition）大於繼承」的設計，是 Flutter UI 的核心精神——**你不是去『設定』一個元件的 100 個屬性，而是用很多小 Widget 組合出你要的樣子。**

這也帶來一個你早晚會遇到的現象：**巢狀很深、縮排很多**。別怕，這是正常的，後面會教你怎麼拆元件讓它好讀。

## 0.7 學前心態建設（這幾點先講，少走很多冤枉路）

1. **不要怕巢狀很深**：Flutter UI 縮排多是常態，不是你寫錯。學會「拆 Widget」就好讀了（第 03 章教）。
2. **錯誤訊息會很長，但很有用**：Flutter 的報錯常常直接告訴你「哪個 Widget、哪一行、可能的原因」。請養成「讀完紅字第一段」的習慣，不要看到紅字就慌。
3. **Hot Reload 是你的好朋友**：改一點、存檔、馬上看結果。請用「小步快跑」的方式學，不要一次寫一大段才跑。
4. **Dart 不難**：如果你會任何一種 C 系語言（JS / Java / Kotlin / Swift），Dart 大概半天就能上手，第 02 章會幫你補齊。
5. **官方文件與 pub.dev 是標配**：套件都放在 [pub.dev](https://pub.dev)，文件在 [docs.flutter.dev](https://docs.flutter.dev)。這門課教你建立心智模型，細節 API 隨時去查。

## 小結

- 跨平台的核心痛點是「一個功能寫兩次」；Flutter 的承諾是「一套 Dart 程式碼，原生級體驗」。
- Flutter 跟 React Native 最大的不同：**RN 命令系統元件來畫，Flutter 自己畫每個像素**。這是後面所有設計的源頭。
- Flutter 堆疊：你的 Dart Widget → Framework（排版）→ Engine（Impeller/Skia 繪圖）→ Embedder（跟系統要畫布）。
- Dart 的 JIT 給你 Hot Reload，AOT 給你正式版的順暢。
- 「一切皆 Widget」＝用很多小 Widget **組合**出 UI，看得到的、看不到的排版意圖、整個 App 都是 Widget。
