# 第 08 章：架構擴展 —— 讀寫分離、Replication、Partition、Sharding

> 當單一資料庫撐不住時，你有一整套武器：加從庫分擔讀取、把大表切成分區、把資料分散到多個節點。
> 但每一種擴展都有代價。這章的重點不只是「怎麼做」，而是「什麼時候該做、又不該過早做」。
> 先把第 01~03 章的 schema、索引、SQL、快取做好，再談這些。

---

## 8.1 學習目標

完成本章後，你應該可以：

- 分辨垂直擴展與水平擴展。
- 說明主從複製（Replication）的原理與複製延遲問題。
- 設計讀寫分離，並知道哪些查詢不能走從庫。
- 用分區（Partition）處理單表過大。
- 說明分片（Sharding）的原理、分片鍵選擇與跨片查詢的痛。
- 判斷一個系統目前該用哪個層級的擴展手段。

---

## 8.2 先問：真的需要擴展嗎？

擴展是有代價的複雜度。動手前先確認你已經做完便宜的優化：

```text
擴展前的檢查清單（由便宜到貴）：
1. schema 設計合理嗎？（第 01 章）
2. 索引建對了嗎？慢查詢優化了嗎？（第 03 章）
3. 熱門讀取加快取了嗎？（第 05 章）
4. 大報表移到分析庫了嗎？（第 07 章）
5. 連線池、機器規格調過了嗎？
```

以上都做了還撐不住，才進入本章的架構擴展。

**過早分片是常見災難**：系統還沒到規模就分片，換來的是暴增的維運與開發複雜度，卻沒有實際收益。

---

## 8.3 垂直擴展 vs 水平擴展

### 垂直擴展（Scale Up）：把單台機器加強

```text
CPU 4 核 → 32 核
記憶體 16G → 256G
SSD → NVMe
```

- 優點：最簡單，不用改架構。
- 缺點：有物理上限、成本非線性飆升、單點故障風險仍在。

### 水平擴展（Scale Out）：增加機器數量

```text
1 台 → 主庫 + 多台從庫
      → 資料分散到多個分片節點
```

- 優點：理論上可持續擴展、可提升可用性。
- 缺點：架構複雜、一致性與跨節點查詢變難。

**實務順序**：通常先垂直擴展（買時間），同時做好讀寫分離，真正到瓶頸再考慮分片。

---

## 8.4 主從複製（Replication）

複製是把主庫（Primary）的資料變更，同步到一個或多個從庫（Replica）。

```text
        寫入
         │
         ▼
    ┌─────────┐   複製 binlog/WAL   ┌─────────┐
    │ Primary │ ──────────────────▶ │ Replica │
    │ 讀 + 寫 │ ──────────────────▶ │  只讀   │
    └─────────┘                     └─────────┘
```

### 複製的用途

1. **分擔讀取**：讀查詢分流到從庫（讀寫分離，下一節）。
2. **高可用**：主庫掛掉時，把某個從庫提升為新主庫（failover）。
3. **備份與分析**：在從庫上做備份或跑報表，不影響主庫。

### 同步 vs 非同步複製

- **非同步複製**（多數預設）：主庫寫完就回應客戶端，不等從庫確認。效能好，但主庫突然故障時，還沒複製過去的資料可能遺失。
- **半同步複製**：主庫至少等一個從庫確認收到才回應。更安全，但延遲略高。
- **全同步**：等所有從庫確認。最安全也最慢，少用。

### 複製延遲（Replication Lag）：最重要的陷阱

從庫的資料**永遠比主庫慢一點點**（毫秒到秒級，負載高時更久）。這帶來一個經典 bug：

```text
1. 使用者送出「新增留言」→ 寫入主庫
2. 頁面重整，讀取留言列表 → 查從庫
3. 從庫還沒複製到那則留言 → 使用者看不到自己剛發的留言
```

這就是複製延遲造成的「讀不到自己剛寫的資料」。下一節講怎麼處理。

---

## 8.5 讀寫分離

讀寫分離：**寫走主庫，讀走從庫**，用從庫分擔讀取壓力。適合讀多寫少的系統（絕大多數 Web 應用）。

```text
寫請求（INSERT/UPDATE/DELETE）→ Primary
讀請求（SELECT）             → Replica（可多台，負載均衡）
```

### 哪些讀「不能」走從庫

因為複製延遲，以下情況要走主庫（或有其他處理）：

1. **寫入後立刻要讀的資料**：如上一節的「發完留言馬上看」。
2. **交易內的讀取**：交易要一致，不能跨主從。
3. **強一致需求**：如結帳前確認庫存、餘額。

### 處理「讀自己剛寫的資料」（Read-Your-Writes）

常見策略：

- **寫後短時間強制讀主庫**：使用者寫入後的 N 秒內，他的讀請求都走主庫。
- **關鍵頁面固定走主庫**：如「下單成功頁」直接查主庫。
- **前端樂觀更新**：先在前端顯示剛送出的資料，不依賴立刻回查。

### 實作層級

- **應用層**：程式判斷 SQL 是讀還是寫，路由到不同連線。
- **中介層**：用 ProxySQL、MaxScale 這類代理自動分流。
- **框架/ORM**：許多 ORM 支援讀寫分離設定。

**心智模型**：讀寫分離是「用最終一致的讀，換讀取的水平擴展」。你要明確知道「哪些讀不能容忍延遲」。

## 8.6 分區（Partition）：把大表切小，但還在同一個庫

當單表資料量極大（例如上億筆訂單），即使有索引，維護、查詢、刪除舊資料都變慢。分區把一張邏輯表，在物理上切成多個小塊。

### 範圍分區（Range，最常用）

按時間切，最常見於日誌、訂單、事件：

```sql
-- PostgreSQL 宣告式分區
CREATE TABLE orders (
    id          BIGINT,
    user_id     BIGINT,
    total       NUMERIC(12,2),
    created_at  TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_01 PARTITION OF orders
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

CREATE TABLE orders_2026_02 PARTITION OF orders
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
```

好處：

- **分區裁剪（Partition Pruning）**：查 `WHERE created_at >= '2026-02-01'` 時，資料庫只掃 `orders_2026_02`，跳過其他分區。
- **刪舊資料極快**：要刪一整月的資料，直接 `DROP` 或 `DETACH` 該分區，不用逐列 `DELETE`。
- 每個分區的索引更小，維護更快。

### 其他分區方式

- **List 分區**：按離散值，例如按地區 `region IN ('TW','JP','US')`。
- **Hash 分區**：按 hash 平均散開，用於沒有明顯範圍但想均分負載時。

### 分區 vs 索引的差別

索引是「在表內快速定位」；分區是「先決定只碰哪一塊資料」。兩者互補：分區裁剪先縮小範圍，分區內的索引再精準定位。

### 分區的限制

- 分區鍵的選擇很關鍵，通常要出現在查詢條件裡才吃得到裁剪。
- 唯一約束通常必須包含分區鍵。
- 跨很多分區的查詢不會更快，甚至可能更慢。

---

## 8.7 分片（Sharding）：把資料分散到多個資料庫節點

分區是「一個庫內切塊」；分片是「切到**不同的資料庫/機器**」。當單機的儲存或寫入吞吐到達上限，才需要分片。

```text
             ┌──────────────┐
   user_id ─▶│  路由/分片鍵  │
             └──────┬───────┘
        ┌───────────┼───────────┐
        ▼           ▼           ▼
   ┌────────┐  ┌────────┐  ┌────────┐
   │ Shard0 │  │ Shard1 │  │ Shard2 │  各自是獨立資料庫
   └────────┘  └────────┘  └────────┘
```

### 分片策略

1. **Hash 分片**：`shard = hash(user_id) % N`。
   - 優點：資料分佈均勻。
   - 缺點：加減節點時要大規模搬資料（可用一致性雜湊緩解）。

2. **Range 分片**：按範圍，如 `user_id 1~100萬` 在 Shard0。
   - 優點：範圍查詢友善、擴容簡單。
   - 缺點：容易出現熱點（最新的資料都打在同一片）。

3. **查表路由（Directory）**：用一張映射表記錄「哪個 key 在哪個分片」。
   - 優點：最靈活。
   - 缺點：映射表本身成為關鍵依賴。

### 分片鍵（Shard Key）選擇：分片成敗的關鍵

分片鍵選錯，整個系統會很痛。好的分片鍵要：

- **分佈均勻**：避免資料傾斜（某片特別大、特別忙）。
- **貼合查詢**：最高頻的查詢應該能只打到一個分片。

範例：電商用 `user_id` 分片。

- 「查某使用者的所有訂單」→ 只打一個分片，很快。
- 但「查某商品的所有訂單」→ 要問所有分片（跨片查詢），很慢。

所以分片鍵要對齊你「最重要、最高頻」的查詢維度。

### 分片帶來的痛

1. **跨片查詢（Scatter-Gather）**：要問所有分片再彙總，慢且複雜。
2. **跨片交易**：分散式交易極難，通常改用最終一致 + 補償（呼應第 04 章）。
3. **跨片 JOIN**：基本上做不到，要靠反正規化或應用層組裝。
4. **全域唯一 ID**：不能用單庫自增，要用 Snowflake、UUID 等分散式 ID。
5. **重新分片（Resharding）**：擴容搬資料極其麻煩。

### NewSQL：把分片自動化

TiDB、CockroachDB 這類 NewSQL（第 00 章提過）在底層自動做分片與複製，同時保留 SQL 與交易。當你需要分片但不想自己維護分片邏輯時，可以考慮。代價是運維這類分散式資料庫本身也需要能力。

## 8.8 擴展路線圖：什麼規模用什麼

```text
階段 1：單機 PostgreSQL/MySQL
        └─ 做好 schema、索引、SQL

階段 2：單機 + Redis 快取
        └─ 擋住熱門讀取（第 05 章）

階段 3：主庫 + 多從庫，讀寫分離
        └─ 分擔讀取，提升可用性

階段 4：垂直擴展主庫 + 分析庫分流報表
        └─ 買時間，報表移去 ClickHouse（第 07 章）

階段 5：大表分區
        └─ 按時間分區訂單/日誌

階段 6：分片 或 NewSQL
        └─ 單機寫入/儲存到頂，才動這步
```

多數系統一輩子停在階段 3~5。真正需要階段 6 的系統，通常已經是相當大的規模。

**心智模型**：擴展是「不得不」時才付出的複雜度成本，不是越早越潮。每一步都要有數據支撐（監控、壓測）證明真的到瓶頸了。

## 8.9 常見錯誤

### 錯誤 1：過早分片

系統一天幾萬筆訂單就上分片，換來十倍開發複雜度、零實際收益。先垂直擴展 + 讀寫分離。

### 錯誤 2：所有讀都無腦走從庫

把「下單後確認頁」也丟給從庫，使用者看到「查無此訂單」。要識別哪些讀不能容忍複製延遲。

### 錯誤 3：分片鍵選了不常查的維度

用 `order_id` 分片，但業務最常查「某使用者的訂單」，導致幾乎每個查詢都跨片。分片鍵要對齊高頻查詢維度。

### 錯誤 4：分區鍵沒進查詢條件

按 `created_at` 分區，但查詢幾乎都不帶時間條件，吃不到分區裁剪，等於白分。

### 錯誤 5：以為複製 = 備份

複製是即時同步：你在主庫誤刪一張表，從庫也會立刻被刪。複製提升可用性，但不能取代備份（第 09 章）。

## 8.10 本章練習

### 練習 1：判斷擴展手段

一個社群 App，讀遠多於寫（看貼文 vs 發貼文 = 100:1），單庫 CPU 讀取吃滿，但資料量還不算大。該用什麼擴展？

#### 參考解答

優先做**讀寫分離**：加從庫，把大量「看貼文」的讀請求分流到多台從庫，寫仍走主庫。

理由：

- 瓶頸是「讀取吃滿 CPU」，且讀寫比 100:1，讀寫分離正對症。
- 資料量還不大，不需要分區或分片。
- 搭配 Redis 快取熱門貼文（第 05 章）效果更好。

注意：使用者「發完貼文馬上看自己貼文」要走主庫或前端樂觀更新，避開複製延遲。

### 練習 2：複製延遲的 bug

使用者改了個人暱稱，跳轉到個人頁卻還顯示舊暱稱，重整幾次才更新。說明原因與至少兩種解法。

#### 參考解答

原因：改暱稱寫進主庫，個人頁的讀取走了從庫，而從庫還沒複製到這筆變更（複製延遲），所以讀到舊值。

解法：

1. **寫後強制讀主庫**：使用者寫入後的一小段時間內（或該使用者的關鍵頁面），讀請求路由到主庫。
2. **前端樂觀更新**：送出成功後，前端直接用新暱稱渲染，不依賴立刻回查資料庫。
3. **關鍵頁固定走主庫**：把「個人資料頁」這類對自己資料一致性敏感的頁面固定查主庫。

### 練習 3：設計訂單表分區

訂單量每月數千萬筆，查詢幾乎都帶時間範圍，且要定期刪除兩年前的舊訂單。請設計分區方案。

#### 參考解答

按 `created_at` 做**範圍分區**，以月為單位：

```sql
CREATE TABLE orders (
    id         BIGINT,
    user_id    BIGINT,
    total      NUMERIC(12,2),
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_2026_07 PARTITION OF orders
    FOR VALUES FROM ('2026-07-01') TO ('2026-08-01');
-- 每月新增一個分區
```

好處對應需求：

- 查詢帶時間範圍 → 分區裁剪，只掃相關月份分區。
- 刪兩年前舊訂單 → 直接 `DROP`/`DETACH` 舊分區，秒級完成，不用逐列 `DELETE`。
- 每個月分區的索引較小，維護快。

補充：唯一約束需包含分區鍵 `created_at`；可寫排程自動預建下個月分區。

### 練習 4：選分片鍵

一個多租戶 SaaS，每個客戶公司（tenant）的資料量差很多，最高頻查詢是「某公司的所有資料」。你會用什麼當分片鍵？要注意什麼？

#### 參考解答

用 `tenant_id`（公司 ID）當分片鍵。

理由：

- 最高頻查詢是「某公司的所有資料」，用 `tenant_id` 分片可讓這類查詢只打一個分片，避免跨片。
- 天然的隔離邊界，符合多租戶特性。

要注意的問題：

- **資料傾斜**：大客戶的資料量可能遠超小客戶，某些分片會特別大、特別忙。需要監控，必要時把超大租戶單獨拆到專屬分片。
- 若有「跨公司的全域統計」需求，那會是跨片查詢，應改用分析庫（第 07 章）處理，而非在分片主庫上硬跑。
- 需要全域唯一 ID 方案（Snowflake/UUID）。

### 練習 5：複製能不能取代備份

團隊說「我們有 3 台從庫即時複製，資料很安全，不需要備份了」。這說法對嗎？

#### 參考解答

不對。複製不能取代備份。

原因：

- 複製是**即時同步**，主庫的錯誤操作會立刻傳到所有從庫。例如誤下 `DELETE FROM orders`（忘了 WHERE）或 `DROP TABLE`，所有從庫瞬間跟著執行，3 份資料一起沒。
- 複製防的是「硬體/節點故障」（高可用），不防「邏輯錯誤、誤刪、被攻擊、程式 bug 寫壞資料」。
- 備份能回到「過去某個時間點」的狀態（第 09 章的 PITR），複製做不到。

正確做法：複製（高可用）與備份（可回溯）兩者都要，它們解決不同問題。第 09 章會用 RPO/RTO 這組指標把這件事量化——複製改善的是「多久救回來」，備份改善的是「會丟多少資料」。
