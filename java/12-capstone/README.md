## 專題主題：小型電商訂單系統

**核心情境**：使用者瀏覽商品 → 加入購物車 → 下單 → 扣庫存 → 付款 → 出貨狀態流轉。
選這個主題是因為它天然涵蓋了本課所有難點：交易一致性、併發扣庫存、狀態機、權限分離、報表查詢、熱點快取與跨流程的最終一致性。

### 功能範圍

| 模組 | 功能 |
|------|------|
| 帳號 | 註冊、登入（JWT）、角色分為買家 / 賣家 / 管理員 |
| 商品 | CRUD、上下架、分類、關鍵字搜尋與分頁 |
| 庫存 | 併發扣減、防超賣、庫存異動紀錄 |
| 訂單 | 建立、取消、狀態流轉、冪等下單、查詢自己的訂單 |
| 報表 | 銷售統計（刻意用 MyBatis 實作，與 JPA 對照） |
| 快取 | 商品詳情與熱門排行快取、Redis 預扣庫存、分散式鎖、API 限流 |
| 事件 | 下單後的扣庫存 / 通知 / 出貨改用訊息驅動，Outbox 保證不漏、冪等消費保證不重 |
| 維運 | 健康檢查、指標、結構化日誌、Docker 部署 |

## 驗收標準

專題完成時，這些問題你都要能當場回答並展示程式碼：

1. 一筆訂單成立，交易邊界從哪裡開始、到哪裡結束？為什麼？
2. 同一秒 100 個人搶最後 1 件庫存，你怎麼保證不超賣？你用哪種鎖、為什麼？
3. 使用者按了兩次「送出訂單」，系統怎麼確保只成立一筆？
4. 查訂單列表時，怎麼確認沒有 N+1？你怎麼驗證的？
5. 買家 A 直接改網址帶入買家 B 的訂單 ID，會發生什麼事？
6. 資料庫要加一個欄位，從開發到正式環境的流程是什麼？
7. 服務半夜掛了，你從哪裡開始查？
8. Redis 整個掛掉 60 秒，哪些 API 會降級、哪些會直接失敗？資料庫 QPS 會漲幾倍？
9. 訂單寫進資料庫了、訊息還沒送出去，服務就被 `kill -9`。這筆訂單的庫存最後會不會被扣？為什麼？
10. 同一則「訂單已成立」訊息被投遞了 10 次，庫存會被扣幾次？你靠什麼保證？
11. 你的 MQ 為什麼選 RabbitMQ（或 Kafka）？換成另一個要改哪些地方？

## 延伸挑戰（選修）

- 把第 07 章的事件流**用另一個 broker 再做一次**（RabbitMQ 版做完換 Kafka 版），比對設定量與壓測結果。
- 加上熔斷，模擬第三方金流逾時（限流已在第 06 章做過）。
- 把訂單狀態變更寫成事件流並用 log compaction 保留，體驗事件來源（Event Sourcing）的取捨。
