# 08 — JPA / Hibernate 與 MyBatis

> 同一件事的兩種哲學：**JPA 幫你把物件映射成資料庫、MyBatis 讓你自己掌控 SQL**。
>
> 這一站兩個都學，重點不在「哪個比較好」，而在**你要能講出為什麼這個專案選這個**。
> 00 章會先畫一張「六條分歧軸」的表，而 09 章用九章的實測把它填一次 ——
> **六格裡有四格要改。**

---

## 學完你可以

- 說明 ORM 與 SQL Mapper 的根本差異，並依專案特性做出選擇。
- 正確映射 Entity 與關聯，避免雙向關聯造成的無限遞迴與意外刪除。
- 解釋持久化情境、一級快取、髒檢查與 flush 時機 —— 知道「我沒呼叫 `save` 為什麼資料變了」。
- 診斷並解決 N+1 查詢與 `LazyInitializationException`。
- 用 JPQL、Criteria、QueryDSL 或原生 SQL 寫複雜查詢，並知道各自的時機。
- 讓批次寫入真的生效，並說出**讓它靜默失效的四件事**。
- 在無鎖 / 樂觀鎖 / 悲觀鎖 / 原子 `UPDATE` 之間，依「衝突窗口有多長」做選擇。
- 用 MyBatis 寫動態 SQL 與 `resultMap`，並把「2^N 種條件組合都要合法」
  變成一條**不需要資料庫**的 CI 斷言。
- 在同一個專案裡合理混用兩者，並說出**三種切法各自的第一號地雷**。
- 拆開一個效能數字（固定成本 / 每列成本 / 交易 / 建物件），而不是拿 benchmark 當理由。
- 估算遷移成本，並說出「把寫入路徑搬到 SQL Mapper」**要自己補回來的六件事**。
- 用**契約測試**保護「同一個功能兩個實作」，並知道它的兩個陷阱（邊界值、只比第一頁）。
- 回答「兩個都不選行不行」—— JdbcTemplate / jOOQ / 純 JDBC 各自的位置。
- 從這一站的 25 條 CI 斷言裡，挑出**跟框架無關的那七條**放進你自己的專案。

## 這一站會打破的幾個假設

跟前兩站一樣，這一站的每一個結論都來自一個跑得起來的實驗。
**而這一站要拆的，是十個「聽起來完全合理」的句子**：

- 「我沒呼叫 `save()`，資料就不會變」 → **00、03 章**
- 「`@Enumerated` 不寫也沒差」 → **01 章**（預設是 `ORDINAL`，而它是一顆定時炸彈）
- 「`cascade = ALL` 包含 `orphanRemoval`」 → **02 章**（從集合移除**什麼都不會發生**）
- 「JPQL 打了 SQL，拿到的就是資料庫裡的值」 → **03 章**（它回傳快取裡那個舊物件）
- 「改成 `EAGER` 就不會有 `LazyInitializationException`」 → **04 章**（列表查詢上**還是 251 句**）
- 「`join o.items` 回幾筆，`count(o)` 就是幾」 → **05 章**（10 筆 vs 30）
- 「開了 `hibernate.jdbc.batch_size` 就有批次了」 → **06 章**（伺服器剖析的句數一句都沒少）
- 「`#{}` 安全，是因為值沒有進到 SQL 文字裡」 → **07 章**（general log 顯示兩者**一字不差**）
- 「每一個 `<if>` 條件都單獨測過了，就沒問題」 → **08 章**（兩個條件同時成立才炸）
- 「MyBatis 比較快，所以查詢用 MyBatis」 → **09 章**（那個兩倍**不是框架的**）

**每一章的最後都有一份「常見誤區」的完整清單**，逐條指回破解它的那一節。

## 這一站的招牌實測

**十個數字，各自來自一個十幾行的實驗**：

| 這件事 | 數字 | 在哪 |
|---|---|---|
| 一頁 200 張訂單的列表，天真寫法 | **251 句 SQL**（而 20 張的版本是 41 句） | 00 章 0.3.2 |
| 同一段程式碼，只換客戶數 | **204 / 251 / 401 句** —— 所以本機測不出來 | 04 章 4.2.4 |
| 把實體放進一個 `HashSet` | **51 句 SQL**（`equals` 會初始化代理） | 04 章 4.3.3 |
| `JOIN FETCH` 配分頁 | 2000 張取 20 筆 → **107 ms、記憶體裡 6000 個實體** | 04 章 4.5.5 |
| `@BatchSize(25)` | 251 → **11 句**，一行全域組態就生效 | 04 章 4.7 |
| 一頁列表為了顯示 6 個欄位 | 建了 **650 個實體**；換成投影是 **0 個** | 05 章 5.8 |
| `rewriteBatchedStatements` 沒開 | JDBC 說「批次 20 次」，**伺服器還是剖析了 1000 句** | 06 章 6.3.7 |
| `LockModeType.OPTIMISTIC` | 在 MySQL 預設隔離等級下**完全無效** | 06 章 6.6.7 |
| keyset 的「教科書寫法」`(a,b) > (?,?)` | MySQL 當成 `Filter` 掃 5000 列；展開成 `OR` 才是索引範圍掃描 —— **2407 → 299 µs** | 08 章 8.6.8 |
| 「MyBatis 快兩倍」拆開之後 | 同一句 SQL、同一個投影 → **480 µs vs 518 µs（0.93×）** | 09 章 9.4 |

📌 **最後一列是這一站的結論**：
那個「兩倍」是**交易 + Criteria 翻譯 + 建實體**，不是框架。
**選型是常數倍，寫法是量級。**

|---|---|---|

## 程式碼演進：你寫的東西，後面章節會改

這一站是**累積式**的：同一組 `shop-service` 從 01 章一路長到 09 章。
**後面的章節會修改前面寫好的程式碼，而每一次修改都是因為「量到了一個新的事實」。**

**最值得看的八次改動**（完整清單在每一章的「shop-service 落地」那一節）：

| 你在哪一章寫的 | 哪一章改它 | 為什麼 |
|---|---|---|
| 01 章：對代理安全的 `equals` | **04 章 4.3.2** | 它是對的，而**代價**是 `equals`/`hashCode` 會初始化代理 |
| 03 章：`OrderService.view()` | **04 章 4.11.2** | 改用 `@EntityGraph`：**3 句 → 1 句** |
| 04 章：`list()` 回傳實體 | **05 章 5.14.2** | 改成 DTO 投影：3 句 / 80 個實體 → **2 句 / 0 個** |
| 01 章：`Stock` 只有欄位 | **06 章 6.11.1** | 長出領域方法與 `InsufficientStockException` |
| 03 章：`OrderService.place()` | **06 章 6.11.1** | 3 句 → 4 句 —— **這一站第一次「句數往上走」**，換到的是不會超賣 |
| 05 章：`search()`（Specification） | **08 章 8.10.1** | 旁邊多一個 MyBatis 版，**兩個實作刻意並存**，09 章要拿它們結案 |
| 05 章：`OrderSpecifications.of()` | **09 章 9.9.2** | 🔴 它**從一開始就漏掉一個條件**，而抓到它的是一條契約測試 |
| 05 章與 08 章那兩個搜尋實作 | **09 章 9.9.4** | 收斂成第三個實作，舊的兩個留下來當**契約測試的對照組** |

📌 **每一章的「shop-service 落地」那一節，都是那一章結束時的完整版本。**
想看某段程式碼「現在」長什麼樣，看**最後一個修改它的章節**。

⚠️ **而每一章量到的數字，都只是「那一章當時」的數字** ——
同一支 `view()`，03 章是 3 句、04 章是 1 句；
同一頁列表，04 章數「幾句 SQL」、05 章開始數「建了幾個物件」、
06 章開始問「伺服器剖析了幾句」、09 章問「配置了幾個位元組」。
**尺換了，答案就換了。**
