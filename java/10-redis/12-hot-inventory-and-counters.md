# 第 12 章：熱點、計數與預扣庫存

> 09 章 9.10.4 留下一句話：
> **「Redis 的鎖負責減少衝突，資料庫負責保證正確。」**
> 這一章把它兌現，而且會證明一件可能違反直覺的事：
> **這一站教的所有 Redis 技巧，都不是防止超賣的那個東西。**
>
> 先看實測。同一段業務（**200 個人搶 100 件**），六種方案一次跑完：
>
> | 方案 | 節 | 訂單 | **超賣** | 重試 | 耗時 | DB 查詢 |
> |---|---|---|---|---|---|---|
> | ① 沒有保護 | 12.2.3 | 200 | **179 件** | 0 | 158 ms | 200 |
> | ② 悲觀鎖 `SELECT … FOR UPDATE` | 12.2.4 | 100 | 0 | 0 | 694 ms | 200 |
> | ③ 樂觀鎖 `@Version` | 12.2.5 | 100 | 0 | ⚠️ **879 次** | 633 ms | ⚠️ **1,079** |
> | ✅ ④ `UPDATE … WHERE stock > 0` | 12.2.6 | 100 | 0 | 0 | **148 ms** | 200 |
> | ⑤ Redis 分散式鎖（09 章） | 12.2.7 | 100 | 0 | 0 | ⚠️ **1,011 ms** | 200 |
> | ⑥ Redis 預扣 ＋ DB 落帳 | 12.4 | 100 | 0 | 0 | **48 ms** | **100** |
>
> 📌 **請先看 ④ 和 ⑤。**
> ④ 是**一條 SQL**，它正確、最快（148 ms），而且沒有任何 Redis。
> ⑤ 是你花了一整章 09 寫出來的分散式鎖，它**是六種裡最慢的**（1,011 ms，慢 6.8 倍）。
>
> ⚠️ **如果你只需要「不超賣」，這一章到 12.2.6 就可以結束了。**
>
> 那 Redis 預扣（⑥）買到了什麼？把人數從 200 加到 **2000**（真正的秒殺）就看得出來：
>
> | | 訂單 | **DB 查詢** | 白跑的查詢 |
> |---|---|---|---|
> | ④ `UPDATE … WHERE stock > 0` | 100 | **2,000** | **1,900（95%）** |
> | ⑥ Redis 預扣 | 100 | **100** | **0** |
>
> **它買的不是正確性，是「讓 95% 注定失敗的請求連資料庫都碰不到」。**
> 這一章其餘的部分，就是這個交易的代價：**對不上帳的時候要怎麼補回來**（12.5）。

## 12.1 學習目標

完成本章後，你應該可以：

- 從零寫出四種資料庫層的防超賣方案，並說出各自的吞吐量與代價（12.2）。
- 說出為什麼 ⚠️ **分散式鎖是六種方案裡最慢的**，以及什麼時候它才是對的選擇（12.2.7）。
- 判斷你的場景**需不需要** Redis 預扣，而不是預設要（12.3）。
- 寫出 `deduct-stock.lua`，並說出它為什麼要有**三種**回傳值而不是兩種（12.4.2）。
- 設計「Redis 預扣 ＋ 資料庫落帳」的補償，並實測出**沒有補償時有多少庫存賣不出去**（12.5）。
- 用 Redis 做原子計數與排行榜，並算出它們的記憶體與延遲成本（12.6、12.7）。
- ⚠️ 說出 **hot key 的分桶在單機 Redis 上買不到吞吐量**，它真正解決的是什麼（12.8）。
- 說出分桶會帶來的新問題（**明明有貨卻買不到**），並用一段 Lua 修掉它（12.8.4、12.8.5）。

## 12.2 三種防超賣方案，從零寫一次

### 12.2.1 實驗設定

```
商品 1，庫存 100 件
200 個執行緒同時進來，每人買 1 件
臨界區（讀→想→寫之間）5 毫秒
資料庫：H2（in-memory），預設 READ COMMITTED
```

⚠️ **H2 在記憶體裡，所以「資料庫很快」。** 換成真的 MySQL 之後，
下面每一個「資料庫方案」的耗時都會拉長，而 ⑥ 的優勢會更明顯（12.3.2 會再談）。

### 12.2.2 實測

```
═══ 12.2.2 三種防超賣方案：200 個人搶 100 件（臨界區 5ms） ═══
  方案                     | 訂單 | 剩餘 | 超賣 | 例外/重試 | 耗時    | DB 查詢
  -------------------------+------+------+------+-----------+---------+--------
  ① 沒有保護                 |  200 |   79 |  179 |         0 |   158 ms |    200
  ② 悲觀鎖 FOR UPDATE        |  100 |    0 |    0 |         0 |   694 ms |    200
  ③ 樂觀鎖 @Version          |  100 |    0 |    0 |       879 |   633 ms |   1079
  ④ UPDATE…WHERE stock>0    |  100 |    0 |    0 |         0 |   148 ms |    200
  ⑤ Redis 分散式鎖（09章）    |  100 |    0 |    0 |         0 | 1,011 ms |    200
  ⑥ Redis 預扣 + DB 落帳     |  100 |    0 |    0 |         0 |    48 ms |    100
```

（跑三次：① 超賣 179、180、180 件；③ 重試 879、873、873 次；其餘完全一致。
**除了 ① 以外，每一列都穩定到可以當驗收條件。**）

### 12.2.3 ① 沒有保護

```java
@Transactional
public boolean buyNoGuard(Long id, String user, long gap) {
    Product p = em.find(Product.class, id);       // 讀
    if (p.getStock() <= 0) return false;          // 想
    StockService.sleep(gap);
    p.setStock(p.getStock() - 1);                 // 寫
    orders.save(new OrderRow(id, user));
    return true;
}
```

**200 張訂單，庫存剩 79，超賣 179 件。**

> 📌 **注意「庫存剩 79」**，不是 0，也不是 -100。
> 200 次扣減只有 21 次生效——09 章 9.2.3 那個 lost update 的完整版本。
>
> ⚠️ **它包在 `@Transactional` 裡面。** 很多人以為「有交易就不會有這個問題」——
> **交易保證的是原子性與隔離性，不是「不會有人跟你搶」。**
> READ COMMITTED 之下，兩個交易讀到同一個 100 是完全合法的。

### 12.2.4 ② 悲觀鎖

```java
@Transactional
public boolean buyPessimistic(Long id, String user, long gap) {
    Product p = em.find(Product.class, id, LockModeType.PESSIMISTIC_WRITE);   // SELECT … FOR UPDATE
    ...
}
```

**正確，0 超賣，694 ms。**

```
  200 個請求 × 5 毫秒臨界區 = 1,000 毫秒的理論下限
  實測 694 毫秒 ← 因為有些請求在 stock 歸零後直接 return（沒有走完 5 毫秒）
```

| ✅ | ⚠️ |
|---|---|
| 邏輯最直觀，跟單機 `synchronized` 一樣 | **資料庫的連線被佔住整個臨界區** |
| 不用重試 | 臨界區裡有外部呼叫的話，**連線池會先爆**（08 章 8.4.1） |
| | ⚠️ **鎖的範圍是「這一列」**，而它是跨服務有效的——這點比 Redis 鎖強 |

> ⚠️ **悲觀鎖最大的風險不是慢，是「臨界區裡不小心放了慢東西」。**
> `SELECT … FOR UPDATE` 之後如果去呼叫了一個外部 API，
> **那個 API 的 p99 就變成你資料庫連線的持有時間。**

### 12.2.5 ③ 樂觀鎖：879 次重試

```java
@Transactional
public boolean buyOptimisticOnce(Long id, String user, long gap) {
    ProductV p = em.find(ProductV.class, id);     // @Version 欄位
    ...
    em.flush();                                    // ⚠️ 要在這裡 flush，衝突才會在方法內丟出來
    return true;
}

// 呼叫端
for (int attempt = 0; attempt < 50; attempt++) {
    try { return dao.buyOptimisticOnce(id, user, gap); }
    catch (ObjectOptimisticLockingFailureException e) {
        retries.incrementAndGet();
        Thread.sleep(1 + random(5));               // ⚠️ 一定要有抖動
    }
}
```

**正確，但 200 次購買花了 879 次重試、1,079 次資料庫查詢（5.4 倍）。**

> ⚠️ **這是 05 章 5.5.3 那個 `WATCH` 重試風暴的資料庫版本。**
>
> 📌 **樂觀鎖的適用條件是「衝突很少」**，而**秒殺的定義就是「衝突很多」**。
> 200 個人搶同一列 = 每個人平均要重試 4.4 次。
> **把人數加到 2000，重試次數會非線性地爆炸。**
>
> ⚠️ 另外注意 `em.flush()` 那一行：不寫的話，衝突會在**交易提交時**才丟出來，
> 那時候已經在你的 `try` 區塊外面了——**`catch` 抓不到，重試邏輯整段失效。**

### 12.2.6 ✅ ④ 條件更新：一條 SQL

```java
@Transactional
public boolean buyConditionalUpdate(Long id, String user, long gap) {
    int updated = em.createQuery(
            "update Product p set p.stock = p.stock - 1 where p.id = :id and p.stock > 0")
            .setParameter("id", id).executeUpdate();
    if (updated == 0) return false;            // ← 沒扣到 ＝ 沒貨了
    orders.save(new OrderRow(id, user));
    return true;
}
```

**正確、0 重試、148 ms——跟「完全沒有保護」的 158 ms 一樣快。**

> 📌 **為什麼它是對的**：
> `UPDATE … WHERE stock > 0` 是**單一 SQL 語句**，資料庫會在那一列上加行鎖，
> **「讀」與「寫」在同一個語句裡，中間沒有縫。**
>
> 這就是 05 章 5.2「原子」那個定義在關聯式資料庫的版本：
> **不要讀出來再寫回去，要讓資料庫自己算。**
>
> ✅ **`updated == 0` 就是「賣完了」**——不需要另外查一次庫存。

> ⚠️ **這一段是這一章最重要的十行程式碼。**
> 後面所有的 Redis 技巧，都是建立在「**這一行仍然在**」的前提上。
> **它是最後一道防線，不能被 Redis 取代，只能被 Redis 保護。**

### 12.2.7 ⚠️ ⑤ 分散式鎖為什麼最慢

```java
locks.execute("lock:product:1", Duration.ofSeconds(60),
        () -> dao.buyNoGuard(PID, "u" + n, GAP));       // 09 章的 LockTemplate
```

**1,011 ms——六種裡最慢，比條件更新慢 6.8 倍。**

```
每一次購買要付的成本：
  ① 取鎖        → 1 次 Redis round-trip（競爭時還有 pub/sub 等待）
  ② 業務        → 1 次資料庫 round-trip
  ③ 釋放鎖      → 1 次 Redis round-trip（EVALSHA）
  ④ watchdog    → 背景每 10 秒一次 PEXPIRE
      └── 而這一切，只是為了做到資料庫用一條 SQL 就能做到的事
```

> ⚠️ **「用 Redis 分散式鎖防超賣」是一個很常見、但通常是錯的設計。**
>
> 📌 **什麼時候分散式鎖才是對的**（09 章 9.2.4 說過）：
> **當你要保護的東西不在資料庫裡的時候。**
>
> | 要保護的事 | 用什麼 |
> |---|---|
> | 同一列資料不能被同時改 | ✅ **資料庫**（④ 或 ②） |
> | 同一個排程不能跑兩次 | ✅ 分散式鎖 |
> | 同一封信不能寄兩次 | ✅ 分散式鎖 ＋ 冪等（10 章） |
> | 同一個檔案不能同時被兩台機器寫 | ✅ 分散式鎖 |
> | **扣庫存** | ❌ **不要用鎖**——用 ④ |

### 12.2.8 決策表

| | ② 悲觀鎖 | ③ 樂觀鎖 | ✅ ④ 條件更新 | ⑥ Redis 預扣 |
|---|---|---|---|---|
| 正確性 | ✅ | ✅ | ✅ | ✅（**靠的還是 ④**） |
| 衝突多的時候 | 排隊，穩定 | ⚠️ **重試風暴** | 排隊，穩定 | ✅ 大部分請求不進資料庫 |
| 資料庫負載 | 200 | ⚠️ **1,079** | 200 | **100** |
| 實作複雜度 | 低 | 中（要重試 ＋ 抖動） | **最低** | ⚠️ **高**（要對帳、補償） |
| 能表達「扣 3 件」 | ✅ | ✅ | ✅ `stock >= 3` | ✅ |
| 能表達複雜規則（限購、優惠） | ✅ | ✅ | ⚠️ 塞不進一條 SQL | ✅（Lua 裡寫） |
| **建議** | 臨界區裡有多張表要一起改 | ❌ **秒殺不要用** | **預設選這個** | 只在流量遠大於庫存時 |

## 12.3 那 Redis 預扣要解決什麼

### 12.3.1 ④ 已經是對的了

**是的。所以如果你的流量沒有大到讓資料庫喘不過氣，這一章可以在這裡結束。**

⚠️ **不要因為「秒殺」兩個字就上 Redis 預扣。** 它帶來的是：

- 兩份庫存資料要對得起來（12.5）。
- 一條補償路徑要寫、要測、要監控。
- 一個「Redis 掛了怎麼辦」的問題（08 章 8.8 說它**不能降級**）。

### 12.3.2 實測：2000 個人搶 100 件

把人數乘以 10，這才是秒殺的形狀（**95% 的人注定買不到**）：

```
═══ 12.3.2 真正的秒殺：2000 個人搶 100 件 ═══
  方案                     | 訂單 | 超賣 | 耗時     | DB 查詢 | 白跑的 DB 查詢
  -------------------------+------+------+----------+---------+---------------
  ④ UPDATE…WHERE stock>0   |  100 |    0 |   261 ms |   2,000 | 1,900（95%）
  ⑥ Redis 預扣 + DB 落帳    |  100 |    0 |   302 ms |     100 | 0（0%）
     Redis 擋下了 1900 個請求，它們一次資料庫都沒碰到
```

> ⚠️ **注意耗時是差不多的（261 vs 302 毫秒），而且 ⑥ 還略慢一點。**
>
> **這是誠實的數字**：實驗用的是記憶體裡的 H2，一次 `UPDATE` 只要幾十微秒，
> **所以「少查 1,900 次資料庫」在這台機器上省不到時間。**
>
> 📌 **請換算到你自己的環境**：
>
> ```
>              H2（本實驗）      真實 MySQL（同機）    真實 MySQL（跨網路）
>  一次 UPDATE   ~0.05 ms          ~1 ms                ~3 ms
>  1,900 次      ~95 ms            ~1.9 秒              ~5.7 秒
>                                     ↑
>                    而這 1,900 次全部是白跑的，還會佔住連線池
> ```
>
> **Redis 預扣真正的價值不在延遲，在於「保護資料庫的連線池與磁碟」**——
> 那 1,900 次在真實環境裡會變成 1,900 次行鎖競爭、1,900 次 redo log 寫入。

### 12.3.3 它的本質：一道便宜的門

```
  2000 個請求
       │
       ▼
  ┌──────────────┐
  │ Redis 預扣    │  ← 一次 EVALSHA，~0.1 ms，不碰磁碟
  └───┬──────┬───┘
      │      │
  100 個   1,900 個 ──▶ 直接回「已售完」（⚠️ 連資料庫都不用碰）
      │
      ▼
  ┌──────────────┐
  │ 資料庫落帳    │  ← ④ 那條 UPDATE…WHERE stock>0 還在
  └──────────────┘        └── 它才是保證不超賣的那個
```

> 📌 **一句話**：
> **Redis 預扣是一個「過濾器」，不是一個「帳本」。**
> 帳本永遠是資料庫。**忘記這件事，就會寫出 12.5.3 那種賣不出去的庫存。**

## 12.4 Redis 預扣庫存

### 12.4.1 `deduct-stock.lua`

```lua
-- scripts/deduct-stock.lua
-- KEYS[1] = stock:<商品>，ARGV[1] = 要扣幾個
-- 回傳 {結果, 扣完之後剩幾個}
--   結果  1 = 扣成功
--        0 = 庫存不足
--       -1 = 這個 key 還沒初始化（⚠️ 一定要跟「庫存 0」分開）
local current = redis.call('GET', KEYS[1])
if current == false then
    return {-1, 0}
end
local stock = tonumber(current)
local want  = tonumber(ARGV[1])
if stock < want then
    return {0, stock}
end
local left = redis.call('DECRBY', KEYS[1], want)
return {1, left}
```

```java
public Deduction deduct(Long productId, int count) {
    List<?> r = redis.execute(deduct, List.of(key(productId)), String.valueOf(count));
    long code = ((Number) r.get(0)).longValue();
    ...
}
```

### 12.4.2 ⚠️ 三種回傳值，不是兩種

**這是這一節最容易被省略、而且省略之後最痛的一行：**

```lua
if current == false then
    return {-1, 0}          -- key 不存在
end
```

```
  key 不存在  ≠  庫存是 0
       │              │
       │              └─ 正確行為：回「已售完」
       └─ 正確行為：⚠️ 回「系統還沒準備好」，而且要告警
```

**為什麼會不存在**：

| 情況 | 後果（如果當成「庫存 0」） |
|---|---|
| Redis 重開過、資料沒了（04 章） | **整個商品永遠賣不出去**，而且沒有任何錯誤 |
| `maxmemory` 把它驅逐了（11 章 11.6.4） | 同上 |
| 新商品上架，忘了灌庫存 | 上架當天完全沒有訂單 |
| ⚠️ **打錯 key 的前綴** | 同上，而且查很久 |

> ⚠️ **如果不分辨，用一個 `DECR` 就搞定了**：
> ```java
> // ⚠️ 錯的
> Long left = redis.opsForValue().decrement(key);
> if (left < 0) { redis.opsForValue().increment(key); return SOLD_OUT; }
> ```
> `DECR` 在 key 不存在時會**當作 0 開始扣**，得到 `-1`——
> 於是你把「Redis 資料掉了」誤判成「賣完了」。
>
> 📌 **`NOT_LOADED` 這個狀態必須回 503 並且告警，不可以回「已售完」。**
> 這跟 10.11 的原則一樣：**它是正確性機制，不可以靜默降級。**

### 12.4.3 庫存怎麼灌進去

```java
/** ⚠️ 只有這裡可以用 SET。 */
public void load(Long productId, int stock) {
    redis.opsForValue().set(key(productId), String.valueOf(stock));
}
```

⚠️ **「只有這裡可以用 `SET`」不是一句客套話**：
業務程式碼裡任何一個 `SET stock:*`，都會**把正在進行中的預扣結果整個洗掉**
（01 章 1.6 那個「`SET` 會清掉 TTL」的加強版——這裡是清掉庫存）。

**補貨要用 `INCRBY`，不要用 `SET`**：

```java
// ✅ 補 50 件
redis.opsForValue().increment(key(productId), 50);

// ⚠️ 錯的：如果這個瞬間有人正在預扣，他扣的那一個就消失了
redis.opsForValue().set(key(productId), String.valueOf(currentDbStock + 50));
```

📌 **灌庫存的時機有三種，各有取捨：**

| 時機 | ⚠️ |
|---|---|
| 應用啟動時全部灌 | ⚠️ 多實例會**互相覆蓋**（要加分散式鎖，09 章）；商品多的話啟動很慢 |
| 活動開始前由排程灌一次 | ✅ 最常見。⚠️ **要確認灌完了才開放流量**（08 章 8.6 的 readiness） |
| 第一次被查詢時 lazy 灌 | ⚠️ **就是 07 章的快取擊穿**——要用鎖或 `SETNX` |

**lazy 灌的正確寫法**（只有不存在時才寫）：

```java
redis.opsForValue().setIfAbsent(key(productId), String.valueOf(dbStock));   // SET NX
```

## 12.5 對不上帳的時候

### 12.5.1 中間會斷在哪裡

```
  ① Redis 預扣 ──✅──▶ ② 資料庫落帳 ──✅──▶ ③ 回應使用者
        │                    │
        │                    └─ ⚠️ 這裡失敗（逾時、死鎖、連線斷、服務被 kill）
        │                          → Redis 少了一件，資料庫沒少
        │
        └─ ⚠️ 這裡逾時（09 章 9.11.2：逾時不代表沒執行）
              → 你不知道到底扣了沒有
```

### 12.5.2 實測：有回補

30% 的落帳會丟例外（模擬逾時／死鎖／連線斷），資料庫與 Redis 各 100 件，200 個人來搶：

```java
RedisStock.Deduction d = redisStock.deduct(PID, 1);
if (d.result() != RedisStock.Result.OK) return false;
try {
    return dao.settleFlaky(PID, "u" + n, 0.3);
} catch (RuntimeException e) {
    redisStock.giveBack(PID, 1);          // ⚠️ 補償
    return false;
}
```

```
═══ 12.5.2 落帳會失敗：30% 的 settle 丟例外（逾時／死鎖／連線斷） ═══
  資料庫 100 件、Redis 100 件，200 個人來搶
  ✅ 有回補     訂單  74 張｜落帳失敗 31 次｜回補 31 次
               資料庫剩  26｜Redis 剩  26｜差距 0
```

**兩邊剛好對上（26 = 26）。**

### 12.5.3 ⚠️ 實測：沒有回補

```
═══ 12.5.3 ⚠️ 一模一樣，但沒有回補 ═══
  ⚠️ 沒有回補   訂單  79 張｜落帳失敗 21 次｜回補  0 次
               資料庫剩  21｜Redis 剩   0｜差距 21
               ⚠️ 有 21 件商品資料庫裡還有，但 Redis 說沒了 —— 賣不出去
```

> ⚠️ **21 件庫存從此賣不出去，而且：**
>
> - **沒有任何錯誤**——Redis 誠實地回「已售完」。
> - **沒有超賣**——正確性沒有被破壞。
> - **只有營運會發現**：「這款為什麼還有 21 件卻顯示完售？」
>
> 📌 **這就是「多一份資料」的代價。**
> 兩份資料一定會不一致，問題只是**你有沒有一條路把它們拉回來**。

### 12.5.4 ⚠️ 回補本身也會失敗

```java
catch (RuntimeException e) {
    redisStock.giveBack(PID, 1);      // ⚠️ 如果這一行也失敗呢？
}
```

**Redis 掛掉的時候，回補一定會失敗**——而且失敗的正是「需要回補」的那些請求。

所以**回補不能是唯一的機制**，它只是「快的那一條路」。必須有第二條：

```
  ① 立即回補（99% 的情況）── 便宜、即時，但不可靠
  ② 對帳任務（兜底）      ── 慢，但一定會跑到
```

### 12.5.5 對帳任務

```java
@Scheduled(fixedDelay = 60_000)
public void reconcile() {
    for (Long productId : activeProductIds()) {
        int dbStock    = inventoryDao.stock(productId);         // 真相
        long redisStock = redis.current(productId);

        if (redisStock < 0) {                                    // ⚠️ NOT_LOADED
            log.error("Redis 庫存不存在 productId={}", productId);
            alert(); continue;
        }
        if (dbStock == redisStock) continue;

        if (dbStock > redisStock) {
            // Redis 少了 → 有預扣沒落帳（12.5.3）→ 補回去
            log.warn("庫存不一致 productId={} db={} redis={} 差={}",
                     productId, dbStock, redisStock, dbStock - redisStock);
            redis.giveBack(productId, (int) (dbStock - redisStock));
        } else {
            // ⚠️ Redis 比資料庫多 → 這是危險的方向，會超賣
            log.error("⚠️ Redis 庫存大於資料庫 productId={} db={} redis={}",
                      productId, dbStock, redisStock);
            alert();                       // 不要自動修，先叫人
        }
    }
}
```

> ⚠️ **兩個方向的處理必須不一樣**：
>
> | | 意思 | 風險 | 怎麼處理 |
> |---|---|---|---|
> | **DB > Redis** | 有預扣沒落帳 | **賣不出去**（少賺） | ✅ 可以自動補回 |
> | **Redis > DB** | ⚠️ 有落帳沒扣 Redis，或有人 `SET` 過 | **會超賣**（賠錢） | ⚠️ **不要自動修，先告警** |
>
> 📌 **為什麼 `Redis > DB` 不能自動修**：
> 你不知道差額是「哪裡漏了」還是「有人剛補貨但排程還沒跑」。
> 自動把 Redis 調低，可能會把剛補的貨吃掉。
>
> ✅ **但它其實不會造成超賣**——因為 12.2.6 那條 `UPDATE … WHERE stock > 0` 還在。
> **最壞的情況是「Redis 放行了，資料庫拒絕了」，使用者收到「已售完」。**
> **這就是為什麼那條 SQL 不能拿掉。**

### 12.5.6 ⚠️ 冪等是必要條件，不是加分項

```
  客戶端逾時 ──▶ 重試 ──▶ 又預扣一次 ──▶ 又落帳一次
                              ↑              ↑
                        Redis 少 2 件    2 張訂單
```

**10 章的冪等鍵在這裡不是選配**：

```java
public Order seckill(Long productId, String userId, String idempotencyKey) {
    return idem.execute(idempotencyKey, fingerprint, () -> {     // ① 冪等（10 章）
        RedisStock.Deduction d = redisStock.deduct(productId, 1); // ② 預扣
        if (d.result() == NOT_LOADED) throw new ServiceUnavailable();
        if (d.result() == SOLD_OUT)   throw new SoldOutException();
        try {
            return dao.settle(productId, userId);                 // ③ 落帳（＝ 12.2.6 那條 SQL）
        } catch (RuntimeException e) {
            redisStock.giveBack(productId, 1);                    // ④ 回補
            throw e;
        }
    });
}
```

> 📌 **順序跟 11 章 11.12 那張圖一致**：
> **冪等鍵 ──▶ 預扣 ──▶ 交易**。
> ⚠️ 冪等鍵在最外面，因為「要不要做」這件事必須先決定。

⚠️ **還有一個細節**：10.9.6 說過「業務錯誤要記成 `DONE`」。
「已售完」是業務錯誤——**要記下來**，不然使用者的每一次重試都會再預扣一次。

## 12.6 原子計數

### 12.6.1 實測：14 倍

```
═══ 12.6.1 計數：資料庫 vs Redis，20000 次 +1 ═══
  Redis INCR      20,000 次 →   490 ms（40,816 次/秒），結果 = 20000
  資料庫 UPDATE       400 次 →   134 ms（2,985 次/秒）
  📌 差距約 14 倍（而且資料庫那 400 次已經是同一列的熱點寫入）
  Redis 這個 key 佔 56 bytes
```

> 📌 **14 倍還是低估的**，因為：
> - H2 在記憶體裡，沒有 fsync；
> - 資料庫那一側每次 `UPDATE` 都要在同一列上排隊（行鎖）；
> - **這還沒算 binlog / redo log 的寫入。**
>
> **瀏覽數、按讚數、曝光數這類「量大、精度要求低」的計數，不應該進資料庫。**

### 12.6.2 ⚠️ 計數什麼時候會掉

`INCR` 很快，但它是**記憶體裡的數字**：

| 情況 | 掉多少 | 章 |
|---|---|---|
| Redis 正常重啟（有 RDB） | 上次快照之後的全部 | 04 章 |
| Redis 正常重啟（AOF everysec） | **最多 1 秒** | 04 章 |
| `maxmemory` 驅逐 | **整個計數歸零** | 04、11 章 |
| 主從切換 | 未複製到的部分 | 13 章 |

📌 **所以計數要分兩類：**

```
  可以掉的（瀏覽數、曝光數）      ──▶ 只放 Redis，定期落庫當歷史
  不可以掉的（庫存、餘額、抽獎次數）──▶ ⚠️ Redis 只是前置，資料庫才是帳本（12.3.3）
```

**定期落庫的寫法**：

```java
@Scheduled(fixedDelay = 60_000)
public void flushCounters() {
    // ⚠️ 用 GETDEL（Redis 6.2+）而不是 GET + DEL —— 中間那道縫（09 章 9.2.1）
    String delta = redis.opsForValue().getAndDelete("views:delta:" + id);
    if (delta != null) viewDao.addViews(id, Long.parseLong(delta));
}
```

⚠️ **落庫失敗的話那一段增量就消失了**——如果不能接受，就要先寫庫再刪 key（但那樣會重複計數）。
**這是一個「最多算一次」與「最少算一次」的選擇，沒有免費的正確答案。**

### 12.6.3 不用 `INCR` 的兩種計數

| 需求 | 用什麼 | 記憶體 |
|---|---|---|
| **不重複的**訪客數（UV） | **HyperLogLog**（`PFADD` / `PFCOUNT`） | **固定 12 KB**，誤差 0.81% |
| 「這一億個使用者裡誰簽到了」 | **Bitmap**（`SETBIT` / `BITCOUNT`） | 1 億個 bit = **12 MB** |
| 排名 | **ZSet**（12.7） | 每個成員約 82 bytes |

02 章 2.9 已經量過這兩個，這裡只提醒一件事：
⚠️ **HyperLogLog 沒辦法告訴你「誰」來過**，只能給你「幾個」。要名單就得用 Set（然後付出記憶體）。

## 12.7 排行榜

### 12.7.1 實測：10 萬個商品

```java
redis.opsForZSet().incrementScore("rank:sales", "p" + i, count);   // ZINCRBY
redis.opsForZSet().reverseRange("rank:sales", 0, 9);               // ZREVRANGE 0 9
redis.opsForZSet().reverseRank("rank:sales", "p500");              // ZREVRANK
```

```
═══ 12.7.1 排行榜：ZSet 存 10 萬個商品的銷量 ═══
  10 萬次 ZINCRBY → 14,594 ms
  ZCARD        = 100000
  MEMORY USAGE = 8,249,376 bytes（每個成員約 82 bytes）
  OBJECT ENCODING = skiplist
  Java 端：取前 10 名 1000 次     → 平均 0.170 ms
  Java 端：取前 10000 名 100 次   → 平均 2.399 ms  ⚠️ O(log N + M)
  某商品的排名：76111
```

> 📌 **三個數字值得記下來**：
>
> 1. **每個成員 82 bytes**（`skiplist` 編碼，02 章 2.6）。
>    100 萬個商品的排行榜 = **82 MB**；每個使用者一份的話，⚠️ **想都不要想**。
> 2. **取前 10 名 0.17 毫秒，取前 10000 名 2.4 毫秒**——`M` 是線性的（03 章 3.5）。
> 3. ⚠️ **10 萬次 `ZINCRBY` 花了 14.6 秒**（每次 0.146 毫秒）。
>    **那不是 Redis 慢，那是 10 萬次網路往返**（03 章 3.8）——
>    用 pipeline 打包的話會快一個數量級。

### 12.7.2 ⚠️ 三個實務問題

**① 取「第 50000 ～ 50010 名」很便宜，但取「前 10000 名」很貴**

```
ZREVRANGE key 50000 50010   → O(log N + 11)     ✅
ZREVRANGE key 0 9999        → O(log N + 10000)  ⚠️ 2.4 毫秒，而且是在單執行緒上
```

⚠️ **排行榜頁面的「載入全部」按鈕，就是一次 O(N) 命令**（03 章 3.5 的清單）。

**② 同分怎麼辦**

ZSet 同分時按 member 的字典序排。要「同分時先達成的排前面」：

```java
// score = 銷量 * 10^10 + (10^10 - 時間戳秒數)
double score = sales * 1e10 + (1e10 - epochSeconds);
```

⚠️ **`double` 只有 53 bits 的精度**（約 9×10¹⁵）。上面這個組法已經逼近上限了——
**再多塞一個維度就會開始掉精度，而且不會報錯。**

**③ 時間窗排行榜（「今日熱銷」）**

```
rank:sales:2026-09-18       ← 每天一個 key
  └─ EXPIRE 7 天
"最近 7 天" = ZUNIONSTORE 把 7 個 key 併起來
```

⚠️ `ZUNIONSTORE` 是 **O(N)**（N ＝ 所有輸入集合的元素總數）。
**7 個 10 萬成員的 ZSet 併起來就是 70 萬個元素的操作，跑在單執行緒上**——
**要放排程算好存起來，不要在請求路徑上算。**

## 12.8 hot key

### 12.8.1 什麼叫 hot key

```
一般的 key：  幾十 QPS，分散在幾十萬個 key 上
hot key：    一個 key 吃掉整台 Redis 相當比例的流量
                 └─ 秒殺商品的庫存、首頁的推薦位、當紅直播間的計數
```

### 12.8.2 ⚠️ 實測：單機上分桶買不到吞吐量

把一個庫存拆成 10 個、100 個桶，再打同樣的 10 萬次 `DECR`：

```
═══ 12.8.2 同一個 key vs 分成 10 個桶：單機 Redis 上的吞吐量 ═══
    1 個桶 → 100,000 次 DECR，  955 ms（104,712 次/秒）
   10 個桶 → 100,000 次 DECR，  847 ms（118,064 次/秒）
  100 個桶 → 100,000 次 DECR，  860 ms（116,279 次/秒）
```

> ⚠️ **幾乎沒有差別（10 萬 vs 11.8 萬，13%）。**
>
> 📌 **原因在 03 章第一頁就說過了：Redis 是單執行緒的。**
> 不管你打在 1 個 key 還是 100 個 key 上，**命令都排在同一條佇列裡**。
>
> **「拆 key 可以提高吞吐量」在單機 Redis 上是錯的。**

### 12.8.3 那分桶是為了什麼

**三個真正的理由，沒有一個是「單機吞吐量」：**

```
① Cluster：不同的桶落在不同的 slot ──▶ 不同的節點 ──▶ 真的並行了（13 章）
② 一個 key 的大小：把一個超大的 Hash / ZSet 拆小（02、03 章的 big key）
③ 熱點分散到多個「副本」：讀多寫少時，把同一份資料複製成 N 份，讀取隨機挑一份
```

⚠️ **①、②、③ 在你**沒有** Cluster、value 又只是一個數字的時候，全部不成立。**

📌 **一個很實際的判斷**：
先量一次 `redis-cli --stat` 裡的 `ops/sec` 跟 `INFO stats` 的 `instantaneous_ops_per_sec`。
**如果離 10 萬還很遠，你的問題不是 hot key。**

### 12.8.4 ⚠️ 分桶的代價：明明還有貨，卻買不到

100 件庫存分成 N 個桶，**剛好 100 個人**來搶，每個人隨機挑一個桶：

```
═══ 12.8.4 ⚠️ 分桶的代價：「明明還有貨，卻買不到」 ═══
   1 個桶（每桶 100 件）→ 賣掉 100 件，  0 個人被拒絕，其中   0 個「其實還有貨」，最後剩  0 件
  10 個桶（每桶 10 件）→ 賣掉  91 件，  9 個人被拒絕，其中   9 個「其實還有貨」，最後剩  9 件
  20 個桶（每桶  5 件）→ 賣掉  82 件， 18 個人被拒絕，其中  18 個「其實還有貨」，最後剩 18 件
```

> ⚠️ **20 個桶的時候，18% 的庫存賣不掉，而且 18 個人被告知「已售完」。**
>
> 📌 **這是生日問題的變形**：隨機分配下，有些桶會先空、有些桶還滿著。
> **桶越多，這個現象越嚴重。**
>
> **而它在正式環境的形狀是**：
> 活動結束後庫存顯示還有貨，客服收到「明明有貨為什麼說完售」，
> 而**技術上完全沒有錯誤**。

### 12.8.5 修法：一段 Lua 掃過所有桶

```lua
-- scripts/deduct-bucket.lua
-- KEYS = 所有的桶，ARGV[1] = 從第幾個桶開始（1-based）
local start = tonumber(ARGV[1])
local n = #KEYS
for i = 0, n - 1 do
    local idx = ((start - 1 + i) % n) + 1
    local v = redis.call('GET', KEYS[idx])
    if v ~= false and tonumber(v) > 0 then
        redis.call('DECR', KEYS[idx])
        return {1, idx, i + 1}
    end
end
return {0, 0, n}
```

```
═══ 12.8.5 修法：一段 Lua 掃過所有的桶 ═══
  10 個桶 → 賣掉 100 件，剩 0 件；「第幾個桶才拿到」的分布 = {1=89, 2=7, 3=3, 6=1}
  20 個桶 → 賣掉 100 件，剩 0 件；「第幾個桶才拿到」的分布 = {1=80, 2=6, 3=3, 4=2, 5=1, 6=2, 7=1, 8=1, 9=1, 13=1, 16=1, 19=1}
```

**100 件全部賣完，一件都沒剩。**

> 📌 **「第幾個桶才拿到」的分布很重要**：
> 10 個桶時 89% 的人第一次就拿到；20 個桶時 80%。
> **少數人要掃過十幾個桶**——那是一次 O(桶數) 的 Lua（05 章 5.8.3：腳本要短）。
>
> ⚠️ **所以桶數不能大**。實務上 **8 ～ 16 個**就夠了，
> 而且 ⚠️ **在 Cluster 上這段 Lua 會直接回 `CROSSSLOT`**（05 章 5.6.2、13 章）——
> 要用 hash tag `stock:{1234}:0` ～ `stock:{1234}:9` 把它們綁在同一個 slot，
> **但那樣它們就在同一個節點上，12.8.3 的理由 ① 又沒了。**
>
> **這是一個真的很難兩全的地方，而大部分服務根本不需要走到這一步。**

### 12.8.6 ⚠️ 怎麼找出 hot key（工具沒有你想的好用）

**`redis-cli --hotkeys`**（需要 `maxmemory-policy` 設成 `allkeys-lfu`）：

```
  ① OBJECT FREQ
     stock:hot    FREQ=15        ← 被存取 300 次
     stock:1      FREQ=15        ← 被存取 5 次
     stock:2      FREQ=15        ← 沒被存取過

  ② redis-cli --hotkeys
     hot key found with counter: 15   keyname: "stock:2"
     hot key found with counter: 15   keyname: "stock:hot"
     hot key found with counter: 15   keyname: "stock:1"
     hot key found with counter: 15   keyname: "stock:3"
```

> ⚠️ **它完全分不出來。** 這不是實驗做壞了，是 LFU 計數器的性質：
>
> - 它是**對數的**（`lfu-log-factor` 預設 10），從 5 漲到 15 很快，之後就很難再動；
> - 它會**衰減**（`lfu-decay-time` 預設 1 分鐘）；
> - 上限是 **255**，高流量下所有熱 key 都會頂到 255；
> - `--hotkeys` 是**抽樣**的，而且需要 `SCAN` 整個 keyspace。
>
> 📌 **`OBJECT FREQ` 是給淘汰演算法用的，不是給你做效能分析用的。**

**真正能用的四個方法**：

| 方法 | 怎麼做 | ⚠️ |
|---|---|---|
| ✅ **應用端埋點** | 在你的 `RedisTemplate` 外面包一層，用 key 前綴分組計數 | **最可靠**，而且你本來就需要這些指標 |
| `redis-cli --stat` | 看整體 `ops/sec`，先確認「真的是 Redis 的問題」 | 看不到是哪個 key |
| `MONITOR` 抽樣 | 開幾秒鐘，把輸出丟去統計 | ⚠️ **會讓 Redis 明顯變慢**，正式環境只能開幾秒 |
| Proxy / Cluster 那一層 | 很多雲端 Redis 有 per-key 的熱點分析 | 看你用的是什麼 |

```java
// ✅ 應用端埋點：把 key 收斂成「模板」再計數
private String template(String key) {
    return key.replaceAll("\\d+", "*");       // stock:1234 → stock:*
}
meter.counter("redis.ops", "key", template(key)).increment();
```

### 12.8.7 最後一招：本地快取

**如果那個 hot key 是「讀多寫少」的**（例如活動設定、首頁推薦），
08 章 8.5.3 的本地快取就是答案：**它把 Redis 的 QPS 直接降到 0**。

⚠️ **但庫存不行**——本地快取的庫存數字會是**過期的**，而那正是超賣的來源。

```
  讀多寫少（設定、推薦、商品資訊）──▶ ✅ 本地快取（08 章 8.5.3）
  寫多（庫存、計數、鎖）          ──▶ ❌ 不能快取，只能想辦法少打
```

## 12.9 落地：shop-service 的秒殺流程

### 12.9.1 完整的一條路

```java
public Order seckill(Long productId, String userId, String idempotencyKey) {
    // ① 冪等（10 章）——最外層：「要不要做」先決定
    return idem.execute(idempotencyKey, fingerprint(productId, userId), () -> {

        // ② 限流（10 章）——每個使用者每秒 1 次，擋住連點
        if (!limiter.tokenBucket("seckill:" + userId, 1, 1, now(), 1).allowed())
            throw new TooManyRequestsException();

        // ③ Redis 預扣（12.4）——把 95% 注定失敗的請求擋在資料庫外面
        var d = redisStock.deduct(productId, 1);
        if (d.result() == NOT_LOADED) { alert(); throw new ServiceUnavailableException(); }
        if (d.result() == SOLD_OUT)   throw new SoldOutException();

        // ④ 資料庫落帳（12.2.6）——⚠️ 真正保證不超賣的是這一行
        try {
            Order order = orderDao.settle(productId, userId);
            if (order == null) {                      // 資料庫說沒貨了 → Redis 多算了
                log.error("Redis 放行但資料庫拒絕 productId={}", productId);
                throw new SoldOutException();         // ⚠️ 不回補：資料庫本來就沒有
            }
            return order;
        } catch (RuntimeException e) {
            redisStock.giveBack(productId, 1);        // ⑤ 回補（12.5.2）
            throw e;
        }
    });
}
```

⚠️ **請注意 ④ 裡面那個 `order == null` 的分支不回補**：
資料庫回 0 代表「資料庫真的沒貨了」，Redis 的那一件本來就是多出來的。
**回補它等於把一個不存在的庫存放回去，下一個人還是會失敗。**

### 12.9.3 三條規約（接續 11 章 11.12.2 的第 32 條）

33. ⚠️ **`UPDATE … WHERE stock > 0` 永遠不可以被拿掉。**
    Redis 預扣是過濾器，資料庫是帳本（12.3.3）。
    **code review 時看到「因為有 Redis 預扣了所以不用判斷」就直接退回。**
34. **`stock:*` 這個前綴的 key，除了灌庫存那一支程式以外，任何地方都不可以用 `SET`**（12.4.3）。
    補貨用 `INCRBY`。
35. ⚠️ **預扣的 Lua 必須分辨「庫存 0」與「key 不存在」**，後者要回 503 並告警（12.4.2）。

### 12.9.4 五個該接告警的指標（接續 11 章 11.12.3）

| 指標 | 告警條件 | 代表什麼 |
|---|---|---|
| **`stock.not_loaded`** | **> 0 就告警** | **Redis 庫存不見了**，商品正在「假裝完售」（12.4.2） |
| **`stock.giveback`** | 佔預扣的比例 > 1% | 資料庫落帳一直失敗（12.5.2） |
| **`stock.mismatch`（對帳差額）** | **DB > Redis：> 0 就看**；**Redis > DB：立刻告警** | 12.5.5 那兩個方向 |
| `stock.sold_out_rate` | —— | 看得出活動什麼時候結束、Redis 擋掉多少 |
| **`redis.ops` per key template** | 單一模板 > 總量的 30% | **hot key**（12.8.6） |

## 12.10 常見誤區

**① 「防超賣要用分散式鎖」**

12.2.2 實測：分散式鎖是六種方案裡**最慢的**（1,011 ms vs 148 ms）。
資料庫一條 `UPDATE … WHERE stock > 0` 就夠了，而且更快。

**② 「包在 `@Transactional` 裡就不會超賣」**

12.2.3：包在交易裡照樣超賣 179 件。**交易不保證「沒有人跟你搶」。**

**③ 「樂觀鎖比悲觀鎖好」**

12.2.5：在高競爭下，200 次購買要 **879 次重試、1,079 次資料庫查詢**。
⚠️ **秒殺就是高競爭的定義。**

**④ 「樂觀鎖的 catch 抓得到衝突」**

12.2.5：不寫 `em.flush()` 的話，衝突在**交易提交時**才丟出來——**在 `try` 外面**。

**⑤ 「秒殺一定要上 Redis 預扣」**

12.3.1：它換來兩份要對帳的資料、一條補償路徑、一個不能降級的相依。
**流量沒有遠大於庫存的話，不要上。**

**⑥ 「有了 Redis 預扣，資料庫就不用判斷庫存了」**

⚠️ 12.3.3、12.5.5：**Redis 是過濾器，不是帳本。**
拿掉那條 SQL，任何一次 Redis 資料異常都會變成超賣。

**⑦ 「預扣用 `DECR` 就好」**

12.4.2：`DECR` 分不出「庫存 0」與「key 不存在」。
**Redis 重開之後，你的商品會安靜地永遠賣不出去。**

**⑧ 「補貨用 `SET` 比較直觀」**

12.4.3：`SET` 會把正在進行中的預扣結果洗掉。**補貨用 `INCRBY`。**

**⑨ 「落帳失敗就記個 log 吧」**

12.5.3 實測：**21 件庫存從此賣不出去**，而且沒有任何錯誤。

**⑩ 「有立即回補就不用對帳任務」**

12.5.4：Redis 掛掉時，**需要回補的那些請求正好是回補會失敗的那些**。

**⑪ 「對帳發現不一致就自動修」**

12.5.5：`DB > Redis` 可以自動補；⚠️ **`Redis > DB` 不可以自動修**，要先告警。

**⑫ 「把 key 拆成 10 個桶可以提高 Redis 吞吐量」**

12.8.2 實測：10.5 萬 → 11.8 萬次/秒，**差 13%**。
**Redis 是單執行緒的**（03 章），拆 key 在單機上買不到吞吐量。

**⑬ 「分桶沒有壞處」**

12.8.4：20 個桶時 **18% 的庫存賣不掉**，而且 18 個人被告知「已售完」。

**⑭ 「用 `redis-cli --hotkeys` 找熱點」**

12.8.6：它在實驗裡**完全分不出來**（全部都是 15）。
LFU 計數器是對數的、會衰減、上限 255。**要埋點在應用端。**

**⑮ 「排行榜直接 `ZREVRANGE 0 -1`」**

12.7.2：`ZREVRANGE` 是 **O(log N + M)**，取 1 萬筆要 2.4 毫秒，
**而它跑在那條所有人共用的單執行緒上**（03 章）。

## 12.11 本章小結

**這一章只有一句話：**

> 📌 **能用資料庫一條 SQL 解決的，就不要用 Redis。**
> **Redis 進來的理由只有一個：讓不該碰資料庫的請求碰不到資料庫。**

```
       2000 個請求
            │
    ┌───────▼────────┐
    │ ① 冪等（10章）  │  ← 重試不會變成兩張訂單
    ├────────────────┤
    │ ② 限流（10章）  │  ← 連點不會變成 10 個請求
    ├────────────────┤
    │ ③ Redis 預扣    │  ← ⚠️ 過濾器：擋掉 95%，但它不是帳本
    ├────────────────┤
    │ ④ UPDATE…      │  ← ✅ 帳本：真正保證不超賣的那一行
    │   WHERE stock>0│
    └────────────────┘
            │
    ⑤ 回補 + 對帳（12.5）── 因為 ③ 跟 ④ 一定會不一致
```

**而每一層拿掉之後的症狀都不一樣：**

| 拿掉 | 症狀 | 會被發現嗎 |
|---|---|---|
| ① 冪等 | 重複訂單 | ⚠️ 對帳時才會 |
| ② 限流 | 資料庫被連點打爆 | ✅ 會（延遲上升） |
| ③ 預扣 | 資料庫 QPS × 20 | ✅ 會 |
| **④ 條件更新** | **超賣** | ⚠️ **出貨時才會** |
| **⑤ 回補／對帳** | **賣不出去的庫存** | ❌ **只有營運會發現** |
