# 13 — 服務拆分與分散式一致性（進階 / 選修）

> **這一站在 capstone 之後，不是之前。** 因為它的教材就是你在 [12-capstone](../12-capstone/) 做出來的那個單體 ——
> 沒有那個單體，「拆分」是紙上談兵；有了它，每一刀切下去都會痛在具體的地方。

> **這一站不叫「Spring Cloud」，是刻意的。**
> Spring Cloud 是**一組答案**，而這一站要教的是**問題**：該不該拆、以什麼邊界拆、資料庫怎麼辦、跨服務的交易怎麼收尾。
> 同一個問題在 K8s 原生生態（Service DNS + ConfigMap + Ingress + Istio）也有一套答案，而多數團隊實際上是兩邊混著用。
> 所以工具選型放在第 08 章，用決策表的方式呈現 —— 沿用 [03-rest-api](../03-rest-api/) 與框架無關、[08-jpa-mybatis](../08-jpa-mybatis/) 兩種哲學對照的做法。

> ⚠️ **這一站有一半的篇幅在說服你不要拆。** 這不是反串。
> 絕大多數團隊的正解是「模組化單體 + 一兩個真的需要獨立擴縮的服務」，而不是十五個微服務。
> 課程會給你判斷的依據，而不是一條「大家都這樣做」的路。

---

## 學完你可以

- 用具體指標（而非「感覺變大了」）判斷一個系統該不該拆，並說出拆分的**四項代價**。
- 從模組化單體切出服務邊界：先拆模組、再拆行程，並說明為什麼順序反過來幾乎必然失敗。
- 處理拆分後最痛的那件事 —— **跨服務 JOIN 消失了**：資料所有權怎麼定、報表怎麼做、共享資料庫為什麼是反模式。
- 在同步呼叫、事件、gRPC 之間選擇，並用契約測試守住服務邊界（接 [03-rest-api/09](../03-rest-api/09-api-testing-and-collaboration.md)）。
- 設計 Saga：說出編排（orchestration）與協同（choreography）的差別、寫出補償交易，並知道**哪些操作根本補償不回來**。
- 說明為什麼 [11-messaging](../11-messaging/) 的 Outbox 在單體裡是「有點囉唆」，在拆分之後變成唯一解。
- 用 API 組合或 CQRS 讀模型解決跨服務查詢，並說出讀模型的過時視窗有多長、使用者會看到什麼。
- 把 [05-service/06](../05-service/06-async-and-external-api-calls.md) 的熔斷觀念擴展到整個服務網：級聯故障、重試風暴、逾時預算。
- 讓一個 `traceId` 穿過 HTTP 與 MQ，在出事時三分鐘內指出是哪個服務慢了。
- 為新專案做出有理由的基礎設施選型（Spring Cloud / K8s 原生 / 兩者混用），而不是「公司在用哪個就用哪個」。
- 執行 Strangler Fig 遷移，包含灰度、回滾，以及**把服務合併回單體**的判斷與做法。

## 常見誤區（課程會逐一破解）

- 「系統變大了所以要拆微服務」—— 拆完之後每個改動要協調三個團隊、四次部署。
- 先拆行程、再想模組邊界 —— 邊界切錯就變成分散式單體：所有壞處都有，好處一個都沒有。
- 兩個服務共用同一個資料庫，然後說自己在做微服務。
- 跨服務用 `@Transactional`，或以為 Seata / 兩階段提交能把分散式交易變回本地交易。
- Saga 只寫了正向流程，補償交易「之後再補」—— 上線第一週就出現卡在中間狀態的訂單，沒有人知道怎麼收尾。
- 補償邏輯裡包含「把已寄出的通知信收回來」。
- 每一層都設 3 次重試，五層下去就是 243 倍的流量打在最底層。
- 逾時設定由內而外遞增（外層 3 秒、內層 10 秒），外層早就放棄了內層還在跑。
- 出事時每個服務的 log 都看起來正常，因為沒有 `traceId` 串起來。
- 用了 Spring Cloud Gateway 又用 K8s Ingress，兩套路由規則互相打架，改到能動就不敢再碰。
- 拆完發現不對，卻沒有人敢提「合併回去」—— 因為那聽起來像失敗。

## 產出

拿 [12-capstone](../12-capstone/) 的訂單系統動刀，並附**每一步的量測**：

1. 一份**拆分決策文件**：這個系統該不該拆？如果拆，切在哪、為什麼，以及不拆的版本長什麼樣。兩個方案都要有成本估算。
2. 把庫存拆成獨立服務（含**獨立資料庫**），下單流程改成 Saga，附：
   - 補償交易的完整實作與一份「不可補償操作清單」
   - 一次注入失敗的演練：訂單建立成功、扣庫存失敗，最終狀態怎麼收斂
   - 拆分前後的**下單延遲對照**（p50 / p99）
3. 一份跨服務報表方案：API 組合版與 CQRS 讀模型版各實作一次，附讀模型的過時視窗量測。
4. 一條穿過 Gateway → 訂單 → MQ → 庫存的完整 trace 截圖，以及一次「哪個服務慢了」的排查紀錄。
5. 一份基礎設施選型文件：Spring Cloud 版與 K8s 原生版的對照，說明這個專案選哪個、換過去要付出什麼。
