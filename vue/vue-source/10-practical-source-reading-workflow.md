# 第 10 章：真實專案的源碼閱讀工作流

## 10.1 本章目標

最後一章不再新增知識點，而是把你前九章能力整合成「可重複實戰流程」：

1. 從問題現象快速定位到可能模組
2. 用最小重現案例降低排查成本
3. 沿呼叫鏈追到關鍵分支與資料結構
4. 提出最小修補並做回歸驗證
5. 產出可交付的分析與修正報告

你完成這章後，應該能獨立做一次中小型 Vue 源碼議題分析。

---

## 10.2 實戰框架：5 階段閉環

建議固定使用以下流程：

```text
S1 現象定義
  -> S2 最小重現
  -> S3 呼叫鏈定位
  -> S4 修補與測試
  -> S5 文件化輸出
```

不要跳步。  
多數「查不出來」其實是因為 S1/S2 不夠清楚。

---

## 10.3 S1：現象定義（先把問題描述正確）

一份可用的問題描述至少要包含：

- 輸入條件（資料、模板、互動）
- 預期行為
- 實際行為
- 發生頻率（必現/偶發）
- 影響範圍（dev/prod、特定瀏覽器、特定版本）

範例格式：

```md
場景：列表重排後，子組件 local state 錯位
預期：每個 key 對應原本實例狀態
實際：部分項目狀態被交換
重現率：100%
環境：Vue x.y.z，Chrome xx
```

---

## 10.4 S2：最小重現（你排查速度的分水嶺）

原則：

- 只保留與問題相關的最小模板與資料
- 一次只保留一種可疑特性（例如先去掉 KeepAlive 或 Suspense）
- 重現程式碼控制在可快速迭代的規模

### 具體技巧

- 把大型頁面切成 1~2 個元件
- 把非必要 API mock 掉
- 固定隨機數與時間來源，避免不可重現

---

## 10.5 S3：呼叫鏈定位（用地圖縮小搜尋空間）

你可以先做「問題 -> 模組」映射：

| 現象 | 優先模組 |
|---|---|
| 依賴觸發不符預期 | `reactivity` |
| 更新時序/重複 render | `runtime-core` + scheduler |
| 列表重排或狀態錯位 | diff / `patchKeyedChildren` |
| 模板轉譯異常 | `compiler-core` / `compiler-sfc` |
| `.vue` 熱更新異常 | plugin-vue / Vite 模組圖 |
| `watch` / `watchEffect` 行為 | **3.5 起核心在 `@vue/reactivity`（`watch.ts` / `baseWatch`）**，`runtime-core/apiWatch.ts` 只是包裝 |

接著執行：

1. 找入口 API
2. 設斷點在主鏈關鍵函式
3. 追核心資料（`activeSub`、`subTree`、`queue`、index map）
4. 記錄第一個「與預期分歧」的點

> 術語提醒：`reactivity` 裡「當前作用中的訂閱者」在 3.4+ 原始碼叫 **`activeSub`**（不是 `activeEffect`，見 01 章 1.3.1）；grep 時別找錯名字。

---

## 10.6 S4：修補策略（最小、安全、可驗證）

### 修補原則

- 優先最小差異修改（small diff）
- 不破壞既有契約與邊界條件
- 若是性能修補，保留行為等價性

### 測試策略

- 先寫能穩定重現 bug 的測試（防回歸）
- 再做修補
- 補邊界案例（空資料、快速連續更新、嵌套組件）

---

## 10.7 S5：輸出一份工程可用報告

建議模板：

```md
## 問題摘要
- ...

## 重現步驟
1.
2.

## 根因分析
- 呼叫鏈：
- 關鍵資料：
- 分歧點：

## 修補方案
- 變更內容：
- 為何安全：

## 測試證據
- 新增/更新測試：
- 驗證結果：
```

這份報告會大幅提高團隊溝通效率，也方便 code review。

---

## 10.8 常見實戰陷阱

### 陷阱一：先改再查

沒有定位就先改碼，通常只是在碰運氣，且容易引入新問題。

### 陷阱二：一次改太多

多變因會讓你不知道是哪個改動真的修好問題。

### 陷阱三：只在 happy path 驗證

缺少邊界測試時，修補常在別處退化。

## 10.9 兩個實戰案例題（建議期末使用）

### 題目 A：watch flush 時序誤解

現象：  
在 `watch(..., { flush: "post" })` 內讀 DOM，偶爾拿到舊值。

任務：

- 重現條件
- 解釋時序（含 scheduler）
- 提出修正方式（如 `nextTick`、調整 flush 或更新點）

### 題目 B：列表重排狀態錯位

現象：  
v-for 使用 index 當 key，拖曳排序後輸入框內容錯位。

任務：

- 追 diff 路徑
- 說明根因
- 改成穩定 key 並驗證

## 10.10 你的「源碼解析能力」最終檢核

請自評以下能力是否達標：

- [ ] 能從現象快速映射到可能模組
- [ ] 能在 30 分鐘內建立最小重現
- [ ] 能畫出 5~8 步核心呼叫鏈
- [ ] 能以最小修補修復問題並補測試
- [ ] 能寫出可被團隊採納的分析報告

若有 2 項以上未達標，建議回練第 02、05、09 章。

## 10.11 期末專題建議

你可以從以下方向擇一：

1. **更新效能專題**：比較不同模板寫法的 patch 成本
2. **編譯輸出專題**：分析特定語法在 render code 的最佳化表現
3. **疑難排查專題**：重現並解析一個真實 issue（含修補提案）
4. **mini-vue 擴展專題**：在 mini 框架中加入 watch + scheduler + keyed diff

## 10.12 收官建議

到這章為止，你應該把「讀源碼」變成一套方法，而不只是一次性學習。  
持續進步的關鍵是：每次遇到問題都走同一套閉環，累積自己的案例庫與筆記模板。
