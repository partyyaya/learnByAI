# 05｜Preview、迭代與回滾

> 這章重點是讓你的前端發版流程「可驗證、可追蹤、可回復」，避免把風險集中在 production。

## 學習目標

- 了解 Pages Preview 在團隊協作中的價值。
- 建立可執行的前端迭代節奏（PR -> Preview -> Merge -> Prod）。
- 定義一套 10 分鐘內可啟動的回滾 SOP。

## 前置條件

- 已完成第 `04` 章，前端可部署到 Pages。
- 團隊使用 Git 分支與 PR/MR 流程。

## 成功標準

1. 每個 PR 都有對應 Preview 連結可驗收。
2. 發版前有固定檢查清單（功能 + 環境 + 效能）。
3. 出現事故時能依 SOP 快速回到穩定版本。

## 核心觀念

- **Preview 是防線，不是附加品**
  - 如果只看本地不看 Preview，常會漏掉雲端環境差異。
- **回滾要先設計，不要事故發生才想**
  - 真正可靠的團隊，都是先有流程再談速度。
- **部署頻率可以高，但每次變更要小**
  - 小步快跑 + 可回滾，比大包發版更穩。

## 分支與環境建議

| Git 分支 | Pages 環境 | 用途 |
|---|---|---|
| `main` | Production | 正式對外版本 |
| `feature/*` | Preview | 功能開發驗證 |
| `release/*`（可選） | Preview/Stage | 發版前總驗收 |

## 實作步驟：建立可持續迭代流程

### 1) 把 Preview 驗收寫進 PR 規範

PR 檢查至少包含：

- Preview URL
- 功能驗證清單
- 風險說明（影響頁面、已知限制）

可用的 PR 描述範本：

```md
## Preview
- URL: <貼上 Preview 連結>

## 驗證項目
- [ ] 首頁可載入
- [ ] 主要 CTA 可操作
- [ ] 重要 API 請求正常

## 風險與回滾
- 影響範圍：
- 回滾方式：
```

### 2) 建立「發版前 5 分鐘」檢查清單

必查項目建議：

- 功能：核心流程 smoke test（至少 3 條）
- 設定：Preview/Prod 環境變數是否正確
- 相容：主要瀏覽器（Chrome/Safari）抽查
- 效能：首頁關鍵指標（例如 LCP）是否明顯惡化

### 3) 設定回滾判斷門檻

可用門檻範例：

- 首頁白屏或關鍵流程不可用
- 錯誤率持續超過基準（如 5 分鐘內連續異常）
- 客服/營運回報核心功能中斷

只要命中門檻，就啟動回滾，不在事故時爭論標準。

### 4) 回滾 SOP（最小可行）

1. 宣告事故等級與決策人。
2. 選定「最近穩定版本」作為回滾目標。
3. 執行回滾（Dashboard 或重新部署穩定 commit）。
4. 驗證核心流程恢復。
5. 事故後 24 小時內補 RCA（根因分析）與防呆措施。

## 迭代節奏建議（前端團隊版）

- 每個 PR 只做一件事（UI 調整、API 介面調整、效能優化分開）。
- 每日可小量多次合併，避免大包週更。
- 每次部署保留 release note（至少寫：改了什麼、風險在哪）。

## 常見錯誤與排查

- **有 Preview 但沒人看**
  - 把 Preview 驗收改成合併必要條件。
- **Preview 正常、Production 爆炸**
  - 通常是環境變數、第三方 API 金鑰或 domain 白名單差異。
- **回滾流程只有口頭共識**
  - 沒有文件、沒有演練，事故時幾乎一定失敗。
- **每次變更太大**
  - 導致問題定位困難，應拆小 PR。

## 章末練習

- 必做：建立你的 PR 驗收模板（含 Preview URL 與檢查清單）。
- 必做：寫一份可在 10 分鐘執行的回滾 SOP。
- 選做：安排一次「模擬事故回滾演練」，記錄耗時與阻塞點。

## 章節重點回顧

- Preview 是前端交付品質的第一道門。
- 回滾效率取決於事前 SOP，而不是臨場反應。
- 小步迭代、清楚記錄、可快速回復，才是穩定上線關鍵。
