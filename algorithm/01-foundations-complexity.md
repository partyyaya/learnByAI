# 第 01 章：基礎與複雜度

## 1.1 本章目標

讀完本章後，你應該能夠：

1. 用 **Big-O** 描述演算法在「輸入變大」時，時間與記憶體怎麼成長。
2. 區分 **最佳 / 平均 / 最壞** 情境，並知道面試與競賽通常關心哪一種。
3. 理解 **遞迴** 與 **呼叫堆疊**，知道何時會 stack overflow。
4. 熟悉常見資料結構的「單次操作」與「掃一輪」的複雜度直覺。

本章刻意不一次塞滿所有主題，而是把「之後每一章都會用到的共同語言」打穩。

---

## 1.2 為什麼要先學複雜度？

LeetCode 題目常附帶資料範圍，例如：`n` 最大到 10^5 或 10^6。
若你寫出 **O(n^2)** 的解法，在 n=10^5 時運算量可能是 10^{10} 等級，在一般時間限制內會 **TLE（Time Limit Exceeded）**。

因此解題流程常常是：

1. 先想 **暴力解**（通常較慢，但幫助理解題意）。
2. 根據 **n 的上界** 反推「可接受的複雜度」。
3. 用對應技巧（雙指標、前綴和、單調堆疊……）把複雜度壓下來。

**口訣**：先對齊「時間預算」，再選資料結構與演算法。

---

## 1.3 Big-O 是什麼？（漸進上界）

Big-O 描述輸入變大時的**漸進上界**，通常省略常數與低階項。分析時會盡量給出緊的上界；若要精確表達同階成長，可用 Θ。

- **O(1)**：常數時間，與 n 無關（例如：讀陣列某一個 index）。
- **O(log n)**：每步把問題規模砍半（典型：二元搜尋）。
- **O(n)**：與輸入成線性比例（掃一遍陣列）。
- **O(n log n)**：常見於「分治」或「排序後處理」。
- **O(n^2)**：雙層巢狀迴圈掃全部配對。
- **O(2^n)**：指數（子集合枚舉），n 稍大就爆炸。

### 1.3.1 如何「數」出複雜度？

粗略規則：

1. **單層迴圈** 從頭掃到尾 → 通常是 O(n)。
2. **雙層迴圈**，內層也掃 O(n) → 常見 O(n^2)。
3. **迴圈變數每次除以 2**（或區間每次减半）→ 常見 O(log n)。
4. **排序**：比較排序在解題分析中常採 O(n log n) 模型；內建排序的實際時間與額外空間取決於實作。

### 1.3.2 空間複雜度

除了「時間」，還要看 **額外配置** 的記憶體：

- 只用到幾個變數 → O(1) 額外空間。
- 開了一個長度 n 的陣列 / `HashMap` → 常見 O(n)。
- 遞迴深度最深 n 層 → 呼叫堆疊也是 O(n) 空間（這點很常被忽略）。

---

## 1.4 最佳、平均、最壞

以「線性搜尋找第一個等於 `target` 的位置」為例：

- **最佳**：第一個元素就是 `target` → O(1) 時間。
- **最壞**：沒有或最後一個才是 → O(n)。
- **平均**：依資料分布而定。

**面試與多數 OJ**：若沒特別說明，通常報 **最壞情況** 的 Big-O，因為那決定系統會不會爆。

---

## 1.5 遞迴與呼叫堆疊

遞迴函式每次呼叫自己，系統會把「回到哪一行、局部變數」壓進 **呼叫堆疊**。

### 1.5.1 深度與空間

若遞迴深度是 n，堆疊深度也是 O(n)。
若每層還複製陣列，空間可能變成更糟（要仔細看有沒有切片、複製）。

### 1.5.2 何時改寫成迭代？

遞迴深度過大可能 **stack overflow**，上限依執行環境而異，不應把任何固定層數當成安全保證。
解法之一是改 **顯式堆疊** 或 **迴圈 + 狀態變數**（後面樹與圖章節會常遇到）。

---

## 1.6 常見資料結構：複雜度速查

以下用「平均情況」口述（`HashMap` 最壞在理論上可能退化，但一般題目假設良好雜湊）。

| 結構 | 典型用途 | 查詢 | 插入 | 備註 |
|------|----------|------|------|------|
| 陣列 | 依 index 存取 | O(1) index | 尾端 append 均攤 O(1) | 中間插入慢 |
| 動態陣列（`ArrayList` 等） | 同上 | O(1) index | 尾端均攤 O(1) | 可能 reallocate |
| `HashMap` / `dict` | key → value | O(1) 平均 | O(1) 平均 | key 需可雜湊 |
| `HashSet` / `set` | 是否存在 | O(1) 平均 | O(1) 平均 | 只關心 membership |
| 堆積（Heap） | 取最小 / 最大 | 看頂 O(1) | push/pop O(log n) | 任意查找通常 O(n)；快速定位需額外索引 |

**重要直覺**：若題目要「快速查有沒有出現過」「計數」「最後一次出現位置」，幾乎都會想到 **雜湊**。

---

## 1.7 用「預算表」估算法是否可行

當官方給 n ≤ 10^5，時間限制例如 1 秒，粗略可當 **10^8** 次簡單運算是危險邊緣、**10^7** 較安全（依語言與常數而異，僅作數量級參考）：

| n 上限 | 可考慮的時間複雜度（常見） |
|-----------|---------------------------|
| ≤ 20 | O(2^n) 枚舉 |
| ≤ 100 | O(n^3) 有時可過 |
| ≤ 10^3 | O(n^2) 常見 |
| ≤ 10^5 | O(n) 或 O(n log n) |
| ≤ 10^6 | 常要 O(n) 或接近 |

這張表不是絕對，但能幫你 **第一時間判斷暴力解有沒有機會過**。

## 1.8 從暴力枚舉開始：Two Sum

給定 `nums` 與 `target`，找兩個不同索引，使兩個值相加等於目標。先不用新資料結構，完整枚舉所有配對：

```ts
function twoSumBrute(nums: number[], target: number): number[] {
  for (let i = 0; i < nums.length; i++) {
    for (let j = i + 1; j < nums.length; j++) {
      if (nums[i] + nums[j] === target) return [i, j];
    }
  }
  return [];
}
```

`j` 從 `i + 1` 開始，避免重用同一元素，也避免把 `(i, j)` 與 `(j, i)` 算兩次。測試 `[3, 3]`、目標 `6`，應得到 `[0, 1]`；相同的值仍可來自不同索引。本範例擴充為無解回傳 `[]`，原題保證恰有一組解。

最壞情況的檢查數是 `(n-1) + (n-2) + ... + 1 = n(n-1)/2`，所以時間 O(n²)、額外空間 O(1)。提前找到答案可能很快，但不能因此把最壞時間寫成 O(1)。

下一章會把「逐一尋找另一個數」換成雜湊查找。先有正確的暴力版本，才能確認優化到底省了哪一步。

## 1.9 平均與均攤不是同一件事

- **平均分析**：對某種輸入或隨機假設取平均，例如良好雜湊下的查找。
- **均攤分析**：一次操作可能很貴，但一整串操作的總成本可被分攤，例如動態陣列偶爾擴容。
- **總量分析**：即使 `while` 放在 `for` 裡，若每個元素只進出一次，總操作量仍是 O(n)。第 03、07 章會實際使用。

還要把隱藏工作算進去：每次迴圈裡複製長度 n 的陣列、建立子字串或重新排序，都不是免費操作。

## 1.10 小結

- Big-O 描述 **成長趨勢**；面試常用 **最壞情況**。
- 空間要算 **額外結構** 與 **遞迴堆疊**。
- 看到 n 的上界，先對齊 **時間預算**，再決定要不要排序、雜湊、雙指標等。

| 暖身 | 自訂：線性搜尋第一個目標值 | 分析找到第一格、最後一格與找不到的差異 |
