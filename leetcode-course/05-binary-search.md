# 第 05 章：二元搜尋與答案空間搜尋

## 5.1 本章目標

讀完本章後，你應該能夠：

1. 理解二元搜尋的核心不是「背模板」，而是維護 **區間不變量**。
2. 區分 **找某個值**、**找左界 / 右界**、**找最小可行答案** 這三種常見變形。
3. 把二元搜尋從「搜尋陣列」延伸到 **答案空間搜尋**。

---

## 5.2 二元搜尋真正依賴的是什麼？

很多人把 binary search 理解成：

> 只有在排序陣列裡找數字時才會用

其實更本質的說法是：

> 當搜尋空間具有 **單調性**，就能考慮二分。

常見單調性有兩種：

1. **陣列值有序**  
   例如 `nums[mid] < target` 時，答案只可能在右邊。

2. **判定函式有序**  
   例如某個速度 `speed` 可行，那比它更快的速度也都可行。

第二種就是所謂的 **答案空間搜尋**。

---

## 5.3 先想清楚：你到底在找什麼？

二分題常見分成三類：

### 5.3.1 找某個值是否存在

這是最標準的版本，例如第 01 章的 704。

### 5.3.2 找第一個滿足條件的位置

例如：

- 第一個 `>= target` 的位置
- 第一個 `> target` 的位置
- 最左邊的合法答案

這類本質上是在找 **邊界**。

### 5.3.3 找最小 / 最大可行答案

例如：

- 最小吃香蕉速度
- 最小容量
- 最大可行平均值

這類通常陣列本身不一定有序，但 **答案是否可行** 會形成單調布林值。

---

## 5.4 不變量（Invariant）比模板更重要

二分最容易寫錯的地方，不是語法，而是：

- 你現在的搜尋區間代表什麼？
- `left`、`right` 各自是否仍可能是答案？

若這件事沒先定義清楚，後面的 `mid`、縮區間方式都容易混亂。

### 5.4.1 常見約定一：閉區間 `[left, right]`

特色：

- `left` 與 `right` 都可能是答案
- 迴圈通常寫成 `while (left <= right)`

```text
閉區間：

index:   0  1  2  3  4
nums :  [1][3][5][7][9]
         L-----------R

意思是：從 left 到 right 都還可能是答案
```

這種寫法很適合：

- 找某個值是否存在
- 直接回傳 index 或 `-1`

### 5.4.2 常見約定二：半開區間 `[left, right)`

特色：

- `left` 可能是答案
- `right` 永遠是「答案之外的一格」
- 迴圈通常寫成 `while (left < right)`

```text
半開區間：

index:   0  1  2  3  4
nums :  [1][3][5][7][9]
         L-----------)
                     R

意思是：left 可以是答案，但 right 這格不算進搜尋範圍
```

這種寫法很適合：

- 找第一個滿足條件的位置
- 找最小可行答案

重點不是哪一種絕對更好，而是：

> **同一題只選一種區間約定，並全程一致**

---

## 5.5 找左界與右界

### 5.5.1 左界：第一個 `>= target`

這是很多題的基礎，例如：

- 插入位置
- 範圍查找的左端點

半開區間的典型想法：

- 若 `nums[mid] >= target`，代表答案在 `mid` 或更左邊 → `right = mid`
- 否則答案一定在右邊 → `left = mid + 1`

最後 `left` 會停在「第一個滿足條件的位置」。

示意圖：

```text
nums   = [1, 2, 4, 4, 4, 7]
target = 4

我們要找的是第一個 >= 4 的位置

index:   0  1  2  3  4  5
nums :  [1][2][4][4][4][7]
               ^
             答案在這裡（左界）

當 nums[mid] >= 4 時，不直接停下來，
而是繼續往左半邊縮，確認前面還有沒有更早的 4。
```

### 5.5.2 右界：最後一個 `<= target`

通常不直接寫「最後一個」，而是先找：

- 第一個 `> target` 的位置

然後再减一：

\[
rightBound = firstGreater(target) - 1
\]

這種想法通常比硬寫「最後一個」更穩定。

### 5.5.3 後處理很重要

二分找到的位置不一定真的存在你要的值。

例如找 `first >= target` 後，若：

- index 已經越界，或
- `nums[index] !== target`

那就代表陣列中沒有 `target`。

## 5.6 答案空間搜尋（Binary Search on Answer）

### 5.6.1 什麼叫「答案空間」？

有些題不是問「某個值在不在陣列裡」，而是問：

- 最小可行速度是多少？
- 最小容量是多少？
- 最大可行距離是多少？

這時候你不是在搜陣列索引，而是在搜 **可能答案的數值範圍**。

### 5.6.2 先寫判定函式 `ok(x)`

答案空間搜尋最關鍵的是：

> 給定一個候選答案 `x`，你能不能在合理時間內判斷它是否可行？

只要 `ok(x)` 具備單調性，就能二分。

常見模式：

- `x` 可行，則更大的也可行 → 找 **最小可行**
- `x` 可行，則更小的也可行 → 找 **最大可行**

```text
找最小可行答案時，常長這樣：

x  : 1  2  3  4  5  6  7
ok : F  F  F  T  T  T  T
               ^
            第一個 True

二分的目標就是找到這個邊界點
```

### 5.6.3 為什麼面試官喜歡這類題？

因為它會檢查你是否真的理解二分的本質：

- 不是背陣列模板
- 而是能把問題抽成「單調判定 + 搜尋邊界」

---

## 5.7 常見錯誤

1. **區間定義混用**  
   一下用閉區間，一下又用半開區間，最容易造成漏解或死迴圈。

2. **`mid` 更新後沒讓區間縮小**  
   例如某些情況寫成 `left = mid`，就可能卡住不動。

3. **忘記二分需要單調性**  
   若 `ok(x)` 不是單調的，二分就沒有保證。

4. **只顧找到位置，沒做後處理**  
   找左界、右界時，最後那個 index 是否越界、是否真符合條件，都要再驗一次。

---

## 5.8 小結

- 二元搜尋的核心是 **縮小仍可能有答案的區間**。
- 找邊界時，常比「找精確值」更重要。
- 當題目有 **單調的可行性判定**，就可以把二分用到答案本身。

看到「最小可行」「最大可行」「第一個滿足條件」時，請優先想到二分。

## 課後練習：對應 LeetCode 題目

### 題目：875. Koko Eating Bananas（愛吃香蕉的珂珂）

- **連結**：[https://leetcode.com/problems/koko-eating-bananas/](https://leetcode.com/problems/koko-eating-bananas/)

#### 題意（白話）

有一堆香蕉 `piles`，`piles[i]` 是第 `i` 堆的香蕉數。  
Koko 每小時選一堆來吃，若她的速度是 `k`，則一小時最多吃 `k` 根。

給定總時數 `h`，請找出：

- **最小的整數速度 `k`**
- 使得她能在 `h` 小時內吃完所有香蕉

#### 為什麼選這題當本章收尾？

1. 這題不是在有序陣列裡找值，而是在找 **最小可行答案**。
2. 很適合練習「先定義 `ok(speed)`，再二分」。
3. 是答案空間搜尋的代表題，之後像容量、最短時間、最小成本題型都常長這樣。

#### 關鍵單調性

定義：

- `ok(speed)` = 用速度 `speed` 吃香蕉，是否能在 `h` 小時內吃完

若某個速度 `speed` 可行，那麼：

- 比它更快的速度也一定可行

這就形成了：

```text
false false false true true true
```

這種「先不行，後都行」的單調結構，非常適合找 **第一個 true**。

#### 判定函式怎麼算？

對每一堆 `pile`，若速度是 `speed`，需要的時間是：

\[
\left\lceil \frac{pile}{speed} \right\rceil
\]

全部加起來，若總時數 `<= h`，則這個速度可行。

#### 參考實作（TypeScript）

```ts
function minEatingSpeed(piles: number[], h: number): number {
  let left = 1;
  let right = Math.max(...piles);

  const canFinish = (speed: number): boolean => {
    let hours = 0;

    for (const pile of piles) {
      hours += Math.floor((pile + speed - 1) / speed);
    }

    return hours <= h;
  };

  while (left < right) {
    const mid = left + Math.floor((right - left) / 2);

    if (canFinish(mid)) {
      right = mid;
    } else {
      left = mid + 1;
    }
  }

  return left;
}
```

#### 複雜度整理

- **時間**：每次檢查 `canFinish` 要掃一次 `piles`，是 \(O(n)\)；二分次數約 \(O(\log M)\)，`M` 為最大堆大小，所以總計 **\(O(n \log M)\)**
- **空間**：只用常數變數 → **\(O(1)\)**

#### 常見錯誤

1. **把這題當貪心亂猜速度**  
   真正關鍵是「速度可行性有單調性」，所以應該二分。

2. **上界設錯**  
   最大速度設成 `max(piles)` 就夠了，因為再快也沒有必要。

3. **天花板除法寫錯**  
   整數版常寫成：
   `Math.floor((pile + speed - 1) / speed)`
